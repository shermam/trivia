# Application Functionality

What each screen does, how game state is held and persisted, and how questions are sourced, authenticated, sold and played offline.

**Read this when** you are changing anything under `src/app/` — a component, a route, a service, a guard.

Part of the project overview — start at [`PROJECT_OVERVIEW.md`](../PROJECT_OVERVIEW.md) for the map and the conventions. ## 1. Application Functionality

### 1.1 Game flow

The app is a nine-screen game flow, plus two static legal pages, implemented as lazily-loaded standalone Angular routes:

| Route           | Component                 | Purpose                                                                                                                                                             |
| --------------- | ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `/`             | `GameSetupComponent`      | Configure and start a new game                                                                                                                                      |
| `/play`         | `QuizLoopComponent`       | Answer questions one at a time, against a timer                                                                                                                     |
| `/game-over`    | `GameOverComponent`       | Show final score, submit to leaderboard, view top 10                                                                                                                |
| `/quiz/:quizId` | `QuizDetailComponent`     | One curated quiz: what it is, how many of its questions it can play, and Start (`FEAT-024`)                                                                         |
| `/add-question` | `AddQuestionComponent`    | Submit a new question to the custom question bank (**Pro only**, see §1.6)                                                                                          |
| `/review`       | `ReviewQueueComponent`    | Approve or reject submitted questions, read the reports players have filed about them, and act on everything one account contributed (**reviewers only**, see §1.4) |
| `/my-questions` | `MyQuestionsComponent`    | An author's own contributions, and the two things only they may do to one (§1.13)                                                                                   |
| `/profile`      | `ProfileStatsComponent`   | A player's own lifetime gameplay totals (§1.10)                                                                                                                     |
| `/pricing`      | `PricingComponent`        | Compare Starter vs. Pro and subscribe via Stripe Checkout (§1.6)                                                                                                    |
| `/privacy`      | `PrivacyPolicyComponent`  | Privacy Policy (§1.9)                                                                                                                                               |
| `/terms`        | `TermsOfServiceComponent` | Terms of Service (§1.9)                                                                                                                                             |

Any unmatched route redirects back to `/`.

**Every route carries a `title`, including the two legal pages.** `AppTitleStrategy` reads it out to assistive tech on navigation, because client-side routing is otherwise completely silent (finding G5), and `app.spec.ts` fails on a route that lacks one. Worth stating here because it is exactly what a textual merge cannot see: when these two routes were rebased forward across the G5 work, they merged cleanly and titleless, and only the spec caught it.

**Game setup (`/`)**

- Reactive form to configure a game:
  - **Number of questions**: 5 / 10 / 15 / 20 / 25
  - **Difficulty**: Any / Easy / Medium / Hard
  - **Question source**: `open_trivia` (public API), `custom` (Firestore question bank), or `mixed` (roughly half-and-half, shuffled together)
  - **Topics**: the game's only topic choice (`FEAT-021`, `FEAT-052`, §1.4), with nothing selected meaning any topic for every source. An `open_trivia` game takes one seed tag, a `custom` game up to ten tags of any kind, and a `mixed` game filters its community half on all of them while its Open Trivia half follows the first seed tag among them

  The segmented pickers here and on `/add-question` (Question Source, Question Type, Correct Answer) are real `<input type="radio">` elements hidden with `sr-only`, so each option is natively announced — but the caption above each box is a plain `<span>`, which labels nothing. Each box therefore carries `role="radiogroup"` + `aria-labelledby` pointing at that caption (finding G4); without it a screen reader said "Open Trivia, radio button, 1 of 3" and never mentioned **Question Source**. `e2e/support/a11y.ts` sweeps _every_ radio on the page rather than checking the three known ids, so a picker added later is covered too.

- **The picker's suggestions are the seed tags — Open Trivia DB's twenty-four categories as tags** (`utils/category-tags.ts`, §1.4), because they are the only topics that narrow both sources. They are a first-party table rather than a fetched list, so the setup screen makes no request before Start and has no "categories failed to load" state to degrade to; the request turns a chosen seed tag back into Open Trivia DB's numeric `category` from the same table (§1.2).
- **The community draw's topic filter is additive** (`FEAT-021`). No selection sends byte-for-byte the query an any-topic game has always sent — `status`, the optional difficulty, nothing else — and a selection adds one `array-contains-any` clause on `tags` (`data-model.md` §3); no `category` clause is sent at all. A question with no `tags` array matches no such clause, so a filter that leaked into the default draw would not narrow a custom game, it would empty it of every question nobody had tagged — which is why both the service spec and `trivia.service.spec.ts` assert on the **absence** of the clause rather than on an empty one, and why `scripts/backfill-category-tags.mjs` writes the derived tag onto every stored question before the picker replaces the category (`data-model.md` §3). Ten is the ceiling, in the picker and again in the query builder: Firestore refuses an `array-contains-any` past thirty values outright, and a bound does not live at the call site.
- **Each source takes the selection in the shape it can honour, and the picker says which** (`FEAT-052`). Open Trivia DB takes one `category` per request and refuses a second request inside five seconds, so for an `open_trivia` game the picker is a **single choice of the seed tags**: picking another replaces the one chosen, the way the category `<select>` it replaced did, and a typed topic outside the set is refused with the reason ("Open Trivia plays only the suggested topics — Custom and Mixed take any.") rather than accepted and ignored. **Switching into Open Trivia keeps the selection's first seed tag** and removes the rest — or empties it when there is none — and says what went, in the feedback line and from the picker's live region. A `mixed` game's hint names the seed tag its Open Trivia half follows, or says that half covers every topic until there is one, before Start rather than after it. The config records only what the draw used — at most one seed tag for an Open Trivia game — so a saved snapshot never claims a filter the game was not drawn under. Offline the picker stays usable, and the selection is a preference over the saved pool (§1.8).
- **The picker keeps the card the same size through all of that** (`CLAUDE.md` §4.4). The chip box scrolls inside a fixed height, and the hint and feedback lines are each reserved at the tallest thing they can carry — every source's hint plus one Mixed hint per seed tag, and every Open Trivia notice — stacked invisibly in one grid cell. **The shortcut strip is a fixed-height box from first paint whose chips land on the first idle moment or the first focus inside the picker** (`deferSuggestions`): the card is the home route's largest contentful paint, and rendering a strip of chips with the first frame cost it a measured 0.3–0.5 s when `FEAT-021` tried it. Landing in a box that is already there, they move nothing. `tag-filter.spec.ts` measures both in a real browser — the card and its Start button across every source change at 390×1400 and 1280×1400, tall enough to leave centring slack at both, and the Start button on every frame from the empty strip to the full one.
- On submit, `GameControllerService.startGame()` fetches questions for the chosen config and navigates to `/play`. Loading and error states (e.g. no questions found for the given filters, network failure) are surfaced inline on the form. **The card holds still while `/play`'s chunk loads** (`CLAUDE.md` §4.4): by then the start has committed its game and, for a free player, spent a free game, so the two things that read either — the resume banner (§1.3) and the Pro offer (§1.8) — stay as they were when Start was pressed until the route changes, or until the start ends without changing it.
- **A topic-filtered draw that comes back short says how many were found and waits.** A narrow topic holding fewer questions than a game asks for is the expected result rather than an unlucky one, so a player who asked for twenty questions about one topic and silently got three has been misled by omission — the same argument as the time-limit note above. Pressing Start again plays the questions already in hand, so being told costs no extra read and no allowance; changing anything about the selection draws again instead. Deliberately **scoped to a tag-filtered draw**: an unfiltered one can come back short too — a narrow difficulty, a small bank — and has always played short, and putting a confirmation in front of that would change behaviour this feature has no business changing. Scoring is untouched — the leaderboard bounds `totalQuestions` at one and above, so a short round saves like any other.
- **The curated quizzes are listed under the setup screen, one screen down** (`FEAT-024`, `QuizListComponent`). The list is a sibling _after_ the `min-h-screen` block that centres the card, not a child of it, so it cannot lift the card the way anything inside that block would (`CLAUDE.md` §4.4). `quiz-list.spec.ts` measures it at 390×1000 and 1024×900 — where the card is taller than the window and pinned to the top, with 0px of centring slack, so it could not move whatever the list did — and at 390×1400 and 1280×1400, where it has 78px and 110px of room to move and does not. **It reads nothing until it is scrolled to**: an `IntersectionObserver` with a threshold just above zero, because in an embed, with no top bar, the section starts exactly at the bottom edge of the first screen, and an observer reports a target touching that edge as intersecting at a ratio of 0. The read is the newest ten published quizzes — `isPublished == true`, newest `createdAt` first, `limit(10)`, on a declared composite index (`data-model.md`). **The strip is one height in every state**: fixed-size cards with their text clamped that scroll sideways rather than wrap, three pulsing placeholders before the read, and the empty and failed messages laid over invisible placeholders, so loading, one quiz, ten and none are the same box. A card shows how many questions the quiz names; how many of those can still be played is the quiz page's to say, since finding out costs a read per quiz. **A read that fails says so in the strip, with a retry, and logs a warning rather than an error**: `/`'s console is kept free of errors (Lighthouse asserts `errors-in-console` on it), and on a short window the list is scrolled into view on the way to Start Game, so it reads during ordinary play — `quiz-list.spec.ts` refuses the read and checks the console stays clean. **Offline, a card says it needs a connection and a tap does nothing.** Opening a quiz needs the network twice — its page is a lazy chunk outside the precache (§1.8), and the quiz is a Firestore read — so while `ConnectivityService` says offline every card is a disabled link: a null `routerLink` removes the `href`, so a tap goes nowhere and fetches nothing, and `role="link"` with `aria-disabled="true"` keeps it announced as the link it is. The card goes flat (slate-100, no shadow) and "Needs a connection" takes the question count's place; the two share one grid cell of the fixed-size card, so neither state moves anything (`CLAUDE.md` §4.4). The connection coming back re-enables the same cards with nothing re-read. A plain link would fail offline without saying so — its navigation waits on a chunk that cannot load, so nothing appears, the address stays put and the only trace is `Failed to fetch dynamically imported module` in the console — and the failure would outlast the outage: Chromium keeps a failed dynamic import in its module map, so once the tap has failed, every quiz page fails the same way after the connection returns, until a reload. `offline-play.spec.ts` cuts the page's network and checks the card's state, its box, a forced tap and the way back.

**Curated quiz (`/quiz/:quizId`)**

- **A quiz is a title, a description and an ordered list of community question ids** (`FEAT-024`, `data-model.md`), written from the console or by `scripts/seed-quiz.mjs` and never by a client. It plays through the same loop as a drawn game: only where the questions come from, and their order, differ.
- **The page reads everything on arrival and nothing on Start** (`QuizService.load`): the quiz by its id, then its questions — one `documentId() in` query over at most twenty-five ids, or one `get` per id when that query is refused (below). Reading the questions here rather than on the press is what lets the page say before Start how many it will play.
- **A question that can no longer be played is skipped, and the page says so before Start** — deleted, withdrawn by its author, sent back to `pending` by an edit, or rejected (administrator decision, 8 October 2026, over `FEAT-024` §0.4's "refuse to start"). The count reads "8 questions, in the order they were chosen", and under it "2 of its 10 questions cannot be played right now, so it plays the other 8." **One unreadable id refuses the whole query rather than dropping out of it**: a `__name__ IN` query is authorised against the documents it names, so a pending or deleted question makes `firestore.rules` refuse the lot — measured against the emulator, and for a missing id against `trivimind-dev`'s real Firestore too, while a fake server answers either way, which is why `curated-quiz.spec.ts` plays a quiz holding a pending question. On that refusal each id is read on its own, and a refusal or a 404 there is a skipped question. Whatever comes back is filtered on `status` as well, because a reviewer or a question's author may read it in any status and a quiz plays the same questions to everybody.
- **Five states, one card**: loading, not found, nothing playable, failed and ready. An address naming no published quiz — missing, unpublished, or not a document id at all — is **not found**, inside the app shell with a link to a random game, never a blank page; a draft and a missing quiz read the same on purpose, because `firestore.rules` refuses both with the same 403 and telling them apart would tell a stranger which drafts exist. A quiz none of whose questions can be played says so and offers no Start. A failed read says the quiz could not be loaded — "you're offline, and a quiz needs a connection", without one, since the offline pool has no notion of a quiz — and offers Try again, which moves focus to the heading before the button it was pressed from goes away (`CLAUDE.md` §4.4). The heading names the state in every state ("Loading quiz…", "Quiz not found", the quiz's title), and a permanent `role="status"` region announces the outcome of the read.
- **The time limit is the player's; the quiz only suggests one.** `suggestedTimeLimit` pre-selects the picker and the page says "Suggested for this quiz: 30 seconds."; every option, "No limit" included, stays selectable (WCAG 2.2.1, the guard audit G7 shipped). The picker is the setup screen's — real radios hidden with `sr-only` in a `role="radiogroup"` labelled by its caption — and the note under it says the pace is all the choice changes, since **quizzes are not ranked**. Every variant of the note is stacked in one grid cell, so switching the limit moves nothing below it.
- **A quiz spends a free game like any other**: the allowance row and the Pro offer are the setup screen's (§1.8), and the allowance is consumed after the questions are in hand and before any state is committed.
- **Start hands the questions the page already holds to `GameControllerService.startQuiz`** — the loop's fixed-list mode, beside `startGame`'s draw. The config says what the game is (community source, any difficulty, the quiz's length, the chosen limit), the questions keep the quiz's order with only each one's answers shuffled, and the quiz itself rides beside them as `quiz()` (`{ id, title }`). Everything after that is a drawn game's: the countdown, the lifelines, the votes, the recap and `recordGameResult`, so a quiz counts towards the player's totals, play history and the questions' difficulty counters. Both entry points commit the new game through one method, `beginGame`, so neither can forget to reset a field the previous game left behind.
- **Nothing moves** (`CLAUDE.md` §4.4). The back link and the top of the card are fixed from first paint, and the card grows once, downwards, when the quiz lands — with every control arriving in that frame, so nothing pressable is ever moved under a pointer. Start keeps its box while it says "Starting…" — the day's last free game included: Start spends it before `/play`'s chunk has loaded, so the allowance reads zero mid-start, and the Pro offer waits until no start is in flight rather than taking Start's place under the pointer. "Starting this quiz replaces the game you have in progress" is decided when the quiz is read rather than live: Start commits the quiz's own game before `/play`'s chunk has loaded, so a live read put the line on screen mid-start and moved Start down 24px at 1024 wide and 44px at 390. `curated-quiz.spec.ts` measures all of it — the arrival, the picker and the start at 390×1000 and 1024×900, and the last free game at the default window.

**Quiz loop (`/play`)**

- Guards against direct navigation: if there's no active question in memory, it redirects back to `/`. A game restored from storage (§1.3) counts as in memory, so reloading `/play` mid-game resumes it rather than bouncing.
- **A question has two to six options** (`FEAT-051`), lettered A to F from the index rather than from a fixed list (finding B2), so the letters run as far as the options do. Up to four options sit two to a row from `sm` up; five or six take one column at every width, because a fifth option in a two-column grid leaves an orphan cell and the questions that carry five or six are exam questions whose options read better at full width. Phones are one column throughout. The rule reads the question's own option count, which nothing changes within a question — an option 50/50 removes keeps its cell — so the grid can differ from one question to the next and never re-flows under the reader.
- **A long statement grows the card and the page scrolls; nothing inside the card does** (`FEAT-051`, decided 8 October 2026). A question may run to 2,000 characters, and the card follows its content between questions as it always has: no bounded box, and no measurement of rendered text to decide whether one would overflow. A scrollable region inside the card is the worse reading surface on a phone — scroll chaining, a second scrollbar, a tab stop that exists only sometimes — and a screen reader reads a long paragraph better than it reads a region. `CLAUDE.md` §4.4 is about a box resizing by itself within a state, not about one question being longer than the last, and within a question nothing resizes: the result banner and the vote row below are reserved, which `variable-answer-count.spec.ts` measures through the reveal with a six-option, 2,000-character question at 390×1000 and 1024×900. A fenced code block inside the statement keeps its own horizontal scroll (§1.4). **A long statement gets no extra time** on a timed game: the remedy is per-question time (`FEAT-018`), and until that exists "No limit" is the setting such a question needs.
- Each question has a **15-second countdown timer** (visual ring that turns red in the last 5 seconds). It derives the seconds remaining from the **wall clock** — a deadline captured when the question loads, re-read on a sub-second interval — rather than decrementing a counter on each `setInterval` tick. A tick-counted countdown drifts against real time and, worse, stalls entirely in a backgrounded tab (browsers throttle `setInterval` there to as little as once a minute), so the question would silently never time out until the tab was refocused and would then resume from where it "paused" (finding B10). A `visibilitychange` listener re-syncs the moment the tab becomes visible again so expiry is immediate rather than waiting on the throttled interval; it's torn down in `ngOnDestroy` alongside the interval.
- The result of an answer is announced to assistive tech through a permanent `role="status"` live region (finding G3). It is rendered **always** and only its text changes — a live region inserted into the DOM already carrying its message is routinely missed by screen readers. The wording is deliberately not the banner's: the banner is glanceable ("Correct! Well done."), while the announcement has to stand alone without the colour and icon that carry half the visual meaning, so a wrong answer announces what the right one was.

- **The result banner occupies its space before there is a result**, for the same reason the live region exists before there is a message. The card is vertically centred (`min-h-screen flex items-center`), so a banner that appears on answering does not push the page down — it makes the card taller and centring lifts the whole thing by half of that, right as the reader looks at the option they just picked. Measured at **43px on a 390×1000 phone and 37px at 1024×900**.

  **The viewport height is what makes this easy to miss.** At 390×700 and 1024×800 the same bug measures exactly **0px**, because below a certain height the card already overflows its container and is pinned to the top. A check at either of those sizes would have called it fixed while it was broken, which is why `game-flow.spec.ts` pins the assertion at 1024×1000 and says so.

  The three messages are stacked in one grid cell (all `col-start-1 row-start-1`) so the reserved height is the tallest of them, whatever the copy says. A hard-coded `min-h` would be a number to re-measure every time the wording changed, and guessing it too small brings the shift back one line at a time. The banner is `aria-hidden` because the live region already says it — without that, a screen reader would meet all three stacked messages, and it was hearing the result twice even before they were stacked.

- **The banner does not name the correct answer, and does not point at it either.** Naming it is what made the banner's height depend on the question: a long answer wrapped to a second line. It is also redundant on screen — the correct option keeps an emerald border and badge while every other option drops to 60% opacity. Every phrasing that adds a hint instead ("the answer is highlighted", "see the green answer") was measured wrapping at 320px, and with the space reserved that would cost a permanent second line of empty box on every phone. `resultAnnouncement()` still speaks the answer in full, because the highlight is the one thing a screen reader cannot see.
- **The time limit is a player choice** (finding G7, closing the WCAG 2.2.1 gap): **15 seconds** (the default, and what every game before this used), **30 seconds**, or **no limit**. The picker is a labelled `role="radiogroup"` on the setup screen, same contract as Question Source (G4).
  - **"No limit" means no deadline, not a long one.** `startTimer()` returns before creating the interval, so there is no countdown to run, nothing to draw, no auto-answer, and nothing for a backgrounded tab to throttle. A very large number would satisfy the letter of the criterion and fail its point.
  - The header shows a "No time limit" badge in place of the ring, rather than an empty ring that would imply a deadline.
  - **Each limit has its own leaderboard**, and the setup screen says so under the picker — a player who only discovers that at game over has been misled by omission. See `data-model.md` §3.
  - The choice is part of `GameConfig`, so it is persisted with the in-progress game (§1.3) and survives a reload. It has to be: it decides which board the finished game ranks on.
- Selecting an answer (or the timer hitting 0, which auto-submits a "no answer") locks the question:
  - Correct answer is highlighted green.
  - An incorrect selection is highlighted red; all other options dim.
  - Score increases only on a correct, non-timed-out answer — by the base point **times the streak multiplier** (see below), never by a flat one.
- After a 2-second delay showing the result, it auto-advances to the next question (or to `/game-over` if it was the last one).
- **A community question carries a flag button beside it, so a player reports the question they are actually looking at** (finding H4). One click, no dialog, nothing to confirm — the clock is running, and anything heavier would make reporting compete with answering, which is exactly why reporting originally lived only on game-over. The _detail_ (what's wrong) is still asked for on `/game-over`, where there is no timer; the flag's only job is to remember which questions to ask about, and it says so on screen. Flagging toggles, so a mis-tap is recoverable. Open Trivia DB questions get no flag: their ids are minted per fetch, so a report about one could never be acted on.
  - State is carried by `aria-pressed` plus a **filled** flag glyph, not by the red colour alone (WCAG 1.4.1), and the accessible name changes with it ("Report this question" → "Flagged for reporting…"). The tooltip is a hover-**and**-focus element rather than a `title` attribute, which never appears on touch and can't be reached by keyboard at all.
  - The flag is announced through its own permanent `role="status"` region, separate from the result region above (G3). Its text includes the question's position, so flagging a second question announces something _different_ from the first — identical text set twice is a no-op for a signal, and a live region only announces on mutation.
- **Once the answer is revealed, a community question can be liked or disliked** (`FEAT-027`, §1.14): a "Rate this question" row under the result banner, with two `aria-pressed` toggle buttons. It is kept apart from the flag on purpose — a dislike is taste and a report is a complaint a reviewer acts on — so it differs in glyph, place and words. Three details are load-bearing:
  - **The row is in the card from the moment a community question appears, and the reveal only makes it visible** (`invisible` until then, which also keeps it out of the tab order). The card is vertically centred, so a row arriving on answering would lift the whole card the way the result banner once did (`CLAUDE.md` §4.4); `question-votes.spec.ts` measures it at 1024×1000. Open Trivia DB questions get no row at all — their ids are minted per fetch, so a vote would be stored against an id that never comes back — and neither does an embed, which has no account menu for a guest's tap to open.
  - **The row lasts the two seconds the result is on screen**, which makes it a time limit on an interaction. The recap on `/game-over` carries the same buttons for every community question with no clock, and that is the WCAG 2.2.1 path, not a convenience.
  - **A guest's tap writes nothing and opens the account menu** (Decision 1), and **the round then waits for the menu**: when the pause after an answer runs out with the menu open, the next question is held until it closes and a fresh two-second pause starts. Moving on would start the next question's countdown behind a sign-in form. Only that pause waits — a live question's countdown never does. The outcome of every tap is announced through a permanent `role="status"` region outside the row, because the write can settle after the quiz has moved on to a question with no row.
- **Three single-use lifelines** (`FEAT-002`), in a labelled `role="group"` toolbar **below the answer options**, above the reserved result banner, so the card reads question → answers → help rather than putting the help between a question and its answers (`FEAT-048`). The row is placed there in the template rather than moved with CSS, so the Tab order and a screen reader's reading order match what the eye sees — the answers come before the help for everyone:
  - **50/50** removes every wrong option but one, whatever the count — one on a three-option question, two on four, four on six — so it always leaves exactly two: the correct one and one other (`FEAT-051`, decided 8 October 2026). The rule is `wrongAnswers - 1` rather than a fixed two removals, which would leave three or four of six options standing — not a fifty-fifty. On a question with two options — true/false, or a two-option multiple choice — there is nothing to remove without handing over the answer, so the button is _disabled_, and its accessible name says so in terms that cover both kinds: "unavailable on a question with two options". That is a deliberate departure from `FEAT-002`'s "fewer than 4 choices → remove 1": applied to true/false that removes the only wrong answer and hands over the correct one, which is a free point rather than a 50/50. Eliminated options stay in the grid, muted and `disabled`, because collapsing the cells would move the surviving answers under the reader's cursor (`CLAUDE.md` §4.4). The announcement counts what remains, so it says two every time.
  - **Extra Time** moves _this question's_ deadline forward 15 seconds. It does not change `GameConfig.timeLimit`, does not carry to the next question, and does not move the run to another board — a 15s game with one extended question still ranks on the 15s board (finding G7). The countdown ring is drawn against the question's own duration rather than the game's limit, or an extension gives a ratio above 1 and the ring draws itself inside out.
  - **Skip** ends the question immediately — no result banner, no two-second pause — and **the question still counts**. "Advances without penalty" is not "does not count", and the difference is a leaderboard exploit: every bound `firestore.rules` puts on an entry scales with `totalQuestions` — the score ceiling and the accuracy it will accept alike — so a skip that shrank the denominator would let a player skip nine of ten, answer one, and post a well-formed 100%. Decided explicitly with the owner on 28 August 2026 and pinned by a test.
  - **Hidden vs disabled is decided by whether the reason can change mid-game.** Extra Time is not rendered at all on an unlimited run — there is no countdown, and a control that visibly does nothing is worse than one that isn't there — which is safe only because the limit is fixed before question 1, so the toolbar is two buttons for that whole game. 50/50's availability varies question to question, so it is disabled instead; hiding it would resize the toolbar mid-round. Spent lifelines are always disabled, never removed, for the same reason.
  - Spending one is announced through a `role="status"` region: the visible change is options greying out or a number jumping, which is nothing at all to a screen reader.
- **Streak bonuses and score multipliers** (`FEAT-004`). Consecutive correct answers raise a multiplier, which is what the score is actually built from: **1–2 in a row score 1×, 3–4 score 1.5×, 5–7 score 2×, and 8 or more score 3×** ("on fire"). The tiers and the arithmetic live in `src/app/models/scoring.ts` as pure functions, away from any Angular, so the decision that ends up on a public board is unit-tested on its own.
  - **A wrong answer or a timeout resets the run; a skip does neither.** That last rule is why the run is a tracked counter on `GameControllerService` rather than something re-derived from the answer history on the results screen: the history records a skip as a question nobody got right, so a walk over it would under-report exactly the rounds that spent a lifeline well.
  - **Three numbers that used to be one.** `score` is the point total, `correctAnswers` is how many were right, and `percentage` is accuracy built from the latter — the multiplier never touches it, so no board can render 340%. Anything asking "how many did I get right" reads `correctAnswers`; `recordGameResult` sends it, and sending the score instead would put a number above `totalQuestions` into a payload the callable refuses outright.
- **Every question's outcome is timed, for the play history** (`FEAT-049`). `GameControllerService.answerDurations` runs positionally beside `answerHistory` — entry `i` is how long question `i` was on screen before the player resolved it — and both ride the persisted snapshot, so a reload mid-round does not cost the game its history. The clock starts from `QuizLoopComponent`, which calls `markQuestionShown()` at the two moments a question is rendered, because it is the only thing that knows when either happens: `advanceQuestion()` runs while the previous question's result is still on screen, and `startGame()` runs before the route has even changed. The wall clock rather than accumulated ticks, for the reason the countdown reads it (`CLAUDE.md` §4.4) — and an `unlimited` game has no countdown to derive a duration from at all.
  - **What is sent is built by `buildPlayAnswers` (`src/app/utils/play-history.util.ts`), all or nothing.** Both arrays are positional, so a history one short of the game describes a _different_ game rather than a smaller one — which is reachable, since a save written before either field existed restores empty and an unusable history is dropped whole. The key is then **omitted from the payload entirely**; `recordGameResult` reads a `null` there as the same thing, because the callable SDK encodes a present-but-`undefined` key as `null` and which of the two arrives is decided by how the caller spelled its object rather than by the game.
  - **A field the payload cannot carry costs the whole history, so the client drops it before the server can drop the game.** `recordGameResult` refuses an out-of-bounds submission _whole_, totals included, and `TriviaService.mapToTriviaQuestion` assigns `difficulty`, `id` and `tags` straight through from a source that is not bound by the type — Open Trivia DB is not ours to constrain, and a `custom_questions` document written through the Firebase console never meets `firestore.rules` (`CLAUDE.md` §4.4). So an over-long or empty id is dropped and the entry kept, the topic tags go through the same `topicTagsOf()` every reader uses — the question's own tags filtered by the `readTags` the chips render with, or the one its category derives for a question written before topics replaced categories (`FEAT-052`), so the record names the topic the card showed — and a `difficulty` outside the three sends **no history for that game at all** — there is no key to omit, since the stored record requires one, and one round's history is a far smaller loss than the player's lifetime totals.
  - The payload is identical for every account, anonymous included. The gate is the callable's — the shared caller gate (`stack.md` §2.4) — and nothing on the client duplicates it, because a client mirror of a server gate is a thing that drifts (H6): an anonymous submission is refused before any write, so nothing is stored for a guest.
  - **The answer is read, though.** The callable says whether it banked the game and, when it did not, why — and a refused game is invisible unless something reads that answer: a gate missing a provider refuses that provider's every game while nothing on screen changes and `/profile` goes on promising totals. So `AccountService` asks `AuthService.currentAccount()` who the call is made as — from Auth itself, because `user()` lags `authStateReady()` by a microtask — and then reads the verdict: a guest's refusal is the design and a `duplicate` is a reloaded `/game-over`, so both say nothing, decided from the account rather than from the reason, since an older server names a guest's refusal `unsupported-provider`. Any other refusal of a signed-in account is a game the player believes counted: it is logged with the server's reason and the provider the token named, and held as `unbankedGame` for `/profile` to say so (§1.10). A banked game's answer carries the player's XP after it and what the game added (`FEAT-041`), held as `bankedXp` for the tab — read field by field, dropped when the next game banks without an XP this build can read or is refused, and left alone by a duplicate — so `/profile` can say when the last game crossed a level, which nothing on the document can say once it is written. A failure to get an answer at all — offline, a cold start past the timeout — stays silent, because the SDK's timeout cancels nothing and the game may well have landed.
  - **The exact total can hold half points and the score cannot**, because a 1.5× tier on a one-point base produces one and `firestore.rules` requires `score` to be an `int`. `points` keeps the exact figure and `score` rounds it once, so the number the player watches climb is the number that reaches the board — rather than a 7.5 on screen turning into an 8 on the leaderboard. Both ride the persisted snapshot (§1.3), or a reload would hand back half a point on every 1.5× answer.
  - **The badge is rendered on every question and only made `invisible`** until the run reaches two. It sits in the wrapping row beside the topic and difficulty pills, where a pill that came and went would re-wrap the row and move the question text down mid-round (`CLAUDE.md` §4.4); its contents are a constant width by construction — a two-character `tabular-nums` slot for the run, a multiplier always written to one decimal — rather than by a reserved minimum somebody has to re-measure. It pulses only at the top tier, gated on `motion-safe:`.
  - **Reaching or losing a tier is announced** through its own permanent `role="status"` region, and only on a tier change: the result region beside it already says "Correct." on every right answer, and repeating the running count on top of that would bury the part that matters. The text carries the question's position, so reaching 1.5× twice in a round announces twice (G3).
- **Answering, timing out, spending a lifeline and the countdown's last five seconds each play a sound** (§1.11), unless the player has muted them from the nav drawer or the game is embedded. A skip plays the lifeline cue rather than an answer one.
- Displays running question index, live score, and the question's topic and difficulty badges — the topic as its first tag, `#history`, through the derivation every reader uses (§1.4), and not upper-cased like the difficulty, because a tag's case is part of its spelling. The progress bar under the header reads `GameControllerService.progressPercentage()`, which counts from one so it agrees with the "Question N / M" label beside it — it previously divided the zero-based index directly and was a full question out at every step, showing 0% on question 1 and never filling.

**Game over (`/game-over`)**

- Redirects to `/` unless there's a **completed** game in memory — `totalQuestions > 0` _and_ `isComplete` (§1.3). Requiring the completion flag matters now that game state survives a reload: a half-played game is restorable at any time, and this screen offers to publish its score to the leaderboard.
- **The summary is four tiles**: the point total, accuracy (with a derived performance label — "Outstanding!" / "Great job!" / "Good effort!" / "Keep practicing!"), the correct-answer count as `X / N`, and the best run of the round. Four rather than the two it began as, because the streak multiplier split the score into two different numbers: a point total that can exceed the question count and a correct-answer count that cannot. Rendering the former over the latter's denominator — `7 / 5` — would read as a mistake on the one screen a player goes to check a result they doubt. All four render in every state, so the card is the same size whatever the round did. **Every piece of text in them reaches WCAG AA against its tile in both themes**, and nothing else would check it — Lighthouse never loads this screen. Two consequences shape the palette: the accuracy tile wears its tier's colour on a 12px label as well as on its large figure, so each tier owes 4.5:1 rather than large text's 3:1 — which is why "Great job!" shares emerald-700 with "Outstanding!" instead of the brand emerald-600 — and the muted `/ N` beside the correct-answer count is 20px, below the large-text sizes, so it takes the tile's own caption pairing, slate-500 / slate-400. `color-contrast.spec.ts` plays a four-in-five round in each theme and measures every piece of text in the card (`ci-cd.md` §4.3).
- **Arriving here plays the end-of-round cue** (§1.11) — a brighter one for a round with every answer right — and a **reload** of this screen plays it again, which is a fact about the browser rather than a decision: a reloaded document is still activated, so the audio context it builds starts running (§1.11).
- If fully authenticated (see §1.5), lets the player enter a name (≤30 chars, prefilled from their profile) and submit their score to the Firestore `leaderboard` collection — one entry per account, keeping their best score. Anonymous or unverified players see a sign-in/verify prompt instead of the form.
- **A curated quiz makes no leaderboard entry and shows no board** (`FEAT-024`; administrator decision, 8 October 2026, over the spec's §0.2, which ranked a quiz on the board for the limit played). Everybody plays a quiz's questions in the same order, so a second play is a memory test rather than a score. `isQuizGame()` — the controller's `quiz()` being set, known from the first frame because it is restored with the game — puts the quiz face ("Quizzes aren't ranked on a leaderboard.") in place of the save form for every player, removes the board and its toggle from the page rather than hiding them, and skips both reads they would have cost: the top ten and the country lookup. `saveScore()` refuses a quiz game too, so a template change cannot reopen the write. `curated-quiz.spec.ts` asserts the face, the absent board and that no leaderboard query was sent; `quiz-results.spec.ts` that a verified account's quiz banks its totals, play history and difficulty counters and leaves no entry on any board.
- **The save form also carries a country picker, and it is optional** (`FEAT-028`). Choosing one publishes a **second** entry, on that country's board (`data-model.md` §3) — so a save is two independent writes, and it counts as succeeded if either lands. That is not defensiveness: the two documents have separate improving-score floors, so a player whose global best already stands can still be first in a country they have only just named, and gating one write on the other would deny whichever case the gate ran the wrong way for. Leaving the picker on "Prefer not to say" writes the global entry alone.
  - **What is published is the reader's declaration, never the app's inference.** `RegionService` pre-selects the control from `GeoService.resolveCountry()` — the same first-party `/api/geo` → time-zone chain the pricing page uses (§1.6) — but a guess lives in component state and nothing else: only a country the reader actually picked is written to `localStorage` (`trivia_region`), and what reaches the entry is whatever the dropdown reads when Save is pressed. That is the distinction the Privacy Policy rests on (§1.9), so it is worth stating as a rule rather than as an implementation detail. A guess that arrives after render is also suppressed once the reader has touched the control, so a two-second `/api/geo` answer cannot overwrite a choice made in the first second — and when it lands with the regional board showing it re-reads that board, because a country set without a read leaves the empty-board message claiming "no scores in Brazil yet" about a board nothing asked about (§1.4).
  - **The selected option is bound on the options, not with `[value]` on the `<select>`.** A `[value]` binding on the element is applied before the `@for` has created an option to match it, and Angular does not re-apply a binding whose value has not changed — so a stored declaration reached the signal and never the DOM. That is not a cosmetic mismatch: the control read "Prefer not to say" while the save published a country, which is the one sentence the Privacy Policy makes about this field, and picking "Prefer not to say" fired no `change` because it was already the selected option, so a reader with a stored country had no way out. The unit spec reads `select.value` and an e2e plays a second round, because jsdom has no rendered `<select>` and the signal was never the thing that was wrong (`CLAUDE.md` §4.4).
  - Locally, on the emulator and on every preview channel there is **no `/api/geo`** (functions deploy only on merge, `ci-cd.md` §4.2a), so the chain falls through to the browser's IANA time zone — and `TIME_ZONE_COUNTRIES` maps Brazil's sixteen zones and nothing else. The control therefore opens on Brazil for a Brazilian machine and unset for every other, which is what `regional-leaderboard.spec.ts` asserts with `test.use({ timezoneId })` rather than assuming a blank control.
  - The country list is `src/app/models/regions.ts` — the 249 officially assigned ISO 3166-1 alpha-2 codes, named through `Intl.DisplayNames` in the reader's own language and sorted with `Intl.Collator`, so no table of English names ships in the bundle. It is a copy of `isValidRegion()` in `firestore.rules` and a rules test pins the two equal; the rules copy is the authority (`data-model.md` §3).
- **A Global / Regional toggle sits above the board** — real radios hidden with `sr-only` inside a `role="radiogroup"` with an `sr-only` group label, the same shape as the pricing page's currency switch (§1.6) and for a reason beyond consistency: native inputs already do arrow keys and roving focus, which a pair of `role="radio"` buttons would have to reimplement, and the e2e suite's `expectRadiosAreGrouped` sweep finds `input[type="radio"]`, so building it this way puts the control inside a check that already exists. It defaults to Global. Both options render with fixed labels in every state and the regional one is selectable with no country set, which is the size rule and the never-blocks rule at once: a toggle that appeared once a country was declared would move the board at the moment one is, a label that became "Brazil" when the pre-selection landed would change width under the reader (the account chip's defect, §1.4), and a disabled option explains nothing. Selecting Regional with no country set reads nothing at all — there is no path to query — and shows a line saying where to set one, in the board's already-reserved space. Which population is being ranked is a **second line under the heading**, rendered in both states: "Worldwide" or "In Brazil". Folding it into the heading instead would make "Top 10 in Brazil — 15-second games" wrap at 390px and not at 1024px, which is the viewport-dependent shift §1.4 warns about.
- **The card between the score and the leaderboard has six faces, all the same height, and its default is "signed out".** Which of five of them shows — sign in / verify your email / the save form / saved / save failed — is decided by auth arriving, and both halves of that were wrong.

  **The flash.** It was an `@if`/`@else if` chain gated on `isAnonymous()`, which is `user()?.isAnonymous ?? false` and therefore `false` when there is no user _at all_ — true for every frame before `onAuthStateChanged` fires, and again in the window after it fires with `null` and before the anonymous session lands. So the chain fell through to its "signed in but unverified" arm and told a signed-out visitor to verify an email they had never given us. Identical in shape to the account chip's `?` avatar flash. The chain is now a single `scoreAction()` computed built on `showsRealAccount()` (`user() !== null && !isAnonymous()`), which asserts a positive fact rather than the absence of a negative, so "auth has not answered yet" resolves to the sign-in prompt by construction and not by a second condition somebody has to remember. Moving it out of the template is the other half: an ordering bug inside `@else if` is unreachable by a test, and this one now has seven.

  **The shift.** Measured at 390×1000 before the fix: sign-in 146px, verify 148px, save form **192px** — so a returning player who could actually save watched the leaderboard drop 46px the moment auth resolved. All the faces now sit in one grid cell (`col-start-1 row-start-1`), so the cell is as tall as the tallest and only `invisible` moves; measured after, every face and the cell are 192px at 390×1000 and 124px at 1024×900, with the page below unmoved. The 46px that a signed-out phone player now sees as extra padding is the price, and the alternative — putting the save form's input and button on one row below `sm` to bring the maximum down to ~150px — was rejected as a design change nobody asked for that gets cramped at 320px.

  Two consequences worth knowing. `invisible` is `visibility: hidden`, so the hidden faces keep their boxes (which is what reserves the height) while dropping out of the tab order, the accessibility tree and `innerText` — verified, because `profile.spec.ts` watches `body.innerText` for a "Verify your email" flash and would otherwise trip on the hidden face. And every face is in the DOM at all times, so a spec that reaches for one has to assert `be.visible` rather than existence; `not.exist` now fails outright and a bare `cy.contains` passes vacuously (`CLAUDE.md` §4.6).

  **The sixth face is a curated quiz's** (`FEAT-024`, above). It wins over every auth state, because a quiz is never saved, and it sits in the same cell as the rest, so a quiz's result card is the size a drawn game's is.

- **The leaderboard is ten rows tall before it knows anything**, because ten is the `limit` it asks for. It used to render one line of "Loading leaderboard…" and then up to ten rows — a **508px** jump (68px → 576px, measured against the compiled stylesheet) arriving exactly as a player reads their final score. Now the fetch is covered by ten pulsing skeleton rows, and any slot the board does not fill becomes an invisible filler row. The empty and failed states keep the height too, with their message laid _over_ the reserved rows rather than replacing them — otherwise the shift comes back for precisely the players who see those states: a first-ever game, or a Firestore hiccup.

  All three row kinds are the same box with the same 36px avatar-sized element inside, so their heights match by construction rather than by a matching `h-` guess; measured in a browser, each is 72px and every board configuration is 576px. The skeletons and fillers are `aria-hidden` — ten blank list items would be worse for a screen reader than the shift is for a sighted one — and an `sr-only` `role="status"` region says in words what they say in pixels.

- Displays the **top 10 of whichever board the toggle selects**, sorted by score descending, loaded from Firestore and refreshed after a successful save and on every switch. Each read carries a sequence number and a superseded one discards its answer: two boards are one click apart, so Global → Regional → Global puts two reads in flight and the network would otherwise decide which renders — which is how the world's top ten ends up under "In Brazil". After a successful save, if the player's own entry is present in that fetched top 10, their row is highlighted and their rank is shown — derived entirely from the already-fetched top-10 list (matched by `uid`), not a dedicated rank query, so a saved score outside the top 10 shows no rank claim rather than an invented one. The claim names the board it is about ("#3 on the 15-second leaderboard in Portugal"), because the rank is read off whatever is on screen and the unqualified form would be a statement about the world.
  - **A row reads `N pts · P%`** — points and accuracy, never `score / totalQuestions`, for the same reason the summary does not: a multiplied score is not a fraction of the question count. The game length is still stored on the entry and still returned by an export; it is dropped from the row alone, because the row has one line at 320px and the player's name is what must not be squeezed out of it. The score column is `tabular-nums` and `shrink-0`, so a three-digit entry sitting beside a one-digit one changes neither the row's height nor its shape — which matters indefinitely rather than transiently, since every entry saved before multipliers existed stays on the board.
- **"Review answers" — the recap** (`FEAT-001`). A collapsible card listing every question of the round with what the player picked and, when that was wrong or the clock ran out, what the right answer was. Timeouts carry their own "Time expired" badge, because a timeout and a wrong answer score identically and would otherwise be indistinguishable on the one screen built to explain the score.
  - **It sits after the leaderboard, not "directly below the score summary" as the spec asks.** That slot is the five-face card above, and the two things the player came here to do — save the score, see where it landed — are above it; a collapsible section pushing both down to make room for reflection has the ordering backwards. It sits with the reporting sections instead, which are the other backwards-looking part of the screen. **Measured, not just argued**: hoisting the card back above the score summary in a real browser and expanding it moves the score card and the leaderboard **545px** at 1024×1000, against **0px** as shipped. `game-flow.spec.ts` pins the 0px.
  - It is also a **third** per-question list where the spec expected the existing one to be extended. Both existing lists are `reportableQuestions()`, filtered to `source === 'custom'`, because Open Trivia DB content is not ours to moderate — so extending either would either shrink the recap to the community questions or grow a report affordance onto questions there is nobody to report to.
  - **A skipped question reads as skipped**, with its own badge and "You skipped this" — not as a timeout. Both score zero, and telling a player the clock beat them on a question they chose to leave is exactly the kind of unverified story `CLAUDE.md` §4.4 forbids an error message. This is why `PickedAnswer` is a discriminated union rather than the `string | null` `FEAT-001` shipped: that scalar's one spare value was already spent on "timed out", and the only room left for a third outcome was a magic string, which TypeScript widens back to `string` and the compiler can then never make anyone handle.
  - **Answers are compared by `id`, never by text** (`CLAUDE.md` §4.4). Two options can carry the same string, and letting display text stand in for identity is what made a wrong answer score as correct once already; a recap doing the same would repeat that bug one screen along, in the place a player goes to check the score they doubt.
  - A **disclosure**, not a popup: `aria-expanded` + `aria-controls` and deliberately no `aria-haspopup`, since the panel expands in place (§4.5). The panel is an `<ol>` with an `aria-label`, keeping its implicit `list` role rather than overriding it with `group`.
  - **A question that carries a source offers it as a link, and a justification as prose** (`FEAT-022`, §1.4), after the correct answer. The recap is the right place for both: the player has already answered, so neither can leak anything, and this is the screen someone reaches when they doubt a result. On a question the generation pipeline wrote, the source line reads "Machine-generated from <source>" (`FEAT-020`, §1.4) — the one place in a game a player is told, so nothing in the loop changes — and the fact rides the saved game, so a reload of this screen says the same.
  - **A community question's row shows its measured difficulty** (`FEAT-023`, §1.4) — the band word alone, easy, medium or hard, **in the pill the contributor's label used to occupy** and exactly as that label read, so the row holds the same box whether or not anybody has played the question, and one nobody has reads its label. It is derived from the counters the question carried when this game drew it, off the document the draw already read: no extra read, and the difficulty the player was dealt rather than one their own answer has since moved, on a reload as much as on arrival. An Open Trivia row keeps the label it arrived with, because there is no document behind it to count against and a measured band would only ever be that label in disguise. One word in the same neutral pill as the topic, nothing carried by colour (`CLAUDE.md` §4.5); the score behind the band never reaches the page, and nothing else in the app reads it yet. `question-difficulty.spec.ts` measures a calibrated row against an uncalibrated one of identical content at 390×1000 and 1024×900 (`ci-cd.md` §4.3).
  - **Each community question's row ends with the like and dislike buttons** (`FEAT-027`, §1.14) — the same component the quiz shows after a reveal, here with no clock, which is what makes the vote reachable for a player who needs longer than two seconds to get to it (WCAG 2.2.1). The same gate applies: none on an Open Trivia DB row, none in an embed. Its announcements go to a permanent region outside the card, which renders its rows only while open.
  - **The whole card is absent unless the history covers the round.** A game saved by a build predating this feature restores with no history, and a recap built from one would read "Review answers (0/10 correct)" underneath a score card saying 8/10 — confidently wrong, which is worse than absent. The same all-or-nothing rule covers an entry naming an option on a different question: the array is positional, so dropping one bad row silently renumbers the rest.
- **Finishing a game banks it into the player's lifetime totals** (`users/{uid}`, `data-model.md`). Fire-and-forget from `ngOnInit` — the screen renders entirely from local state and must not wait on a cold start, so a failed call costs one game's totals rather than a broken screen. Signed-in accounts only; anonymous sessions are refused server-side. Both numbers it sends come from the game's own counters and neither is the score: `correctAnswers` above `totalQuestions` is refused outright by the callable, and the longest run is the one the quiz tracked rather than one re-derived here, because a skip leaves a run intact and shows in the recap as an answer nobody got right. A game restored from a save written before those counters existed banks with a streak of 0 — a knowing under-report, since refusing it would lose more.
- **Reporting detail is collected here** (finding H4), because this screen has no countdown and no auto-advance to fight. It comes in two layers, and the split is the whole point:
  - **"Questions you flagged"** — the questions the player flagged during the game (§1.2), and _only_ those. If nothing was flagged the section does not exist. This screen used to list every community question from the game unconditionally, which buried the one or two a player actually cared about under a wall of questions they had no complaint about.
  - **"Found something wrong in this game? Report it here."** — a modal dialog listing every `custom`-source question from the game, for the player who noticed something but didn't flag it. Shown whenever the game had any community question, flagged or not.
- **The two layers are never rendered at the same time**: the flagged card is hidden while the dialog is open. Not tidiness — both render through the same `ng-template` against the same `openReportQuestionId` signal, so a flagged question would exist twice in the document, duplicating `report-panel-{id}` and `report-badge-{id}` (making `aria-controls` ambiguous) and, worse, making `viewChild('reportPanel')` resolve to the card's copy, which is declared first. Opening a report form from inside the modal then moved focus behind the backdrop, outside the trap.
- Either layer opens the same per-question **Report** disclosure (reason radiogroup: wrong answer / inappropriate / spam / other, plus optional detail), open to any player **including anonymous sessions**, writing to `question_reports` (`data-model.md` §3). One `ng-template` renders the row in both places — a second copy is how the two would drift into different accessibility contracts. Open Trivia DB questions get no report affordance anywhere, and a game with no community questions shows neither layer.
- The disclosure follows the auth-menu contract (`aria-expanded`/`aria-controls`, Escape closes, focus moves in on open and back to the opener on close), the radios sit in a labelled `role="radiogroup"` (G4), and outcomes are announced through a permanent `role="status"` region that lives **above both layers** — a report can be sent from the dialog with nothing flagged, so a region inside the flagged-questions card would not exist at the moment it has something to say (G3).
- The dialog is `role="dialog"` + `aria-modal="true"` + `aria-labelledby`, closes on Escape or a backdrop click, moves focus to the dialog itself (so it is announced with its title before Tab reaches Close), and **traps Tab in both directions**. Two details there are not obvious: it is bound to a plain `keydown` rather than Angular's `keydown.tab`, which does not fire for Shift+Tab — the direction that escapes backwards past the first control; and the focusable list carries **no `offsetParent` visibility filter**, the usual idiom, because `offsetParent` is null for any `position: fixed` element (which this dialog is) and unimplemented in jsdom, so the filter silently empties the list and the trap degrades to bouncing everything back to the dialog. Closing restores focus to the trigger element directly rather than to whatever `document.activeElement` was at open time: the dialog has exactly one opener, and a click does not focus a `<button>` on Safari/macOS, so the captured value would be `<body>` — connected, therefore a "successful" restore into nothing.
- "Play Again" resets all in-memory game state and returns to `/`.

**Add a question (`/add-question`)**

- Lets a **fully authenticated Pro subscriber** (leaderboard's anti-flood gate, §1.5, _plus_ an active Pro subscription, §1.6) submit a new question to the shared `custom_questions` bank. Anonymous or unverified players see the same sign-in/verify prompts as game-over; a fully authenticated but non-Pro account sees a friendly "Upgrade to Pro" empty state with a CTA to `/pricing` instead of the form.
- **The form reports what's wrong rather than refusing quietly.** Each field renders its own error with `aria-invalid`/`aria-describedby`, an invalid submit announces a summary through a permanent `role="status"` region and moves focus to the first offending control, and `nonBlank` rejects whitespace-only values so the client agrees with the rules' trimmed length checks. This is a fix, not a flourish: the submit handler used to `markAllAsTouched()` into a template with no error markup at all, so forgetting a required field made the Save button do nothing whatsoever, with nothing on screen to discover. The wrong-answer rows carry their validators only while the type is multiple-choice — a row added later included — so switching to true/false can't leave the form invalid on hidden inputs.
- Reactive form: **topics first** — at least one, through the tag picker (§1.4), with the seed tags suggested ahead of the starter list — then difficulty, question type (multiple-choice vs. true/false), the question text, and answers — a correct-answer text field plus wrong-answer rows for multiple-choice (below), or a True/False picker for boolean (the one wrong answer is derived as the opposite value, whatever rows were left behind before switching). **There is no category field** (`FEAT-052`): the tags are the question's topic, a missing one is named and focused like any other invalid field, and `firestore.rules` refuses a create without one, which is what a browser still on the previous bundle meets once before a reload fixes it.
- **The wrong answers are rows, one to five of them — two to six options in all, four to start with** (`FEAT-051`): "Add an answer" until there are six options, a remove button on each row until two remain, a `boolean` question unchanged. The rows belong to the form — `addIncorrectAnswer`, `removeIncorrectAnswer` and `patchQuestionForm` in `components/question-form/question-form.ts` build and tear them down, so the bounds mirroring `firestore.rules` live in one place — and the label table the validation summary and the focus move are built from maps over whichever rows exist, so an empty fifth row is named "Incorrect answer 5" and focused like any other field, and the labels renumber when a row goes. Three details are load-bearing:
  - **Focus follows the row.** Adding one puts the cursor in it; removing one moves focus to whatever now stands in its place — the next row, or "Add an answer" when the last row went — on the render after the click, since neither element is where it will be until then. Never to the body, which is where a removed control leaves focus when nothing catches it (`CLAUDE.md` §4.5): the remove button that was pressed lives in the row that has just gone. A permanent `role="status"` region says which row was added or removed and how many answers the question now has, and says so when that is the most or the fewest it can have. `answer-rows.spec.ts` drives all of it in a real browser, typing into the focused row rather than clicking it, and submits a six-option question through the real rules.
  - **Each row is bound to its own control — `[formControl]` and `track control` — never `formControlName` by index.** Removing a middle row shifts every index after it, and `FormArray.removeAt` does not re-point a `formControlName` at the control that slid into its index, so the inputs under a removed row would go on editing answers that had left the form.
  - **"Add an answer" is disabled at six rather than removed**, the way the topic picker's input is at its limit, with a hint beside it — two to six answers in all, counting the correct one. Adding or removing a row moves what is below it, and that is the reader's own act, made while looking at it, rather than the box resizing by itself that `CLAUDE.md` §4.4 is about.
- **The question may run to 2,000 characters** — `question` in `firestore.rules`, long enough for a public-exam statement — **and a counter under it says how many are used**, "{n} of 2000 characters", rendered from first paint. It is in the field's description rather than a live region, so it is read when the field is reached instead of after every keystroke, and it turns red past the limit, where the field's own error names the number.
- On submit, the ID token is force-refreshed (`AuthService.refreshIdToken()`) immediately before the write, so a just-granted `stripeRole` claim is never stale at the exact moment `firestore.rules` checks it — then `FirebaseService.addCustomQuestion()` does an auto-id `addDoc` into `custom_questions`; a success state offers "Add another" (resets the form) or "Back to game". Reachable (with a PRO badge) from a link on the game-setup screen and from the profile section of the top-bar auth menu.

**Pricing (`/pricing`)**

- Compares **Starter** (free: unlimited games, leaderboard) against **Pro** (a monthly subscription: everything in Starter, plus creating custom questions). The Pro card's amount is read from the mirrored Stripe catalog rather than written into the template, and a currency switch appears when more than one currency is on sale — see §1.6 for that and for the full subscription flow this page drives.

### 1.2 Question sourcing

`TriviaService` is the single entry point for fetching quiz questions — `getQuestions(config)` for a draw, and `getQuizQuestions(ids)` for a curated quiz (§1.1) — and normalizes both sources into one shared `TriviaQuestion` shape:

- **Open Trivia DB** (`source: 'open_trivia'`): calls `GET https://opentdb.com/api.php` with `amount`, an optional `category` — the numeric id the seed-tag table gives the topic the draw follows (`openTriviaCategoryId`, §1.4), sent only for a seed tag — and optional `difficulty`. Returns `[]` if the API reports a non-zero `response_code` (e.g. not enough questions available). **The adapter stamps every result with its category's seed tag** (`seedTagForCategoryName`), in memory, after decoding — so an Open Trivia question carries a topic like a community one, and the quiz card, the recap, the offline pool and the play history read it the same way. A category name the table does not hold is served without a tag rather than given one the picker could never offer.
- **Custom** (`source: 'custom'`): queries the Firestore `custom_questions` collection with `status == 'approved'`, the chosen difficulty and — when topics are chosen — an `array-contains-any` on `tags` as **server-side `where` clauses and a bounded `limit`** — the game's own question count, or twice it (capped at fifty documents) on a deduplicating draw, for the reason below — then shuffles the batch. It used to read _every_ document in the collection and filter in the browser — billed per document and growing with other people's contributions rather than with anything the player asked for (`data-model.md` §3, and `CLAUDE.md` §4.1).
- **Mixed** (`source: 'mixed'`): splits the requested amount roughly in half between the two sources (Open Trivia questions are best-effort — a failure there is swallowed so a slow/broken third-party API doesn't sink a mixed game), merges, shuffles, and trims to the exact requested count. Each half takes the topics in its own shape (`FEAT-052`): the community half filters on every chosen tag, and the Open Trivia half follows the **first seed tag** in the selection — `firstSeedTag`, the reader's own order — or asks for no category when the selection holds none.
- **A curated quiz** (`FEAT-024`) is not a source a player picks but a named list: `getQuizQuestions(ids)` resolves a quiz's ids in the quiz's own order (§1.1), skipping any it cannot play, through the same mapper as every community question — so its questions are `custom` questions in every respect downstream. No seen-set, because a quiz is the questions somebody chose rather than a pool to prefer unseen ones from, and no offline fallback, because the pool holds questions by source with no notion of a quiz and no moderation state; a failed read throws and the quiz page says it needs a connection.

**A question the player has already answered is not served again while there is one that hasn't** (`FEAT-034`). Candidates are collapsed by a **seen key** so one question reaching the draw twice is one candidate; unseen ones are served first, and any shortfall is filled with the **least-recently-seen**, oldest first. Falling back rather than failing is the whole of what makes it safe on a small bank: every question is eventually answered, and a draw that came back short at that point would be worse than no deduplication at all. A device that has answered nothing takes the plain draw, byte for byte the one described above — and so does the offline fallback, which is `getOfflineQuestions` and is deliberately left alone: a player with no network is being served whatever was cached, and narrowing that pool further to avoid a repeat is the wrong trade when the alternative is no game.

- **The key is the document id for a community question and a hash of the wording for an Open Trivia DB one** (`src/app/utils/seen-key.util.ts`). Open Trivia DB mints an id per fetch (`open-${Date.now()}-${index}`), so there is nothing durable to remember — and it is where the repeats a player actually notices come from, which is why the hash is the point of the feature rather than a workaround. The wording is trimmed, whitespace-collapsed and case-folded first, but deliberately **not** entity-decoded a second time: that already happened at the adapter, and `decodeHtmlEntities` is not idempotent (`&amp;amp;` decodes to `&amp;` and then to `&`). Two contributed questions sharing wording stay two questions, because their ids differ.
- **The custom draw reads a bounded multiple of the game, and only when there is something to filter with.** A page of exactly the game's question count has nothing to substitute _with_ — dropping a repeat from it would shorten the game — so a deduplicating draw asks for twice the count, capped at fifty documents. The `where`, the `limit` and the random cursor are all unchanged (finding C1, `CLAUDE.md` §4.1) and the ceiling is a constant rather than a share of the collection, so the read does not grow as the bank does. A device with an empty seen-set reads exactly the game's count, as it always did.
- **The offline pool is not a reserve for community questions, and that is a moderation rule rather than a cost one.** A pooled question was approved when it was fetched and may have been rejected since; the pool stores no `status` and no client may re-check one (§1.4), so substituting from it would put a withdrawn question back into an online game — the outcome review-before-publish exists to prevent. The widened read above is this source's substitute supply and needs no second one, because every candidate it yields came from a query filtered on `status == 'approved'` moments earlier.
- **Open Trivia DB gets no widened request, and cannot.** Its `amount` is a requirement rather than a ceiling: asking for fifty questions in a category holding eight returns `response_code: 1` and no questions at all, turning a playable narrow game into "no questions were found". Its rate limit — one request per five seconds per IP — rules out a second call in the same draw as well. Substitutions there come from the offline pool, which the background prefetch keeps topped up to a hundred questions (§1.8) and where nothing can go stale, since an Open Trivia DB question has no moderation state to have changed. **The pool substitutes; it never supplies** — the draw is capped at what the network returned, so a legitimate "no questions match this filter" stays empty rather than becoming a game served silently from cache with no offline banner to say so.
- **How much that reserve can do varies with the filters, and is sometimes nothing.** It is the pool narrowed to the seed tag the Open Trivia request followed, if any, and the game's difficulty, while the prefetch fills the pool with unfiltered batches — so an unfiltered game draws on most of it and a narrow one on little. A pooled question matches a topic through the same derivation as everything else (§1.4), so one cached before topics replaced categories — a category and no tags — still counts as being about its seed tag.
- **Collapsing a duplicate is the one path that can shorten a game.** Two questions in a single Open Trivia DB page whose wording normalises alike are one candidate — which is the point of hashing the text — and inside a page of exactly the game's count there is nothing behind them to promote, so the round is one question short. It is the right way round: a repeat inside one round is more noticeable than a four-question five.
- **The background prefetch does not deduplicate.** It is filling the pool the draw substitutes _from_, and nothing it fetches is served to anybody, so widening its read and trimming its own batch would cost something for no benefit.

Shared normalization for every question:

- HTML entities in question/category/answer text are decoded safely via an inert `DOMParser` document (chosen specifically to avoid the classic innerHTML-based decoding XSS footgun) — **at the Open Trivia DB adapter only** (`decodeOpenTriviaText`), because that is the source that encodes them. It used to run in the shared mapper, which also rewrote Firestore-authored questions: those are stored exactly as a contributor typed them, so a question about HTML deliberately reading `&lt;div&gt;`, or an answer written out as `Tom &amp; Jerry`, silently became something else with no way to express the original. The transformation belongs to where the text came from, not to text in general (`CLAUDE.md` §4.4).
- Answers (`correct_answer` + `incorrect_answers`) are merged into a single `all_answers` array and shuffled with a Fisher–Yates shuffle, so the correct answer's position varies per question/render. Each entry is an **`Answer` (`{ id, text, isCorrect }`)**, not a bare string: the id comes from the answer's position in the source arrays, never from its text, and correctness is stated rather than re-derived. Both matter because a question can legitimately carry the same text twice — the quiz used to `track` by the string (duplicate keys) and to score by comparing the clicked string against `correct_answer`, which let the **wrong** option score as correct.

### 1.3 State management

`GameControllerService` is a single injectable, app-wide store (Angular signals, no NgRx/state library) holding the entire lifecycle of an in-progress game: config, question list, the curated quiz being played if it is one (`quiz()`, §1.1), current index, the exact point total and the correct-answer count, the run of consecutive correct answers and the longest one, completion flag, loading/error state, the ids of flagged questions, the per-question answer history, and derived signals (`totalQuestions`, `currentQuestion`, `isLastQuestion`, `score`, `scoreMultiplier`, `percentage`, `progressPercentage`, `hasResumableGame`). It also owns navigation between the three routes, so components stay thin and mostly declarative.

**That state survives a reload.** It used to live only in these signals, so a refresh, a tab crash or a PWA relaunch dropped a game part-way through with no way back — worst for exactly the offline/mobile players §1.8 exists to serve. `GamePersistenceService` (`src/app/services/game-persistence.service.ts`) now mirrors it into IndexedDB and `GameControllerService` reads it back on `restoreSavedGame()`, which an **app initializer awaits before the first route activates** (`app.config.ts`) — `/play` and `/game-over` both redirect to `/` when they find no question in memory, so a restore that resolved after route activation would bounce the player off the screen they were returning to. The guards **await** that restore rather than assuming it has finished. Bootstrap's wait is bounded (2s) so the app always starts, but `giveUpAfter` stops waiting without stopping the work — so the read is still in flight, and the guard awaits the same promise with a longer bound. Without that, a read slower than the bound is indistinguishable from "there is no saved game" and the guard redirects while the game sits intact in storage. A late restore also declines to overwrite a game the player has since started.

**Finding B11 was not that race**, though it was found looking for it, and the two are easy to conflate. Reloading mid-game lost the game because the record was being **rejected on read**: `GameConfig.amount` is declared `number`, and the setup form's question-count `<select>` bound its options with `[value]`, so Angular's `SelectControlValueAccessor` wrote the string `"5"` into a control typed `FormControl<number>`. Every consumer coerced it silently — the Open Trivia query string, Firestore's `limit()`, `Math.min`, `Array.slice` — except the one that type-checks, `parseSavedGame`, which discarded the save and cleared it. The control's _initial_ value stays a real number until the accessor overwrites it, so this only ever bit players who touched the picker, which is what made it look intermittent. Fixed with `[ngValue]`, which is what keeps a non-string option value intact; pinned by `game-setup.component.spec.ts` (driving the real `<select>`, since `setValue(5)` would pass against the bug) and by the browser-level `game-resume.spec.ts`. That spec now covers the whole feature rather than the one reload that found the bug — `/game-over` reloaded, the resume banner reached by a fresh page load, Discard, and a flag round-tripping — and reintroducing B11 fails five of its six tests, which is the coverage the finding went without. See `ci-cd.md` §4.3.

- **IndexedDB, in the same database as the offline question pool** (`OfflineDbService`, `src/app/services/offline-db.service.ts`), rather than `localStorage`. `localStorage` is the simpler API and holds this payload comfortably — a few kilobytes for a typical round, and under 200 KB for twenty-five community questions with every field at its cap, the 2,000-character statement included (`FEAT-051`) — but it is synchronous and blocks the main thread on every read and write, and §1.8's question pool is already an IndexedDB store — so one storage mechanism, one schema and one place to reason about eviction beats two, which matters more as further state becomes worth persisting. The cost is the async bootstrap above.
- **One database, one version, one schema, owned by `OfflineDbService`.** IndexedDB gives a database a single version shared by every connection, so two services opening it at different versions is not a benign arrangement: the higher one triggers an upgrade, the lower one blocks it, and each one's `onupgradeneeded` only knows about its own stores, so whichever runs would drop the other's. Centralising is what makes a second store safe to add. The schema is at **v6** (`questions`, `game-state`, `daily-limit` and `seen-questions`), and the upgrade is written additively — `questions` is deliberately _preserved_ across v2→v3, because wiping a player's offline pool as a side effect of adding an unrelated store would take the questions away exactly when they may have no network to refill them. A test pins that, and fails against the "recreate every store" upgrade. (v4 re-keyed `questions` from the question text to a source-aware `dedupeKey`, finding C4, which does have to recreate it — a store's `keyPath` cannot be changed in place — and `game-state` is preserved across that one for the same reason. v5 and v6 are purely additive — `daily-limit` and `seen-questions` are created if missing and nothing existing is touched.)
- **A ~6h TTL**, stamped on write and checked on read. Long enough for a reload, a crash or a short break; short enough that yesterday's abandoned game doesn't resurface as an offer to "resume" something the player has forgotten starting. A save timestamped in the _future_ is kept rather than expired, so a clock correction doesn't silently eat a live game.
- **What's restored is progress, not the moment**: config, questions (including each one's shuffled `all_answers` order, so the options don't move under the player), current index, the exact point total and the correct-answer count, **the streak in progress and the best one so far** (§1.1 — eight correct in a row is most of the value of a round, and the current run cannot be recovered from the answer history because a skip leaves it intact while the history records one), **which questions the player flagged for reporting** (§1.2), **what the player answered** (the recap's data) **and how long each answer took** (`FEAT-049`'s play history, positionally beside it and dropped with it if the pair cannot be lined up), and **the game's own id** (the idempotency key that stops a reload of `/game-over` banking the same game twice into `users/{uid}` — minted at start, never on the results screen, because an id created there would be fresh on every refresh). The transient per-question state — which option was selected, the result banner, the seconds left — is not; a resumed question starts on a fresh 15s timer. Flags belong on the persisted side of that line precisely because they are a promise: the flag tells the player they'll be asked for detail at the end, and a reload that silently dropped it would break that promise with nothing on screen to say so.
  - **Both are cleared by `startGame()` as well as by `clearGameState()`.** Only the latter used to do it, and it is reachable just from "Play Again" and the resume banner's Discard — but the top bar's logo is a plain `routerLink="/"`, so a player can abandon a flagged game and start another through neither, with the restore putting the old flags back into the signal on the way. Custom question ids are stable Firestore document ids, so this was not a harmless stale byte: draw the same question again and it rendered pre-flagged, and game-over led with "Questions you flagged" for a question never flagged in that game. A leaked answer history is worse still: the recap would render the abandoned game's answers underneath this game's score.
  - **The answer history rides the same record** (`FEAT-001`): what the player picked per question, in order, as an answer `id` or `null` for a timeout. `registerAnswer` used to take a `boolean` and throw the rest away, which made a timeout and a wrong answer identical the moment they left the quiz component — the recap has to tell them apart and only the caller knows. Only the picked id is stored, not `isCorrect`/`isTimedOut` alongside it: three fields that can disagree are worse than one in a record that round-trips through disk, and the other two are a lookup away.
    - The array is **positional** — entry `i` answers question `i` — rather than a map keyed by question id. A map would be robust to a reordering that cannot happen inside a round, and would lose the one property worth having: that a short history means an unfinished game rather than a question nobody answered.
    - It is therefore validated and **dropped whole**, where the flags are filtered. Removing one bad entry would shift every later answer onto the wrong question, and the recap would confidently show the player picking things they never picked. The per-entry check is against _that question's own_ options, because an id that exists in the game but on a different question is exactly the input that produces a plausible wrong recap instead of an obviously broken one.
    - Additive, no `SCHEMA_VERSION` bump, same call as the flags below and `timeLimit` before them.
  - **Lifeline availability and the options 50/50 removed ride the record too** (`FEAT-002`), as two fields because they expire differently — the availability flags last the round, the eliminated ids last one question. They still restore _together_: bringing back "50/50 spent" without the options it removed takes the lifeline and hands nothing back, so an unusable value for either resets both. And the reset direction matters — filling a partial record's missing keys with `true` would **refund** whatever was left out, making a truncated save worth manufacturing.
    - Extra Time is the one part that does not survive a reload, because the countdown itself never has: a resumed question starts on a fresh full timer regardless. The lifeline stays spent.
  - **A curated quiz's identity rides the record too** (`FEAT-024`): `quiz: { id, title }`, or `null` for a drawn game, so a quiz reloaded on its last question is still a quiz when `/game-over` renders — without it the results screen would offer to rank it. Additive, no `SCHEMA_VERSION` bump, the same call as the flags: a record written before quizzes existed restores as a drawn game, which is exactly what `null` says. An unusable value restores as `null` rather than discarding the game, because the questions and the score are worth more than the label. Like the flags and the history it is reset by every way into a new game, through the `beginGame` both entry points share.
  - `flaggedQuestionIds` was added to the stored record **without** bumping `SCHEMA_VERSION`, unlike every field before it. The addition is purely additive and the reader treats a missing value as "nothing flagged", so a v1 record written by an older build restores correctly; bumping would have thrown away every in-progress game on deploy to avoid a problem that doesn't exist. On load the ids are filtered against the questions actually in the save, so a hand-edited record can't carry a flag for a question that isn't there.
- **Writes are queued, not concurrent.** Each one persists a whole snapshot rather than a delta, so ordering is the only thing that matters — and unordered async writes could land a stale snapshot on top of a fresh one, leaving a resumed game a question behind. Chaining also keeps a failed write from rejecting into an `effect`, where nothing is listening.
- **Everything read back is validated before it reaches a signal** (schema version, TTL, config enum membership, question shape, `currentIndex` in range, `score` within the same ceiling `firestore.rules` enforces, the counts within the length of the game); anything unrecognised is discarded and the record dropped. The counts fall back rather than discarding — a total is worth less than the round it belongs to — and a record with no `points` at all is a save written before multipliers existed, whose `score` _was_ its exact total. This is a _robustness_ boundary, not a security one — it's the player's own browser holding their own score, and a leaderboard write is validated server-side by `firestore.rules` regardless. The point is that the database outlives deploys, so this code is guaranteed to meet shapes written by older builds, and an exception here fires during bootstrap, which white-screens the app rather than merely losing a game.
- **A save from before topics replaced categories still restores** (`FEAT-052`). A question with no `category` is valid — nothing contributed since carries one — and a config still holding the `category` key the old setup screen wrote is restored **without** it rather than refused: refusing would discard an in-progress game over a field nothing reads any more, and translating it into a topic would record a filter the game was not drawn under. `game-persistence.service.spec.ts` saves and restores both shapes.
- **The setup screen offers a resume banner** ("You have a game in progress — question N of M", with Resume / Discard) whenever `hasResumableGame()` is true. This is what covers the case a reload cannot: a PWA relaunch or a tap on the logo opens at `/`, not `/play`, so the saved game would otherwise sit in storage unreachable.
  - **While a start is in flight the banner holds what it said as Start was pressed** (`resumeOffer`, a `linkedSignal` over `isLoading()` and the game). `startGame` commits the new game (`beginGame`) before it navigates, and `/play` is a lazy route, so for as long as that chunk downloads the screen is still up holding a loaded, unfinished game — which is what `hasResumableGame()` means. A live read would raise the banner for the very game being started, making the card 122px taller and lifting its top 61px under the pointer at 390 and 1280 wide alike. Hiding the banner for the length of a start would be the same shift the other way, under a player starting a new game over a saved one — so it holds, still naming the game that was in progress, until the route changes, or until a start that fails or is refused ends and it says whatever is then true. `game-resume.spec.ts` measures both shapes of start with the chunk held, at 390×1400 and 1280×1400.
- **A completed game is persisted but never offered as "resume"** — refreshing `/game-over` keeps the score about to be submitted, while resuming would send the player back to replay and re-score the final question. `isComplete` is what distinguishes the two, and `GameOverComponent`'s guard now requires it: since game state outlives the session, a half-played game is restorable at any time, and this screen offers to publish its score.

### 1.4 Custom question bank

Firestore collection `custom_questions` acts as a first-party question bank alongside Open Trivia DB. It's populated both manually via the Firebase console and by players themselves through the in-app **Add a question** screen (`/add-question`, §1.1) — gated to fully authenticated accounts _with an active Pro subscription_ (§1.6) and validated server-side by `firestore.rules` (`data-model.md` §3). The question-generation pipeline (`FEAT-020`, `shermam/trivia-pipeline`) is the third writer: it promotes machine-generated questions on the Admin SDK as `pending`, under the `[generated]` author and with a `provenance` map, and a reviewer decides them like any other (`data-model.md` §3). An author can edit or withdraw their own contribution afterwards, from `/my-questions` (§1.13); nobody else can edit one at all, and only the console can delete somebody else's.

**A contributor may say where the answer comes from and why it is the answer** (`FEAT-022`): three optional fields — `sourceUrl`, `sourceTitle` and `explanation`, the last of them labelled **Justification** on the form — offered on `/add-question` and rendered wherever the question is shown, which is the reviewer's queue card and game-over's recap (§1.1). Six decisions are worth knowing.

- **All three optional, and said so on each label rather than only by the absence of an asterisk.** Requiring a citation would push contributors toward pasting _something_, and a citation that was guessed at is worse than none because it looks checked; the same argument applies word for word to reasoning invented to fill a box. Each field works without the others: a book has a title and no URL, a bare link with no publication name is still worth following, and a tricky question can need its reasoning spelled out without having a citation to point at.
- **The Justification box is for the question where knowing the subject is not enough** — where it is not obvious why the right answer is right or why a plausible wrong one is wrong. The reviewer reads it before deciding, which turns "does this look right?" into "does this reasoning hold?"; the player reads it in the recap, after answering, which is where an unexpected result gets explained rather than argued with.
- **A question without any of them renders nothing at all** — no badge, no "unverified", no reserved empty line. That is not a detail: almost nothing in the bank carries them, everything from Open Trivia DB never will, and a placeholder would turn a missing optional field into an accusation on every question in the app. The unit and e2e suites both assert the absence, because a regression here is invisible — an empty element looks like a question that simply has no source.
- **The rules' bounds are checked in the form first.** `firestore.rules` refuses a non-`https://` URL and anything past 500 / 200 / 1000 characters (`data-model.md` §3), but a rules refusal arrives as a bare `permission-denied` that names no field. The form's `httpsUrl` and `maxLength` validators catch the same cases and report them against the input. All three controls are in `fieldLabels`, which is what makes the summary name them and the focus move to them — a control missing from that table is invisible to both, and the first version of this shipped that way: a malformed link blocked the submit while naming nothing and focusing nothing, which is finding B4's symptom reached by a different route. Nothing carries a native `maxlength`, here or anywhere else on this form, because a silently truncated paste is a worse failure than a named error.
- **Two small components own the rendering for both callers**, because the interesting part is not the markup. `SourceLinkComponent` (`components/source-link/`) re-parses the URL and renders an anchor only for a real `https:` one, degrading to plain text otherwise (`CLAUDE.md` §4.4 — the reader has to be right regardless of the writer, and a dead `unsafe:` anchor is a worse outcome than no anchor). It carries the three obligations of `target="_blank"` together: `rel="noopener noreferrer"`, an `sr-only` "(opens in a new tab)", and a visible external-link glyph — any one of which is easy to drop in a copy-paste and impossible to spot in review. The label is the title, else the URL's hostname, so a contributor who supplies only a link does not leave the reader staring at a 300-character URL — and on **the reviewer's card only**, `showHost` appends the hostname inside the anchor, because the label is text the contributor typed and a `sourceTitle` of "Wikipedia" over a link to anywhere at all would read as Wikipedia on the one screen whose job is approving on evidence. A player meets the link after answering and after a reviewer has vouched for the question, so there the title is the useful thing. `QuestionJustificationComponent` (`components/question-justification/`) trims the stored text and renders nothing when what is left is empty, and hands the rest to `RenderedTextComponent` with the question's own `format` — so a plain justification keeps the contributor's line breaks (`white-space: pre-line`, escaped rather than parsed) and a Markdown one carries the same code and formulas the question does.
- **A question a machine wrote says so where its source is named** (`FEAT-020`). A question the generation pipeline promoted carries a `provenance` map (`data-model.md` §3), and where its `source` is `'ai'` both surfaces read the line as "Machine-generated from <source>" — honest and short, and the only difference such a question makes anywhere in a game. `SourceLinkComponent`'s `machineGenerated` input puts the words outside the anchor, so the link is still named by the page it opens rather than claiming to lead somewhere machine-generated, and it drops the `sr-only` "Source:" the words now carry. With no usable source the line still reads "Machine-generated": the Privacy Policy promises the label, and the reader cannot rely on the writer to have cited anything. `isMachineGenerated()` (`utils/question-provenance.util.ts`) is the one test of the map, and it re-checks it — anything but a `source` of exactly `'ai'` reads as a person's question — while `TriviaService` carries the one fact into a game as `provenance: { source: 'ai' }` and nothing more, so the model and the run never reach the saved game or the offline pool.

**A question can be written in Markdown with LaTeX maths** (`FEAT-019`), decided per document by an optional `format` field whose only meaningful value is `'markdown'`; absent — every question in the bank today, and every Open Trivia question forever — means plain text rendered exactly as typed. The form offers a **Formatting** toggle that defaults to plain, and a live preview beside it.

- **One component renders every surface**: `RenderedTextComponent` (`components/rendered-text/`) is used for the prompt and every answer in the quiz loop, the recap, the reviewer's card, `/my-questions`, the justification and the contribute form's preview. Not a pipe called from six templates — the allowlist, the MathML handling and the prose styles are the feature, and a second call site is how the screen a reviewer approves from and the screen a player sees grow apart.
- **The pipeline is `marked` → KaTeX → DOMPurify → the element**, and the order is the argument. `marked`'s two HTML tokenizers are switched off, so raw HTML in a contribution is _escaped_ before the sanitiser ever sees it and DOMPurify is a second line rather than the only one. Maths is a `marked` extension rather than a pre-pass over the source, which is what makes a `$` inside a fenced code block stay a `$`. DOMPurify then runs against an explicit tag/attribute allowlist — the supported Markdown plus the MathML element set, no `annotation-xml`, no `style`, no `data-*`, no ARIA, `https:` links only, `target="_blank"` and its `rel` added afterwards by a hook. That allowlist is **per document, not per element**, which is the part of DOMPurify's configuration most easily misread: an attribute added for one tag is legal on every other, so the same hook confines `href` and `title` to `<a>`. MathML has an `href` of its own and Firefox honours it on any MathML element, so without that an `<mi href>` would be a live link that never passed the `https:` parse and never collected a `rel`.
- **The sanitised markup is written to the element rather than bound with `[innerHTML]`.** Angular's own sanitiser knows nothing of MathML and would blank every formula, so it has to be told not to run either way — and the two ways of telling it are not the same price. A `[innerHTML]` binding plus `DomSanitizer.bypassSecurityTrustHtml` retains that sanitiser, and it lands in the shared chunk `main` imports: **2,615 bytes gzip on every first load**, `/` included, for code the home route can never use. Measured across all four combinations; dropping either half alone saves 100–355 bytes, dropping both puts the chunk back to its size on `main`. The write happens in an `afterRenderEffect`, because it touches an element a template binding creates (`CLAUDE.md` §4.4). The security boundary is unchanged: `bypassSecurityTrustHtml` _means_ "Angular will not check this", so DOMPurify's allowlist is the boundary in both designs.
- **KaTeX emits MathML, and that is a CSP requirement.** Its default renderer positions every glyph with an inline `style`, which `style-src 'self'` refuses _silently_ — the attribute stays in the DOM with its declarations dropped (`CLAUDE.md` §4.4) — so a formula would render as overlapping characters with nothing in any console. MathML positions nothing itself, needs no stylesheet, and is native in every current browser. A unit test asserts that no `style` attribute and no `<style>`/`<link>` survives, which is what would catch a KaTeX upgrade changing its default.
- **Nothing new is in the initial bundle.** Both engines are dynamic imports and the maths one is behind a second condition — the text has to contain a delimiter — so a plain question fetches neither, and both are in the service worker's lazy group rather than its precache (`stack.md` §2.1). Until an engine arrives, and forever if it never does, the component renders the **source text**: a formula written as `$x^2$` is ugly, a blank question is unrecoverable.
- **Anything not on the allowlist is stripped, not escaped and not rendered**, and a payload inside a code fence renders as visible text — which is what a question about HTML injection needs. Headings, images and tables are outside it deliberately: a heading would out-shout the card's own, and `img-src 'self'` would refuse a contributor's image anyway.
- **An answer option renders in `[inline]` mode, which is narrower than prose in two ways the host element dictates.** The option is a `<button>`, so a link inside it would be interactive content nested in interactive content — invalid, announced as a link within a button, and a click that both answers and navigates; a Markdown link therefore renders as its own label, in the parser _and_ in the sanitiser, which drops `<a>` from the inline tag set. A `$$…$$` formula compiles undisplayed for the same reason: `display="block"` is what gives a formula its own block box, margins and scroll container, and that inside a line of button text is a hole in the row. Prose keeps both.
- **What KaTeX emits is measured against the allowlist rather than assumed.** Too narrow a list fails silently — no error, no console line, just a formula quietly missing part of itself, which is how `\boxed{x}` rendered as a bare `x`. `markdown-engine.spec.ts` compiles a corpus of formulas and asserts the sanitised output keeps every element and attribute KaTeX put there. The one deliberate loss is `\rule`, which KaTeX fills with `mathbackground`: a colour attribute that ignores the reader's theme, so the rule keeps its space and loses its ink.
- **A code block or a display formula scrolls inside its own container** and never widens the question card, because the answer buttons underneath would move (`CLAUDE.md` §4.4). Measured in a real browser at a tall viewport by `e2e/specs/authenticated/markdown-rendering.spec.ts`, which is the only layer that can see a box.
- **The configuration is published, for the renderer this repository does not run.** The question-generation pipeline (`FEAT-020` §B) renders every candidate the way this component will before a reviewer sees it, so the two have to agree, and a transcription would drift. `render-contract.json`, at the repository root, states it: the `marked` options with its replaced tokenizers and renderers, the math tokenizers and their delimiters, the KaTeX options and the defaults the renderer leans on by not passing them (`trust` above all), the DOMPurify configuration for each mode with its one hook, the release series of the three packages — and **which of two instances a source takes**. Each mode has a `marked` instance built with the KaTeX renderer and one built without, configured alike; the component hands a source the first only when `containsMath` finds a delimiter in it, so most questions take the second, and the file publishes that pattern. `render-contract.spec.ts` holds the file to the live engines rather than to a copy, all four instances of them — the `marked` options read off the instances `renderMarkdown` parses with, the KaTeX and DOMPurify ones captured on the call, the hook found where DOMPurify keeps it, the selection pattern compared with the one `containsMath` tests — so a value changed on either side fails.
- **`render-contract.golden.json` is the renderer's output for forty-nine inputs**, written from the live renderer under jsdom by `scripts/render-contract-golden.mjs` through the instance the selection rule picks, and re-rendered by the same spec twice: through the engine, and through `RenderedTextComponent`, which also has to have parsed each one with the instance the rule picks. A change that moves any output — a dependency bump included — fails until the script is run on purpose and its diff committed, and the corpus is what the pipeline's renderer has to reproduce byte for byte, in jsdom, whose parse5 writes `<` and `>` inside an attribute value where Chromium escapes them. What it covers: every element and attribute on the allowlist that any input can reach — all the prose ones, and every MathML one KaTeX 0.18 emits — with each of the four instances shown working with GFM; each construct the allowlist refuses; the KaTeX output the sanitiser has to clean (an error's inline style, a colour, a rule's fill, an untrusted command); the Markdown a rendering check has to rule on (an unclosed fence, unbalanced emphasis, an indented code block that renders exactly as a fence with no language, so only the tokens tell them apart); a link whose scheme is uppercase; inline mode's narrower rules; and **the renderer's known defects, as it renders them today and labelled as such** — `\overset`, `\underset`, `\stackrel` and `\mathop…\limits` lose their content (KaTeX nests them inside a token element, which the parser re-homes in the HTML namespace and DOMPurify drops with what is in it), `mathsize`, `linebreak` and an ordered list's `start` are stripped, and a table loses its header row — so the fix shows up as a diff there. Five MathML elements and three attributes on the list are not covered, because KaTeX 0.18 never emits them and raw HTML never reaches the sanitiser: `ms`, `merror`, `mmultiscripts`, `mprescripts`, `none`, `symmetric`, `form` and `movablelimits`. The spec holds the corpus to exactly that list. (`data-model.md` §3 has the bounds file it sits beside.)
- **`/terms` says which formatting a contribution may use** and that anything outside it is stripped rather than displayed (§1.9) — a statement about what the app does with submitted text, so it moves when the allowlist does, and `terms-formatting.spec.ts` fails when it has not.

**A question's topics are up to eight free-form tags** (`FEAT-021`, `FEAT-052`) — the only topic a question has since they replaced categories: a `tags` array of normalised kebab-case strings, chosen on `/add-question` (at least one) and on `/my-questions`' edit dialog, rendered as chips wherever a question is read, and filtered on from the setup screen (§1.1). A question written before the change carries a free-text `category` and no tags, and **every reader derives a tag from it** through one function, `topicTagsOf()` in `utils/category-tags.ts` — the quiz card's pill, the recap, the reviewer's card, `/my-questions`, the offline pool's narrowing and the play history all call it, so they cannot disagree, and a question's own tags win whenever it has both. What the derivation cannot do is serve the draw, which filters in the query; that is what the backfill is for (`data-model.md` §3).

- **Open Trivia DB's twenty-four categories are the seed tags.** `OPEN_TRIVIA_CATEGORIES` is a first-party table of id, name and tag, each tag the rule applied to the name — drop an `Entertainment:` or `Science:` family prefix, then normalise — so `Entertainment: Film` is `film` and `Science & Nature` is `science-nature`; `category-tags.spec.ts` pins every row against the rule. The table was taken from `FEAT-052`'s spec rather than from `api_category.php`, which was not reachable from where it was written, and the endpoint is what to check a row against. The same rule turns a free-text category nobody put in the table into the tag a contributor typing the same words would get — `Science` → `science`, `World War 2` → `world-war-2` — and a string that normalises to nothing (`!!`, or past thirty-two characters) derives no tag at all. The Open Trivia adapter's lookup is the table alone: a category the API adds tomorrow is served without a tag rather than given one the picker cannot offer or the request turn back into an id.

- **Free-form, and therefore normalised.** Nothing validates a tag against a vocabulary: no document holds the list, and a tag nobody has used before is perfectly valid. What keeps that from meaning "unbounded" is `normalizeTag()` (`utils/normalize-tag.util.ts`), the one pure function every writer and every filter goes through — symbols removed, letters folded to ASCII, lower-cased, whitespace and underscores collapsed to single hyphens, everything outside `[a-z0-9-]` dropped, and `null` under two characters or over thirty-two. So `World War 2`, `world_war_2` and `WORLD WAR 2` are one tag, and the filter, the recommender and (later) the generator all compare the same strings. Letters are **folded rather than dropped** because dropping one turns `matemática` into `matemtica` and `Straße` into `strae`, tags nobody types twice — the exact failure a normaliser exists to prevent. Folding is an NFKD decomposition, which takes the accent off a letter and splits a ligature or a compatibility form (`ﬁ` → `fi`, full-width `Ｆｕｌｌ` → `full`, `CO₂` → `co2`, the ordinal `2ª` → `2a`), followed by one explicit table for the twelve letters no decomposition reaches — `æ` → `ae`, `ø` → `o`, `ß` → `ss`, `œ` → `oe`, `ł` → `l`, `đ` → `d`, `þ` → `th`, `ð` → `d`, `ı` → `i`, `ŧ` → `t`, `ħ` → `h`, `ŋ` → `ng` — looked up after lower-casing, so the capitals reach it too. A letter outside the table with no decomposition is still dropped. Symbols go **before** the decomposition, because NFKD would otherwise spell `™` as the letters `tm` and turn a spacing accent into a word break: `McDonald´s`, typed with the acute accent a dead-key layout gives for an apostrophe, would become `mcdonald-s` instead of the `mcdonalds` that `McDonald's` gives. Folding can lengthen a tag (`ß` is two letters once folded), so the bounds apply to the folded text — `foldTag()` is that text before them, and it is what the picker measures to say whether a refused draft was too long or had nothing in it. `firestore.rules` cannot call this function, so it independently enforces the shape it produces (`data-model.md` §3).
- **The suggestion lists are hints, never gates.** `utils/tag-suggestions.ts` holds about forty English starter tags, and `QUESTION_TAG_SUGGESTIONS` — what the contribute form and the edit dialog offer — puts the twenty-four seed tags ahead of them, sixty-three in all once the five they share are counted once; the setup screen offers the seed tags alone, the only topics that narrow both sources. Both lists are exported for `FEAT-020`'s generator to be given in its prompt. Nothing validates against them. Reading the bank to discover which tags exist would be an unbounded read of a public collection (`CLAUDE.md` §4.1), and a `usageCount` per tag would be a Cloud Function, a volume cap and an idempotency problem for a number whose only job is ordering an autocomplete list. A static list buys most of the coherence for the price of a constant: somebody who sees `world-war-2` in the picker does not type `ww2`.
- **Difficulty is not a tag.** It is an existing validated enum the draw already filters on, and a `#hard` beside it would be a second place for the same fact to be wrong. It is absent from the suggestion list for that reason.
- **One `TagSelectorComponent` (`components/tag-selector/`) for all three places that choose tags** — the contribute form, the edit dialog and the setup screen's topic picker — and the edit dialog is why that matters: an owner update re-validates the whole payload (§1.13), so a dialog that could not show the tags would delete them on every edit, which is how a Markdown question came back rendering its own asterisks. It is a `ControlValueAccessor` rather than a two-way `model()` for the same reason: the dialog opens by `reset()`ting the shared form, and only a form-owned value hears about that. Every route in — typing, a suggestion, a paste — goes through the normaliser and the chip shows what would be **stored**, so nobody is surprised by what lands; a refusal says which bound it hit, because a chip that simply fails to appear reads as a broken control. Suggestions are `aria-pressed` toggles in a labelled `role="group"` and stay in the list once chosen, each remove button is named after its own tag, and every change is announced from a live region that exists from first paint (`CLAUDE.md` §4.5).
  - **What a caller can set** (`FEAT-052`): `max`, which at one makes the picker a single choice whose next pick _replaces_ the one chosen rather than being refused; `allowedTags`, which refuses a well-formed tag outside the set with the caller's `notAllowedMessage`; `required` and `errorMessage`, which make it a field like any other on the question form — `aria-required`, the error under the input and first in its `aria-describedby`, and no "(optional)" on the label; and `replaceSelection()`, through which a caller whose constraint tightens under a selection — the setup screen switching into Open Trivia — writes the survivors and has the picker say what went, the way it says every other change.
  - **Nothing in it changes size** (`CLAUDE.md` §4.4). The chip row and the suggestion strip are fixed-height and scroll rather than grow, and the hint line and the feedback line are each reserved at the tallest thing they can carry rather than the one showing. That needs the caller's help, because the component cannot know what it will be handed next: a caller whose hint or notices change passes **every** string it can show as `hintVariants` and `feedbackVariants`, stacked invisibly in the one grid cell. The setup screen passes twenty-eight hints and three notices, and the hints are why it has to — at desktop width two of them wrap to one line and two, so an unreserved switch between them moved the Start button 16 px at 1280 and not a pixel at 390, the viewport-dependence §4.4 warns about. With `deferSuggestions` the strip is empty on the first frame and its chips land on the first idle moment — bounded at two seconds, a half-second timer where `requestIdleCallback` does not exist, both cancelled with the component — or on the first focus or press inside the picker, whichever comes first, so a reader reaching for the control never finds it empty.
- **`QuestionTagsComponent` (`components/question-tags/`) owns the read side** — the reviewer's card, game-over's recap and `/my-questions` — as plain-text `<li>` chips in a named `<ul>`. A tag never goes through `RenderedTextComponent` whatever the question's `format` says: it is a key the filter compares, not prose, and a tag that could be Markdown could be a link. Stored values are re-checked rather than trusted — a non-string, an over-long string, a duplicate and anything past the eighth are dropped — because `custom_questions` is a public API the console can write to directly (`CLAUDE.md` §4.4). Every caller hands it `topicTagsOf(question)` (`FEAT-052`), so a question written before topics replaced categories shows the tag its category derives, and only a question with neither renders nothing. The recap labels each row with the question's first topic, as the quiz card does, and adds the chips only when there is more than one — the label has already said the first.

**A question's difficulty is calibrated from real play** (`FEAT-023`). Every community question carries two counters, `answered` and `correct`, which only `recordGameResult` writes — one answer for each signed-in game the question was in, and one right answer where it was answered right (`data-model.md` §3). `difficultyScore()` (`utils/difficulty-score.util.ts`) turns them into a number from 0 (everybody gets it right) to 1 (nobody does) at read time, and nothing derived is stored, so a change to the formula is a deploy rather than a migration. Three steps, each checkable by hand:

- **The contributor's label is the prior** — `easy` 0.25, `medium` 0.5, `hard` 0.75 — and a question nobody has answered scores **exactly** its label, which is what every question in the bank did before the counters existed. No reader needs a special case for an uncalibrated question, and nothing was backfilled.
- **The accuracy is corrected for guessing** before the prior meets it: `(accuracy − 1/n) / (1 − 1/n)`, with `n` the question's option count, two to six (`FEAT-051`) — the share of players who knew the answer if everybody who did not guessed. The same half-right record is pure chance on a true-or-false question and real knowledge on six options, and the bank holds both. Below chance clamps to "nobody knew it"; a perfect record lands exactly on the other end.
- **The label is shrunk towards what players did as `answered` grows**: the label counts as ten answers, `(10 × label + answered × observed) / (10 + answered)`. A question three players have answered stays close to its label, one three hundred have answered reads essentially as played, and nothing switches at a threshold — `answered` is the sample size, so no confidence field sits beside it. Ten because ten answers is roughly where the observed accuracy's spread (about ±0.16) meets a label bin's half-width (0.125).

The recap shows the band alone — `easy`, `medium` or `hard`, in the label's own words and pill (`difficultyBand()`, §1.1) — read off the score rounded to hundredths by the spec's table: `0.00`–`0.33` easy, `0.34`–`0.66` medium, `0.67`–`1.00` hard. Each label's own value therefore sits inside its own band, so a question nobody has played reads exactly as it was labelled; the score itself stays in code for the readers below. The counters are re-checked on the way in, the way the tags are: `TriviaService` carries a pair only through `readCounters`, which drops one a console edit has broken, whole. Neither response time nor lifeline use is an input — both are facts about a player, and they live in the play history, where its retention reaches them. **The recap is the only reader today**; `FEAT-029`'s difficulty band and `FEAT-018`'s ramping mode are the consumers it was built for, and drawing to a difficulty is theirs.

**The queue that reviews all this is `/review`** (`ReviewQueueComponent`), gated in the UI by `ReviewerService` and in the server by `isReviewer()` — the page decides what to render, the rules decide whether any of its buttons do anything (`CLAUDE.md` §4.2). Four tabs in one picker: the three moderation statuses, and **Reports** (`FEAT-026`), the complaints players file from game-over (§1.1). The tabs are a single `role="radiogroup"`, and one `ng-template` renders the question card in all four, so a decision made from a report is the same `status` write the status tabs make rather than a second path to keep in step. From any card with an account behind it, **"Everything this account contributed"** opens the abuse tooling (`FEAT-006`): one account's whole set, every status, with one action on the selection (below).

- **Whether to show any of it is one read of the caller's own `user_roles/{uid}`, made only for a real account, and made so that "no role" is not an error.** `ReviewerService` re-reads it whenever the account changes and caches the answer per uid. An anonymous session is answered without a request: it is handed a uid it did not choose, so it can never name a document a role was granted on (`data-model.md` § `user_roles`), and reading anyway would bill a request on every visitor's page load to learn nothing. The gate is the session saying it is anonymous — a user that is there — never the absence of one (`CLAUDE.md` §4.4); and it is not `isFullyAuthenticated()`, because `isReviewer()` asks for a signed-in caller rather than a verified one, so an unverified password account can hold a role and use it. For everybody else the read goes through `FirestoreRestClient.batchGetDocument` rather than `getDocument`, because of what absence looks like on the wire: a `GET` answers it with a `404`, and Chromium writes `Failed to load resource … 404` to the console at error level for every response with an error status, `fetch` included — so the answer almost every signed-in account gets would log an error on every page load whatever the app did with it. `review-queue.spec.ts` pins the `200`, because Lighthouse cannot: its visitor is anonymous and is not read for (`ci-cd.md` §4.4). `documents:batchGet` answers `200` with a `missing` entry instead, and `firestore.rules` evaluates each document of it as a `get`, so the boundary is unchanged: another account's document is still a `403` for the whole request. That, a network failure, or a success naming the document neither way still throws and is logged as a failed read, rather than passing for an account with no role.
- **A report is shown with the question it is about, not a link to it.** A complaint is unreadable on its own — "the answer is wrong" means nothing without the answer — so a page of reports costs two bounded reads: `ReviewerService.getQuestionReports` for the newest `REPORTS_PAGE_SIZE` (25), then one batched `getQuestionsByIds` for the distinct questions they name, in `IN` filters of thirty (`data-model.md` § `question_reports`). **Show more reports** fetches the page after the last row from a cursor and appends it, so a second click costs one page rather than two — and it disappears when the service says there is no next page rather than staying to fetch nothing.
- **A report whose question is not there renders as a report, whatever the reason.** The question may have been deleted from the console since it was filed — nothing cascades — or its stored `questionId` may be unusable as a document ID at all, which the console can write and which `firestore.rules` never sees because the field is only validated on create. The batched lookup leaves both out instead of failing, and the row says the question is gone: one malformed document must not take every complaint on the page down with it behind an error that retrying cannot clear.
- **Who filed it is never shown.** The uid is the one field in the document that identifies a person, and it is dropped in the service rather than merely left out of the markup, so it does not reach a component, a template or a screenshot. The report's document id ends in the same uid — it is the row's `@for` key and is likewise never rendered, which is pinned by a rendered unit test.
- **A rejection can say why** (`FEAT-007`). Each card carries an optional reason box, bounded at 500 characters to match `firestore.rules`, whose contents are written to the question as `rejectionReason` and shown to its author on `/my-questions` — except on a question the generation pipeline wrote (`FEAT-020`), which has no author to show it to: once one is rejected its box reads "Reason kept on the record" where a person's reads "Reason shown to the author", and every label fits one line at 390px, so a decision made from a report, which changes the label in place, does not change the card's height. Three details are deliberate. It is **rendered on every card rather than revealed by clicking Reject**, so the row does not resize under the reviewer's cursor (`CLAUDE.md` §4.4) and so the reason is typed before the decision, which is the order a reviewer works in. Its drafts are **keyed by question id**, because one `ng-template` renders every row and a single shared value would send the words typed about one question with another one's rejection. And the box **starts as whatever reason the question already carries**, so re-rejecting to correct a typo does not silently wipe a note the author has already read; typing into it, including emptying it, is what clears one.
- **Approving clears the reason in the same write.** The rules refuse a `rejectionReason` on a question that is not `rejected`, so an approval carrying a stale note is refused outright rather than merely untidy — and a rejection note on an approved question would be a false statement shown to its author.
- **On the Rejected tab the same button reads "Update reason", and it is the only control that reaches the rule the reviewer's note exists for.** `firestore.rules` deliberately permits a write that changes `rejectionReason` while leaving `status` where it is, so a reviewer who thinks of the wording afterwards does not have to decide the question again. Hiding the button as a no-op — which is right for Approve on an approved card — left the box pre-filled and editable with nothing able to send it, and Approve, the one button remaining, discarding what was typed. Two things follow from a decision whose status equals the tab it was made in: the row is **updated in place rather than dropped**, because it still belongs to the list it is in, and the announcement says **"Reason updated."** rather than "Question marked rejected", which would narrate a decision nobody made (`CLAUDE.md` §4.4).
- **Reports are not resolved or dismissed.** There is no "handled" flag: adding one means a client write path into a collection that deliberately has none, and rejecting the question is the act the report was asking for. So a decision made from a report updates that row's copy of the question in place — every row naming it, since several complaints about one question is the normal case — and leaves the report standing as the record that somebody complained.
- **The tab's messages share one grid cell**, rendered from first paint and switched with `invisible`, so "No reports have been filed" occupies exactly the space "Loading reports…" had and the tab does not resize when the read lands (`CLAUDE.md` §4.4). A failed read outranks an empty one: a refused or timed-out read says so and offers "Try again", because telling a reviewer their queue is clear on the strength of a read that never answered is the false narration §4.4 forbids — and here it would hide complaints rather than merely mislead.
- **The card's `Author:` line names who wrote the question** — the uid; "Unattributed (predates attribution)" for a question with no `createdBy`; or "Question pipeline" for one the generation pipeline wrote (`FEAT-020`), whose run has a `Run:` line of its own under it, read from its `provenance`, cut to 32 characters (`shownRunId`) and absent where the map names none. **Nothing on either line is cut**: a reviewer reads an author or a run to act on it, and a clipped identifier names nobody, so every value is readable whole at a phone's width — the author on one line, and the run id's 32 characters on one line from a 390px phone up, wrapped by `break-all` rather than clipped on anything narrower. `generated-questions.spec.ts` checks both lines for content wider than their box at 320 and 390px, since a text assertion reads the DOM whether or not the box shows it, and their height against a uid's line — the author line at 320, 390 and 1280px, the run line from 390 (`CLAUDE.md` §4.4). The card's source line reads as the recap's does, "Machine-generated from …", because this is the card that has to show a question as a player will meet it.
- **Everything one account contributed is reached from a question, never from a uid** (`FEAT-006`, `AuthorContributionsComponent`). Every card with an account behind it — in a status tab or under a report — offers "Everything this account contributed"; a question written before attribution has no `createdBy` to look up, one whose author erased their account carries the `[deleted-user]` sentinel, which every erased author shares, and one the generation pipeline wrote carries `[generated]`, which every question every run promotes shares (`FEAT-020`) — so none of the three offers it, and the pipeline's whole output is never presented as one account's under copy about a reason shown to its author. The view names the account by the question it was opened from, and the uid travels from that card to the read as a filter value and is rendered nowhere in it. The queue is hidden rather than destroyed while it is open — its rows, its drafts and the button that opened the view are all still there — and the view is in-page state rather than a route, the same as the tabs, so no uid reaches the address bar or the history.
- **The read is `/my-questions`' query at the review page size**: `FirebaseService.getQuestionsByAuthor` sends `where('createdBy','==',uid)`, `createdAt` descending with the document id breaking ties, and a `limit` of `AUTHOR_PAGE_SIZE` (50, `REVIEW_PAGE_SIZE`), paged on a cursor. It rides the `(createdBy ASC, createdAt DESC)` composite index that already existed, and both readers build the query from `models/contributions-query.ts`, from which `firestore-tests/indexes.spec.ts` derives the index it needs (`data-model.md` §3). No rule changed: the `isReviewer()` read branch admits a reviewer whatever the filter, and anybody else naming somebody else's uid is refused outright. The UI gate is the queue's own — the same `user_roles` document the rule reads — so it cannot drift broader than the server's (`CLAUDE.md` §4.2).
- **One action, on the selection: reject with a reason, and the reason is required.** It is the single decision's `status` + `rejectionReason` patch, issued once per selected document by `FirebaseService.rejectQuestions` — ten in flight at a time, with a count that moves while they go — never a batched commit and never a Cloud Function. Separate writes are what let a partial failure be reported as one: the rows that landed change status where they stand, the ones that could not be confirmed **stay selected**, so pressing Reject again is the retry, and the sentence says "could not be confirmed" rather than "was not saved", because a write that timed out may still have landed (`CLAUDE.md` §4.4). A question already rejected cannot be selected — re-rejecting it would only overwrite a note its author has already been shown, which "Update reason" on the Rejected tab does on purpose, one question at a time — and the reason box carries the same 500-character bound as the rules.
- **A selection never leaves its page, so one action names at most fifty questions.** Paging replaces the list rather than appending to it ("Newer contributions" / "Older contributions") and clears the selection, and `rejectQuestions` refuses more than `MAX_BULK_DECISIONS` ids or a blank or over-long reason before sending anything — the bound lives at the write as well as in the screen.
- **Nothing in it is destructive.** No deletion — a reviewer still cannot delete somebody else's question — and no account action: suspending or deleting an account is the owner's job in the Firebase console, and the view says so. Every rejection is reversible from the Rejected tab. Coming back, the queue's own copies are brought up to date without a second read — the Pending and Approved lists drop what was rejected, a report row shows its question's new status — and focus returns to the button that opened the view, or to the tab when that button left with its row.
- **Nothing in it moves under the reviewer** (`CLAUDE.md` §4.4): the read's messages share one grid cell, with fixed sentences so the failed face holds its height from the first frame; the selection line holds the count, the progress and the outcome in one cell beside an invisible copy of the longest outcome a page can produce; the reason box's error lands in a line held under its hint the same way, beside invisible copies of both its messages, so a refused submit does not push the Reject button just pressed, and every row, down a line; each row's status pill stacks all its labels in one cell, so a row the action rejects does not hand its question text more room and re-wrap; and the Reject button stacks "Reject selected" and "Rejecting…" so it is one width throughout. Focus moves to the heading when the view opens and to the status block before a page or a retry starts, since starting one disables the button that was pressed, and the Reject button is `aria-disabled` rather than `disabled` while the writes are out, for the same reason. `review-author-view.spec.ts` measures all of it in a browser.

### 1.5 Authentication & the leaderboard

Every visitor gets a **Firebase Anonymous Auth** uid shortly after the app loads (`AuthService.ensureSignedIn()`, started once from the root `App` component, on the first idle moment after first paint — `FEAT-017` §3.2, and §1.8 below for what else rides that callback) — there's no sign-in wall before playing. Signing in with a real provider is optional and only needed to save a score to the leaderboard, to keep lifetime totals and a play history (§1.10), or to like or dislike a question (§1.14).

Because that bootstrap is no longer part of boot, **anything that needs auth sooner starts it itself**. `AuthService.getAuth()` is memoised and lazy, so `whenAuthStateReady()`, `getIdToken()` and `whenProStatusReady()` all pull it forward at no cost when it has already run.

**That first attempt is retried, because one of them is not enough.** `ensureSignedIn()` swallows every failure — a visitor who cannot reach Firebase still gets a fully playable game, which is the point — and for as long as that was the end of it, a single dropped round trip, or one slower than the ten seconds `giveUpAfter` allows it, left the tab with **no uid for the rest of its life**: every game unsaveable, and nothing saying so until the player tried to save a score. A failed attempt now schedules the next at **2s, 5s, 15s and 30s** and then stops scheduling. The bound is the argument: a dropped round trip is retried twice over, while a refusal — a throttle, an exhausted quota — is not hammered by a client that will not take no for an answer. Stopping is not giving up, because every gesture that needs a uid calls `ensureSignedIn()` itself. The policy is a pure function (`src/app/utils/sign-in-retry.util.ts`) so it can be read and tested without a Firebase SDK, a timer or an injector near it.

Three details of that are worth knowing before touching it. Two events cut the wait short while a retry is pending — coming back **`online`**, and the tab becoming **visible** again, since a backgrounded tab throttles its timers to roughly once a minute and the schedule effectively pauses while nobody is looking. Those listeners exist only while a retry is pending and go with it, or with the injector (`CLAUDE.md` §4.4). And an attempt already in flight is **shared, not duplicated**, so a timer firing beside a click cannot mint two accounts — with the memoised attempt cleared however it settles, since a remembered rejection would be the original defect wearing a new hat (§4.4 again). It is invisible against the emulator, where the round trip is a millisecond and nothing fails on its own, so the coverage forces the failure instead: `e2e/specs/unauthenticated/anonymous-sign-in-retry.spec.ts` aborts the first `accounts:signUp` and asserts the session arrives regardless.

**Which screens can be caught inside that window is decidable rather than a guess**, and worth knowing before adding an interaction: every Firestore read goes through `FirestoreRestClient`, which awaits `getIdToken()` on each request, so any screen that reads anything has started the bootstrap before its own content renders. That leaves `/`, `/privacy` and `/terms`, which read nothing — and so the two gestures reachable from them start it explicitly: `AuthMenuStateService.open()`/`toggle()` (§1.5's account chip, whose panel would otherwise sit on "Loading…" and then grow into the sign-in form under the reader) and `DonationDialogStateService.open()` (§1.12, where the click that follows needs a uid to own the session document). The third thing in that window is the daily allowance, and it deliberately starts nothing: it renders at first paint, so pulling the bootstrap forward from it would simply undo the deferral. It renders optimistically until the claim lands instead — §1.8.

- **Top bar** (`TopBarComponent`, rendered as a sibling of `<router-outlet>` in `app.html`) shows a `/pricing` nav link, a `/review` link for reviewers, a light/dark theme toggle (§1.7), plus a sign-in trigger top-right on every screen.

- **It has two layouts, split at Tailwind's `sm` (640px).** Below it the bar is a hamburger, a centred brand and the account trigger, with the links and the theme toggle moved into a slide-out drawer; at and above it, the original row. The bar had reached five items, and the `/review` link made it worst for reviewers specifically. The drawer also carries **"Your stats"** (§1.10), which has no twin in the wide bar for exactly that reason — a sixth item there is what the split was done to avoid, and the auth menu already offers the same link at every width. Four details are worth knowing before touching it:
  - **The drawer renders outside `<header>`, and must stay there.** The header carries `backdrop-blur-md`, and a `backdrop-filter` ancestor becomes the containing block for `position: fixed` descendants — so a drawer inside it collapses to the header's 4rem box instead of covering the viewport. It fails silently, at runtime, only in a browser. `e2e/specs/unauthenticated/mobile-nav.spec.ts` asserts the panel is viewport-height for that reason.
  - **Below 360px the brand shrinks a notch, because at 320 it ran under the account chip.** Centring the brand in the _bar_ means its right edge is `W/2 + brandWidth/2`, while the chip is right-aligned at `W - padding - chipWidth` — so clearance is `W/2 - 171.7`, which goes negative below ~343px. Measured on production: at 320 the brand reached 220.34 against a chip starting at 208.64, an **11.7px overlap**, with the signed-out chip that a first-time visitor sees. Something has to give at that width; what gives is size (`max-[359px]:` on the wordmark, the mark, and the bar's side padding) rather than the wordmark or the chip's "Sign in" label, both of which survive intact. Swept 320–639 after: no overlap at any width, worst clearance 7.8px. **`mobile-nav.spec.ts` had asserted this exact property all along and passed throughout**, because it only ever ran at 390 where the brand clears by 23px — a single wide-enough viewport cannot fail this, and tells you nothing about the widths that can. There is a 320px describe block now.
  - **The brand is centred with `minmax(0,1fr) auto minmax(0,1fr)`, not `auto 1fr auto`.** The latter centres it between its neighbours rather than in the bar, which measured 21px off centre because the account chip is far wider than the hamburger. Plain `1fr` is not enough either — it is `minmax(auto,1fr)`, so a track grows past its share for a long display name and the symmetry breaks. Pinned by a measurement in the e2e spec, because it looks approximately right by eye at any of these.
  - **The drawer is in the DOM at all times, hidden, and it slides.** It was an `@if`, which can only ever animate one way — a CSS transition needs the element to still be there while it plays. Angular's `animate.leave` is the framework's answer and was rejected: it defers the _DOM_ removal while tearing the view down synchronously, so for the length of the exit there is a visible, focusable, tappable drawer on screen whose `(click)` handlers are already gone. Instead the overlay is permanent and hidden by three things bound to the same signal — `invisible` (**not** `hidden`; only `visibility` keeps the box laid out for a transition to start from, and it is the one property whose interpolation is defined to favour `visible`, which is what holds the drawer on screen for the whole exit and drops it exactly at the end), `inert`, and `pointer-events-none`. The last two land with the signal rather than with the animation, so the page underneath is usable the instant the drawer is dismissed. Panel slides on `transform`, backdrop fades on `opacity`, 250ms `ease-out`, all three gated on `motion-safe:` (`scripts/verify-motion.mjs` now enforces that for `transition-transform` too). **The backdrop is `absolute inset-0` and sits behind the panel**, which is a correction rather than the first design: it began as a `flex-1` sibling covering only the strip the panel does not, which was invisible while the drawer was open and obviously wrong the moment it closed — the panel slid left off bare, undimmed page, with the dim ending in a hard vertical line travelling across the screen. Covering the whole viewport is what makes the fade read as a fade. Its centre is then genuinely under the panel, so the e2e dismissal clicks its right edge (`click('right')`), which is a real click at an exposed point rather than `{force: true}`. Measured in Chromium: closed, the panel sits at x=-288 with the overlay `visibility: hidden` and `elementFromPoint` reaching the page behind it; 120ms into the exit it is still painted at x=-234 and already `inert`, `pointer-events: none`, and untouchable.
  - **Two silent focus bugs came out of that change, and both are worth knowing because neither is visible to a unit test.** Opening the drawer moves focus into the panel, and `focus()` on an element that is `inert` — or `visibility: hidden` — does nothing at all and reports nothing. (1) A plain `effect()` runs _before_ its bindings reach the DOM; instrumenting `focus`, `setAttribute` and `classList` in a browser shows `focus(panel)` at seq 1 and `removeAttribute(inert)` at seq 2. That ordering was always wrong — the effect reads a `viewChild`, which used to resolve late and force a second run once the DOM was correct, and making the panel permanent removed the accident. It now uses `afterRenderEffect`. (2) With the `visibility` transition applied in both directions, the first frame after opening sits at progress 0 where `visibility` still computes to `hidden`, so focus failed again — a reduced-motion browser focused the panel correctly while a normal one did not, which is what gave it away. A transition takes its properties from the after-change style, so it is now listed on the _closed_ class list only: it delays hiding and never delays showing. `mobile-nav.spec.ts` asserts focus lands in the panel, because jsdom enforces neither `inert` nor `visibility` and the unit spec passes either way.
  - **Widening past the breakpoint closes the drawer**, via a `matchMedia` listener with a matching teardown (§4.4). Without it the panel is unmounted by its own `sm:hidden` while focus is inside, dropping focus to `<body>` and leaving `aria-expanded="true"` on a trigger nobody can see. The 640px in the listener and the `sm:` in the template have to agree.

- **The chip never changes height, and that took fixing two real defects rather than a transition.** Measured in a browser, a cold mobile load moved through _three_ boxes: `Loading…` at 109×34, a `?` avatar at 64×42, and `👤 Sign in` at 107×**54**. Both intermediate states were bugs.
  - **The `?` was a wrong-state flash.** `onAuthStateChanged` fires once with `null` and flips `authReady` before `signInAnonymously()` delivers anybody, and `isAnonymous()` is `user()?.isAnonymous ?? false` — `false` for a null user. So the template fell through to the signed-in arm and rendered the `initials()` fallback, which is precisely what the `authReady()` gate exists to prevent, reintroduced one branch down. The chip now branches on `showsRealAccount()` (`user() !== null && !isAnonymous()`); the same window reopens on every sign-out, so this is not a cold-start-only fix.
  - **The 54px was "Sign in" wrapping to two lines**, squeezed by the `minmax(0,1fr)` grid track that the mobile layout introduced. Fixed with `whitespace-nowrap` plus hiding the decorative chevron below `sm`, which buys the ~22px that keeps it on one line. It shipped because the mobile-nav spec measured width, overlap and centring but never height — `mobile-nav.spec.ts` now asserts the height too.
  - **The loading placeholder is a skeleton shaped like the resolved chip**, not the word "Loading…" — an avatar-sized circle plus an `invisible` "Sign in" reserving its width, with the label kept as `sr-only` and `aria-busy` on the trigger. Sized to the anonymous chip on purpose: that is what a first load almost always becomes, so height _and_ width are now identical before and after (95×42 at 320/390, 123×42 at 1024). There is nothing left to animate. A returning signed-in session still changes the chip's width once — unavoidable without knowing the outcome in advance — but not its height, and the centred brand does not move because the grid tracks are fixed.

- **The loading placeholder is the pulsing avatar, and the chip grows into "Sign in" only if that is the answer.** The placeholder is deliberately the shape of the _signed-in_ chip — 42px on a phone, 70px with the chevron above `sm` — because that is what a returning player resolves into, so the common case moves not at all. If auth resolves to nobody, the label region opens and the chip widens to 95.4px / 123.4px. A width-reserving skeleton **bar** (the real label rendered `text-transparent`, so the box kept the text's metrics) stood here while the resolved chip still showed a display name; once it stopped, the bar was reserving room for something that never arrives, which is the same shift in the opposite direction.

- **The chip has exactly two widths on a phone, and that is a product decision before it is a technical one.** Avatar-only (42px) or avatar-plus-"Sign in" (95px). Everything except the signed-out state collapses to the first, so the transition only ever widens and it fires precisely when the bar has something to offer. A returning player's chip resolves to their avatar without moving, which is what you want when the next thing they do is start a game; a signed-out player gets a small movement in the corner of their eye pointing at the one action available to them. The cost, stated plainly: the pulsing skeleton **bar** cannot also be shown on a phone, because it is the wide state the animation grows into.

- **A content-driven width is not directly animatable, so what animates is `max-width`.** A transition animates a change to a **property**; the chip's change comes from its content while `width` stays `auto`, so there is nothing to hook. The label region goes `max-width: 0` → a 5rem cap with `overflow-hidden`, and the label wipes into view from behind the avatar.

- **`grid-template-columns: 0fr` → `1fr` was tried first, does not work here, and is worth recording because it fails silently.** It is the technique every accordion recipe reaches for, and the reason it works there is a condition this chip does not meet: an `fr` track only collapses when the grid container has a width of its **own** to divide up. Every box in this chain — the region, the button, the `div.relative` around it — is shrink-to-fit, so the container is sized _from_ the track's max-content and the `fr` then fills exactly that. Measured in the real bar, `0fr` left the track at **53.36px, identical to `1fr`**, and an inline `style="grid-template-columns:0fr"` did the same.

  **Every layer of verification missed it except the last.** The unit tests passed, because they assert which class is set and the class was set correctly. A standalone probe against the compiled stylesheet passed, because its ancestor chain was a plain flex row rather than the real header, and there the track genuinely did collapse. A frame-by-frame trace of the running app passed, showing 42px → 95.4px over 15 frames — which was the label _appearing_, exactly the failure mode the JavaScript version was replaced for. Only the e2e suite caught it, on the one state whose content is genuinely zero-width: a signed-in chip measured 50px against the 42px it has to match, because the `ml-2` wrapper stayed in flow. The lesson is narrow and worth keeping: **a probe is only evidence about the layout it reproduces**, and this one's ancestors were the whole variable.

- **The cost of `max-width` is timing, and the cap and duration are chosen together to pay it.** Motion stops the instant the cap passes the content width, so the ratio of label to cap _is_ the fraction of the transition you can see. With `ease-out` that bites harder than the arithmetic suggests, because the curve spends its distance early: measured against the 53.4px label, a 5rem cap finished at **150ms of a 450ms transition** — 33%, nine frames, over before it registered. A 4rem cap at `600ms` gives **300ms of real movement across 18 frames**, which is the shipped setting.

- **The cap is a permanent-clip risk, not a transient one, so it was measured rather than assumed.** A label wider than its cap is not cut for the length of the animation — it is cut forever. The 4rem headroom survives the cases that would break it: every generic fallback face is _narrower_ than the shipped one (sans 50.8px, serif 48.1px, against 53.4px), and a larger root font scales the cap along with the text (at 125%: 66.7px against an 80px cap), so the ratio holds instead of drifting. `mobile-nav.spec.ts` asserts `scrollWidth <= clientWidth` on the label region — against measured widths rather than a fixed number, since the font, the copy and the root size are exactly what would move the label past the cap — plus `clientWidth > 0`, because an overflow check on a collapsed region would pass vacuously.

- **This replaced a JavaScript animation, and the reason is worth keeping.** The previous version was a FLIP: read the width in an `effect()` (Angular has updated the signals but not the DOM, so it is still the previous render), read it again in `afterNextRender`, set an inline width and transition to the new one. It was correct in principle and unreliable in practice — it needs the chip to have painted at least once before auth resolves, and when the two land in the same frame there is nothing to measure. Reported from a real phone emulation as "the animation seems to rarely run". The CSS version ran on 18 of 18 cold loads at 1× and 4× CPU throttling; the browser owns the interpolation and Angular's whole contribution is one class on one element. It also made the behaviour testable: jsdom cannot measure a width, but it can read a class, so the unit suite now pins the behaviour itself instead of the scaffolding around it.

- **One honest limitation: this animates a layout property, so it cannot be composited.** Every frame runs layout on the main thread. At 8× CPU throttling the sweep degrades to about two intermediate frames — it still completes and never jumps, but it is choppy. For a 53px change in a top bar that is an acceptable trade, and there is no transform-based alternative that can size itself to its content.

- **A failed auth bootstrap no longer strands the chip.** `AuthService.getAuth()` memoised the dynamic `firebase/auth` import plus the runtime-config fetch with no `.catch` clearing it, so one failed chunk fetch was replayed for the life of the tab (`CLAUDE.md` §4.4). The compounding part was downstream: `authReadySignal` is only set inside the `onAuthStateChanged` callback, which then never registers, so `authReady()` stayed false **forever** and the chip pulsed at a user whose auth was never coming. The cache now clears on rejection _and_ resolves `authReady`, because "ready, and nobody is signed in" is the true statement once the attempt has failed — rendered as the "Sign in" prompt, which retries when clicked. Note this widens what `authReady()` asserts, from "auth resolved" to "we know the answer, and it may be nobody"; every gate on it wants the second meaning.

- **The account chip is its avatar at every viewport**, and the desktop exception that used to survive here was the last layout shift in the bar. Below `sm` this began as an overlap fix — a long display name plus the PRO badge ran into the centred brand. Above `sm` there was room, so the name stayed, and that made the chip's width a function of two things that arrive late and _separately_: the name when auth resolves, then the PRO badge a beat later when the Stripe claim does. Measured at 1024px against a 123.4px skeleton, a short name landed at 104.4px, a short name with PRO at 144px, and a 29-character name at 277.5px — up to three widths per load, in both directions.

  **Reserving the space instead was measured and rejected.** A label slot fixed to the width of the string "Sign in" makes every state 123.4px, but fits **four characters and an ellipsis** — and PRO-as-a-ring does not rescue it, because the badge was not the binding constraint. A slot sized to the widest name makes every state 276.8px and leaves a signed-out user looking at ~150px of nothing. Remembering the last name's width in `localStorage` is the only route that keeps the name at a readable size, and it still shifts on first load and after a rename elsewhere.

  Two details are load-bearing. The name and badge text are `sr-only`, not `hidden`: `sr-only` positions them absolutely, so they contribute no width or gap, while the button's accessible name still reads "Bartholomew Featherstonehaugh PRO". The avatar beside them is `aria-hidden` (§1.15), so without them the trigger would be announced with no name at all — a worse bug than the shift and a much quieter one. And the `sr-only` span sits **outside** the region that collapses to zero width; Chromium exposes clipped text either way (measured, not assumed), but a zero-width `overflow: hidden` box is exactly the shape engines disagree about, which is why the `sr-only` recipe uses 1px rather than 0.

- **Pro status is a ring on the avatar, not a badge.** `ring-2 ring-emerald-400` with an offset is a box-shadow, so it marks a paid account for **0px** of layout — where the pill it replaced cost 20.6px and, because it depended on the Stripe claim rather than on auth, arrived after the chip had already settled once. The PRO text itself stays in the `sr-only` name, so nothing is lost to a screen reader, and the auth menu still shows the full badge.

- **The avatar in a signed-in chip is the player's own choice** (§1.15): `AvatarComponent` at its `sm` size, which is the same 28px box whatever it draws — the initial on first paint, then the built avatar or the Google photo once `AvatarService` has read the stored choice, and the initial again if a photo fails. So the choice arriving changes the picture and never the chip. The PRO ring and the unverified-email dot sit on that box exactly as before; the dot is projected into it after the drawing, so it paints on top of a photo too. `avatar-choice.spec.ts` measures the chip across all three kinds at 390 and 1280px, side by side in one run. The loading skeleton and the signed-out 👤 are unchanged — they are states of auth, not of a choice.

- **The drawer follows the same disclosure contract as the auth menu** (`CLAUDE.md` §4.5): `aria-expanded` + `aria-haspopup="dialog"` + `aria-controls` on the hamburger (constant now that the panel is permanent, rather than dropped while closed to avoid naming an element that was not in the document), `role="dialog"` with a label on the panel, Escape from anywhere, focus into the panel on open and back to the trigger on close. Like the auth menu it is deliberately **not** `aria-modal` — nothing traps focus or inerts the page, and claiming otherwise would be a promise the markup does not keep. It's a self-contained, removable component — dropping it (or gating it behind `EmbedModeService`, see below) leaves just the game panel.
- **The auth menu is a disclosure, and says so** (findings G1/G2): the trigger carries `aria-expanded`, `aria-controls` and `aria-haspopup="dialog"`, and the panel is `role="dialog"` with an `aria-label`. **Deliberately `dialog` and not `menu`** — an ARIA menu promises `menuitem` children and arrow-key navigation, and this panel holds a sign-in form, text inputs and links, which a screen reader would then announce as menu items. It is not `aria-modal`, because the page behind stays usable.
- **Focus follows the menu.** Opening moves focus to the panel (which is why it has `tabindex="-1"`), so it is announced as a dialog and Tab reaches the close button first; Escape closes it from anywhere; and closing returns focus to **whatever opened it**, captured at open time rather than assumed to be the top-bar trigger — game-over's "Sign in to save your score" opens the same panel (`AuthMenuStateService`), and sending focus to the top bar after closing a menu opened mid-page would be its own bug. The restore falls back to the trigger if the opener can no longer take focus — **and "can no longer" had to grow twice.** Focusing a detached node silently drops focus to `<body>`; so does focusing a `visibility: hidden` one, which is the state game-over's "Sign in" prompt is now left in rather than being removed outright. But the check itself was in the wrong place: as a plain `effect()` it ran _before_ the bindings it inspected reached the DOM, so it always saw the previous frame and the `isConnected` guard had never once fired. Traced in Chromium on `main`: `in:open-sign-in` immediately followed by `out:open-sign-in->null`, focus handed to an opener Angular was about to take away in the same tick. It is an `afterRenderEffect` now (`CLAUDE.md` §4.4), and `sign-in-save-score.spec.ts` asserts focus lands on the trigger — jsdom enforces neither the refusal nor the ordering, so the unit spec passes either way. All of this is pinned by `e2e/specs/unauthenticated/auth-menu-a11y.spec.ts`: **Lighthouse scored accessibility 1.0 before and after**, which is precisely why it needed a real browser test rather than a tool.
- **Form inputs declare their purpose** (finding G6, WCAG 1.3.5): the sign-in form's email and password inputs carry `autocomplete="email"` and `current-password`/`new-password` switched with the sign-in/sign-up mode — those predate the audit and only needed confirming — while the two fields collecting the user's display name (the profile section here, and game-over's leaderboard name input) carry `autocomplete="nickname"`, which is what the confirmation actually turned up missing. Pinned by `e2e/specs/unauthenticated/auth-form-autocomplete.spec.ts` plus assertions in `profile.spec.ts`/`sign-in-save-score.spec.ts`, because no tool flags an absent `autocomplete` attribute.
- **Sign-in options**: Google and email/password are the prominent choices; a "more sign-in options" disclosure reveals Facebook, GitHub, Microsoft, Apple, Twitter/X, and Yahoo (`AuthService.signInWithOAuth`). Play Games and Game Center are Firebase console options with no Web SDK equivalent (native Android/Apple only) and are intentionally not offered here.
- **Anonymous-to-real upgrade**: signing in from an anonymous session links the new credential to the existing uid (`linkWithCredential`/`linkWithPopup`) instead of minting a new one, so anything already saved carries forward. When the server refuses the link because the account already exists, `signInWithOAuth` signs in with the credential the popup just produced (`credentialFromError` → `signInWithCredential`, falling back to a second popup in the rare case the SDK attached none) rather than handing the user an error. That switches uid and abandons the anonymous one — there is no merging two accounts. Two codes arrive there and are handled identically: `auth/credential-already-in-use`, where the provider account itself is already linked to another uid, and `auth/email-already-in-use`, where the provider's **email address** belongs to another account — which under this project's "one account per email" setting is enough for the server to refuse the link, and in practice means an email/password account owns that address. A third, `auth/account-exists-with-different-credential`, deliberately does **not** go through that branch and still shows its own message: the provider did not report the email as verified, so the server will not hand the account over on its say-so, and linking it needs a flow this app does not have (`known-gaps.md` §6).
- **What an OAuth sign-in then does to a password account holding the same email is decided by the server, not by this code**, and it turns on whether that account's email was ever verified. Measured against the Auth emulator's implementation of Identity Toolkit (`firebase-tools`, `handleIdpSigninEmailRequired` in `lib/emulator/auth/operations.js`), signing in with a Google credential whose email the provider reports as verified lands on the **existing account's uid**, never a new one — and from there:
  - if that account's email **was verified**, `google.com` is added alongside `password` and the password goes on working;
  - if it was **never verified**, the password hash is erased and the `password` provider unlinked, the account's email is marked verified, and outstanding refresh tokens are invalidated (`validSince` moves). The account, its uid and everything stored under it survive — only the way in changes. "Forgot password?" puts a password back on the same uid, and in that same implementation a password reset unlinks the federated providers in turn, so an account carries whichever sign-in method was established last rather than both at once.
- **Lazy OAuth popup resolver**: `AuthService` calls `initializeAuth(app, { persistence: browserLocalPersistence })` — deliberately _not_ the `getAuth()` convenience wrapper, which wires in `browserPopupRedirectResolver` unconditionally and, as a side effect, eagerly loads a third-party iframe on the Firebase `authDomain` (plus Google's gapi.js) on every page load to check for a pending redirect result, whether or not that visitor ever uses OAuth. Since most visitors only ever play anonymously, `signInWithOAuth` instead passes `browserPopupRedirectResolver` explicitly at call time, so that iframe/script only loads for someone actually clicking a provider button. Confirmed via a Lighthouse best-practices "third-party cookies" audit failure on a real (non-Incognito) browser profile that reproduced only when that iframe loaded — a network trace before/after this change showed the `firebaseapp.com/__/auth/iframe` and `apis.google.com` requests disappearing entirely from the anonymous-only page-load path.
- **Email alias blocking**: sign-up rejects `name+tag@domain.com`-style addresses client-side (`isAliasEmail`, `utils/email-alias.util.ts`) — this stops the UI from creating alias accounts but not a direct Auth API call; see the anti-cheat note below.
- **Password reset** (finding H1): the sign-in form carries a "Forgot password?" action that sends Firebase's reset email via `AuthService.sendPasswordReset`. The confirmation is deliberately neutral — "if an account exists for that email…" — and **identical whether or not one does** (`auth/user-not-found` is swallowed as success): a reset form that answers differently for known and unknown addresses is an account-enumeration oracle. Real transport failures still surface. The auth panel's async outcomes (this one, verification sent, save/delete failures) are announced through a **permanent sr-only `role="status"` region** whose text changes, never inserted mid-announcement — the same pattern, for the same reason, as the quiz result region (G3). `password-reset.spec.ts` pins both the sent path and the unknown-address path against what actually reached the Auth emulator.
- **Email verification**: an email/password account is not treated as "fully authenticated" (`AuthService.isFullyAuthenticated`) until its email is verified. Anonymous and unverified-password users can play and view the leaderboard but the "Save Score" action is replaced with a sign-in/verify prompt.
- **Anti-cheat enforcement is server-side, in `firestore.rules`**, not just the client: a leaderboard write is only accepted if `request.auth.token.firebase.sign_in_provider` isn't `anonymous`, and — for password accounts — `email_verified` is `true`. This is what actually stops someone from bypassing the UI to flood the board with throwaway accounts; the client-side gating above is just so the UI reflects the same rule.
- **`EmbedModeService`** reads `?embed=1` from the URL to hide the top bar entirely for iframe/widget use — anonymous-only play, no leaderboard saves, no code changes needed on the embedder's side. Every button that opens the auth menu is gated on the same check and disappears with it, since the menu it would open is no longer on the page: game-over's "Sign in to save this score" (§1.1) and `/profile`'s signed-out "Sign in" (§1.10).

### 1.6 Pro subscription & billing (Stripe)

A single paid tier, "Pro" — one monthly subscription, sold in whichever currencies the Stripe catalog carries a price for — gates the ability to add custom questions (§1.1, §1.4). The whole flow is serverless, backed by a `functions/` Cloud Functions package this repo owns outright (`stack.md` §2.4) rather than a third-party SDK or a marketplace extension — the original implementation used the official "Run Subscriptions with Stripe" Firebase Extension, but that entire product line [announced it's shutting down in March 2027](https://firebase.google.com/docs/extensions/faq-and-troubleshooting) (new installs already blocked at the time this was migrated), so it was replaced with equivalent functions using the _same_ Firestore schema and custom-claim contract — the frontend below didn't need to change shape, only where the data comes from.

- **`SubscriptionService`** is the client-side entry point: an `isProUser` signal derived from the `customers/{uid}/subscriptions` Firestore subcollection (`stripeWebhook` keeps this synced from Stripe, `stack.md` §2.4) filtered to `active`/`trialing` status, `startProCheckout()` (creates a `customers/{uid}/checkout_sessions` doc through the shared `SessionHandshakeService`, carrying only a price ID and this browser's origin — `data-model.md` §3 — and waits for `createCheckoutSession` to write back a hosted Stripe Checkout URL, then redirects; for an eligible reader that handshake has already run in the background, so the click is the redirect alone — see below), and a dynamic Pro-price lookup from the public `products`/`prices` collections (`data-model.md` §3) — no Stripe price ID is ever hardcoded client-side, so changing the price in the Stripe Dashboard needs no frontend deploy. That lookup **selects on `role: 'pro'`, the same predicate `createCheckoutSession` enforces server-side** (`functions/src/checkout-request.ts`), rather than on "first active product with a monthly price": those are the same question only while exactly one product exists, and the day a second is added the client would send a price the server is bound to reject. Both its queries carry a `limit`, and the per-product `prices` reads run **in parallel** — they used to be awaited one at a time, so the wait was the sum of the round trips rather than the slowest. Which price wins is decided by catalog order, never by which response arrives first.
- **Currency is a choice of _price_, and Brazil is why it exists.** The lookup resolves **every** active monthly price of the active Pro product(s), one per currency (a duplicate currency keeps the first in catalog order; a price the catalog carries no `currency` for is dropped), and exposes each as `{ priceId, currency, unitAmount }`. `PricingComponent` renders the selected one — amount formatted with `Intl.NumberFormat`, in the **currency's own** locale rather than the reader's, so R$ 5,90 is never shown wearing US punctuation — and offers a two-option segmented control (`CurrencySwitchComponent`, `role="radiogroup"`, `CLAUDE.md` §4.5) when more than one currency is on sale — the same control the donation dialog uses (§1.12), so there is one segmented picker in the app rather than two that can disagree about their ARIA. Choosing a currency chooses which Price ID `startProCheckout()` writes, and nothing else: there is no currency field on the session document, so the function's existing catalog check covers the choice exactly as it covers any other price ID a client can send. **The default is BRL for a visitor the app places in Brazil** (`defaultProCurrency`, fed by `GeoService` below), otherwise USD, otherwise the catalog's first — and it is a requirement rather than a nicety: a Brazilian-issued card cannot be charged in USD by this Brazilian Stripe account, and Stripe's Adaptive Pricing does not rescue it, because it localises prices only for buyers _outside_ the merchant's own country (`stack.md` §2.4). The country is a UI signal and nothing more (`CLAUDE.md` §4.2); what is charged is decided by the price ID the server validates.
- **Where the visitor is comes from `GeoService`, in four steps, and language is not one of them.** The chain is the app's own server, then the server's last answer, then the browser's IANA time zone, then nothing — and "nothing" means the catalog's default currency, which is what a reader outside Brazil gets anyway.
  1. **`/api/geo`**, a same-origin `fetch` with a 2 s `AbortSignal.timeout`, answered by a Cloud Function behind a Firebase Hosting rewrite that reads the `X-Country-Code` header Hosting resolves from the client IP (`stack.md` §2.4, `ci-cd.md` §4.1). Only `200` with a JSON content type and a two-letter `country` counts; a `5xx`, a timeout, or the `200 text/html` SPA shell that a deployment without the rewrite answers with all read as "could not say". A real answer is memoised for the tab; a failure deliberately is not (`CLAUDE.md` §4.4).
  2. **What the server said last time**, kept for a day in `localStorage` (`PricingCacheService`). It outranks the clock below because it is still an answer about an _address_ rather than about a machine's settings, and it is what `knownCountry()` — the synchronous answer a cache-first render opens on — reads first. Only a real answer is ever stored: caching "could not say" would turn one blocked request into a day of never asking again.
  3. **`Intl.DateTimeFormat().resolvedOptions().timeZone`**, matched against Brazil's sixteen IANA zones. It costs no request, it is what `ng serve` and every PR preview channel actually run on (`ci-cd.md` §4.2a — preview channels deploy Hosting only, so the function is not there), and on a Brazilian machine it is already the right answer, so the pre-selection lands on the first frame the control exists rather than moving a beat later.
  4. Nothing, and the price's own default.

  Two properties are load-bearing. **The server outranks the clock**: a laptop still set to São Paulo in a New York hotel is a Brazilian clock and an American card, and the address is the half that decides whether the charge goes through. And **a manual choice made before the server answers wins** — the control is on screen from the moment the catalog lands, up to two seconds before the country does, and an answer that silently reverted a deliberate click would be undoing the one gesture the control exists for. `SubscriptionService` records that the reader chose, and drops the record only when the currency they chose stops being on sale. That rule now covers one more window than it used to: a returning visitor's control is checked from the first frame, off a remembered country, so their click can land well before this visit's own answer does.

- **Choosing a currency is only free until the account has been billed in one, and the page cannot tell in advance which account that is.** Stripe bills a customer in a single currency: whatever commits them first — a live subscription, an invoice item, a completed payment — fixes it for every later checkout. The client has no way to see that. `customers/{uid}` mirrors the Stripe customer _id_ and nothing else, and the currency lives on the Stripe object, which the browser must never be able to read. So **both options keep showing to someone who is already committed**, and the refusal arrives from the server on the Subscribe click: `createCheckoutSession` answers it with which currency the account is fixed to, and `PricingComponent` shows that message under the button like any other checkout failure (`stack.md` §2.4). Stated rather than papered over — mirroring the customer's currency into Firestore to grey the other option out would be a new field, a new webhook path and a new thing that can go stale, for a case that only reaches someone who has already bought once in the other currency. The far commoner version of the same refusal is not a commitment at all but an abandoned checkout holding the currency for 24 hours, and that one the click clears itself: the function expires the customer's open sessions before it creates a new one.
- **The page renders from this browser's own copy first and revalidates behind it.** The resolved catalog (`{ priceId, currency, unitAmount }` per currency) and the country the server last named are kept in `localStorage` under one namespaced key each with a stored-at stamp and a **24-hour TTL** (`PricingCacheService`, which owns every storage key, its parsing and its expiry). A returning visitor therefore has the amount, the currency and the switch on the first frame, with no geo round trip and no Firestore read in front of them; a first-time visitor gets exactly what they got before, a placeholder for as long as the read takes. Every load then re-reads both in the background and publishes the answer **only if it differs**, so the usual case — nothing changed — is a render nobody sees. **A price edited in the Stripe Dashboard reaches a returning visitor on their next visit**, and a reader sitting on the page while it is edited keeps the old amount until they reload; what they are _charged_ is never stale, because the price ID is validated against the live catalog by `createCheckoutSession`. A cached catalog that cannot be parsed in full is discarded rather than partly trusted — the list is ordered, and the order decides the default currency — and storage that is unavailable outright (Safari private mode, a quota refusal) costs the page its speed and nothing else.
- **The read is paid for before the reader arrives, where anything signals they are coming.** Hovering or focusing any link to `/pricing` or "Upgrade to Pro" — the top bar, the nav drawer, the auth menu, the daily-limit offer, the add-question gate — calls `SubscriptionService.primePricing()`, which resolves the catalog and the country into the same cache without rendering anything. The same runs once per page load on `requestIdleCallback` for a signed-in, non-anonymous reader the subscription read has just confirmed is **not** Pro: the people who can actually buy. It deliberately does **not** run on every anonymous page load — that is the read cost this page has always refused to pay for visitors who never open it.
- **The cost, stated plainly.** A page load that reaches `/pricing` still spends roughly two public reads (the products query plus one prices query per active Pro product) plus one `/api/geo` request; the cache makes them late rather than absent, because an amount nobody revalidated is an amount nobody can trust past the Dashboard's next edit. Priming moves that spend earlier for a reader heading there, and adds it for a signed-in non-Pro reader who never does. Everything after the first read within a page load is free: the lookup is memoised for the service's lifetime, so the Subscribe click reuses it and so does navigating away and back. A rejected lookup is not cached (`CLAUDE.md` §4.4), so a catalog fixed in the Dashboard is picked up on the next attempt. A load that fails leaves the card showing whatever it had — a cached amount, or a placeholder — rather than a guessed price, and the cause is reported when the reader clicks Subscribe.
- **The card is the same height in every one of those states**, because two of its rows are filled by that read: the amount, and the currency cell beside it. Both are rendered from first paint — a dash and a non-breaking space — and the currency cell is the same box with the same padding and background whether it holds a placeholder, one currency, or a two-option radiogroup, so a second currency fills a control that is already there instead of creating one (`CLAUDE.md` §4.4). That is what makes the cache-first render safe: it fills the same boxes the placeholder was holding, so arriving early changes nothing about the layout. Pinned in `pricing.spec.ts` from both directions — holding the catalog read open with an empty cache and measuring the placeholder state, and again with a seeded cache and measuring the cached state — because jsdom has no layout and Lighthouse only ever loads `/`.
- **Subscribe is a redirect, not a wait, because the Checkout Session already exists.** The seconds that click used to spend were an Eventarc delivery, a cold start of `createCheckoutSession`, Stripe's own customer and session creation, and our 500 ms poll on top — none of which get faster, and all of which can happen while the reader is still reading the card. So `PricingComponent` runs the ordinary handshake in the background **one second after the currency last changed**, for a reader who could actually complete it: a real account, verified email, not already Pro, catalog resolved, and not on the `?checkout=success` page they have just been redirected back to. The resulting `{ uid, priceId, url, readyAt }` is written to `localStorage`, and the click then has three paths — a ready URL for the selected price redirects at once; a handshake still in flight is awaited rather than duplicated (the button says "Redirecting…" for the remainder); anything else takes the original path unchanged. Six properties are deliberate, and all six exist because **`createCheckoutSession` expires the customer's open sessions before creating another**, so there is only ever one live session and anything holding a stale URL sends the reader to Stripe's "this session has expired" page:
  - **A currency change discards the ready URL**, because the new session's creation expires the old one server-side — so keeping it "in case they switch back" would hand the reader a Stripe page that has already closed. Switching back creates a third session rather than reusing the first.
  - **A reload, and a second tab, reuse the stored entry.** Without it, five refreshes of a page somebody is thinking about would spend the whole ten-per-five-minutes volume cap (`data-model.md`, `checkout_sessions`) and the sixth click would be refused. It is `localStorage` rather than `sessionStorage`, and that is not a detail: a per-tab entry is invisible to the tab next to it, so a second `/pricing` would pre-create, its create would expire the first tab's session, and the first tab would go on believing its URL was live. One entry per device, checked against the current uid, usable for **20 hours** — a margin under Stripe's own 24-hour session expiry, since the stamp is the reader's clock and the expiry is Stripe's. It is written when the URL arrives rather than when the handshake starts, so a reload during the second or so it takes finds nothing and pre-creates again; that is one wasted session against the alternative of storing a URL that does not exist yet.
  - **It is re-read from storage on every use, never remembered in a field**, for the same reason: another tab can have replaced or cleared it since. A price that no longer matches means "create a fresh one", which is what the click then does.
  - **Only one handshake runs at a time.** A currency change while a pre-creation is in flight does _not_ start a second: two concurrent creates race, and whichever lands second kills the other's session with nothing on the client able to see it. The reader's new currency is picked up by a single retry once the slot is free — **a retry that belongs to pre-creation, not to the handshake**, because Subscribe runs the same handshake and a retry attached to it would fire on the click path too, dispatching a second create before the redirect and expiring the very session the tab is navigating to. A click that cannot wait simply creates its own session.
  - **Pre-creation is capped at three sessions per five-minute window**, out of the ten the rules allow, so idly flicking the currency switch cannot exhaust the cap the deliberate click needs. The count lives on the service, so it is really three _per page load_; a reload resets it and reuses the stored session rather than making another, and the rules' ten per window is the bound that actually holds. Running out is invisible: Subscribe falls back to creating its own session. So is a browser that will not store the entry at all (a private window, a quota refusal) — pre-creation stops after the first attempt there, because a URL nothing can find again is a session spent for nothing.
  - **A failed pre-creation is silent and is not cached.** Nobody asked for it, so there is nothing to report; the click re-runs the handshake and shows whatever it says — which is how "your account is already set up to pay in BRL" still reaches the screen.
  - **Each eligible visit to `/pricing` therefore creates a Stripe Checkout Session that may go unused.** They cost nothing, expire themselves after 24 hours, and are visible in the Stripe Dashboard; the document behind each one carries the same TTL as any other (`data-model.md`).

  **What remains is stated rather than solved**: a session can stop being live for a reason this page cannot see. Another tab can complete the checkout, or start one, after this tab last read the entry; and a Subscribe click that overtakes a pre-creation still in flight leaves two creates racing on Stripe's side, where the loser is decided by arrival order rather than by which URL the browser is about to use. Both end the same way — Stripe's "this session has expired" page — and clicking Subscribe again works, because the click finds no usable entry and creates a fresh session. Closing either would need the client to learn the state of a Stripe object it must never be able to read.

  Nothing changed server-side for any of this, and `minInstances` was deliberately **not** added to any function: pre-creation moves the cold start off the click path, so paying to keep an instance warm is now a separate cost decision rather than a latency fix.

- **Subscription status is read, not watched** (`BACKLOG.md` item 2). It used to be an `onSnapshot` listener, which was one of the two things keeping the 558.98 kB Firestore SDK in the bundle; REST has no equivalent, so the signal is now read when the signed-in user changes, and polled for up to 20 s on `/pricing?checkout=success` (the redirect back from Stripe races our own `stripeWebhook`, and often wins). **What is genuinely lost is a second tab updating without a reload** — for a tier costing around a dollar a month in whichever currency it is sold in, whose only entitlement is an "Add a question" link, against the largest thing the app shipped. Note it is also _cheaper_: a listener bills the initial read plus every change delivered for as long as the tab lives.
- **The actual security gate is a custom claim, not the subscription read above**: `stripeWebhook` sets `stripeRole: 'pro'` on the user's Auth ID token once an active/trialing subscription's price carries `firebaseRole: 'pro'` metadata (set once in the Stripe Dashboard, `ci-cd.md` §4 setup notes), and `firestore.rules` checks that claim directly (`AuthService.isProUser`, `data-model.md` §3). **Losing the subscription unsets the claim and revokes the user's refresh tokens** (`claims.ts`, `stack.md` §2.4) — but revocation forces re-authentication, it does not retract the ID token already in the browser. Firestore rules don't check revocation, so a lapsed subscriber's existing token still satisfies `isProUser()` until it expires, up to an hour. That residual window is **accepted, deliberately** (A13 in `AUDIT_REMEDIATION.md`, closed by decision 2026-08-10): closing it needs rules to compare `request.auth.token.iat` against a stored timestamp (a billed read on every privileged write) or against a fixed freshness bound (rules coupled to the client's refresh behaviour), and neither is worth it while the worst case is a lapsed subscriber adding questions for under an hour. Revisit if `stripeRole` ever gates something more valuable. `SubscriptionService`'s signal is read-your-own-writes UX only — the first time a read shows a subscription active, it proactively calls `AuthService.refreshIdToken()` so the claim doesn't have to wait on the SDK's ~1hr natural token refresh; `AddQuestionComponent` also force-refreshes immediately before its own write as a last-mile safety net against a stale cached token.
- **Checkout redirect UX**: on success, Stripe returns the browser to `/pricing?checkout=success`, which also surfaces a "Start playing" link back to `/`; on cancel, `/pricing?checkout=cancelled`. `PricingComponent`'s Subscribe button is gated on `AuthService.authReady()` (not just `isAnonymous`/`isFullyAuthenticated`, which both default to `false` before the very first auth state resolves) so a click landing in that brief window can't misfire the "verify your email first" branch. Once subscribed, the Starter card's "Your current plan" label is hidden (only the Pro card's "You're subscribed" shows) so the two don't both claim to be current at once.
- **A checkout or portal that fails to start says why, whenever the client has verified why.** `SubscriptionService` throws a `SubscriptionError` — a message written for the screen — for every failure it can explain: the caller is signed out; the catalog holds no active monthly Pro price (what an environment looks like before its Stripe webhook has delivered a single event, `dev-environment.md` §3.1 steps 8–9); the `firestore.rules` volume cap is spent; the handshake reached its 20 s deadline with nothing written back; or the function wrote an `error` onto the session document, which is its own client-facing message (`clientMessageFor`, `stack.md` §2.4). `PricingComponent` and `AuthMenuComponent` show that message as is, through `subscriptionFailureMessage`. A failure the service could _not_ explain — a `FirestoreRestError` from a dropped connection, a refused read, a 500 — keeps the generic "Could not start checkout. Please try again." / "Could not open the billing portal. Please try again." and goes to the console, the only place its cause survives once the screen has said "try again". That is `CLAUDE.md` §4.4 applied in both directions: distinguish the cases or stay generic — never narrate a cause nobody checked, and never hide one the code has already established. The person this is for is whoever is standing up a new environment: an empty catalog and a function that never ran both end in a red line under the Subscribe button, and "please try again" is the wrong instruction for either.
- **Nav surfacing**: the top-bar auth-menu and game-setup's "Create custom question" link both show a PRO badge (grey when locked, indigo once subscribed) next to the "Add a question" link. The menu's profile section also links **Your questions** (§1.13), above "Add a question" and with no badge — that screen is where a contribution is corrected or withdrawn, and neither needs a current subscription.
- **Self-service billing management**: a subscribed user sees a "Manage subscription" link in the auth-menu profile section (replacing the "Upgrade to Pro" link shown to non-Pro users) that opens Stripe's hosted Billing Portal — `SubscriptionService.openBillingPortal()` creates a `customers/{uid}/portal_sessions` doc and waits for `createPortalSession` (`functions/`, `stack.md` §2.4) to write back a portal URL, then redirects; same doc-create-then-poll handshake as `startProCheckout()` above. Lets a subscriber update their payment method or cancel without needing Stripe Dashboard access.

### 1.7 Light/dark theme

A manual toggle in the top bar (sun/moon icon button) switches the whole app between light and dark mode — this is a real user choice, not just following the OS setting.

- **`ThemeService`** (`src/app/services/theme.service.ts`) is a small signal-based service: `toggle()` flips a `currentTheme` signal between `'light'`/`'dark'`, adds/removes a `dark` class on `document.documentElement`, and persists the choice to `localStorage` (`trivia-theme`).
- **Tailwind is repointed at that class**, not its default `prefers-color-scheme` media strategy: `@custom-variant dark (&:where(.dark, .dark *));` in `src/styles.css` makes every `dark:` utility class key off an ancestor `.dark` instead. Every themed template/component pairs its light-mode utility classes with `dark:` variants inline (mapping documented in `BRAND_DESIGN_SYSTEM.md` §1's "Dark Theme" section) rather than a separate dark stylesheet.
- **No flash of the wrong theme on load**: `public/theme-init.js`, referenced as a render-blocking `<script src>` in `index.html` so it runs before Angular bootstraps, reads the same `trivia-theme` `localStorage` key (falling back to `prefers-color-scheme: dark` if nothing's stored yet) and applies the `dark` class immediately. `ThemeService`'s constructor just reads that already-applied class back into its signal rather than deciding the initial theme itself, so the two stay in sync by construction. It is an **external file rather than an inline script** because the CSP (`ci-cd.md` §4.1) allows no inline script at all. A `'sha256-…'` allowance would also have worked, but it fails _silently_: breaking the hash on purpose showed the browser refuses the script while the app still boots and still ends up correctly styled — `ThemeService` reapplies the class once Angular is up — so nothing goes red in the console, in Lighthouse or in e2e, and all that remains is the very flash this exists to prevent. An external file cannot drift out of sync with a hash that no longer describes it. It is served `no-cache` (`ci-cd.md` §4.1) because `public/` is copied without a content hash, the same reason `ngsw-worker.js` is excluded from the immutable rule.
- Not persisted server-side or per-account — it's a local browser preference, same as most theme toggles.

### 1.8 Installable PWA & offline play

The app is an installable Progressive Web App (scaffolded via `ng add @angular/pwa`, the Angular-recommended path — see `INFRASTRUCTURE.md` §2a for the setup notes) and can start a game with no network connection at all.

- **`public/manifest.webmanifest`**: name/short_name "Trivimind", `theme_color`/icons matching the brand mark (`BRAND_DESIGN_SYSTEM.md` §1's Primary Emerald `#059669`), `display: standalone`, and `icons` at every size Chrome's installability check + Android's home-screen/splash-screen icons need (72–512px, rasterized from `public/favicon.svg`, `purpose: any`), **plus two `purpose: "maskable"` variants at 192 and 512** — the two sizes Chrome's installability check reads and Android actually uses. The maskable pair is separate artwork rather than a relabelling of the `any` icons: measured, the mark's glyph reaches **49.9% of canvas width against a 40% safe-circle budget** (×1.247 over), so an adaptive-icon mask would clip the "?" mid-stroke. `scripts/make-maskable-icons.mjs` rebuilds them from the same `favicon.svg` — scaled to 0.78 and, critically, on a **full-bleed** ground with the `rx="32"` corners dropped, since a transparent corner on a maskable icon shows the launcher background through as an icon-inside-an-icon. The `any` icons keep their exact bytes; a padded icon shown unmasked just looks small. **Nothing else can check this claim** — Lighthouse dropped its PWA category in v12 — so `scripts/verify-icons.mjs` measures every committed PNG against the `purpose` the manifest declares, and runs in `lint.yml` (`npm run icons:verify`). It is pure Node: generating needs Chromium, checking does not. Linked from `index.html` alongside a `theme-color` `<meta>` tag matching the manifest.
- **`@angular/service-worker`** (`ngsw-config.json`, registered in `app.config.ts` via `provideServiceWorker('ngsw-worker.js', { enabled: !isDevMode() && !navigator.webdriver, registrationStrategy: 'registerWhenStable:30000' })`) precaches what the offline game needs and nothing else, in three asset groups — this is what makes a repeat visit (and the install prompt itself) work offline. The `navigator.webdriver` half is not scaffolded — added after a real preview-e2e CI run showed registering/activating the worker measurably slowing down Firebase Auth-dependent specs even with the offline-prefetch task (below) separately gated off the same way: `profile.spec.ts`'s two tests went from ~7s combined to 46s+ with a timeout, `sign-in-save-score.spec.ts` from ~55s to 1m+ with a timeout, confirmed against a clean baseline run with no PWA changes at all. Same reasoning as the prefetch's own `navigator.webdriver` check below — never true for a real user's browser.

  **The three groups, and why they are in that order.** `deferred-routes` (`installMode: lazy`, `updateMode: prefetch`) names the eight route chunks neither first paint nor an offline game reaches — add-question, my-questions, pricing, profile, a curated quiz's page (which cannot load its quiz without a connection anyway), review, and the two legal pages. `app` (`prefetch`) then sweeps up `/*.js`, `/*.css`, `index.html`, the manifest and the favicon, which is everything left: the shell, the framework and Firebase chunks, and `/`, `/play` and `/game-over`. `assets` (`lazy`) is the icons and fonts, as scaffolded. Order is load-bearing rather than stylistic — the config generator assigns each file to the **first** group whose globs match it and skips it thereafter — and it is what lets a catch-all group coexist with an exception list instead of every group carrying the other's negation.

  **Firebase stays in the prefetch group** even though `/` no longer needs it to paint (§1.5). Its 129 kB chunk is what restores a signed-in session, and restoring one is entirely local — persistence is an IndexedDB read — so a returning player who opens the app with no network sees their own account rather than a "Sign in" chip. That is worth an install-time fetch; a route they have never visited is not.

  **Two things make the split checkable rather than hopeful.** `namedChunks: true` in `angular.json` is what gives a lazy chunk a filename a glob can name at all — without it every one of them is `chunk-<hash>.js`, and the whole scheme is unaddressable. And `npm run ngsw:verify` (`scripts/verify-ngsw-groups.mjs`, chained into `build:prod`, `build:dev-project` and `build:lighthouse`) walks the built bundle graph from `main` and from each game route's entry chunk and fails the build if anything that closure reaches is not in the prefetch group, or if any chunk it can name by more than a hash is in neither list — so a new route, or a new dynamic import that is not one, forces the decision rather than defaulting into every visitor's install. The deliberate exceptions are Firebase's three `index.esm` entry chunks, listed in the script with the reason. What it cannot see is whether the worker really installs what the manifest says; `e2e/specs/unauthenticated/service-worker-precache.spec.ts` reads Cache Storage on a deployed channel for that, and `offline-play.spec.ts` plays a round from the pool with the network gone on the emulator (`ci-cd.md` §4.3, which records why those are two specs rather than one).

  **A change here reaches workers that are already installed, unlike a change to the headers.** §4.4's stamping bullet is about the worker _script_, whose bytes are identical across any deploy that does not move the CSP fingerprint — so the update algorithm's byte comparison installs nothing and a header-only change never lands. The asset groups are not in the script: they are in `ngsw.json`, which the worker re-fetches on its own update check, and a changed `hashTable` is what makes it build a new `AppVersion` and install that. So re-scoping the precache takes effect for existing clients at their next update check, without the script needing to move at all.

  **The residue is the unnamed shared chunks.** A chunk two deferred routes have in common is emitted as `chunk-<hash>.js` whatever `namedChunks` says, because it belongs to no single route — so it stays in the catch-all and is still precached. Measured, that is 20.6 kB raw of the install: 17.1 kB shared by add-question and my-questions, and 3.4 kB shared by the two legal pages.

- **Pre-boot recovery notice (`src/index.html`, `.boot-fallback` in `src/styles.css`)**: markup inside `<app-root>` that a CSS delay reveals after ten seconds, for the one failure where **no application code runs at all**. A worker installed against an older manifest serves that manifest's cached `index.html`; if the hashed entry script it names has since left both the worker's cache and the origin, the document renders and nothing boots — a blank body, with the worker still in control. Reproduced against a production build: one blank load, then the next navigation recovers, because the worker's on-navigation update check installs the current version _during_ the failed load. So the notice only has to tell the reader to reload, and its link does exactly that.
  Three properties are load-bearing. It is **markup, not code**, because the bundle that would have detected the problem is the one that did not arrive. It is revealed by a **CSS animation delay** for the same reason — there is no JavaScript available to schedule it — and the delay is what makes it free on the happy path, since Angular replaces `<app-root>`'s contents on bootstrap at roughly two seconds and the element is out of the document long before ten. And it deliberately does **not** use `SwUpdate.unrecoverable`, which cannot fire here: `ngsw-worker.js` raises that event only on a `404` for a hashed asset, while `firebase.json` rewrites every unmatched path to `/index.html`, so the stale asset comes back `200` with HTML. Measured — no `404`, no `UNRECOVERABLE_STATE`, the driver never left `NORMAL`. A listener would have been dead code, and silently so.
  Pinned by `e2e/specs/unauthenticated/boot-fallback.spec.ts`, which holds down both directions: gone from the DOM on a normal load, and revealed when the entry script is intercepted with a `404`. The reveal delay is asserted on the computed `animation-delay` rather than by waiting on a clock, so the check does not depend on how fast the runner is.
- **Daily free-game allowance (`DailyGameLimitService`, `src/app/services/daily-game-limit.service.ts`)** — five games a day for a free player, counted in IndexedDB alongside the offline pool and the saved game. `GameSetupComponent` renders the count and, at zero, replaces Start with an in-place offer of Pro — **once no start is in flight**, the quiz page's rule (§1.1). Start spends the day's last free game when the questions are in hand and only then navigates, so the count reads zero while `/play`'s chunk downloads, and the offer, a far taller box, would otherwise take Start's place under the pointer for that long; a start the allowance refuses ends with `limitReached` set, so a player who really is out of games still lands on it. `daily-game-limit.spec.ts` holds the chunk and measures Start through the fifth game.
  **Why the device and not the server** is `FEAT-014` §0, and the reasoning matters more than the mechanism: the anonymous uid lives in `browserLocalPersistence`, which is the same browser storage a local counter uses — so a server counter keyed on that uid is cleared by exactly the gesture that clears this one, while costing a Cloud Function on the critical path of every game. Nothing keyed on the anonymous uid can beat device-local storage, because the uid _is_ device-local storage. `FEAT-047` carries the server-side version for when a real chokepoint exists; today the client fetches questions straight from `opentdb.com` and Firestore, so there is nothing to decrement at.
  Three properties are deliberate. **It is spent when a game is served**, after the questions are in hand — a fetch that fails costs the player nothing, which is the one moment a paywall would be least forgiven. **Every storage failure grants the game**: IndexedDB is unavailable outright in some private-browsing modes, and a limit that failed closed would make the app unplayable there, turning a conversion nudge into a bounce. And **the allowance row renders for everybody from first paint** — including Pro, where it reads as unlimited rather than disappearing — because a row that arrives when a signal resolves moves the Start button at the moment the reader is reaching for it (§4.4, pinned by `daily-game-limit.spec.ts`).
  The Pro check is `SubscriptionService.isProUser` and nothing else. `CLAUDE.md` §4.2 forbids gating a _privileged_ operation on a client signal; playing a game is not privileged and there is no server gate for this to be broader than, so the client signal is the whole check rather than an optimistic mirror of one.
  **The count and the entitlement no longer arrive together**, and the offer follows the slower of the two. The count is an IndexedDB read that answers at once; `isProUser` waits on the `stripeRole` claim, which since the bootstrap moved off the critical path (§1.5) can be up to two seconds behind it. Read together the moment the first lands, a subscriber past their fifth game of the day would be shown the free tier's upsell card and then have it replaced by the Start button — so `hasGamesLeft` stays optimistic until `SubscriptionService.isProStatusKnown()` says the claim has been read (`AuthService.proStatusReady`, which is _not_ `authReady()`: the claim is read from the token after the user arrives). `consumeGame()` closes the loop by awaiting the same answer before it refuses anybody — but only in the branch where the count is already spent, since a player with allowance left does not need the entitlement to spend one, and waiting there would put Firebase back on the path of starting a game.
- **Offline question pool (`OfflineQuestionsService`, `src/app/services/offline-questions.service.ts`)**: a small IndexedDB-backed store (raw `indexedDB` API, no dependency — same no-added-dependency convention as `FirebaseService`/`AuthService`, `stack.md` §2.3) holding a rolling pool of up to 200 previously-fetched `TriviaQuestion`s, upserted by a **source-aware key** (so re-fetching the same question is a no-op, not a duplicate) and trimmed oldest-first past that cap. That key used to be the question text alone, which meant anything sharing wording collided and one row silently replaced the other — and across sources that was worse than losing a row: since `getOfflineQuestions()` never crosses `source`, a custom question overwriting an Open Trivia one didn't merely evict it, it moved the surviving copy into the other source's pool while `cachedCount` still reported a full one. The two sources need different identities because only one has a stable id: a `custom` question is keyed by its Firestore document id (stable across fetches, unique per document, so two contributors submitting the same wording stay two questions), while an `open_trivia` question is keyed by its text, because its id is minted at fetch time (`open-${Date.now()}-${index}`) and keying on that would fill the pool with copies of the same question. It shares its database with the in-progress game (§1.3): both go through `OfflineDbService`, which owns the version and every object store, because IndexedDB versions are per-database and two services disagreeing about one is how a store gets silently dropped.
- **Seen-question set (`SeenQuestionsService`, `src/app/services/seen-questions.service.ts`)**: a second store in the same database, holding `{ key, source, seenAt }` for up to 2,000 questions this device has answered, oldest evicted past the cap — the same machinery as the pool above, and deliberately **not** the pool itself. The two sets are not the same set: the prefetch drops up to 50 questions per run into the pool that nobody has ever been shown, so reading it as a seen-set would suppress questions the player has never met. What it feeds is the draw in §1.2.
  - **A question is marked when it resolves, and only then.** Correct, wrong, timed out and skipped all mark it, because all four mean the player read it; drawing a question and abandoning the game does not, so a closed tab never burns questions nobody saw. The mark is one line in `GameControllerService.record()` — the single funnel all four outcomes already pass through, which is what keeps a fifth outcome from arriving unmarked.
  - **Per device, never per person.** Nothing is keyed by uid and nothing reaches `users/{uid}`. A server-side seen-set would be a record of what each player has been shown, which is the profile this feature exists not to build, and it would pull `CLAUDE.md` §4.0 in with it. The costs are stated in `known-gaps.md` §6.
  - **Every access is wrapped, and the failure mode is "no deduplication".** An unreadable store and an empty one are collapsed into the same signal — `readSeenSet()` returns `null` for both — so a private window where IndexedDB is refused plays exactly the game this app played before the feature existed, rather than a broken one.
- **Background prefetch (`TriviaService.initOfflinePrefetch()`, called once from the `App` root component alongside `AuthService.ensureSignedIn()`, on the first idle moment after first paint)**: schedules a best-effort refill of the offline pool up to 100 questions — once when the browser goes idle (`requestIdleCallback`, capped at a 10s timeout; `setTimeout` fallback where unsupported), and again on every `window` `online` event. Fetches a `mixed`-source batch (same Open Trivia DB + `custom_questions` split `getQuestions()` already does) capped at 50 questions per run (Open Trivia DB's own `amount` ceiling) and stores it via `OfflineQuestionsService`. Failures are swallowed — a missed refill just means it retries on the next idle window/reconnect.
- **`TriviaService.getQuestions()` falls back to the offline pool only when the network fetch itself throws** (`TriviaService.playingOffline` signal reflects this, and `QuizLoopComponent` surfaces it as a banner on `/play` — "You're offline — these questions are from your saved offline pool" — so a player mid-game on cached questions is actually told; the signal was previously set but read by nothing) — a legitimate "no questions matched this filter" _result_ (empty array, no error, e.g. a very narrow topic/difficulty combo) is left alone. Deliberately does **not** pre-check `navigator.onLine` to skip straight to the offline pool: that property is well-known to misreport `false` in some headless/CI/sandboxed browser environments even when the network is fine — confirmed the hard way when it made a real GitHub Actions preview-e2e run silently serve cached content instead of a perfectly working live Firestore fetch (root-caused via the preview deploy's own screenshot artifact, which showed a random cached Open Trivia question instead of the two just-seeded custom ones). Every underlying network call already has its own timeout, so always attempting the real fetch first costs nothing in the genuinely-offline case.
- **`OfflineQuestionsService.getOfflineQuestions()` never crosses `source`**: a `'custom'` request only ever draws from cached `custom`-sourced questions (never substituting `open_trivia` ones, or vice versa) — this is what the bug above actually surfaced once the `navigator.onLine` fast-path was masking it: the offline pool's `mixed`-source prefetch data was getting served for an explicit `'custom'`-only request. Within a source-scoped pool, the chosen topics and difficulty are only a _preference_ — falls back to the rest of that same-source pool if too few match, since a mismatched-topic offline game beats no offline game at all. A pooled question matches a topic through `topicTagsOf()` (§1.4), so one cached before topics replaced categories — a category and no tags — matches the tag its category derives rather than nothing (`FEAT-052`).
- **`GameSetupComponent` shows an inline banner** (`ConnectivityService.isOnline`, a small signal-based service listening to `window`'s `online`/`offline` events, same pattern as `ThemeService`) when offline, telling the player how many questions are cached (`OfflineQuestionsService.cachedCount`) before they even submit the form. The curated-quiz cards under the card read the same signal and disable themselves, because a quiz cannot be opened offline at all (§1.1).
- **Disabled under the `e2e`/`lighthouse` Angular build configurations** (`environment.enableOfflinePrefetch`, `false` only in `environment.e2e.ts`) **and under `navigator.webdriver`** (true for every browser-automation framework by spec, never for a real user's browser): the background prefetch's own `opentdb.com`/Firestore requests would otherwise satisfy a stubbed request an e2e spec was waiting on and, confirmed live against a real deployed preview, compete for a real, shared, rate-limited backend closely enough on a CI runner to time out unrelated specs. The environment flag alone doesn't cover the preview-e2e job specifically — that one deploys the plain production build (`environment.ts`), which is exactly why the `navigator.webdriver` check exists as a second, environment-independent layer.
- Not wired into `ngsw-config.json`'s `dataGroups` — Open Trivia DB is a third-party, rate-limited API, and `custom_questions` needs Firestore-rules-aware normalization the service worker can't do; the IndexedDB pool above is the deliberate alternative.
- **`ngsw-worker.js` is excluded from `firebase.json`'s blanket `**/\*.@(js|css)` immutable-cache rule** (`no-cache` instead, via a dedicated header rule declared after it) — Angular's own guidance is that the service worker script itself must never be cached long-term, or the browser's own update-check mechanism (which needs to re-fetch and byte-compare it) can't detect a new deploy. Caught by inspecting the live preview's actual response headers, not by assumption.

### 1.9 Legal pages (`/privacy`, `/terms`)

**The footer also names the build.** Hovering the brand name shows the environment label, the short commit hash and that commit's date (`FooterComponent`, `src/app/build-info.ts`, stamped in by `ci-cd.md` §4.5). It exists because "is the fix deployed here?" had no answer from inside the app, and the absence cost a diagnosis: after [#153](https://github.com/shermam/trivia/pull/153) fixed the CSP refusing Google sign-in on dev, every preview channel picked it up and `trivimind-dev.web.app` did not — nothing deployed it — and from the browser the two were indistinguishable, so the investigation started at the client and stayed there through a storage clear, a service-worker unregister and several cache-disabled reloads.

Two carriers on **separate** elements: `title` for the hover tooltip, and an `sr-only` span for the accessibility tree. `title` alone would have been the smaller change and the wrong one — it is not reachable by keyboard and its screen-reader support is inconsistent, so on its own it hides a diagnostic from exactly the people who cannot hover. Putting both on one element would instead make the title an accessible _description_ of text that already says it, which some screen readers announce twice. This is deliberately **not** the WAI-ARIA tooltip pattern (§4.5) and does not claim to be: there is no focusable trigger and no `role="tooltip"`, because the information is fully present in the text either way and the title is a convenience for a pointer rather than the only route to it.

Two documents, reachable from a persistent `FooterComponent` (a sibling of `<router-outlet>` alongside `TopBarComponent`, hidden in embed mode for the same reason). Both render through a shared `LegalPageComponent` shell so neither can drift from the other or lose its attribution line, with the bodies projected in via `<ng-content>` — which keeps those two templates pure prose, reviewable as copy rather than as markup.

- **The data-handling sections are written from source, not from a template.** Every factual claim — that an anonymous account is created before any interaction, that the leaderboards are world-readable, that the app sets no cookies, that only an email address and a uid reach Stripe, that there are no analytics of any kind — was derived by reading the code that makes it true. That is the point of writing a policy this way: **a policy describing practices the app doesn't have is itself a misstatement about data handling**, which is the exact risk publishing one is supposed to close.
- **…which means keeping them true is part of changing the app.** This has already failed once. The pages sat unmerged for 165 commits while the code moved underneath them, and by the time they were rebased forward they claimed the app hot-linked Google Fonts (self-hosted since, H5), that contributions recorded no author (they do, A10), that there was no way to delete an account or export data (both shipped, H3), and that there was one leaderboard (there are three, G7). None of that was wrong when written. `CLAUDE.md` §2 applies to these files as much as to this one.
- **`LEGAL_AWAITING_PROFESSIONAL_REVIEW` (`legal.ts`) gates a banner, and the banner does not say "draft".** It says the documents are in force but have not been read by a lawyer. The distinction is deliberate: the Terms have to bind to do anything at all, and a document that introduces itself as a draft is a poor candidate for a contract. What is disclosed is the narrower true thing. Flip the flag when a professional has actually reviewed them, and set `LEGAL_LAST_UPDATED` in the same commit.
- **There are no unresolved-item callouts on the live pages, by decision.** A `ReviewRequiredComponent` used to render an amber block around each passage needing legal judgement; thirteen became three as the features they depended on shipped, and the last three were then moved off the page entirely (review of [#37](https://github.com/shermam/trivia/pull/37)). The reasoning is that such a notice is a message to the maintainer: a reader cannot act on it, and its only effect on them is to invite discounting the rest of the document. One of the three — reporter-identifier retention — turned out to be a design decision rather than a legal question and is now `BACKLOG.md` item 5; the other two (children under Brazil's stricter LGPD threshold, and whether a liability cap is worth having) live in `BACKLOG.md` §5 alongside the other work needing a human. The component is deleted rather than left unused. **If it comes back, the page-level banner has to come back with it** — that banner previously said "a few passages marked Review required are waiting on one", and removing the callouts without editing the banner would have left the page pointing at markers that no longer existed. `legal-pages.spec.ts` now asserts both halves.
- **What is deliberately absent** is as considered as what is present: no numeric liability cap, no blanket warranty disclaimer, no arbitration clause, no class-action waiver, and no claim of compliance with any regime. Under Brazilian consumer law a clause excluding the supplier's liability is a nullity, and an unenforceable clause is worse than none because it marks the whole document as copy-pasted. "We comply with GDPR" is a representation rather than a description, and a false one is a misstatement in its own right — so the documents describe behaviour throughout and assert compliance nowhere. `legal-pages.spec.ts` pins that last one.
- **The contributed-content licence is the load-bearing clause.** Account deletion _anonymises_ questions rather than removing them (`functions/src/account.ts` replaces `createdBy` with `[deleted-user]`), and that behaviour needs a licence that is explicitly **irrevocable and surviving termination** to stand up. The grant also covers a future open release of the question bank — included from the start because it cannot be added retroactively against people who have already contributed, the same one-way door as the exact-key `hasOnly()` allowlist in `data-model.md` §3.
- **`legal-pages.spec.ts`** pins the structural properties, not the prose: that each page renders, carries the document date, links the contact address **from within the projected body**, carries the CC BY attribution, shows the review notice, avoids calling itself a draft, makes no compliance claim, and — the one that matters most — that the Terms still tell contributors their questions survive account deletion. The body-scoping is not incidental: an unscoped query passed while all five contact links were deleted from the Privacy Policy, because the shell's own banner carries one. Found by mutation, not by review.
- **The Terms' formatting paragraph is held to the renderer's published allowlist** by `terms-formatting.spec.ts`. "Anything outside that list is removed rather than displayed" is a claim about what the sanitiser does, true only while the list names everything it keeps, so the spec reads the tag list from `render-contract.json` (§1.4) and fails when an HTML element on it has no words on the page — an element added to the allowlist fails until the Terms say what it is. The same section says typed HTML is shown as typed, which is true of markup and not of a character reference outside code and formulas — the renderer decodes `&amp;` to `&` there and shows it as typed in a code span or a formula — so the spec asks the renderer both ways and holds the page to saying exactly that. The opposite drift, the page naming something the allowlist refuses, cannot be derived from a tag list and stays a matter for review.
- **`prose-legal`** (`src/styles.css`) is the one place in the app that styles elements rather than applying utility classes per element. Declared centrally as an `@utility`, same convention as the shadow tokens; justified because these are the only long-form documents in the app and their reviewability as copy is the whole point.
- **Structure and tone are adapted from [Basecamp's open-sourced policies](https://github.com/basecamp/policies) under CC BY 4.0**, which requires attribution — rendered at the foot of both pages. Basecamp's were chosen over Automattic's specifically because Automattic's are CC BY-**SA**, whose share-alike term would have obliged these pages to carry the same licence. Worth knowing on the next revision: that repository was **archived in December 2023**, so it is a source of structure, never of currency — and the three sections that matter most here (the contributed-content licence, consumer withdrawal rights, Brazilian law) are precisely the three a US B2B SaaS template does not cover, and were written from scratch.

### 1.10 Lifetime stats (`/profile`)

`ProfileStatsComponent` shows a player the five totals `users/{uid}` already holds — games played, questions answered, correct answers, accuracy derived from the last two, and best streak — plus the date they have been counted since (`FEAT-005`, reduced to what the substrate carries). Reachable from the auth menu's profile section and from the mobile nav drawer (§1.5). Its header carries the player's avatar; below the totals sit the progress card — level and XP (`FEAT-041`, below) — and then the avatar picker (§1.15).

- **Nothing on this page writes the document from the client.** The totals are written by the `recordGameResult` callable and the avatar choice by `setAvatar` (§1.15), both on the Admin SDK, which is what lets the collection carry no exact-key `hasOnly()` allowlist and therefore gain a field without a rules deploy or a migration (`data-model.md`). A client write rule would spend that property, so the totals card reads and nothing more. One `FirestoreRestClient.getDocument` per visit, at a known path — the only shape the rules permit, since `users` grants `get` to the owner and refuses `list` to everybody.
- **A document is not the same thing as totals.** An avatar chosen before the first finished game creates `users/{uid}` holding that choice and nothing else, so `getGameplayStats` reads a document without `gamesPlayed` as `null` — "nothing banked yet" — rather than as five zeroes.
- **Nothing here is shown to anyone else, and that is a property of the numbers rather than a preference.** They are bounded, not attested: the callable range-checks a payload the client supplied (audit decision A1), which is enough to show somebody their own history and not enough to rank anyone against anyone.
- **Five states, decided in one `computed` rather than a template chain** — loading, signed out, no games yet, the totals, and a failed read — for the reason game-over's `scoreAction` is one (§1.1): the ordering of those branches is itself a defect no template test can reach. The default is the least alarming of them: anything not positively known to be a signed-in account resolves to "signed out", built on `user() !== null && !isAnonymous()` rather than on `!isAnonymous()`, which reads `false` for a null user and would treat every pre-auth frame as an account (`CLAUDE.md` §4.4).
- **An anonymous visitor gets an explanation, not a redirect.** There is no document for an anonymous session and never will be — the callable refuses to create one, because nothing would ever delete it (`data-model.md`) — so the page says that and offers the sign-in button, which opens the same auth menu game-over's prompt does (`AuthMenuStateService`) — and is hidden under `?embed=1` for the same reason game-over's is, since an embed has no top bar and therefore no menu for it to open (§1.5). A guard that bounced the visitor would answer a question they did not ask, and the "Your stats" link is offered to everybody in the drawer for the same reason `/pricing` is: the page explains what to do, where a link appearing once auth resolves would shift the rows under it.
- **A failed read is a fourth state, never the empty one.** `getGameplayStats` returns `null` only for a 404 and lets a refusal or a transport failure throw, so "you have not finished a game yet" is never shown to somebody whose totals are fine but unreachable — and the failed state is the only one carrying a retry (`CLAUDE.md` §4.4). The real cause goes to the console, the only place it survives once the screen has said "try again". **Retrying moves focus off the button before it re-reads**, onto the status line: the retry puts the card back into loading, "Try again" turns `visibility: hidden`, and focus asked to stay on a hidden element drops silently to `<body>` — which would send a keyboard user back to the top of the document to reach the button a second time.
- **A game the server refused to bank is said, not papered over.** When `recordGameResult` refused the signed-in account's last game in this tab (`AccountService.unbankedGame`, §1.1), the status line reads "Your last game could not be added to your totals." in place of "Nothing banked yet…" or "Tracking since…", both of which promise totals that are not coming, and the live region says it too; the tiles keep whatever was banked before. It is a refinement of the sentence rather than a sixth view, so a read in flight, a failed read and a signed-out visitor keep their own. Nothing is written for a refused game, so there is nothing to read back on a later visit: it lasts as long as the tab, and only for the account the refused call was made as.
- **The card is the same height in every one of those states.** Each number is rendered from first paint as an em-dash so the answer fills a box that is already on the page, the six sentences are stacked in one grid cell so the reserved space is the tallest of them rather than a re-measured `min-h`, and the three actions (start a game / sign in / try again) are one grid cell holding the same box three times. `profile-stats.spec.ts` holds the read open, measures the card, releases it and measures again — jsdom has no layout and Lighthouse only ever loads `/`, so nothing below a real browser can see this.
- **Accuracy is the one derived number, and zero answered questions is a real state** — a game whose every question was skipped or timed out banks with `questionsAnswered: 0`, and `0 / 0` renders as "NaN%". It shows the placeholder instead. Counts and the date are formatted with `Intl` in the reader's own locale, unlike a price, which is pinned to its currency's conventions because it is a fact about a charge rather than about the reader (§1.6).
- **The totals needed no privacy-policy edit.** The `users/{uid}` totals were already disclosed in the data inventory when `recordGameResult` shipped, and showing somebody data the app already stores about them changes nothing about what is collected, kept or shared (`CLAUDE.md` §4.0). The avatar choice did need one — §1.15 — and so did the XP: a new field, a number worked out from a player's own play, and a level that decides something — so the inventory names it and says where it comes from and who sees it, the profile paragraph's "nothing else is used to categorise you" names the level as the one other thing worked out from play, the automated-decisions paragraph counts the unlock as its third decision, and the lawful-basis table has a row for it (§1.9).
- **The progress card shows a player's level, their XP, a bar to the next level, and the next set it unlocks** (`ProgressCardComponent`, `components/progress-card/`, `FEAT-041`). **It shares the totals' read and their states**: `xp` is a field of the document the page already reads, so the page hands the card a state and a number instead of the card reading anything — `ready` for a signed-in account, nothing banked included, since zero is a real total once somebody is signed in; `loading`, `signedOut` (anonymous included) and `failed` show em-dashes, and the totals card's "Try again" re-reads both. The XP is the read's, raised to the callable's answer when a game banked in this tab after the read (`AccountService.bankedXp`, §1.1): that answer is what the transaction committed, and XP only grows, so the larger of the two is never ahead of the document. **The level is derived, never stored** — `levelFor(xp)` in `models/levels.ts`, the app's copy of the functions module `setAvatar` enforces, pinned equal by `levels.spec.ts` — and the picker's locks are decided on the same number, so the card and the picker cannot disagree.
- **Designed from the signed-out state, and one height in all of them.** A guest is told how XP is earned — "Sign in to earn experience points (XP) from the games you finish. Guest games earn none." — rather than shown a zero that would read as a total. Every box is on the page from first paint and only filled: the level and the XP as em-dashes, the bar as an empty track, the unlock row's avatar as `AvatarComponent`'s reserved box (the neutral face for a guest, the set's first avatar over the player's initial otherwise), and the sentences — loading, signed out, failed, the explanation, a level-up — stacked in one grid cell. `xp-and-levels.spec.ts` measures it through signed out, a held read, loaded and a failed read, at 390 and 1280.
- **The bar is a `progressbar` once there is a value** — `aria-valuenow` the XP earned within the level, `aria-valuemin` 0, `aria-valuemax` the level's span, an `aria-valuetext` saying "40 of 300 XP towards level 3", and the visible line under it saying how many are still to go. With no value it is an empty track hidden from assistive tech, because the sentence above it says why there is no number and an indeterminate bar would announce a wait that is not happening. The fill is a `[style.width.%]` binding, which goes through the CSSOM rather than a `style` attribute the CSP would drop (`CLAUDE.md` §4.4), and does not animate.
- **A level crossed by the last game is said, on the card and through the page's live region** — "Your last game took you to level 3." in place of the card's explanation, and "Your stats are ready. Your last game took you to level 3." in the region — worked out from `bankedXp`'s total and the share the game added. Only over loaded totals: over "Nothing banked yet" it would contradict the line above it, and a refused last game crossed nothing. Like the refused-game line, it lasts as long as the tab, for the account it belongs to.
- **Nothing about XP or a level appears anywhere but this page.** The XP is bounded, not attested (`data-model.md` §3), so a level unlocks a cosmetic for the player's own picture and is shown on no board, beside no name, and through no rule.
- **The totals card stays the five totals, and the play history it now sits on top of has no screen at all** (`FEAT-049`). The per-game record is exported and deleted like everything else, and read by nothing in the app — building a history view is a separate feature, and shipping the record first is what lets a player inspect, export and delete a profile before anything acts on it. The export is where they read it.

### 1.11 Sound effects (`AudioService`)

Five short cues — a correct answer, a wrong answer or timeout, the countdown's last five seconds, a lifeline being spent, and the end of a round — synthesised in the browser with Web Audio (`FEAT-003`). `QuizLoopComponent` plays the first four and `GameOverComponent` the fifth; `AudioService` (`src/app/services/audio.service.ts`) owns the cues, the `AudioContext` and the mute.

- **Nothing is fetched, and nothing could be.** `firebase.json` sends `default-src 'self'` and allowlists no CDN, so an audio clip from anywhere else is refused at runtime (`ci-cd.md` §4.1), and a self-hosted one would be bundle bytes, a `ngsw-config.json` cache entry and a request on the critical path of the first correct answer. Each cue is a table of tones instead — an oscillator and a gain envelope per tone, fresh nodes per play so two cues that overlap sound together rather than cutting each other off, and every node disconnected in its own `onended` (`CLAUDE.md` §4.4). Peak gain is capped well under a third of full scale and the ceiling is pinned by a test, since nothing else in the repository listens.
- **Nothing is built, and nothing is scheduled, until the document has had a user gesture** — two rules, and the second is the one that is easy to miss. The first is the familiar autoplay one: a context constructed before any activation starts `suspended` and logs a warning saying so, so the service checks `navigator.userActivation.hasBeenActive` before building one at all. The second is that a suspended context does not _refuse_ work — its clock is frozen, so a tone scheduled at `currentTime + ε` is **queued**, and the queue empties the moment something else resumes it, over whatever screen the reader has reached by then. So a cue is scheduled only onto a context confirmed `running`; anything else is dropped, because a missed cue costs nothing and a queued one is heard in the wrong place. Where a context cannot be had at all — a Safari private window, a headless runner, jsdom — every method is a **silent** no-op: no sound, and no console error, because a game logging an exception on every answer is worse than a game with no sound.

  **A reload is not the un-activated case, which is the guess worth correcting.** Measured in Chromium: after a reload `navigator.userActivation.hasBeenActive` still reads `true` and a fresh context starts `running`, so reloading `/game-over` genuinely replays the fanfare rather than skipping it. What the activation gate covers is colder — a document that has never been touched at all, where a context would be built suspended and become somewhere to queue. What covers the reload is the `running` check. `sound-effects.spec.ts` follows the whole sequence and asserts the invariant that holds either way: no tone is ever started on a context that is not running.

- **The tick rides the countdown that already exists.** `QuizLoopComponent` derives "one tick per remaining second, inside the last five" from the wall-clock deadline it reads anyway, rather than scheduling a second interval — which would be a second thing to tear down and would drift against the deadline it is supposed to be announcing. It follows the _question's_ own duration, so Extra Time pushes it back out of the window, and an unlimited game never ticks at all because no countdown is started (§1.1). Answering stops the interval, which is the tick's teardown too.
- **All three lifelines share one cue**, a short upward sweep, and it plays only when one is genuinely consumed — a press on a button that is unavailable or already spent is silent, or the sound reports something that did not happen. It is a glide rather than discrete notes so it cannot be mistaken for the correct answer's chime, which fires on an adjacent gesture. **A skip gets that cue and neither answer cue**: it ends the question without producing an outcome, unlike a wrong answer and a timeout, which share the one failure cue.
- **The end-of-round cue is chosen by accuracy**, with a brighter variant for a round where every question was answered correctly. Deliberately **not** a personal best: the leaderboard keeps one best entry per account and enforces it in `firestore.rules`, so the only signal the client gets is a bare `permission-denied` that could mean half a dozen other things (`CLAUDE.md` §4.4) — a fanfare fed by a guess would be a claim the app cannot check. Accuracy rather than points for the reason the summary tiles use it: a multiplied score can exceed the question count (§1.1).
- **Sound is on by default and the mute is remembered**, in `localStorage` under `trivia_sound_muted`, every access wrapped because a private window throws on the accessor itself (§1.6). It stops the _next_ cue rather than one already scheduled: a tone handed to the audio thread runs to its end, so muting during the longest cue can be followed by up to about 0.7s of sound, and cutting that off would mean tracking every live node for a fraction of a second nobody has complained about.
- **The toggle is rendered twice, exactly as the theme toggle is** — an icon button in the bar above `sm`, and a labelled row in the nav drawer below it — because the bar's controls are `hidden sm:flex` and the drawer is `sm:hidden`, so either one alone leaves half the viewports with no way to silence the game. The phone half is the one that motivated it: the drawer is the only surface reachable mid-question, which is exactly when somebody decides they want silence. Both carry `aria-pressed` **and** an accessible name that says what pressing will do, the same pairing as the quiz's flag button (§1.1) — the name is what a reader acting on it needs, the state is what a reader arriving at it needs — and both are the same size in either state, the drawer row because it stretches to a fixed-width panel and the bar button because it is a fixed `h-9 w-9`. Like the theme toggle, the drawer's copy does not close the drawer, since the control you would use to change your mind is inside it.
- **An embedded game plays nothing** (`EmbedModeService`). `?embed=1` renders no top bar, and both copies of the toggle live in it, so audio there would be a noise with no way to switch it off (§11.7 of `UI_INVENTORY.md`).
- The mute key is listed in the Privacy Policy's device-storage section, which is exhaustive by construction (§1.9), and pinned there by `legal-pages.spec.ts`.

### 1.12 One-time donations ("Buy me a coffee")

A tip jar beside the subscription: a one-off payment that unlocks nothing, priced from the Stripe catalog in the same currencies Pro is sold in (`FEAT-013`). Everything it shares with the Pro flow it shares by reusing the code, and everything it does not share is separate on purpose.

- **`DonationService`** is a sibling of `SubscriptionService`, not a part of it. Shared: the write-then-poll handshake (`SessionHandshakeService`, which all three flows — checkout, donation, billing portal — now run through), the country signal (`GeoService`, §1.6), and the rule that turns a country into a currency (`preferredCurrency`, so the pricing page and the dialog can never disagree about what a Brazilian visitor is quoted). Separate: the catalog it reads (`products` filtered on `kind == 'donation'`, then each product's active `prices` filtered to `type: 'one_time'` carrying the same marker) and the subcollection it writes (`customers/{uid}/donation_sessions`, `data-model.md`), which is what keeps the two volume caps and the two server-side validations apart.
- **Three presets per currency, cheapest first, and never a free-text amount.** An amount a client chooses is a client-writable value with billing consequence and the server has nothing to check it against (`CLAUDE.md` §4.1); a catalog price id is a value the mirrored catalog can answer for. So each preset is a real one-time Stripe Price, the dialog renders it with `Intl.NumberFormat` in the **currency's own** locale (§1.6), and `startDonation()` sends the price id and this browser's origin — the same two fields a checkout session carries and nothing else. Which three: sorted by amount and capped at three, ties broken by price id, so the row never depends on which document came back first.
- **The dialog is imported statically, and `@defer` was tried and measured worse.** The obvious move for a dialog most readers never open is to defer it, and it does take 2.06 kB of transfer off the initial bundle — but **the service worker precaches every emitted chunk** (`ngsw-config.json`), so nothing is actually saved on a first load, and the extra chunk boundary split the vendor chunk in two and cost **4 kB of transfer in lost compression**. Measured on `/`: 301.1 kB of total byte weight on `main`, 304.1 kB with the dialog imported statically, and 308.7 kB deferred. The general point is worth more than the decision: **a lazy boundary is only a saving where something is genuinely not fetched**, and on this app's caching policy nothing is.
- **The catalog is read when the dialog is opened — on every open, and never on page load.** The tip jar renders nothing until somebody asks for it, so paying two public reads on every page load for a dialog most readers never open is the cost `/pricing` already refuses to pay for a page they are not on. There is no `localStorage` cache and no prime: a dialog opened deliberately can afford a round trip, and neither would earn its extra storage key or its policy line. **Every open rather than only the first**, because a flag remembering the first would remember a _failed_ read just as faithfully, which is the cached rejection `CLAUDE.md` §4.4 forbids: one blocked request and the dialog would tell every later open that donations are unavailable, for the life of the tab. Re-entering costs nothing when the read worked — `DonationService` stores the promise synchronously, so a second open mid-flight joins the first rather than starting a second query, and only a failure is dropped from the memo.
- **It degrades honestly while the catalog is empty**, which is what every environment looks like before the donation Product has been created in the Stripe Dashboard (`stack.md` §2.4). The CTA still renders, the dialog still opens, nothing throws, and the dialog says donations are not available — the same shape and the same reasoning as `NO_PRO_PRICE_MESSAGE`. Loading and empty are distinct states (`catalogResolved`), so the unavailable message is never shown to somebody whose answer is still in flight (`CLAUDE.md` §4.4).
- **Anyone signed in may donate, anonymous sessions included** — the one client-writable path in the app that accepts an anonymous write, and deliberately (`data-model.md`). What the account decides is whether the donation can be **attributed**: `createDonationSession` attaches a Stripe customer and a `firebaseUID` only for a real account, so a guest's payment leaves no `donations` document and nothing that could link it back to them — the short-lived `donation_sessions` document that carried them to Stripe is written under their anonymous uid either way, and expires with the rest. The dialog says exactly that before anybody pays — and says nothing about a badge, because there is no supporter badge in the app to promise (`FEAT-013` §1 defers it until there is a screen to hang one on).
- **Opening the dialog starts the auth bootstrap, and `startDonation()` awaits it.** The uid owns the `donation_sessions` document, so there is no donation without one — and since the bootstrap moved to the first idle moment after paint (§1.5) while the footer's CTA is on `/` from first paint, a reader who opened the dialog and clicked straight through used to be refused with "still starting up", a state they had done nothing to cause. `DonationDialogStateService.open()` starts it (so the click has nothing left to wait for) and `startDonation()` awaits it (so a fast click waits rather than fails); reaching the no-uid branch now means auth could not be reached at all, and the message says only that.
- **The CTA is in the footer, and one entry in the auth menu reaches the same dialog.** Both are hidden on `/play` by the same predicate (`isGameplayRoute`, which strips a query and a fragment before matching) — an active quiz round is the one screen the app keeps free of anything competing with the question — and both are gone in embed mode already, because the footer and the top bar are (§1.5). `FooterComponent` mounts the dialog, so there is exactly one of it on the page and it sits beside the control focus returns to when it closes; the auth-menu entry closes the menu on its way, since two `role="dialog"` panels open at once is not a state to leave a screen reader in.
- **The dialog's accessibility is the report dialog's, copied deliberately** (`CLAUDE.md` §4.5, and the three traps it records): Tab is trapped in both directions by a plain `(keydown)` handler rather than `keydown.tab`, which never fires with Shift held; the focusable list is not filtered on `offsetParent`, which is `null` for a `position: fixed` dialog and unimplemented in jsdom; and focus is restored to a captured element rather than to whatever `document.activeElement` was at open time. The presets are a `role="radiogroup"` with `aria-labelledby` and real radios kept `sr-only` behind their labels, and the currency switch is the same `CurrencySwitchComponent` the Pro card uses — one control, one set of ARIA, and a test-id prefix per instance so the two can be on screen together without a locator matching both.
- **Coming back from Stripe lands on `/`**, at `?donation=success` or `?donation=cancelled`, following the `?checkout=` pattern `/pricing` already uses rather than adding a route. `GameSetupComponent` reads the parameter from the route snapshot at construction, so the banner is part of the first frame and nothing below it moves (`CLAUDE.md` §4.4); dismissing it clears the query parameter so a reload does not thank the donor twice.
- **What a donation leaves behind** is `customers/{uid}/donations/{checkoutSessionId}` — amount, currency, time — plus `supporterSince` on the customer document, both written by `stripeWebhook` and readable only by their owner (`data-model.md`, `stack.md` §2.4). The client cannot write either; it can only read its own. Nothing in the app renders a supporter badge yet.

### 1.13 Your questions (`/my-questions`)

`MyQuestionsComponent` lists everything the signed-in account has contributed to the shared bank, newest first, with what became of each one — and offers the two things only its author may do to a question: rewrite it, or take it out of the app (`FEAT-007`). Reachable from the auth menu's profile section (§1.5).

- **The screen exists because the read rule widened for it.** `custom_questions` served an approved question to anybody and everything else to reviewers only, so an author who submitted a question and came back to check on it was refused — the statuses this page is entirely about were the ones they could not see. The rule now also admits `resource.data.createdBy == request.auth.uid` (`data-model.md` §3), and because **rules are not filters** the query has to carry `where('createdBy','==',uid)` for Firestore to be able to prove that branch: without the filter it is refused outright rather than narrowed to the caller's own rows.
- **One page at a time, newest first, paged on a cursor.** `FirebaseService.getUserQuestions` asks for `MY_QUESTIONS_PAGE_SIZE` (25) ordered by `createdAt` descending with the document id breaking ties, and **Show more** fetches the page after the last row rather than growing the limit — which would re-read and re-bill every row already on screen. The tiebreaker is not decoration: two questions submitted in the same millisecond put one at a page boundary and its twin immediately after the cursor value, where an exclusive `startAfter` on `createdAt` alone steps over it. The ordering needs the `(createdBy ASC, createdAt DESC)` composite index (`data-model.md` §3).
- **Five states, decided in one `computed`** — loading, signed out, nothing contributed yet, the list, and a failed read — for the reason `/profile`'s five are (§1.10): the ordering of those branches is itself a defect no template test can reach. The default is the least alarming: `showsRealAccount()` asserts `user() !== null && !isAnonymous()`, because `isAnonymous()` reads `false` for a null user and every pre-auth frame would otherwise fall through to "you have contributed nothing". A failed read outranks the empty state for the same reason the reports tab's does. All five messages share one grid cell, so the page does not resize when the read lands.
- **A signed-out or anonymous visitor gets an explanation, not a redirect.** There is no guard in this app and no `/login` route to send them to, and an anonymous session can never have written a question — `create` requires a real, verified, Pro account. The sign-in button opens the same auth menu game-over's prompt does, and is hidden under `?embed=1` for the same reason (§1.5).
- **A rejected row shows the reviewer's words, and says so plainly when there are none.** `rejectionReason` is optional in every direction: a reviewer may reject without writing one, and every question rejected before the field existed has none — so absent is the normal case and the row reads "No reason was given" rather than as something having gone wrong.
- **Editing reuses `/add-question`'s form rather than a second copy of it.** `components/question-form/` holds the form factory, the validators that mirror `firestore.rules`' bounds field by field — held to the published `question-bounds.json` by `question-bounds.spec.ts`, which drives each control at its bound and one past it (`data-model.md` §3) — the label table that makes an invalid submit name the offending field and move focus to it, and the fields component both screens render. A second copy would be a second set of bounds to keep in step with the rules, and the way it would fail is the way it already failed once — a control missing from the label table blocked the submit while naming nothing and focusing nothing. The dialog passes an `idPrefix`, because a DOM id is global.
- **The dialog builds the rows the stored question has** (`FEAT-051`): a five-option question opens on its four wrong answers, and the author adds and removes rows exactly as on `/add-question`. The save rewrites the whole document, so a row the dialog did not build would be an answer the save deleted. A true/false question opens on a new question's three empty rows, since its one wrong answer is derived and never shown. Every stored row is kept even past the five the rules allow — a document written from the console could carry more — because dropping an answer the author wrote is worse than showing it, and the remove buttons are right there.
- **Saving sends the question back to `pending`, and drops the reviewer's note with it.** The note was about the wording that has just been replaced, and the rules refuse an owner edit that leaves it standing. The write is a patch whose `updateMask` deliberately omits `createdBy` and `createdAt` — so "unchanged" is true by construction rather than by the client resending the same values — and deliberately includes every optional field, so clearing a source link removes the key instead of leaving the old one there. **It never names the difficulty counters** (`FEAT-023`), which the rules require an author's edit to leave exactly as stored: they are the server's record of how players did, and they survive the rewrite (`data-model.md` §3).
- **A question written before topics replaced categories opens on the tag its category derives** (`FEAT-052`), and the list row shows the same derived chip. The form requires a topic, so it would otherwise refuse to save a legacy question its author had not touched the topic of — and since `category` is one of the optional fields the patch always names and the form never supplies, the first save writes that tag and deletes the category: the topic moves from the old field to the new one, through the author's own edit.
- **Removal is confirmed, and the confirmation says what removal actually does.** "Remove from the app", never "delete permanently": the licence granted at contribution is irrevocable, and the removal reaches neither copies already served nor a player's offline pool. It does stop the question being drawn, and it takes it out of the reviewers' queue. Both the dialog and `/terms` say all of that (§1.9).
- **Both dialogs follow the auth menu's contract** (`CLAUDE.md` §4.5): the trigger carries `aria-haspopup="dialog"` and an `aria-expanded` that tracks whether **this row's** dialog is the one showing — per row, because a page-level "a dialog is open" would announce every trigger on screen as expanded whenever any one of them was — and the panel is `role="dialog"` + `aria-modal` + `aria-labelledby`, Escape closes it, and Tab is trapped in both directions by `utils/focus-trap.util.ts`, shared with game-over's report dialog because the three ways of writing that trap wrongly are subtle enough that a second hand-written copy is a second chance to reintroduce one.
- **Focus on close has two destinations, and the second is the ordinary path rather than an edge case.** It returns to the button that opened the dialog, captured at open time rather than read from `document.activeElement` (each row has its own buttons, and a click does not focus a `<button>` on Safari/macOS). But confirming a removal **deletes the row that button lived on**, and focus asked to stay on a detached element drops silently to `<body>`, returning a keyboard user to the top of the document with no announcement — so it falls back to the status block, which is present in every state and is where the sentence saying what just happened appears.

### 1.14 Private likes and dislikes (`QuestionVoteService`)

A signed-in player can like or dislike a community question — after its answer is revealed on `/play`, and on its row in the recap on `/game-over` (§1.1) — and nobody else can see that they did (`FEAT-027`). One document per account per question in `question_votes` (`data-model.md`), no count anywhere, nothing triggered by a write. The vote is a preference signal for the recommender `FEAT-029` will build; until then the only thing that reads it is the player's own buttons.

- **One component, `QuestionVoteComponent` (`components/question-vote/`), renders the buttons in both places**, so the two cannot drift into different accessibility contracts: a group labelled by its visible "Rate this question" caption, two toggle buttons whose names say what they do and whose `aria-pressed` says what they are, and a filled glyph for the pressed state so it never rests on colour alone (WCAG 1.4.1). Both buttons are the same fixed box in every state, so pressing one moves nothing. **The component does not write**: it reports which button was pressed, and the host writes through the service and announces the outcome in a region of its own, because the write can settle after the buttons are gone.
- **`QuestionVoteService` holds the state, and it is optimistic and honest about it.** A tap moves the button at once and the write follows — it is a like button, and nobody should wait on a round trip for one. Pressing the pressed button removes the vote; pressing the other one changes it. A failed write puts the button back to what is stored, or — when nothing was ever read — to what it showed before the tap, and the host says so: "your vote could not be saved", with no cause narrated, since a refusal, a timeout and a dead network look alike from here (`CLAUDE.md` §4.4).
- **A question's writes are chained, not raced.** A like and its removal sent together could land in either order, and the one landing second would decide what is stored while the button showed the other. Every write states the outcome it wants — "store a like", "store nothing" — rather than a change, so a retried or reordered one cannot double anything, and only the last tap on a question is announced.
- **One read per game, bounded and owner-scoped**: `FirebaseService.getOwnQuestionVotes` names the caller's own ids for the game's community questions in one `IN`, at most 25, with a `limit` of the same size (`CLAUDE.md` §4.1). `/game-over` asks only about questions the service does not already know, so it is usually free; it pays once after a reload of that screen. A failed read is not remembered (§4.4): the buttons show no vote, a tap still works, and the next call asks again. A tap made while the read is out wins over the read's answer, which is older than the write behind the tap.
- **A create and an update are different writes under the rules** — a first vote carries `questionId`, `value` and `createdAt`; a changed one patches `value` alone, leaving the time of the first vote where it was — and the service sends the one its state suggests. When that guess is stale (the read had not landed, another tab voted), the refusal is answered with the other shape, once (`FirebaseService.setQuestionVote`).
- **Real accounts only, decided on a positive fact.** A tap from an anonymous or signed-out session writes nothing and comes back as "sign in to like or dislike questions"; an unverified password account's as "verify your email…". The predicate is `isFullyAuthenticated()`, the client mirror of `isRealAuthedUser()` — never broader than the server's gate (`CLAUDE.md` §4.2) — and "verify" is chosen only for a user that exists and is not anonymous, because `isAnonymous()` reads `false` for a null user. Either way the host opens the account menu (`AuthMenuStateService.open()`).
- **Scoped to one account.** The state belongs to the uid that read or wrote it and is dropped the moment a different account is signed in; a write still out for the previous account reports nothing when it lands. Signing in mid-game from the prompt re-reads the game's votes, which is the moment the buttons can first show one.

### 1.15 Avatars (`AvatarComponent`, `AvatarService`, `/profile`'s picker)

A signed-in player chooses how they appear on their own account chip and profile header (`FEAT-038`): their **initials** (the default, and every fallback), the **profile photo** their Google account carries, or an avatar they **build** from a shape and a colour, from a set their level has unlocked (`FEAT-041`). A separate switch, **off by default**, records whether the choice may ever be shown to another player. Nothing public shows an avatar today — the leaderboard draws its own initials for every row — so the switch is what a later public surface has to ask, and the picker says exactly that.

- **One component draws every surface.** `AvatarComponent` (`components/avatar/`) renders the chip (`sm`, 28px), the picker's options (`md`) and the profile header (`lg`); the fallback chain and the reserved box exist there once. **The box is the host element and its size comes from `size` alone** — the letter is the only thing in flow, and the photo and the built SVG are absolutely positioned over it — so loading, initials, photo and built are the same box by construction (`CLAUDE.md` §4.4). A `null` letter is the neutral 👤 face, which `/profile` shows to anybody who is not a signed-in account. The host is `aria-hidden` and the image `alt=""`: every surface puts the name beside it.
- **A photo shows initials until it has loaded, and initials when it never does.** The `<img>` is laid over the letter and kept `invisible` until `load`; on `error` it is removed, so a revoked, rate-limited or offline photo leaves the initial and no broken-image icon, and the same address is not asked for again in that view. It carries `referrerpolicy="no-referrer"`, so Google's image server is not told which page asked, and `loading="eager"` only in the chip, which is on every page from the first paint; everywhere else it is `lazy`.
- **The photo URL is never copied anywhere of ours.** The stored choice says only `photo`; the address is the one Firebase Authentication holds on the sign-in account, read from the Firebase user's `photoURL` at render time (`AvatarService.photoUrl`), and only when it is on `https://lh3.googleusercontent.com` — compared as a parsed origin, not a prefix. That is the one image host the CSP admits, so the picker offers the photo only to an account that has one there: a Facebook or GitHub picture lives on a host the policy refuses, and a choice that can only resolve to initials is worse than no choice. Signing out of Google does not strip the choice; the chip simply falls back. **The photo is loaded in exactly two places**: the picker's photo tile, which previews the photo as a choice it offers to any account that has one, and every surface showing the avatar of an account that chose it. So an account with a photo that never chose it makes one request to Google's image host on `/profile` and none anywhere else — what the Privacy Policy says, and what `avatar-choice.spec.ts` counts.
- **The built avatar is generated, not fetched** (`components/avatar/built-avatar.ts`): two sets of two short tables each — six shapes as path data in a 32×32 box and six colour pairs from `BRAND_DESIGN_SYSTEM.md` — drawn as inline SVG with presentation attributes only (`fill="…"`, never `style`, which the CSP would drop while leaving it in the markup). `core` is plain geometry on the brand's greens and golds; `bold` is emblems — star, bolt, heart, crown, moon, shield — on its reds, ambers, slate and jade, so the two read as different families at a glance. Lines and arcs only, in both. No sprite files, no `public/` assets, no dependency, no request. It is 2.0 kB minified (0.9 kB gzipped), so it rides the initial bundle with the chip rather than going lazy behind the choice — a bold avatar has to be drawable wherever the chip is.
- **A seed names a variant, and a level unlocks a set.** A seed is `<set>-<shape digit><colour digit>` — `core-35` is the `core` set's square on mint, `bold-21` the `bold` set's heart on amber — so sets lock and unlock by name with no change to the stored field: which sets a player may choose is the rule over the part before the dash in `models/levels.ts` — `core` from the start, `bold` at level 3 (600 XP) — the app's copy of the one `setAvatar` enforces (`stack.md` §2.4). The tables draw every seed they know, locked or not, because **what was granted is never re-locked**: a stored seed stays drawn, and saveable again, whatever its set's threshold. Each set decides what its two digits mean, and **a shipped set is frozen**, because a stored seed is a reference into it — `built-avatar.spec.ts` pins both sets entry by entry, and that no two sets share a shape or colour name. A seed this build cannot draw — a set a newer app added, a digit past a table's end — renders as initials.
- **`AvatarService` reads the choice once per account per session, and no listener.** It is injected by the top bar, so its read starts as soon as a real account is known — which is after first paint, because auth itself is deferred to the first idle moment (§1.5) — and only for a signed-in, non-anonymous user; a guest is answered without a request. The read is a `documents:batchGet` rather than a `GET`, for the reason `ReviewerService`'s is: most accounts have no `users/{uid}` yet, and a `GET` would log a `404` to the console on every page load. Until it answers, every surface draws **the copy this device kept** of the last choice the server returned — `localStorage` under `trivia-avatar`, with the uid it belongs to — or initials when there is none for this account, the least alarming answer while the real one is on its way (`CLAUDE.md` §4.4). That copy is what draws a built avatar offline, from the bundled generator, instead of initials. It is UX and never authority: it is drawn only for the account it names, the server's answer replaces it and rewrites it, `status` stays `loading` until the server answers so the picker never opens on it, every storage access is in a `try`, and signing out removes it — the frames before auth has restored a session are "nobody yet", not a sign-out, and leave it alone. A failed read is not "initials": the chip draws them anyway, but the picker shows a failed state with "Try again" rather than presenting the default as the stored choice. Signing out forgets the previous account's choice; an answer that lands after the account changed is dropped.
- **Saving is one round trip through `setAvatar`** (`stack.md` §2.4), via `AccountService.setAvatar`, which owns the lazy `firebase/functions` bootstrap. The callable answers with the choice as stored, and that lands on the chip, the header and the picker at once without a re-read. `seed` is sent only for a built avatar — the callable SDK encodes a present-but-`undefined` key as `null`, and the server refuses a seed on any other kind. **A timeout is not a failure**: the callable's `timeout` stops waiting and cancels nothing (`stack.md` §2.3 — the SDK races a timer against a `fetch` it gives no abort signal), so on `deadline-exceeded` the service reads the stored choice back before saying anything — the save is reported as made if the server now holds it, and otherwise as **could not be confirmed**, never as not saved, with the reader's draft kept for another try. A `functions/not-found` refusal — the preview-channel case, where Cloud Functions are not channel-scoped and the callable does not exist until the merge deploys it — is told apart from a failure, so the picker says avatars cannot be saved on this deployment rather than inviting a retry that can never succeed.
- **The picker (`AvatarPickerComponent`) is usable in the signed-in state only, and the card is one height in all five** — loading, signed out (anonymous included), unverified, a failed read, and the picker. An anonymous session has no `users/{uid}` and never will, so the card says why it cannot save and offers "Sign in" (hidden under `?embed=1`, like every opener of the auth menu); an unverified password account is told to verify first, because `setAvatar` refuses it the way `isRealAuthedUser()` refuses it every other write about itself. The gate is `isFullyAuthenticated()` — the whole of the server's predicate, never broader (`CLAUDE.md` §4.2), with one lag it does not control: it reads the user record where `setAvatar` reads the ID token, and for up to an hour after a player verifies their address the two disagree (`known-gaps.md` §6). The messages share one grid cell, the picker is laid out in every state and shown in one (`invisible` plus `inert`, the pair the nav drawer uses), and the three actions are one cell holding the same box three times — `ProfileStatsComponent`'s construction.
- **Named radiogroups and a checkbox**, built the way every picker here is (G4): real `<input type="radio">` elements `sr-only` behind their labels, each group `role="radiogroup"` with `aria-labelledby` — "Show as", then a shape and a colour group for each set, named by the set's heading and the row's label together ("Core Shape", "Bold Colour") — the focus ring on the label. The options draw themselves through `AvatarComponent`. **The kinds are a fixed three-column grid at every width**, and the photo's cell is there from the first paint — invisible, `aria-hidden` and holding nothing focusable — for an account with no photo, so the row is the same three cells whoever is signed in and cannot wrap when the photo arrives with auth — a wrapping row would grow the card 66px at 390px. The placeholder is the tile's own markup minus the radio, so it is the same height by construction, and `avatar-choice.spec.ts` measures the card for an account with a photo as well as one without. Picking a shape or a colour is building one, so it selects "Build your own" too — and while another kind is chosen no shape or colour reads as checked, because a radio that already reads as picked fires no `change` when clicked. The switch is a checkbox labelled "Show my avatar to other players", described by a line saying nothing shows avatars to other players yet.
- **A locked set is shown locked, never hidden** (`FEAT-041`). Every set is its own block — a heading, its shapes, its colours — and one the player's level has not reached keeps every tile on the page: `aria-disabled` rather than `disabled`, so Tab still reaches it and a keyboard user finds out the set exists; dimmed; and described by the line beside the heading — "Unlocks at level 3", "Unlocked at level 3", or "Checking your level…" while `/profile`'s read is out, the honest "do we know yet" rather than a guess either way (`CLAUDE.md` §4.4). A click, Space and the arrow keys are held on a locked tile the way a save in flight holds them, and the choice handlers check again. Locked or not, the block is the same markup and its line one grid cell, so the card is one height either way — `xp-and-levels.spec.ts` measures a locked and an open account side by side at 390 and 1280. The XP is `/profile`'s own read, the number its progress card shows (§1.10), and the rule is never broader than the server's: `setAvatar` reads the same field, at least as late (`CLAUDE.md` §4.2). A stored seed from a locked set stays checked, and saving again sends it, because the server accepts the seed already stored. A set's tiles are drawn in the draft's colour or with its shape when the draft is from that set, and on the set's first otherwise, so a tile shows exactly the avatar choosing it builds.
- **While a save is in flight every control is `aria-disabled`, never `disabled`**, which would throw focus off the button just pressed and onto `<body>`. A click on a radio or the checkbox is cancelled — the browser then restores the group, which jsdom does not model, so `avatar-choice.spec.ts` asserts it in Chromium — and arrow keys are held at `keydown`, before they move a selection. The outcome is announced through `/profile`'s existing `role="status"` region rather than a second one: the picker emits an empty string when a save starts and the outcome when it ends, so a second identical outcome is still a change the region announces, and the page shows whichever of the stats line and the save outcome happened last.
