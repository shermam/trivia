# Project History & Known Gaps

How the project got here, and an honest list of what is missing, deferred or accepted.

**Read this when** you are planning work, or want to know whether something is a bug or a known, accepted gap.

Part of the project overview — start at [`PROJECT_OVERVIEW.md`](../PROJECT_OVERVIEW.md) for the map and the conventions. Sibling documents: [Application Functionality](app.md) · [Frameworks, Tools & Libraries](stack.md) · [Data Model (Firestore)](data-model.md) · [Deployment & CI/CD](ci-cd.md).

## 5. Project History (from commit log)

1. **Initial scaffold** — Angular + Firebase + Open Trivia DB, "Phase 1" of the trivia app (setup/play/game-over flow, services, Tailwind).
2. **Firebase Hosting integration** — connected the app to the `intellectura-3b26a` Firebase project.
3. **CI fix** — granted `checks`/`pull-requests` write permissions to resolve a 403 from the Hosting deploy GitHub Action.
4. **CI enhancement** — added automatic Firestore rules/indexes deployment on merge (previously only Hosting deployed).
5. **Tooling** — added an Angular CLI analytics ID to `angular.json`.
6. **Custom question submission** — added the `/add-question` screen and its Firestore-backed question bank (`app.md` §1.1, `app.md` §1.4).
7. **Pro subscription tier (Stripe)** — added the `/pricing` screen, gated `/add-question` behind a Pro subscription, and stood up the backend twice: first via the "Run Subscriptions with Stripe" Firebase Extension, then — once that product line announced its March 2027 shutdown, before this even shipped — migrated to an owned `functions/` Cloud Functions package with the same Firestore schema/custom-claim contract (`app.md` §1.6, `stack.md` §2.4).
8. **Installable PWA & offline play** — added a web app manifest + `@angular/service-worker` (via `ng add @angular/pwa`) for Chrome/Android installability, plus an IndexedDB-backed offline question pool and background prefetch so a game can start with no network connection (`app.md` §1.8).
9. **The audit and its remediation series** — a full review of security, correctness, data model, CI/CD, testing and accessibility produced 55 findings that grew to 60, closed as one small PR each. `AUDIT_REMEDIATION.md` is the record; the invariants it established are `CLAUDE.md` §4.
10. **Firestore client SDK → REST** — every Firestore call now goes over `fetch` rather than `firebase/firestore`, which cut the bundle and, more importantly, gave every call a real cancellation story (`AbortSignal`) that the SDK did not offer. `FIRESTORE_SDK_VS_REST.md` carries the measurements.
11. **Published Privacy Policy and Terms** — `/privacy` and `/terms`, written by reading the source rather than from a template, with a banner saying they have not had professional legal review (`app.md` §1.9). `CLAUDE.md` §4.0 exists because their correctness decays silently when the code changes underneath them.
12. **Review before publish** — a Pro subscriber's submission is stored `status: 'pending'` and served to nobody until a reviewer approves it from `/review`. Reviewers are named by hand in `user_roles`; there is deliberately no admin role.
13. **A leaderboard per timing constraint** — the 15s/30s/unlimited picker meant one board was ranking runs played under different rules, so `leaderboards/{limit}/entries` replaced the single `leaderboard` collection.
14. **Three environments** — `trivimind-dev` was stood up so local development and PR previews stop reading and writing production. `npm start` runs against emulators, previews deploy to the dev project, and `npm run env:verify` fails the build if that stops being true (`dev-environment.md`).
15. **Game-over recap, and lifelines** — the finished round is now explained rather than just scored (`FEAT-001`), and 50/50 / Extra Time / Skip give the player three ways to spend one round's help (`FEAT-002`).
16. **Lifetime gameplay totals** — `users/{uid}`, written only by a Cloud Function on the Admin SDK, unblocking the several roadmap features that needed a per-user document to hang fields on (`data-model.md`).

## 6. Known Gaps / Not Yet Implemented

> A full audit of this repo (security, correctness, data model, CI/CD, testing, accessibility) was carried out and addressed as a series of individually-reviewable PRs. Each of those PRs added or struck its own entry in this list as it landed, so this section is the running record of what's still open in the product.
>
> **That series is complete** — `AUDIT_REMEDIATION.md` is its closed record: the full findings register with per-finding status, the decisions taken, and a narrative of what each fix actually shipped. **New work is queued in the roadmap repo (`shermam/trivia-project`)**; start there to pick the work up. [`BACKLOG.md`](../BACKLOG.md) is retired as a queue as of 2026-08-26 and is kept for its per-item analysis, which the roadmap specs reference rather than duplicate — its remaining open items became `FEAT-042`, `FEAT-043`, `FEAT-044`, and folded into `FEAT-007` and `FEAT-038`. Several entries below are items from that queue, and several others are deferrals the audit recorded deliberately — the distinction matters, so check before treating one as an oversight. The **invariants** the fixes establish — the things that must not silently regress once fixed — are a contract in `CLAUDE.md` §4 (app layer) and `INFRASTRUCTURE.md` §10 (infra layer). Read those before adding a feature that touches Firestore rules, the Stripe backend, auth/claims, or any new interactive UI.

- ~~Anonymous Auth accounts accumulate, and nothing deletes them yet.~~ **Closed 2026-08-16**: Firebase's built-in auto-deletion of anonymous accounts is enabled, so dormant ones are removed after 30 days without activity, and the Privacy Policy states that as a retention period. For context on why it mattered: every visitor gets an anonymous account (`app.md` §1.5) and every sign-out mints another, so the count only grew — measured 2026-08-09, **822 of the project's 829 Auth accounts were anonymous**, rising ~150/day. They held almost no data: `isRealAuthedUser()` excludes anonymous accounts from the leaderboard, `custom_questions`, `users/{uid}` and both Stripe session subcollections. The one exception is `question_reports`, whose `create` rule asks only for `request.auth != null` — reporting a bad question is deliberately open to anyone playing — so an anonymous uid can own a report, and does. Everything else was Auth-table clutter rather than orphaned user data. Most of the growth was not real visitors but the preview-e2e job (`ci-cd.md` §4.2a) leaking one account per test into the real project — closed separately as C6.
- ~~The quiz's 15-second limit is not adjustable (WCAG 2.2.1).~~ **Closed by G7**: the limit is a player choice — 15s, 30s or no limit — with a separate leaderboard per constraint so runs played under different rules are not ranked against each other. See `app.md` §1.2 and `data-model.md` §3.
- **Email-alias blocking is enforced in the sign-up form, not at the Auth API.** Hardening it further means a Firebase Auth blocking function (`beforeUserCreated`), which is an **Identity Platform** feature — an upgrade that is irreversible and changes the billing model — so it is deferred rather than pending; the roadmap repo carries the decision and the revisit condition. The thing actually defending the question bank is the rules-enforced "not anonymous, verified if password" check (`isRealAuthedUser()`, `data-model.md`), which does not depend on any of this. Worth knowing before anyone tries the upgrade: functions deploy post-merge from `firebase-deploy.yml` with no `continue-on-error`, so a missing IAM permission fails the merge deploy and takes the Hosting deploy down with it, rather than failing the PR.
- ~~**`/game-over` shows the wrong auth state while auth is still resolving.**~~ **Closed by `FEAT-045`** ([#132](https://github.com/shermam/trivia/pull/132)) — struck late, in the `FEAT-001` PR, having been missed when the fix landed. The middle card used to render "verify your email to save this score" before auth resolved, telling a signed-out visitor about a verification problem they did not have: `isAnonymous()` is `user()?.isAnonymous ?? false`, so a null user fell straight through to the signed-in branch. It is a single `scoreAction()` computed on an explicit `showsRealAccount()` predicate now, and all five faces share one grid cell so the card cannot change height as auth lands. See `app.md` §1.3 and the sizing rule in `CLAUDE.md` §4.4.
- **The game-over recap accordion opens instantly, where `FEAT-001` asked for a transition.** Deferred by the owner on 28 August 2026 as a nice-to-have behind higher-priority work, and tracked as **`FEAT-046`** in the roadmap repo — recorded here rather than left as a loose end in a merged PR body. The animation itself is trivial; what it costs is an always-mounted panel (`grid-template-rows: 0fr → 1fr` is the only way to transition to an `auto` height), which is the change that hollowed out e2e assertions in [#131](https://github.com/shermam/trivia/pull/131) and again while fixing `FEAT-045`, and which would need `inert` + `aria-hidden` to keep ten questions out of the accessibility tree while collapsed. The sibling report-form disclosure on the same screen is `@if`-gated and instant for the same reasons. Closing `FEAT-046` as "won't do" is a sanctioned outcome. Whoever does take it on has a guard already in place: `game-flow.spec.ts` measures that expanding the recap moves the score card, the leaderboard and the toggle itself by 0px, and an always-mounted panel is exactly the change that could break that.
- **A long statement gets the game's time per question, not time for its length.** A question may run to 2,000 characters (`FEAT-051`, `app.md` §1.1), which takes a minute or more to read, and a 15-second game still gives it fifteen seconds — so on a timed game such a question cannot really be answered. Deliberate: time that follows the content is `FEAT-018`'s per-question `timerSeconds`, not a stretch of the existing boards, whose limits are what each one ranks. Until that ships, "No limit" is the setting a long question needs, which is worth remembering when a batch of public-exam questions is planned.
- **Lifetime gameplay totals are bounded, not attested, and the Functions quota on that path is unprotected.** `users/{uid}` (`data-model.md`) is written by the `recordGameResult` callable from a client-supplied payload — bounded at 1..25 questions per game, `correct <= answered`, `streak <= correct`, one write per game id and 60 games per rolling hour, but not proven. That is audit decision **A1** applied to a second surface, and it is why the totals are shown only to their owner and never appear on a leaderboard: a number nobody has reason to believe should not be published. The per-hour counter bounds stat inflation and explicitly does **not** discharge `CLAUDE.md` §4.1's volume cap — a callable is billed before the counter is read — so quota there wants App Check or a `maxInstances` ceiling. Both close together if A1 is ever reopened with a signed game token.
- **A question's difficulty counts are bounded, not attested, and they survive its author's edit** (`FEAT-023`, `data-model.md` §3). The outcomes `recordGameResult` counts are client-supplied, so somebody can skew a question's calibrated difficulty by lying about their own rounds — by one game's worth per call and sixty games an hour, which is **A1** accepted once more: the score is calibration, not a boundary. And an author's edit keeps the counts, deliberately — an author able to clear them could wipe the evidence that their question is mislabelled — so a rewrite that changes a question substantially, a corrected answer or a different number of options, inherits counts gathered under its previous wording, which the guessing correction then reads against the new option count. The cost is small while the bank is young; closing it would need the server to tell a correction from a rewording, which is a feature of its own.
- **`FEAT-014` (daily game limits for free players) is stranded by the anonymous exclusion, deliberately.** `users/{uid}` is not created for anonymous sessions, and `FEAT-014` as specified requires every guest to have one. Decided 27 August 2026: ~99% of Auth accounts are anonymous, `deleteAccount` never runs for them and Firebase's auto-deletion removes only the Auth record, so a document per guest would accumulate undeletable — and a guest can mint a fresh uid by signing out, so a per-uid limit buys that feature less than it appears to. Whoever picks `FEAT-014` up needs a different mechanism, not a widening of this one.
- ~~**The Terms describe account termination as removing everything but contributed questions, and that is now two exceptions out of date.**~~ **Closed by `FEAT-042`** ([#206](https://github.com/shermam/trivia/pull/206), 9 October 2026): the termination sentence names the one other exception that is now true — the reports the account filed, kept with its identifier removed — and the Terms and the Privacy Policy say the same thing about reports again (`app.md` §1.9).
- Play Games and Game Center sign-in are listed in the Firebase console but not offered in the app — no Web SDK equivalent exists for either (native Android/Apple only).
- **There is no manual account-linking flow, so `auth/account-exists-with-different-credential` is still a dead end** — the address is owned by an account the server will not hand over on the new provider's say-so, and closing it means asking the user to sign in with the method they already have and then `linkWithCredential`-ing the pending one. The two commoner conflicts are handled without it (`app.md` §1.5). Worth knowing before starting: the canonical recipe for this flow is built on `fetchSignInMethodsForEmail`, which the installed SDK marks **deprecated** and which returns an empty list whenever Email Enumeration Protection is on — so "which method does this account have?" has to come from somewhere else, or be asked.
- ~~The `/add-question` screen only supports _creating_ a question — no in-app way to edit or delete an existing `custom_questions` doc.~~ **Review before publish shipped** ([#120](https://github.com/shermam/trivia/pull/120), [#121](https://github.com/shermam/trivia/pull/121), [#122](https://github.com/shermam/trivia/pull/122) and the 4c PR): a Pro subscriber's submission is stored with `status: 'pending'` and is not served in anyone's game until a reviewer approves it. Reviewers are named by hand in a `user_roles` register (`data-model.md`), there is deliberately no admin role yet, and the `/review` queue is where approvals and rejections happen. Both published policies were rewritten in the same PR, because "submissions are published immediately, without review" was the sentence it falsified (`CLAUDE.md` §4.0). **Editing and withdrawing shipped too** (`FEAT-007`): an author edits or removes their own contribution from `/my-questions`, and both published policies were rewritten in the same PR, because both stated in present tense that neither was possible.
- **An abusive account's questions can be rejected in bulk, but the account itself can only be acted on from the Firebase console** (`FEAT-006`, `app.md` §1.4). The reviewer's view of everything one account contributed rejects up to a page of fifty per action and does nothing to the account: suspending it, deleting it or stopping it submitting is the owner's job in the console, because there is no admin tier above reviewer — parked on 13 September 2026, and its absence is a security property while `user_roles` has no client write path (`data-model.md` § `user_roles`). So an account rejected wholesale can go on submitting, each new question waiting in Pending like any other, for as long as it holds Pro and at most twenty an hour (`custom_question_quota`, `data-model.md` §3).
- Deleting an account **anonymises** contributed questions rather than removing them, which recreates the unattributable rows finding A10 existed to fix. Accepted deliberately: the questions belong to a shared bank other players draw from, and one prolific contributor leaving should not empty a category. The cost is that an abuse report about such a question can no longer be traced to anyone.
- ~~**There is no per-user rate limit on `custom_questions` writes.**~~ Closed by [#119](https://github.com/shermam/trivia/pull/119) (`BACKLOG.md` item 3): **20 per hour per account**, enforced in `firestore.rules` against a `custom_question_quota/{window}-{uid}` counter the client must increment in the same batched commit, which `getAfter()` reads post-commit. Not a Cloud Function, and not the document-ID trick the other two caps use — see `data-model.md` for why each was rejected.
- **Nothing may embed the app in an iframe** (`frame-ancestors 'none'`, `ci-cd.md` §4.1), which closes the clickjacking exposure but also parks the embeddable-quiz idea. `?embed=1` still works when the app is loaded top-level — it just can't be framed by anyone. Making third-party embedding safe is a real piece of work rather than a header tweak, because **the thing being framed today is the whole app, session and all**: a framed page carries the visitor's live Firebase session, and the account menu inside it contains Delete account (a two-click in-place confirmation, which an overlay can drive as easily as one), Export my data, and Subscribe. A secure embed needs a surface with none of those in its DOM at all. Two things it would take:
  1. **Move embed mode from a query parameter to a path.** It is `?embed=1` today, and Firebase Hosting header rules match on _path_ only — so there is currently no way to relax `frame-ancestors` for the embeddable view without relaxing it for the entire app. An `/embed` route can carry its own header rule; a query string cannot.
  2. **Strip it to anonymous play**, ideally on a separate origin so the frame cannot reach the app's session or storage at all. No auth menu, no leaderboard write, no account actions — just the quiz.
     Worth noting for the Google Ads idea specifically: ad units are their own sandboxed frame with their own rules, and would likely want a static or self-contained build rather than this SPA.
- **Offline navigation to a route the worker did not precache fails silently.** Since the precache was scoped to what `/` and the game need (`app.md` §1.8), a player with no network who taps Pricing, Your questions, Profile, the review queue or a legal page gets a rejected dynamic import — and Angular's router has no `withNavigationErrorHandler` here, so nothing happens at all: the URL does not change, no message appears, and the screen they are on stays put. **It does not recover when the connection does**: Chromium keeps a failed dynamic import in its module map, so that route goes on failing, online, until the page is reloaded — measured on the quiz page's chunk with its cards' offline guard removed, where the click after reconnecting failed exactly like the tap before it. The previous behaviour was to have precached every route for every visitor, which is the cost this bought back; the right fix is a handler that says "this screen needs a connection" rather than un-scoping the precache, and it is a follow-up rather than part of `FEAT-017` phase 1. The curated-quiz cards on `/` are the one entry point that already says it for its own route — offline, they are disabled links reading "Needs a connection" (`app.md` §1.1) — which covers that link and no other.
- **`/add-question` tells a visitor to verify an email they have not got, until auth resolves.** Its first branch is `authService.isAnonymous()`, which is `false` while `user()` is still `null`, so a cold load of that route falls through to "Verify your email to submit a question." and then corrects itself — the exact null-falls-through-a-negative shape `CLAUDE.md` §4.4 names, on a screen it does not list. The window widened when the auth bootstrap moved after first paint (`app.md` §1.5). It is not a one-line fix, which is why it is here rather than closed: the four states of that screen are different heights, so gating them on an explicit "auth resolved" predicate means reserving the space first, or the corrected state arrives by pushing the page around.
- **The donation dialog's guest notice arrives after the dialog has painted and pushes the Donate button down.** The notice is gated on `isGuest()`, which needs auth to have resolved, and opening the dialog is now one of the gestures that _starts_ the auth bootstrap (`app.md` §1.5) — so an anonymous reader who opens it early sees the paragraph land a few hundred milliseconds later and the button move under the pointer (`CLAUDE.md` §4.4). Reserving the paragraph's height would be a number to re-measure every time the copy changes, and showing the notice while the answer is unknown would tell a signed-in reader something false; the honest fix is §4.4's second technique — always render the paragraph and swap its wording between the guest and signed-in states so both are the same height — which is a copy decision that has not been taken yet.
- The offline question pool (`app.md` §1.8) is refilled only in the foreground (idle callback + `online` event) while the app has a tab open — it doesn't use the Background Sync API, so a PWA installed but never opened between sessions won't have a freshly-topped-up pool. ~~The manifest icons are `purpose: any` only.~~ **Closed**: two `purpose: "maskable"` variants now ship at 192 and 512 (`app.md` §1.8), generated from the same source and checked in CI. **Still open, same root cause:** `public/apple-touch-icon.png` has four transparent corners, and iOS does not honour alpha in a touch icon — it composites onto **black** and then applies its own superellipse mask, so the home-screen result is a black-cornered tile inside a rounded tile. The fix is different geometry from the maskable one (iOS wants full-bleed at _full_ scale, not padded), and the file is referenced by a fixed name served `immutable` for a year, so it needs a rename plus an `index.html` edit rather than an overwrite. Queued in `BACKLOG.md` item 1.
- **Nothing in the app listens to the service worker.** `SwUpdate` appears nowhere in `src/` — no `versionUpdates`, so there is no "a new version is available" prompt, and no `unrecoverable` listener either. **The blank page that gap used to describe is handled**, by the pre-boot recovery notice in `index.html` (`app.md` §1.8): a stale worker serving a cached `index.html` whose hashed entry script no longer exists leaves a blank body with no application code running, so the notice is markup already on the page that a CSS delay reveals after ten seconds. Reloading is a genuine fix — the worker's on-navigation update check installs the current version during the failed load, so the next navigation serves an `index.html` whose scripts exist.
  **`unrecoverable` is the wrong instrument here and would not have worked**: `ngsw-worker.js` raises it only when a hashed asset returns `404`, and `firebase.json` rewrites every unmatched path to `/index.html`, so a stale asset returns `200` with HTML. Measured against a production build — no `404`, no `UNRECOVERABLE_STATE`, the driver never even left `NORMAL`. A listener would have been dead code on this hosting configuration, and nothing would have said so. Distinct from the _policy_ staleness [#115](https://github.com/shermam/trivia/pull/115) fixed — a worker running a stale CSP is healthy by its own lights.
- The e2e suite (`ci-cd.md` §4.3) covers the core unauthenticated/authenticated flows plus Pro-gated `/add-question` access and the checkout-session creation function, but not OAuth sign-in (Google/Facebook/etc. — popup-based, not practical to automate against the emulator) or the "mixed" question source end-to-end (unit-level coverage only).
- ~~ESLint covers `src/` only; the e2e suite and `functions/` are not linted.~~ **Closed** — every source tree has its own flat-config block, and the e2e tree is typechecked too (`stack.md` §2.2). Still unlinted, and deliberately out of that change's scope: **`firestore-tests/`** (the rules suite — Vitest transpiles without typechecking it either, so it is in the position the e2e tree was in) and **`scripts/`** (standalone `.mjs` files with no tsconfig, so they need a JS-flavoured block rather than a type-aware one). Neither has produced a defect yet; both are recorded in `BACKLOG.md`.
- **Production is live, and the catalog is per-mode — which is the standing trap.** `STRIPE_SECRET_KEY` in Secret Manager for `intellectura-3b26a` is a live key, so the deployed functions (`stack.md` §2.4) transact against real Stripe and `trivimind.com` takes real money; `trivimind-dev` and the emulator stay on test keys, and the `livemode` assertion derives which is which from the key itself rather than from the project name (`CLAUDE.md` §4.3), so the two can never cross. What has to be remembered every time the catalog changes is that **products, prices, webhook endpoints and portal configurations are stored separately per Stripe mode and nothing carries over**: a price added in test mode does not exist in live, and vice versa. So selling in a new currency means creating that monthly price in **both** modes, with `firebaseRole: pro` metadata on it (`dev-environment.md` §3.2 step 8, and the `customers` note in `data-model.md` for what breaks silently without it) — and saving it, since `products`/`prices` are mirrored only from events Stripe emits after the endpoint for that mode exists. A currency missing from one mode is invisible from the other: the switch simply does not appear there. **The donation catalog is a second product with the same property** (`stack.md` §2.4): a `kind: donation` product with three one-time prices per currency, in both modes, and two extra events on each endpoint. Until it exists in a given mode the tip jar reports that donations are not available there, which is the intended degradation rather than a fault.
- **The Stripe account's public details are blank.** `business_profile.url`, `support_url` and `support_email` are all unset, and those are what render on the hosted Checkout page and on every emailed receipt — so a real customer would meet a payment page and a receipt carrying no website and no support contact. They **cannot be set through the API**: `POST /v1/accounts/{id}` refuses your own account ("you may only use it on connected accounts"), so the Dashboard (Settings → Business → Public details) is the only path. Test mode otherwise swept clean on 2026-08-08 — no stale `.web.app` URL is held anywhere in Stripe, no leftover Payment Links exist, and exactly one webhook endpoint is registered, pointing at the current `stripeWebhook` Cloud Run URL with no orphan left behind by the extension migration (`stack.md` §2.4).
- **The Billing Portal carries no privacy-policy or terms-of-service link — and this is now unblocked.** The portal configuration's `business_profile` has neither URL set, so the portal footer shows no policy links at all. It was blocked rather than forgotten: `/privacy` and `/terms` did not exist on `main`, and the router's `**` catch-all means an absent path returns HTTP 200 and then client-side redirects into the game — which would have satisfied Stripe's URL validator while sending a customer who clicked "Privacy" to a trivia quiz. **Both routes now exist** ([#37](https://github.com/shermam/trivia/pull/37), `app.md` §1.9), so `https://trivimind.com/privacy` and `/terms` can be set on the portal configuration. That is a console/API step, so it is tracked in `AUDIT_REMEDIATION.md` §7 rather than here. `default_return_url` **is** set (`https://trivimind.com/pricing`), though it only ever acts as a fallback, since `createPortalSession` always passes an explicit `return_url` built from the caller's validated origin.

- **The free tier's daily game limit is a device-local conversion nudge, not an entitlement boundary** (`app.md` §1.8). It is accepted as such rather than overlooked, and the reasoning — including what a server-side counter would and would not buy — is in the roadmap repo's accepted-risk register. The shape of the constraint that keeps it where it is: there is no question-delivery chokepoint to enforce it at, because the client fetches from `opentdb.com` and Firestore directly and offline play could not consult a server at all. `FEAT-047` carries the server version for when one exists.

- **A regional leaderboard ranks whoever says they are there** (`app.md` §1.1). The country on an entry is the player's own declaration and nothing checks it, so somebody who wants to top a small board can set their country to one and do it. Accepted rather than rate-limited: this is a trivia game, not a ranked ladder, and the alternatives all cost more than the problem — an IP check would make the app infer and store a location the Privacy Policy says it never keeps, and a cooldown on changes would punish the people it is meant to serve, who move house or travel. Nothing bounds the number of boards one account can appear on either, so a script writing straight to Firestore could hold an entry on all 249 — every one of them a schema-valid score under that account's own uid, which is the same exposure the global boards already accept (A1) spread wider rather than a new one. There is deliberately no minimum participant count, so a country with one player reads as a board of one; an empty national board is an invitation rather than a defect.

- **A like or dislike can only be changed where its question appears** (`app.md` §1.14). The buttons are the only way in — after a reveal on `/play`, and on that game's recap — and there is no screen listing a player's votes, so a vote on a question that has since been withdrawn, or simply never comes round again, stays until the account is deleted. It is private, counted nowhere and returned by "Export my data", which is why a list screen was not built with the feature; it is the obvious companion if `FEAT-029` ever makes a stale vote matter.

- **A curated quiz is ranked nowhere** (`FEAT-024`, `app.md` §1.1). The administrator decided on 8 October 2026 that a quiz makes no leaderboard entry — everybody plays its questions in the same order, so a second play is a memory test — where the spec ranked it on the board for the limit played, and no board of its own exists either. Reversing it is small: drop the quiz face's precedence in `GameOverComponent.scoreAction` and the guard in `saveScore()`, and the board comes back with the save form.

- **The quiz list shows the newest ten published quizzes and nothing older, and cannot be browsed by topic** (`app.md` §1.1). An older quiz still plays from its address; paging is for when there are more than ten, and `tags` on a quiz is validated by the seed script and used by nothing until `FEAT-021`'s browsing lands. A card shows how many questions the quiz names, not how many it can still play — finding out costs a read per quiz, so the quiz page says it instead, before Start.

- **Question deduplication is per device, so a shared browser shares a seen-set** (`app.md` §1.2). Two people playing on one browser suppress each other's questions, and clearing site data — or picking up a different phone — starts the bank over. A per-player record of what each account has been shown now exists — `users/{uid}/plays` (`FEAT-049`, `data-model.md` §3) — but the seen-set does not read it, and moving deduplication onto it would not close this: the history is written for **signed-in accounts only**, so a guest and a shared browser would be exactly where they are today. Reading it would also be a Firestore read on the draw path, which is the cost the device-local set exists to avoid — the same trade the offline pool and the daily allowance already make. The other edge is arithmetic rather than design: once every question matching a game's filters has been answered, the draw falls back to the least-recently-seen, so a narrow category keeps repeating — the fix for that is more questions in the bank, not more code.

- **Five Firestore indexes that name `category` outlive the queries they were built for** (`data-model.md` §3). Since topics replaced categories (`FEAT-052`) the draw sends no `category` clause, but a browser still on the previous bundle does until it updates, so `category+difficulty` and the four `status+category…` indexes stay declared. Retiring them is a later change with a console step in it on both projects, because removing a declaration does not delete an index and the deploy refuses a live index its file does not declare. Until then each costs index storage and a little write work on every question.

- **A question whose stored category derives no tag has no topic** (`app.md` §1.4). A free-text category with no letters or digits in it, or one past thirty-two characters, normalises to nothing — so no reader shows a topic for it, no topic filter can draw it, and `scripts/backfill-category-tags.mjs` reports it rather than inventing one. Only its author's edit, which requires a topic, gives it one.

- **A tag stored before the normaliser folded `ß`, `æ`, `ø` and the other letters no decomposition reaches keeps the spelling it was stored with** (`app.md` §1.4). Until then those letters were dropped rather than folded, and so were ligatures and compatibility forms such as `ﬁ`, the ordinal `ª` and superscript digits — so a contributor who typed `Straße` has `strae` stored where the same word now gives `strasse`, and `2ª Guerra Mundial` is stored as `2-guerra-mundial` where it now gives `2a-guerra-mundial`. Both spellings are well-formed tags, so nothing is refused, mis-rendered or in need of a backfill; they are two tags for one topic, and a filter typed today does not draw the questions stored under the older one. That is the free-form-tag inconsistency `FEAT-021`'s curation pass exists for — a script mapping aliases onto canonical tags — rather than a migration, because a stored tag does not record what was typed: `strae` cannot be re-derived. The tags the category backfill wrote and those a play history snapshotted carry the older spelling the same way, and re-running `scripts/backfill-category-tags.mjs` would append the newer one beside it, since it appends whatever its category derives now.

- **The published policies have not had a professional legal review**, and a banner on both pages says so (`app.md` §1.9). Everything factual in them was written from the source. Two questions genuinely need a lawyer — whether Brazil's stricter under-12 rule needs an actual age gate rather than a stated minimum age of 13, and whether a liability cap is worth having at all — and they are listed in `BACKLOG.md` §5 rather than rendered on the page, because an unresolved-item notice is a message to the maintainer and a reader can do nothing with it. A one-off review is planned; until then the banner is what stops anyone mistaking these for reviewed policy.

- **A donation earns no supporter badge, deliberately, and there is nowhere to put one yet.** `FEAT-013` ships the payment and the record (`customers/{uid}/donations` and `supporterSince`, `data-model.md`) and no badge at all: `/profile` is a read-only view of gameplay totals, the leaderboard renders inside game-over rather than as a component of its own, and showing supporter status **beside a name on the public board would need a new public document** — neither `users/{uid}` nor `customers/{uid}` may be widened for it, since one is described in the Privacy Policy as gameplay totals and the other is payment state readable only by its owner. So the substrate is there and the badge is a follower of whichever screen wants it, not an oversight in this one.

- ~~**A question report survives the reporter's account deletion, identifier and all.**~~ **Closed by `FEAT-042`** ([#206](https://github.com/shermam/trivia/pull/206), 9 October 2026): a report keeps its reporter for thirty days — the daily pass in `sweepPlayHistory` then copies it to a fresh id without `reportedBy` and deletes the original — and `deleteAccount` does the same at once for every report the leaver filed, deleting none, so no report names a deleted account, in a field or in an id (`data-model.md` § `question_reports`).
- **The daily report pass re-reads every report older than thirty days, every run** (`FEAT-042`, `data-model.md` § `question_reports`). An anonymised copy keeps its original's `createdAt` — the reviewers' queue orders by it — so it stays inside the range the pass reads, and each run starts from the oldest. That costs a read per old report per day, and past the run's ceiling of 5,000 the pass can no longer reach the newest expired reports: it then throws `ReportSweepIncompleteError` on every run, loudly, rather than leave reports past their thirty days quietly named. At today's report volume that is years away. The fix when it matters is a cursor that survives between runs — one server-written document recording where the last run stopped — so a run reads only what expired since.
- **`www.trivimind.com` has no DNS record.** The apex serves the app through Firebase Hosting; the `www` name resolves to nothing and fails outright rather than redirecting. `CUSTOM_APP_ORIGINS` (`functions/src/checkout-request.ts`) lists both names deliberately — listing an unwired name costs nothing, omitting a wired one breaks checkout — so the allowlist is correct and the gap is purely DNS. The trap is that the allowlist reads like evidence that `www` works: any outward-facing link, Stripe setting or marketing copy using it is dead today.
