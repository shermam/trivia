# Project History & Known Gaps

How the project got here, and an honest list of what is missing, deferred or accepted.

**Read this when** you are planning work, or want to know whether something is a bug or a known, accepted gap.

Part of the project overview — start at [`PROJECT_OVERVIEW.md`](../PROJECT_OVERVIEW.md) for the map and the conventions. Sibling documents: [Application Functionality](app.md) · [Frameworks, Tools & Libraries](stack.md) · [Data Model (Firestore)](data-model.md) · [Deployment & CI/CD](ci-cd.md).

## 5. Project History (from commit log)

1. **Initial scaffold** — Angular + Firebase + Open Trivia DB, "Phase 1" of the trivia app (setup/play/game-over flow, services, Tailwind).
2. **Firebase Hosting integration** — connected the app to the `intellectura-3b26a` Firebase project.
3. **CI fix** — granted `checks`/`pull-requests` write permissions to resolve a 403 from the Hosting deploy GitHub Action.
4. **CI enhancement** — added automatic Firestore rules/indexes deployment on merge (previously only Hosting deployed).
5. **Tooling** — added an Angular CLI analytics ID to `angular.json`.
6. **Custom question submission** — added the `/add-question` screen and its Firestore-backed question bank (`app.md` §1.1, `app.md` §1.4).
7. **Pro subscription tier (Stripe)** — added the `/pricing` screen, gated `/add-question` behind a Pro subscription, and stood up the backend twice: first via the "Run Subscriptions with Stripe" Firebase Extension, then — once that product line announced its March 2027 shutdown, before this even shipped — migrated to an owned `functions/` Cloud Functions package with the same Firestore schema/custom-claim contract (`app.md` §1.6, `stack.md` §2.4).
8. **Installable PWA & offline play** — added a web app manifest + `@angular/service-worker` (via `ng add @angular/pwa`) for Chrome/Android installability, plus an IndexedDB-backed offline question pool and background prefetch so a game can start with no network connection (`app.md` §1.8).

## 6. Known Gaps / Not Yet Implemented

> A full audit of this repo (security, correctness, data model, CI/CD, testing, accessibility) was carried out and is being addressed as a series of individually-reviewable PRs. Each of those PRs adds or strikes its own entry in this list as it lands, so this section is the running record of what's still open in the product.
>
> **`AUDIT_REMEDIATION.md` tracks that series itself** — the full findings register with per-finding status, the working rules, and the decisions taken. Start there to pick the work up. The **invariants** the fixes establish — the things that must not silently regress once fixed — are a contract in `CLAUDE.md` §4 (app layer) and `INFRASTRUCTURE.md` §10 (infra layer). Read those before adding a feature that touches Firestore rules, the Stripe backend, auth/claims, or any new interactive UI.

- **Anonymous Auth accounts accumulate, and nothing deletes them yet.** Every visitor gets one (`app.md` §1.5) and every sign-out mints another, so the count only grows: measured 2026-08-09, **822 of the project's 829 Auth accounts were anonymous**, rising ~150/day. They hold no data — `isRealAuthedUser()` excludes anonymous from the leaderboard, `custom_questions` and both session subcollections, so an anonymous uid cannot own a Firestore document anywhere — so this is Auth-table clutter rather than orphaned user data. The fix is Firebase's built-in auto-deletion of anonymous accounts (30 days inactive), which is a project setting rather than anything in this repo: it is tracked as the C3 manual step in `AUDIT_REMEDIATION.md` §7 and was confirmed **off** at that date. Most of the growth is not real visitors but the preview-e2e job (`ci-cd.md` §4.2a) leaking one account per test into the real project — tracked separately as C6.
- **The quiz's 15-second limit is not adjustable (WCAG 2.2.1).** Decided but unbuilt — see G7 in `AUDIT_REMEDIATION.md` §4: a player-chosen timer including unlimited, with a **separate leaderboard per timing constraint** so runs played under different rules are not ranked against each other. The leaderboard split is the substantive work (schema, rules, and the game-over screen), not the timer control.
- Email-alias blocking is client-side only (regex on sign-up) — a determined user could still call the Auth API directly to create alias accounts. Closing that gap requires a Firebase Auth blocking Cloud Function (`beforeCreate`) — the `functions/` package and its CI deploy step (`stack.md` §2.4, `ci-cd.md` §4.2) now exist for the Pro subscription backend, so the infrastructure blocker is gone, but the blocking function itself still isn't written. The rules-enforced "not anonymous, verified if password" check is the actual anti-flood defense and doesn't depend on this.
- Play Games and Game Center sign-in are listed in the Firebase console but not offered in the app — no Web SDK equivalent exists for either (native Android/Apple only).
- The `/add-question` screen only supports _creating_ a question — no in-app way to edit or delete an existing `custom_questions` doc yet (console-only for now, per the rules comments). **There is still no review step before a question goes live**: any fully authenticated Pro subscriber publishes directly to the shared bank. What exists now (finding H4): submissions are attributed (`createdBy`, `data-model.md` §3) and any player can **flag** a question while playing it and file the report at game over (`question_reports`, `data-model.md` §3), so abuse is actionable end-to-end — report → attributed author → console removal. **Review-before-publish is decided but unbuilt** (`AUDIT_REMEDIATION.md` §4): it is a product feature with a schema migration (a pending/approved status against the exact-key `hasOnly()` allowlist, an admin role, query/index changes) that also changes the Pro promise — contributions would stop appearing instantly — so it is reserved as its own piece of work rather than folded into the reporting PR.
- Deleting an account **anonymises** contributed questions rather than removing them, which recreates the unattributable rows finding A10 existed to fix. Accepted deliberately: the questions belong to a shared bank other players draw from, and one prolific contributor leaving should not empty a category. The cost is that an abuse report about such a question can no longer be traced to anyone.
- **There is no per-user rate limit on `custom_questions` writes.** A single Pro subscriber can still submit in a loop. This was deliberately not bundled with the attribution change because Firestore rules cannot count a user's documents: enforcing a cap needs either a companion counter document the client also writes (which the client can then simply decline to update, unless both writes are forced into one batch) or a Cloud Function on the write path. Both are a different mechanism and a different PR, and neither was worth delaying attribution — which, unlike a rate limit, cannot be added retroactively.
- **Nothing may embed the app in an iframe** (`frame-ancestors 'none'`, `ci-cd.md` §4.1), which closes the clickjacking exposure but also parks the embeddable-quiz idea. `?embed=1` still works when the app is loaded top-level — it just can't be framed by anyone. Making third-party embedding safe is a real piece of work rather than a header tweak, because **the thing being framed today is the whole app, session and all**: a framed page carries the visitor's live Firebase session, and the account menu inside it contains Delete account (a two-click in-place confirmation, which an overlay can drive as easily as one), Export my data, and Subscribe. A secure embed needs a surface with none of those in its DOM at all. Two things it would take:
  1. **Move embed mode from a query parameter to a path.** It is `?embed=1` today, and Firebase Hosting header rules match on _path_ only — so there is currently no way to relax `frame-ancestors` for the embeddable view without relaxing it for the entire app. An `/embed` route can carry its own header rule; a query string cannot.
  2. **Strip it to anonymous play**, ideally on a separate origin so the frame cannot reach the app's session or storage at all. No auth menu, no leaderboard write, no account actions — just the quiz.
     Worth noting for the Google Ads idea specifically: ad units are their own sandboxed frame with their own rules, and would likely want a static or self-contained build rather than this SPA.
- The offline question pool (`app.md` §1.8) is refilled only in the foreground (idle callback + `online` event) while the app has a tab open — it doesn't use the Background Sync API, so a PWA installed but never opened between sessions won't have a freshly-topped-up pool. The manifest icons are `purpose: any` only; the Trivimind mark wasn't designed with a maskable safe zone, so a true `maskable` icon variant (padded so Android's adaptive-icon mask never crops the glyph) isn't provided yet.
- The e2e suite (`ci-cd.md` §4.3) covers the core unauthenticated/authenticated flows plus Pro-gated `/add-question` access and the checkout-session creation function, but not OAuth sign-in (Google/Facebook/etc. — popup-based, not practical to automate against the emulator) or the "mixed" question source end-to-end (unit-level coverage only).
- ESLint (`stack.md` §2.2) covers `src/` only. `cypress/` (its own tsconfig plus Cypress globals) and `functions/` (a separate npm package with its own tsconfig — and the one that actually ships to the Cloud Functions runtime) are not linted yet; both need their own flat-config entry with the right `projectService` wiring.
- **The Stripe account is not live yet — production runs in test mode, deliberately.** `STRIPE_SECRET_KEY` in Secret Manager for `intellectura-3b26a` is an `sk_test_…` key, so the deployed functions (`stack.md` §2.4) transact against Stripe test mode and `trivimind.com` accepts test cards only. This is a pre-launch state rather than a defect, but it does mean nothing in the payment path has ever been exercised against real money. Activating live payments is blocked on business banking setup for the registered company, expected to complete within a few business days of 2026-08-08. Going live is then a checklist rather than a switch, because **portal configurations, payment links and webhook endpoints are stored separately per Stripe mode and none of them carry over from test**: a live secret key has to replace the Secret Manager value, a live webhook endpoint has to be registered against the deployed `stripeWebhook` URL, `STRIPE_WEBHOOK_SECRET` has to be swapped for that endpoint's own live signing secret, and a live Billing Portal configuration has to be built from scratch. Until that happens the live-mode side of all four has never been inspected.
- **The Stripe account's public details are blank.** `business_profile.url`, `support_url` and `support_email` are all unset, and those are what render on the hosted Checkout page and on every emailed receipt — so a real customer would meet a payment page and a receipt carrying no website and no support contact. They **cannot be set through the API**: `POST /v1/accounts/{id}` refuses your own account ("you may only use it on connected accounts"), so the Dashboard (Settings → Business → Public details) is the only path. Test mode otherwise swept clean on 2026-08-08 — no stale `.web.app` URL is held anywhere in Stripe, no leftover Payment Links exist, and exactly one webhook endpoint is registered, pointing at the current `stripeWebhook` Cloud Run URL with no orphan left behind by the extension migration (`stack.md` §2.4).
- **The Billing Portal carries no privacy-policy or terms-of-service link.** The portal configuration's `business_profile` has neither URL set, so the portal footer shows no policy links at all. This is blocked rather than forgotten: `/privacy` and `/terms` don't exist on `main` (they're still in the unmerged [#37](https://github.com/shermam/trivia/pull/37)), and the router's `**` catch-all means both paths return HTTP 200 and then client-side redirect into the game — which would satisfy Stripe's URL validator while sending a customer who clicks "Privacy" to a trivia quiz. Merge #37 before pointing Stripe at either path. `default_return_url` **is** set (`https://trivimind.com/pricing`), though it only ever acts as a fallback, since `createPortalSession` always passes an explicit `return_url` built from the caller's validated origin.
- **`www.trivimind.com` has no DNS record.** The apex serves the app through Firebase Hosting; the `www` name resolves to nothing and fails outright rather than redirecting. `CUSTOM_APP_ORIGINS` (`functions/src/checkout-request.ts`) lists both names deliberately — listing an unwired name costs nothing, omitting a wired one breaks checkout — so the allowlist is correct and the gap is purely DNS. The trap is that the allowlist reads like evidence that `www` works: any outward-facing link, Stripe setting or marketing copy using it is dead today.
- **The critical `tar` advisory `npm audit` used to report is resolved** — it arrived via `firebase-tools@14`'s `@google-cloud/pubsub`/`gaxios` transitive chain, and the bump to `firebase-tools@15` (`^15.26.0`, `stack.md` §2.2) was its fix, unblocked once JDK 21 was installed locally (`AUDIT_REMEDIATION.md` §7 — `@15` hard-requires it for the Firestore emulator, so local `e2e`/`rules:test` runs now need it on `PATH`; see `stack.md` §2.2). Re-checked 2026-08-10 after the bump: the root `npm audit` reports 16 findings (2 low, 13 moderate, 1 high) — still devDependency-only, never shipped in the app bundle — and all with the same shape: every direct dependency is already at its latest major, and `npm audit fix --force`'s suggested "fixes" are multi-major downgrades (`@lhci/cli` 0.15.1 → 0.1.0, `@angular/cli` 22 → 21, `firebase-tools` 15 → 14.23) that only avoid the vulnerable subtree by reverting to a version that predates it, not a real patch — don't take them. The high is `tmp` (symlink/path-traversal in temp-file creation) via `@lhci/cli` → `inquirer` → `external-editor`; the moderates include `@hono/node-server` via `@angular/cli`'s bundled MCP SDK, `@opentelemetry/core` via `firebase-tools@15`'s own `@google-cloud/pubsub`, and the same `uuid` advisory the functions tree had, here via the root's `firebase-admin` devDependency (Cypress's seeding tasks). `functions/`'s production tree carried the same moderate `uuid` finding (GHSA-w5hq-g745-h8pq, reached via `firebase-admin` → `@google-cloud/storage` → `gaxios`/`teeny-request`) with every direct dependency already on its latest major — resolved with an npm `overrides` entry pinning `uuid` to `^11.1.1` (finding A12), so `npm audit --omit=dev` in `functions/` now reports zero vulnerabilities and a new advisory there is signal again rather than noise. The override is scaffolding, not policy: remove it once Google's storage chain ships a fixed `uuid` of its own accord. `npm audit fix --force`'s suggestion for this one was `firebase-admin@10.3.0` — a multi-major _downgrade_, the same trap described above; don't take it.
