The visual design system (colors, typography, shadows, radii, component styling directives) is documented in **`BRAND_DESIGN_SYSTEM.md`** — the single reference for styling any new or restyled UI component; there is no Figma export in the repo to cross-check against. Icons are inline SVG (lucide-static path data, ISC license) rendered via a single shared `IconComponent` (`src/app/components/icon/icon.component.ts`) — same no-dependency convention as `ProviderIconComponent`'s OAuth brand marks — rather than an `lucide-angular`/icon-font dependency. `Inter` (the brand typeface) is **self-hosted** from `public/fonts` — two variable-weight `woff2` subsets (`latin`, `latin-ext`) covering the whole 100–900 axis, declared as `@font-face` in `src/styles.css`, with the `latin` file preloaded from `index.html`. It used to be hot-linked from Google Fonts, the one standing exception to this app's third-party-request avoidance (`app.md` §1.5's OAuth-popup-resolver note); that exception is gone. Hot-linking sent every visitor's IP to Google before the page asked for any consent — LG München I (3 O 17493/20) held that to be a GDPR breach — and cost two preconnects and a render-blocking stylesheet on the critical path. `unicode-range` keeps `latin-ext` free: the browser fetches it only when a glyph in that range is actually rendered, which was verified in a real browser rather than assumed. Filenames carry Google's `v20` revision because `public/` is copied into the build with no content hash while `firebase.json` serves `woff2` as `immutable` for a year — see `public/fonts/README.md` for the refresh procedure, and `LICENSE.txt` beside it for the SIL OFL text the licence requires to travel with the files.

App icons (`public/favicon.svg`/`.ico`, `public/apple-touch-icon.png`, linked from `index.html`) are the Trivimind mark: a `#059669` (Primary Emerald, matching `BRAND_DESIGN_SYSTEM.md` §1 exactly) rounded-square (`rx="32"` on a 144×144 box) with a bold white `?` glyph on top. An earlier version used a much more intricate brain/lightbulb/`?` illustration, but that much line art doesn't survive being scaled down to actual favicon sizes (16–32px) — it reads as a blurred blob rather than a mark, no matter how the raster assets are generated — so it was replaced with this single bold glyph, which stays legible from 16px up to a full-size hero icon. `favicon.ico` still embeds six sizes (16 up to 256px), each rasterized directly from the vector. Static icon files hardcode this hex directly (no ambient CSS `color` for a browser-tab/OS icon to inherit from), unlike the in-app mark below.

The same mark is also used in-app as the brand badge — top bar logo, `GameSetupComponent`'s hero icon, and the Pro card badge on `/pricing` — via a dedicated `LogoComponent` (`src/app/components/logo/logo.component.ts`, selector `app-logo`) that inlines the identical SVG (byte-identical path data to `favicon.svg`), fills its background with `fill="currentColor"`, and sets `host: { class: 'inline-block' }` in the `@Component` decorator. Both of those matter: the background is `currentColor` (not a hardcoded hex) so callers set the exact shade via a `text-emerald-600` class on `app-logo` itself, keeping it tied to the same design-system value everywhere instead of a second hardcoded copy that can drift out of sync (as it once did — an earlier hardcoded `#0fa968` didn't quite match Primary). `inline-block` matters because `app-logo` is a real host element wrapping the `<svg>`, not the svg itself — Tailwind's preflight already makes a raw `<svg>` size correctly from its own `width`/`height` attributes (it's a replaced element), but the host has no intrinsic size of its own, so a plain `block` class left it stretching to 100% of its container width; any `rounded-*`/`shadow-*` class on `app-logo` then wrapped that invisible full-width box instead of the icon, producing a left-aligned icon with an elongated shadow trailing off to the right. The glyph's white fill is a **presentation attribute** (`fill="#ffffff"`), not an inline `style` — the CSP (`ci-cd.md` §4.1) refuses style attributes, and when it does the attribute stays in the DOM while its declarations are silently dropped, so the mark rendered with the wrong fill and still looked correct to `getAttribute('style')`. The Inkscape residue that came with it (`font-family`, `text-anchor`, `-inkscape-font-specification` …) was dropped at the same time; none of it affects a `<path>`. `LogoComponent` is kept separate from the shared `IconComponent`'s single-color 24×24 stroke-icon `@switch` (same convention as `ProviderIconComponent`'s OAuth brand marks) since it's a fixed filled mark, not a 24×24 stroke glyph. The purely decorative sparkle accents elsewhere (game-setup's "Start Game" button, pricing's "Subscribe" button, add-question's hero badge) still use `IconComponent`'s `sparkles` icon — only the three brand-badge placements above were switched.

### 2.2 Tooling

- **Node 24** — the version floor everywhere: `functions/package.json`'s `engines.node` (the actual Cloud Functions deploy runtime), every CI workflow's `actions/setup-node`, and the repo-root `.node-version` for local `nodenv` users (`nodenv` auto-selects it on `cd` into the repo; other version managers should match it manually until/unless an `.nvmrc` is added). All three are bumped together on purpose, so `npm ci`-vs-local drift and the functions deploy runtime never disagree — see INFRASTRUCTURE.md §7.
- **Angular CLI 22** (`@angular/cli`, `@angular/build`) — build, dev-server, scaffolding.
- **Vitest 4** — the project's unit test runner (Angular CLI's new default test builder, `@angular/build:unit-test`), using **jsdom** as the DOM environment. Run via `npm test` (`ng test`). **Coverage runs on every `npm test`** (`@vitest/coverage-v8`, configured in `angular.json`'s test target) and the run fails under measured-baseline floors — statements 54 / branches 57 / functions 56 / lines 54, set ~2% under the observed 56.5/60.2/59.5/56.8 of 2026-08-10 (finding E5). Components are deliberately e2e-covered here, so this is a whole-`src/` **ratchet**, not a target: raise the floors as suites grow; lowering them is forbidden (`CLAUDE.md` §3). The functions suite enforces its own floors through Node's native coverage (`--test-coverage-*` in `functions/package.json`, 95/95/85 against an observed 96.5/96.9/91.7) with one caveat worth knowing: `node --test` only reports files the tests actually **load**, so an entirely untested module is invisible to the floor rather than counted at zero — the ratchet catches regressions in covered files, not gaps in reach. Both floors ride the existing `test`/`functions-tests` CI checks, since they fail those same commands.
- **fake-indexeddb** (devDependency) — polyfills `indexedDB` for `OfflineQuestionsService`'s/`TriviaService`'s/`GamePersistenceService`'s unit tests (jsdom itself has no IndexedDB implementation); imported via `fake-indexeddb/auto` at the top of the relevant `.spec.ts` files only, never shipped in the app bundle. **Database names are global to the origin and Vitest shares one environment across spec files**, so any test that needs a known schema version must work on a database of its own (`OFFLINE_DB_NAME`, overridden per test in `offline-db.service.spec.ts`) rather than trying to reset the shared one. `deleteDatabase()` is the specific trap: it blocks for as long as _any_ connection is open, and a blocked delete never settles — so a suite built on it passes locally and hangs on CI, where the run is slower and the ordering differs. Closing connections in teardown is good hygiene but does not fix it, because the files can be in flight together.
- **@angular/service-worker** — scaffolded via `ng add @angular/pwa` (`app.md` §1.8); precaches the app shell for offline/installable use. See `INFRASTRUCTURE.md` §2a for the setup notes (including an `ng add` version-pinning pitfall worth knowing before re-running it).
- **Cypress 15** — end-to-end tests (`npm run e2e` / `npm run e2e:open`), driven against a real local Firebase Emulator Suite instance rather than mocks; see `ci-cd.md` §4.3.
- **firebase-admin** (devDependency) — used only from Cypress's Node-side tasks to seed/reset emulator Auth users and Firestore docs, bypassing `firestore.rules`; never shipped in the app bundle.
- **@lhci/cli (Lighthouse CI) 0.15** — audits the production build's performance/accessibility/best-practices/SEO scores (`npm run lighthouse`); see `ci-cd.md` §4.4.
- **Prettier 3** — code formatting; configured for 100-char print width, single quotes, and the Angular HTML parser for `.html` templates (`.prettierrc`), with a `.prettierignore` covering build output, generated reports and lockfiles. Enforced by `npm run format:check` in CI (`lint.yml`) — before that step existed it was advisory only, and 12 files had drifted.
- **ESLint 10 + angular-eslint 22 + typescript-eslint 8** — static analysis (`npm run lint`, `eslint.config.js`, flat config, scaffolded via a version-pinned `ng add angular-eslint@22.1.0`). Runs the recommended TS/Angular/template sets plus `templateAccessibility`, extended with **type-aware** `no-floating-promises`/`no-misused-promises` (via `projectService`) and four template rules the recommended sets omit (`button-has-type`, `no-duplicate-attributes`, `no-positive-tabindex`, `eqeqeq`). Enforced in CI by its own `lint.yml` workflow alongside `format:check` (`ci-cd.md` §4.6), one workflow per concern like the rest.

  **Covers three source trees**, one config block each — `src/`, `functions/src/` and `cypress/` (plus the two root-level Cypress config files) — with the Angular set and the inline-template processor scoped to `src/` alone, since neither of the others contains a component. Each block resolves its own nearest `tsconfig.json` through `projectService`, so type-aware rules are live in all three. Two rules differ under `cypress/` and both are about chai and Cypress's types rather than a lower standard: `no-namespace` allows the `declare global { namespace Cypress }` command augmentation, which ES2015 module syntax cannot express, and `no-unused-expressions` is off because `expect(x).to.be.false` is a property access indistinguishable from a dead expression. Under `functions/src/`, `no-floating-promises` exempts `node:test`'s `describe`/`it`/`test` by package name — they return a promise the runner awaits, and without the exemption the suite reports 118 non-defects.

  **Both halves of the wiring have to change together**: `eslint.config.js` decides the rules, `angular.json`'s `lintFilePatterns` decides which files reach them. Editing one alone does nothing, which is why `cypress/` and `functions/` stayed unlinted despite the config already matching them.

- **`tsc --noEmit` over `cypress/`** (`npm run typecheck:cypress`, third step of `lint.yml`). The only tree nothing else typechecks: `src/` goes through `ng build`/`ng test`, `functions/` through the `tsc` that `functions:test` runs first, but `cypress/tsconfig.json` was referenced by no script and no CI step — inert config. Running it for the first time found a real error (`win.Storage` on a bare `Window`; the global constructors are declared as `var`s in the global scope, not as members of `interface Window`). Type-aware lint loads that tsconfig now too, but lint reports rule violations, not type errors, so the two checks are not substitutes.
- **PostCSS** — pipes Tailwind through `@tailwindcss/postcss` (`.postcssrc.json`).
- **EditorConfig** — enforces 2-space indentation, UTF-8, single quotes in TS across editors.
- **Firebase CLI** (`firebase-tools`) — local emulation and deployment; invoked both from local npm scripts and CI. The **`devDependency` is `^15.26.0`** and backs every script that calls the bare `firebase` binary (`e2e`, `e2e:open`, `rules:test`, `firebase:emulate`, `firebase:deploy`) — `npm` scripts already put `node_modules/.bin` first on `PATH`, so those scripts always get the exact locally-installed version, with no per-run npx cache/registry round-trip. It was `^14.27.0` until the critical `tar` advisory in `@14`'s transitive tree forced the major bump (`known-gaps.md` §6); `@14` was itself required over `@13` for anything touching `functions/` because `@13`'s bundled Functions tooling unconditionally probes for `functions.config()`, an API `firebase-functions` v7 removed outright, crashing every invocation — `@14`+ detects v7+ and skips that legacy path (confirmed by running the emulator directly with `--debug` and comparing the two). **`@15` hard-requires a JDK ≥ 21 for the Firestore emulator, and refuses to start on an older one rather than warning** — so every local script that starts that emulator through it (`npm run e2e`, `e2e:open`, `rules:test`, `firebase:emulate`) needs JDK 21 on `PATH`. On this machine the Homebrew install is keg-only (`java` still resolves to 14), so `export PATH="/usr/local/opt/openjdk@21/bin:$PATH"` first — see `AUDIT_REMEDIATION.md` §7. CI is unaffected: `e2e.yml`, `rules-tests.yml` and `lighthouse.yml` already set up Temurin 21. **`@13`** still backs the single `lighthouse` script via `npx --yes firebase-tools@13` — the one emulator run that doesn't touch `functions/` (`hosting,auth,firestore` only), so `@13`'s crash doesn't apply; a second major can't coexist as a second `devDependency` entry under the same package name, and `--yes` skips npm's interactive "ok to install?" prompt the first time that pin isn't already in the local npx cache (CI never sees that prompt either way, since its shell is non-interactive). The CI functions-deploy step (`firebase-deploy.yml`, `ci-cd.md` §4.2) is deliberately left on `npx firebase-tools@14 deploy` rather than switched to the devDependency too — a one-shot deploy on a fresh runner doesn't benefit from the local-cache win, and keeping that line's version pin self-contained makes "what exact tool deployed production" answerable by reading that one line alone.
- **firebase-functions 7** / **stripe (Node SDK) 22** — the `functions/` package's only two runtime dependencies beyond `firebase-admin`; see §2.4.

### 2.3 Firebase client integration details

`AuthService` and `AccountService` wrap the Firebase modular SDK (`firebase/app`, `firebase/auth`, `firebase/functions`) directly — **no AngularFire** — by design, so they can later be reused unmodified in non-Angular shells (e.g. Capacitor/Tauri) per an in-code comment.

**The Firestore SDK is gone.** `firebase/firestore` is imported nowhere in `src/`; every read and write goes through `FirestoreRestClient` (below). `firebase/app`, `firebase/auth` and `firebase/functions` stay — only Firestore moved. See `BACKLOG.md` item 2 and `FIRESTORE_SDK_VS_REST.md` §11 for the measured result: **−553,133 bytes raw / −139,575 bytes brotli**, about 41% of all the JavaScript the app shipped.

Notably, the app **never commits a Firebase config/API key to source**. Instead it fetches `/__/firebase/init.json` at runtime — a reserved endpoint that Firebase Hosting auto-generates for whatever project is serving the current origin. In local dev, `src/proxy.conf.json` proxies that path to the live Hosting site (`https://intellectura-3b26a.web.app`) so `ng serve` gets a real config without any secrets in the repo. `FirebaseAppService.getApp()` fetches that config and calls `initializeApp` exactly once, shared by both Firestore and Auth. `FirebaseAppService.getConfig()` exposes the same memoized config **without** initializing the app, for the REST client below — which needs the `projectId` and `apiKey` but has no use for a `FirebaseApp`.

#### `FirestoreRestClient` — the Firestore SDK's replacement, being phased in

`src/app/services/firestore-rest/` holds a `fetch`-based client for Firestore's REST API. It is the first step of `BACKLOG.md` item 2, and the case for it is `FIRESTORE_SDK_VS_REST.md`: the Firestore client SDK is **558.98 kB raw / 141.26 kB transfer**, the single largest thing the app ships — roughly 5× the app's own code — for thirteen API symbols over five collections of flat documents, with its headline feature (offline persistence) deliberately switched off.

Two files:

- **`firestore-value.ts`** — the wire codec. REST tags every value with its type (`{"stringValue": …}`, `{"integerValue": "7"}`) and **sends integers as strings**. All eleven Firestore value types are handled in both directions, and two things are rejected rather than coerced: `undefined`, and any number that cannot survive the round trip (non-finite, or an integer outside the safe range). `FIRESTORE_SDK_VS_REST.md` §7 names this the migration's main correctness risk — a `"7"` where `7` was meant reaches `firestore.rules`, fails `is int`, and returns a `permission-denied` that names no cause.
- **`firestore-rest.client.ts`** — `getDocument` / `setDocument` / `createDocument` / `runQuery`, each with a real `AbortSignal.timeout` rather than a `Promise.race`. Requests carry the project's API key for quota and the user's ID token as a bearer token for `firestore.rules`; the token is optional, because `custom_questions`, `products` and the leaderboards are all `allow read: if true`.

**`firestore.rules` is unaffected.** A REST request authenticated with a Firebase ID token goes through the same rules engine with the same `request.auth`, so the security boundary and `npm run rules:test` are unchanged by the transport.

**Token handling stays the Auth SDK's job**, which is a smaller manual surface than §7 of the design document anticipated: Auth is not being migrated, so `AuthService.getIdToken()` delegates to the SDK's `getIdToken()`, which already caches and re-mints within five minutes of expiry. Only attaching the header is manual.

**Every network call carries a deadline, using whatever cancellation the API actually offers.** `fetch` (the runtime-config load, and now every Firestore call) uses `AbortSignal.timeout`, which tears the connection down; Firebase callables (`deleteAccount`, `exportAccountData`) use `HttpsCallableOptions.timeout`, which the SDK documents as cancelling the request; the checkout/portal handshake bounds its poll on the wall clock (`pollUntil`). That last one used to be the delicate case — a `Promise.race` around an `onSnapshot` left the listener attached for the rest of the session, still billing for a checkout nobody was waiting on. Polling has nothing to detach, so the hazard is gone by construction rather than by care.

`giveUpAfter()` (10s) covers what is left, and the list is shrinking. It stops _waiting_ without stopping the work, and is named to say so. `signInAnonymously` takes no options argument at all — `AbortSignal` appears nowhere in the Auth SDK's type definitions — and Auth is not being migrated, so that one is permanent; `GameControllerService`'s restore is an IndexedDB read rather than a network call, where "stop waiting" is genuinely the right verb. There are no Firestore holdouts left: every Firestore call goes over `fetch` and genuinely cancels.

Everything in `FirebaseService` now uses `AbortSignal.timeout` instead, which tears the connection down rather than abandoning it. The deadline itself stays load-bearing either way: the Firestore SDK's promises never reject on their own if the backend is unreachable (e.g. placeholder/misconfigured credentials), which would leave the UI stuck in a permanent loading state, and `TriviaService`'s offline fallback only triggers when the fetch throws.

### 2.4 Cloud Functions backend (`functions/`)

A separate npm package (own `package.json`/lockfile/`tsconfig.json`, TypeScript compiled to `lib/` — never committed) holding the entire Pro-subscription backend, deployed alongside Hosting/Firestore rules but as its own `firebase deploy --only functions` target:

- **`createCheckoutSession`** (`onDocumentCreated` on `customers/{uid}/checkout_sessions/{sessionId}`): validates the triggering document's `price` and `origin` against things only the server knows (`data-model.md` §3), lazily creates the Stripe customer on first use (`customers.ts`, storing `stripeId` on `customers/{uid}`), creates the Stripe Checkout Session with redirect URLs and a `mode` it decides itself, and writes `{sessionId, url}` (or `{error}`) back onto the triggering doc — the other half of the handshake `SubscriptionService.startProCheckout()` (`app.md` §1.6) is waiting on.
- **`createPortalSession`** (`onDocumentCreated` on `customers/{uid}/portal_sessions/{sessionId}`, `billing-portal.ts`): same handshake shape as `createCheckoutSession`, and the same origin check, but creates a Stripe Billing Portal session for the caller's existing `stripeId` and writes back `{url}` (or `{error}`) — the other half of `SubscriptionService.openBillingPortal()` (`app.md` §1.6).
- **`checkout-request.ts`** holds the pure half of that validation — the redirect-origin allowlist, the price-ID shape, and the catalog predicate — plus `RejectedRequestError`/`clientMessageFor`, which decide what a rejected caller is told. A refusal collapses to a generic "reload and try again"; naming which field was rejected would be free reconnaissance for someone probing the path, and the three possible causes aren't separately actionable by a user anyway. A genuine backend failure keeps its own message.
- **`environment.ts`** resolves the project ID from the runtime and answers whether it's a `demo-` project. Same pure-function-per-decision convention as `role.ts` and `account-policy.ts`.
- **`stripeWebhook`** (`onRequest`, HTTPS, `invoker: 'public'`): verifies the Stripe signature (`stripeWebhookSecret`), **asserts `event.livemode` matches the mode the deployed `STRIPE_SECRET_KEY` talks to** (`isEventForThisEnvironment`, `environment.ts` — the key's `_live_`/`_test_` infix is the deployment's own statement of which Stripe it is configured against, so the check cannot contradict reality the way an earlier project-ID-derived version did; a `demo-` project is pinned to test, since the emulator's placeholder secrets classify as neither), then dispatches `customer.subscription.created/updated/deleted` to `subscriptions.ts` (upserts `customers/{uid}/subscriptions/{id}`, keyed by a `firebaseUID` carried in the Subscription's own metadata since checkout time — no Firestore reverse-lookup needed — then recomputes the `stripeRole` custom claim from _all_ of that user's subscription docs, so an unrelated subscription canceling can't clobber a still-active one) and `product.*`/`price.*` to `products.ts` (mirrors the public `products`/`prices` catalog, `data-model.md` §3). `invoker: 'public'` is required explicitly: Cloud Run (what 2nd-gen `onRequest` functions deploy onto) defaults to requiring a Google-issued auth token on every invocation, but Stripe's webhook deliveries carry none — they authenticate via the `Stripe-Signature` header instead, verified inside the handler — so without it every real delivery is rejected with a 403 at the Cloud Run/IAM layer before the handler ever runs. **This has now been exercised against real Stripe deliveries** (manually triggered events against the deployed endpoint), confirming signature verification, event dispatch, the Firestore subscription upsert, and the resulting `stripeRole` claim all work end to end — not just the simulated outcome the e2e suite seeds via `setProSubscription` (`ci-cd.md` §4.3).
- **`deleteAccount`** (`onCall`, `account.ts`): permanently deletes the caller's account across all four systems it touches — cancels any live Stripe subscription and deletes the Stripe customer, strips the author link from their contributed questions, deletes `leaderboard/{uid}`, deletes `customers/{uid}` and its subcollections, then deletes the Auth user. Callable rather than a Firestore trigger because it must span Stripe/Auth/Firestore and because the Admin SDK bypasses `firestore.rules` — the only way to touch documents the client is deliberately forbidden from writing (`leaderboard` has no delete rule; `custom_questions` is create-only). **The uid comes from the verified token and is never read from the payload**, so a caller can only ever delete themselves. Ordering is deliberate: Stripe first (the only step with a cost attached to failing), Auth last (while it exists the caller can retry; once gone this function can never run for them again). `account-policy.ts` isolates the two decisions worth testing directly — which subscription statuses still represent live billing, and the `[deleted-user]` sentinel.
- **`exportAccountData`** (`onCall`, `account.ts`): returns everything the app holds about the caller — Auth profile and sign-in providers, leaderboard entry, contributed questions, Stripe customer ID and billing records. Same authorisation boundary as `deleteAccount`: the uid comes from the verified token, never the payload. Returned inline rather than written to Storage and linked — the payload is a handful of documents, and an inline response avoids minting a signed URL that would itself become a way to reach someone's personal data. `account-export.ts` holds the shaping logic as a pure function so _what gets included_ is unit-testable without standing up Auth and Firestore, and it carries a `notHeldHere` section naming what deliberately isn't in the file (card details, password, analytics, browser-local caches) — an export that silently omits payment data reads like concealment even when the honest answer is that Stripe holds it.
- **`role.ts`** holds the pure claim-role decisions — `deriveClaimRole(status, priceRole)` (does this status grant this role) and `chooseStripeRole(docs)` (the role derived from _all_ of a user's subscription documents, so an unrelated cancellation can't clobber a still-active one) — unit-tested directly (`node --test`, via `npm run functions:test`) without mocking Stripe or Firestore. **`subscription-mirror.ts`** (the Stripe-Subscription → Firestore-doc mapping, including the firebaseUID guard that is the only link back to an Auth user) and **`webhook-routing.ts`** (the event-type → handler map, where a mistyped case would drop deliveries silently — the 200 tells Stripe never to retry) follow the same pure-function-per-decision convention and are tested the same way (finding E3).
- **`event-order.ts`** makes those writes safe against Stripe's delivery model. Stripe guarantees delivery _at least once_ and guarantees nothing about **order** — and retries make reordering likely exactly when things are already going wrong. Duplication was never the problem (every write is `set(..., {merge:true})` or `delete()`, so a replay is a no-op); reordering was, since a stale `cancelled` overwriting a fresh `active` also drags the `stripeRole` claim backwards with it. Each mirrored document therefore records the `created` of the event that last wrote it, and a transaction drops anything older. Deliberately per-document rather than a global processed-event log: ordering only matters between events touching the same object, and a global log would need its own collection, its own TTL, and a read on every delivery. Deletes go through the same check — removing a document takes its high-water mark with it, so a late `deleted` arriving after the object was recreated has nothing left to compare against unless it is caught here.
- **`claims.ts`** owns how the `stripeRole` claim is written and when a change has to invalidate a session. Two things worth knowing. **`setCustomUserClaims` replaces the entire claims object**, so writing `{ stripeRole }` deletes every other claim just as thoroughly as writing `null` does — `withStripeRoleClaim()` reads the existing claims and edits one key. That costs nothing while `stripeRole` is the only claim, which is exactly why the bug was invisible; it would have started deleting data the day a second claim was added. And **a downgrade revokes refresh tokens** (`isPrivilegeDowngrade()`), because unsetting a claim only changes what the _next_ token says. Gaining a role deliberately does not revoke — an old token asserting less than the truth is harmless, and signing someone out seconds after they paid is the worst possible moment to do it.
- **Secrets**: `STRIPE_SECRET_KEY` / `STRIPE_WEBHOOK_SECRET` are bound via `firebase-functions/params`' `defineSecret` (Secret Manager–backed, set once per project with `firebase functions:secrets:set`) — never committed, never touch `process.env` directly in source.
- **`STRIPE_MOCK_CHECKOUT`**: a plain (non-secret) flag, true only for the `demo-trivia-app-e2e` project via a committed `functions/.env.demo-trivia-app-e2e` (Firebase Functions v2 auto-loads `.env.<project-id>` files). **The flag alone is not enough to enable it** — `isMockMode()` also requires the project ID to start with `demo-` (`environment.ts`), a property a real Stripe-backed deployment structurally cannot have. An environment variable can be set anywhere: a copy-pasted `.env`, a mistyped deploy target, a CI secret on the wrong workflow. If any of those had reached production under the old check, production would have handed out fake checkout URLs that look like they worked and take money from nobody. When enabled, `createCheckoutSession` skips the real Stripe API call entirely and writes back a deterministic, **same-origin, hash-only** mock URL instead of an external one — deliberately, since `Location.assign`/`href` are non-configurable/read-only in real Chromium/Electron and can't be stubbed in Cypress, so letting the real (harmless, in-page) navigation happen was the only way to exercise the redirect for real. This is what lets the e2e suite (`ci-cd.md` §4.3) drive the _actual_ `createCheckoutSession` function against the Functions emulator, not just a Firestore-seeded simulation of its outcome.
- **`functions/.secret.local`** (gitignored; materialized by the root `postinstall` from the committed, placeholder-only `functions/.secret.local.example`) lets the emulator run without real Secret Manager access — and, more importantly, pins both Stripe secrets so it never _tries_ to get that access. Measured while closing D5: with no `.secret.local`, the emulator attempts a real Secret Manager fetch at the first invocation of any function declaring `secrets: [...]`, and errors only when the machine has no Google credential — on a logged-in machine that fetch silently succeeds, handing the local emulator the real production `STRIPE_SECRET_KEY`. The file used to be committed under its real name; it isn't any more, because a tracked file named `.secret.local` is one careless commit away from publishing whatever real keys a developer put in it — which is now the supported way to run the emulator against a real Stripe account (see the template's comment).
