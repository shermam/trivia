## 4. Deployment & CI/CD

### 4.1 Hosting & Functions configuration (`firebase.json`)

- Hosting serves the compiled Angular app from `dist/trivia-app/browser`.
- `theme-init.js` is served `no-cache` by its own rule (declared after the blanket `**/*.@(js|css)` immutable rule so it wins), for the same reason `ngsw-worker.js` is: it lives in `public/` and therefore has no content hash in its filename, so a year-long immutable cache would make any edit invisible to returning visitors.
- SPA rewrite: all paths (`**`) fall back to `/index.html` (client-side routing).
- **Security headers** are set on the catch-all `**` rule so they cover every route: a strict `Content-Security-Policy` (below), `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, and a `Permissions-Policy` denying every powerful feature the app doesn't use (camera, microphone, geolocation, payment, USB, …). `Strict-Transport-Security` is deliberately **not** set here — Firebase Hosting already sends it on the live domain (`max-age=31556926`), confirmed by inspecting real response headers; the emulator does not, which is worth knowing when comparing the two.
- **The CSP contains no `unsafe-inline`, no `unsafe-hashes` and no hashes at all**, because the production build emits no inline `<script>`, no inline `<style>` and no inline `on*=` handler. Two things had to change for that: the theme initialiser moved to an external file (`app.md` §1.7), and Angular's critical-CSS inlining was turned off (`optimization.styles.inlineCritical: false` in `angular.json`, for both the `production` and `lighthouse` configurations). That setting is what injected the 10 KB inline `<style>` **and** a `<link … media="print" onload="this.media='all'">` — an inline event handler, which under a strict CSP is refused, leaving the stylesheet stuck at `media="print"` and the app rendering with critical CSS only. Disabling it measured as **free**: Lighthouse performance was 0.90/0.94/0.91 with it on and 0.89/0.94/0.92 with it off, i.e. inside run-to-run noise. The purged Tailwind stylesheet is small enough that inlining part of it and deferring the rest buys nothing here.
- **`frame-ancestors 'none'`** — nothing may embed the app in an iframe. See `known-gaps.md` §6 for what this means for the embeddable-quiz idea.
- `script-src` allows `https://apis.google.com` and `frame-src` allows the Firebase `authDomain` of **every project this config is deployed to** (`intellectura-3b26a.firebaseapp.com` and `trivimind-dev.firebaseapp.com`) — both are needed only by the OAuth popup resolver, which loads lazily (`app.md` §1.5). **`apis.google.com` is also in `connect-src`, and that is not redundancy.** The Angular service worker responds to every fetch the page makes, cross-origin included, and re-issues the ones it does not cache as a `fetch()` **from inside the worker** — where the governing directive is `connect-src`, not the `script-src`/`frame-src` the page would have used. Leaving it out breaks Google sign-in the moment the service worker takes control, which is what it did: `apis.google.com/js/api.js` came back as a synthetic `504 Gateway Timeout` (Angular's `safeFetch` turns a refused fetch into one), the popup resolver could not initialise, and sign-in failed with a message the client could not explain. The authDomain is a different case and does **not** need this: `__/auth/iframe` is an iframe navigation and `__/auth/handler` a popup, and a navigation is matched to a service worker by the _target_ origin, so our worker never sees either. Its `connect-src` entry is inert, and is being left in place only until the remaining OAuth investigation concludes. A hard reload bypasses the service worker and made it go away, which is why it went undiagnosed for weeks. `npm run csp:verify` fails the build on that, and on the harder version of the same mistake: an origin the app requests that is in **no** directive, which no self-comparison can see. `httpsCallable`'s `us-central1-…cloudfunctions.net` host was exactly that — `deleteAccount` and `exportAccountData` were refused in production while every emulator run passed, because the emulator points them at localhost with no CSP served at all.
- **The CSP is fingerprinted into `ngsw-worker.js` at build time** (`scripts/stamp-service-worker.mjs`, run by `build:prod`, so both `firebase-deploy.yml` and `firebase-preview.yml` get it). A service worker keeps the CSP it was installed with, and `ngsw-worker.js` is a static file that never changes between deploys — so the update check compares bytes, finds none changed, installs nothing, and the old policy survives indefinitely. That is why the `connect-src` fix above did not reach existing visitors: their worker went on refusing `apis.google.com/js/api.js` and synthesizing the `504`, with the console quoting the pre-fix `connect-src` verbatim while the server served the new one. Appending a hash of the policy makes the bytes move when the policy moves, which forces the re-install. The stamp is asserted against the deployed artifact by `service-worker-oauth-origins.cy.ts` (§4.3), recomputed from the header actually served rather than from `firebase.json` — a stamp describing a policy nobody serves is no protection. Unrelated headers deliberately do not move it: a `Referrer-Policy` tweak should not re-install everyone's worker.
- **A client already stuck on an old policy recovers by itself, unattended, and does not need to close the tab.** This was left as inference when the fix shipped, and it is worth pinning down, because "the fix is deployed" and "the fix has reached anyone" are different claims. The chain, end to end: the app calls `register()` on every load (`app.config.ts`, `registerWhenStable:30000`), and per the service-worker spec `register()` on an existing registration triggers a soft update — a script fetch and a byte comparison. That fetch genuinely revalidates rather than being served from the HTTP cache, because `/ngsw-worker.js` carries `no-cache` (§4.1); the stamped bytes therefore differ and the new worker installs. Angular's worker then calls `skipWaiting()` in its `install` handler and `clients.claim()` in `activate` (`ngsw-worker.js`), so it does **not** sit in "waiting" for every tab to close — it takes over the open page immediately. A stale visitor is therefore back on the current policy roughly thirty seconds into their next visit, having done nothing.
- **What is still stale on that first load is the _page's_ CSP**, which came out of the old worker's cached `index.html` and is only replaced on the next navigation. It does not matter for this bug and it is worth knowing why: the OAuth resources are loaded by the page under `script-src`, which allowed them before and after. The directive that was actually refusing them is the one governing the **worker's** `fetch`, and that belongs to the new worker the moment it claims the client.
- **One `firebase.json` serves more than one Firebase project, and three of the origins in the CSP are named after the project.** So a policy that is correct for one deployment is silently wrong for another, and it was: the CSP named production only, so on `trivimind-dev` — and therefore on every PR preview channel, which is the same project — Google sign-in was refused with `Framing 'https://trivimind-dev.firebaseapp.com/' violates ... "frame-src https://intellectura-3b26a.firebaseapp.com"`, and `deleteAccount`/`exportAccountData`/`recordGameResult` would have been refused the same way. `dev-environment.md` §3.1 said the headers were "the same by construction rather than by discipline"; they were the same, and being the same was the bug.

  **Nothing caught it, and the reason generalises.** Every check here compares the policy against itself or against a fixed host list, and both are blind to project _identity_ — `frame-src` naming _a_ `firebaseapp.com` origin satisfies them whichever project it belongs to. `csp:verify` was green, `lint` was green, and `E2E (preview)` was green **while running against the very deployment whose sign-in was broken**. `csp-rules.mjs` now carries `DEPLOY_TARGETS` and a third check, `findDeploymentOriginProblems`, which takes the project identity as an argument: `verify-csp.mjs` runs it over every target on disk, and the preview spec runs it with what the deployed channel's own `/__/firebase/init.json` reports — the stronger of the two, because it cannot be wrong about which project is actually being served. Adding a third deployment is one line in `DEPLOY_TARGETS`.

  **A related sharp edge worth knowing before editing `csp-rules.mjs`:** its types live in a hand-written `scripts/csp-rules.d.mts`, because the Cypress tsconfig is `strict` with no `allowJs`. A new export is invisible to the spec until it is declared there — which fails loudly (`TS2305`), so the missing direction is self-catching; a _wrong_ signature would not be.

- **OAuth sign-in is still not in the e2e suite**, so the origins themselves come from `app.md` §1.5's recorded network trace and want a manual sign-in check after any CSP change. What `csp:verify` catches is the _shape_ of the mistake above, not whether the list is complete.
- **Header rule ordering matters here**: the catch-all `**` headers rule (the security headers above, no-cache, and `Cross-Origin-Opener-Policy: same-origin-allow-popups`, needed so Firebase Auth's popup-sign-in polling can read `popup.closed` without the browser blocking it — see `app.md` §1.5) is listed _first_, with the more specific hashed-asset rules (`**/*.@(js|css)`, images/fonts) listed _after_ — Hosting applies the last-declared matching rule per header key, so the specific rules' `immutable` `Cache-Control` correctly overrides the broad one for those paths. An earlier version of this scoped the no-cache/COOP headers to the literal `source: "/index.html"`, which silently never matched any real request — every route (`/`, `/play`, `/game-over`, ...) is served via the `**` rewrite above, never a literal request for `/index.html` itself.
- `functions` config points at the `functions/` package (`stack.md` §2.4), with a `predeploy` hook (`npm --prefix functions run build`) so `firebase deploy --only functions` always deploys freshly-compiled code.
- Local emulator ports: Firestore `8080`, Auth `9099`, Functions `5001`, Hosting `5000`, plus the Emulator UI. `singleProjectMode` is enabled. The Auth and Functions emulators exist solely for the e2e suite (§4.3) — the app never talks to either outside that configuration.

### 4.2 GitHub Actions workflow (`.github/workflows/firebase-deploy.yml`)

**Trigger**: fires only when a pull request targeting `main` is **closed and merged** (not just closed).

Steps:

1. Checkout `main`.
2. Set up Node 24 (with npm cache, keyed off both `package-lock.json` and `functions/package-lock.json`).
3. `npm ci`.
4. `npm run build:prod` (production Angular build).
5. Deploy **Firestore rules + indexes** via `npx firebase-tools@13 deploy --only firestore:rules,firestore:indexes`, using the service account written to a temp `GOOGLE_APPLICATION_CREDENTIALS` file.
6. `npm ci --prefix functions`, then deploy **Cloud Functions** (`stack.md` §2.4) via `npx firebase-tools@14 deploy --only functions` (`@14`, not `@13` — see `stack.md` §2.2) — a separate step from #5 on purpose, so a functions-only failure is easy to spot on its own.
7. Delete the temp credentials file, immediately after its last user rather than at the end of the job — the Hosting step below authenticates from the secret directly and never reads it.
8. Deploy the built app to **Firebase Hosting** via `FirebaseExtended/action-hosting-deploy@v0` (channel: `live`), authenticated with the `FIREBASE_SERVICE_ACCOUNT_INTELLECTURA_3B26A` repo secret. **Last on purpose** — see the ordering note below.
9. Always clean up the temp service-account credentials file, even on failure.
10. **Smoke-test production** (`node scripts/smoke-test.mjs https://trivimind.com`): app shell served, CSP/`X-Content-Type-Options`/`Referrer-Policy` intact, `/__/firebase/init.json` resolving to this project, `theme-init.js` reachable, and the callables deployed and still rejecting an unauthenticated caller with 401. It runs last and cannot undo anything — by the time it fails the deploy has shipped — but it is what turns a broken production into something someone is told about.

A separate **`report-failure` job opens a GitHub issue** (labelled `deploy-failure`, de-duplicated to one open issue) whenever **either** deploy job fails. This exists because the pipeline once failed on **four consecutive merges** while Hosting kept shipping and nothing surfaced it — see `INFRASTRUCTURE.md` §6.3a, which also holds the rollback procedure. The issue names both jobs and says to check which one failed, because a red run no longer implies production is affected. It previously said the steps ran Hosting → rules/indexes → functions, leaving a newer client against an older backend; that was **stale and backwards** — it contradicted the paragraph immediately below it, which is the one that was right.

**A second job, `deploy-dev`, ships the same commit to `trivimind-dev`** — checkout, `npm ci`, `npm run build:dev-project`, Firestore rules + indexes, then Hosting on channel `live`, authenticated with `FIREBASE_SERVICE_ACCOUNT_TRIVIMIND_DEV`. It runs **independently** of the production job: dev is not downstream of production, and holding one behind the other only widens the window in which they disagree. The commit is the one `E2E (preview)` already exercised end to end against this very project.

**Why it had to exist.** Nothing deployed dev's live channel before: `firebase-preview.yml` creates a per-PR channel on the same project, and `npm run firebase:deploy:dev` is a laptop command somebody has to remember — so `trivimind-dev.web.app` served whatever was last pushed by hand, indefinitely. That cost a diagnosis: [#153](https://github.com/shermam/trivia/pull/153) fixed a CSP that refused Google sign-in on dev, the next PR's preview channel picked the fix up immediately (it is built from that PR's head), and `trivimind-dev.web.app` went on refusing sign-in. Every client-side remedy — clearing storage, unregistering the service worker, reloading with cache disabled — was doomed by construction, because the stale artifact was a **response header** on the server. **The rules are the sharper edge:** `E2E (preview)` runs against this project's real Firestore, so a `firestore.rules` change that merged without reaching dev leaves the preview suite green about the _previous_ rules.

`deploy-dev` ships **hosting, Firestore rules/indexes and Cloud Functions**, so the mirror is complete. Functions were held back on the first cut, because the step needs `STRIPE_SECRET_KEY`/`STRIPE_WEBHOOK_SECRET` in the dev project (`dev-environment.md` §3.1 step 8) and a missing one would have failed on every merge — a guardrail that cries wolf on every commit gets switched off. Those secrets are set, so the steps are in.

**Its first run failed, and the reason is worth carrying.** Not the secrets — the _rules_ step, with `403, The caller does not have permission` from `firebaserules.googleapis.com`. The credential had been deploying preview channels to this same project on every PR for weeks, which read as proof that it worked and proved only that it could deploy **Hosting**: a key generated from Project settings carries the Admin SDK service agent role and nothing else, and Hosting, Firestore rules, Firestore indexes and Cloud Functions are four separate grants. **A credential already in use is not evidence it is sufficient for a new use of it.** The roles are now listed at `dev-environment.md` §3.3 step 10, beside the step that issues the key.

Note also which way that failure fell: backend-first ordering stopped the job before Hosting ran, so dev stayed on its old bundle. Once the IAM grants landed, the rules and indexes deployed cleanly and the **next** step failed instead — on GitHub, not Firebase: `403 Resource not accessible by integration` against `api.github.com/repos/…/check-runs`. `action-hosting-deploy` opens a check run named "Deploy Preview" whichever channel it targets, so `contents: read` alone is not enough; the job needs the same `checks: write` and `pull-requests: write` the production job carries. This paragraph two lines up already recorded that exact 403 against the production job, and giving the new job narrower permissions repeated it — **a permission set is a property of the action, not of the job's importance**, and "deploy-dev only reads the repo" was reasoning about the wrong thing. That is the right trade — a half-deployed mirror is worse than an un-deployed one — but it means a rules-permission problem presents as "the site did not update", which points at Hosting.

**The order is backend-first, deliberately.** Hosting used to deploy first, which put a new client live against an old backend for the length of the remaining steps — a window that only ever bites on the release where it matters, because that is the release that changed both (finding D2). The build also runs before any deploy, so a compile error aborts without having touched production at all.

The reverse exposure — an _old_ client against a _new_ backend — cannot be fixed by ordering: a visitor with the app open across a deploy, or one served the precached shell by the service worker (`app.md` §1.8), is running an old client whichever order the steps take. So a backend change has to stay compatible with the already-deployed client regardless, and once that is true, backend-first strictly dominates: it is the only order that also closes the new-client window.

Job permissions are scoped to `contents: read`, `checks: write`, `pull-requests: write` — the minimum needed for the hosting-deploy action to post a check/PR comment (this was tightened in a dedicated fix after the action initially hit a 403).

This is a **merge-to-deploy** pipeline: every PR merged into `main` auto-deploys hosting + Firestore rules/indexes + Cloud Functions to production (`intellectura-3b26a`), and hosting + Firestore rules/indexes to `trivimind-dev`. It deliberately doesn't re-run e2e itself — see §4.2a for why that's still safe.

**One-time setup this pipeline depends on** (not automatable from CI, done once by someone with Stripe/GCP console access): `firebaseRole: pro` metadata on **both the Stripe Product and the Price** — see the warning below, this is not either/or — and a webhook endpoint pointed at the deployed `stripeWebhook` URL (`stack.md` §2.4); `STRIPE_SECRET_KEY`/`STRIPE_WEBHOOK_SECRET` set via `firebase functions:secrets:set`; and the deploying service account granted the IAM roles a Gen 2 functions deploy needs. **That list is longer than it looks and this line used to understate it** — it said Cloud Functions Admin / Service Account User / Secret Manager Secret **Accessor**, and `secretAccessor` is the wrong secret role: it grants permission to read a secret's _value_ and none to see that the secret exists, so a deploy fails at `secretmanager.secrets.get` before it reads a payload. `dev-environment.md` §3.3 step 10 now carries the corrected set, with the gcloud commands, for both projects. This has now been completed against the real project, so step 7 above is expected to succeed on every merge going forward (no longer `continue-on-error`, so a regression here will now turn the workflow red instead of failing silently).

### 4.2a Preview channel deploy + real-preview e2e (`.github/workflows/firebase-preview.yml`)

**Trigger**: every PR targeting `main`, on open/sync/reopen **and close**. A `concurrency` group keyed on the PR number cancels a stale in-flight run if the PR gets pushed again before it finishes.

**It deploys to `trivimind-dev`, not to production.** A preview run is not read-only — the Cypress tasks create real Auth users, real `custom_questions` documents and real `leaderboards/{limit}/entries` rows, on every PR. `trivimind-dev` runs the same production build against the same rules, the same indexes and the same `firebase.json` headers, so what the preview validates is unchanged; what changed is whose data it writes to. `npm run env:verify` fails if this workflow names the production project again (§4.6).

Three jobs — the first two sequential on open/sync/reopen, the third only on close:

1. **`deploy-preview`** — checkout → Node 24 → `npm ci` → `npm run build:prod` → `FirebaseExtended/action-hosting-deploy@v0` deploying to an ephemeral channel named `pr-<number>` (7-day expiry) instead of `channelId: live`. The action posts/updates a PR comment with the preview URL on every push. The step's `urls` JSON output is parsed (`jq`) into a job output consumed by the next job.
2. **`e2e-preview`** (job name `E2E (preview)`) — runs a scoped slice of the Cypress suite (§4.3) against the just-deployed preview URL, hitting the real `trivimind-dev` project instead of an emulator.
3. **`cleanup-preview`** (job name `Delete preview channel`) — deletes the PR's channel when the PR closes, merged or not. A channel is created per PR and the 7-day TTL expires them more slowly than this repo merges, so without this they accumulate to Firebase's 50-channel-per-site cap, at which point _every_ new PR fails to deploy with `429 channel quota reached`. A missing channel counts as success; anything else fails the job, deliberately not `continue-on-error`, which would swallow a credential problem and let the channels pile up again.

Both credentialed jobs skip for Dependabot: they run `npm ci` and `npm run build:prod` — the install scripts and build-time code of the very dependency under review — and only then hand over a Firebase deploy service account. A job skipped by a job-level `if` reports "skipped", which branch protection treats as success.

> **A new Cloud Function will look broken on its own preview channel.** Preview channels deploy Hosting only; the functions in the project are whatever §4.2's merge-to-deploy pipeline last shipped. So a PR that _adds_ a callable serves client code calling a function that does not exist yet, and the feature fails with `functions/not-found` on the preview while working perfectly against the emulator. This is expected, not a regression — verify such a feature with `npm run e2e` (which runs the Functions emulator) and re-check on the live site after merge. `AccountService` detects that specific error code and says so, rather than telling the user to retry something that can never succeed.

> **The same is true of `firestore.rules`, and it is worse, because the failure does not name itself.** Rules are per _project_, not per channel, so a preview channel is the PR's client running against whatever rules `main` last deployed — there is no way to preview a rules change at all. A PR that changes a rule and the client code that satisfies it will look broken on its own preview, and the symptom is a bare `403 PERMISSION_DENIED` on `documents:commit`, surfaced by the app as its generic "please try again".
>
> Contrast the Functions case above: `functions/not-found` is a distinct error code that says exactly what is wrong. `PERMISSION_DENIED` is what a **genuine** rules bug looks like too, and the two are indistinguishable from the browser. That is the actual hazard here — not the false alarm, which costs a few minutes, but the true alarm dismissed as one.
>
> **So the rule is: before concluding a permission error on a preview is expected, diff the PR's `firestore.rules` against `main`'s and check the specific predicate the refused write hits.** If the PR does not touch rules, a `PERMISSION_DENIED` is real. This bit review-before-publish ([#123](https://github.com/shermam/trivia/pull/123)): the PR flipped `statusOnSubmission()` from `'approved'` to `'pending'` in both the rules and the client, so the previewed client wrote `status: 'pending'` into a project whose deployed rules still demanded `'approved'`, and every submission was refused. Verify that class of change with `npm run e2e` — which runs the rules in the emulator alongside the client — and re-check on the live site after merge.
>
> Note the preview e2e suite cannot cover this either, and not by oversight: `add-question-pro-gating.cy.ts` is already excluded from `cypress.preview.config.ts` for an unrelated reason (§4.3). Adding it would not help — it would fail on exactly the PRs where the mismatch is expected, turning a real signal into a red that reviewers learn to ignore.

Preview channels are a **Hosting-only** feature — there's still a single Firestore database for the project, so a preview build (and its e2e run) reads/writes the same production `custom_questions`/`leaderboard` data as `main` and live. Firestore rules/indexes are also not redeployed per-preview (they're project-wide, not channel-scoped); only §4.2's merge pipeline touches them. There is no isolated staging _database_ — just an isolated hosting URL, backed by production data, that's now also exercised end-to-end before merge.

**Merge gating is live, and it covers every CI check — not just this one.** `main` is protected by a repository **ruleset** (`enforcement: active`) requiring the status checks below to pass before a PR can merge, and therefore before §4.2's deploy can fire at all:

| Required check           | Workflow               |
| ------------------------ | ---------------------- |
| `test`                   | `unit-tests.yml`       |
| `e2e`                    | `e2e.yml`              |
| `lighthouse`             | `lighthouse.yml`       |
| `Deploy preview channel` | `firebase-preview.yml` |
| `E2E (preview)`          | `firebase-preview.yml` |
| `lint`                   | `lint.yml`             |
| `rules-tests`            | `rules-tests.yml`      |
| `functions-tests`        | `functions-tests.yml`  |

> **`lint` is three steps, not one.** `format:check`, then `npm run lint` over all three source trees, then `npm run typecheck:cypress`. They share a job because they are one "does this code meet the static bar" question and splitting them would buy a second `npm ci` and nothing else. The typecheck in particular went here rather than into a fourth workflow — a deliberate exception to one-workflow-per-concern — because `lint` is already required, so a step added to it gates a merge **today**, whereas a new workflow reports without blocking until an admin adds it. See the row immediately below for what that state looks like in practice.

> **`functions-tests` is not in the ruleset yet.** It runs on every PR and reports pass/fail, but a workflow cannot add itself as a required check — that needs a repo admin in Settings → Rules. Until then a red `functions-tests` will not block a merge (the other seven checks above are all required — `lint` and `rules-tests` went through this same lifecycle and have since been added, verified against `GET /repos/{owner}/{repo}/rules/branches/main` on 2026-08-10). The suite previously ran as a step inside the `e2e` job, so it was already gated there under the wrong name; splitting it out trades a short gating gap for a permanently clear signal — the accepted cost of one workflow per concern (see `INFRASTRUCTURE.md` §8).

`strict_required_status_checks_policy` is on, so a branch must also be up to date with `main` before merging. The ruleset additionally requires a pull request (with zero required approvals — this is a solo repo) and blocks branch deletion and non-fast-forward pushes.

One practical gotcha when verifying this: it's a **ruleset**, not classic branch protection, so the legacy `GET /repos/{owner}/{repo}/branches/main/protection` endpoint returns **404 "Branch not protected"** even though `main` is fully protected. Check `GET /repos/{owner}/{repo}/rules/branches/main` (or `/rulesets`) instead — the legacy endpoint's 404 is not evidence of anything.

### 4.3 E2E testing (Cypress + Firebase Emulator Suite)

- Suite lives under `cypress/e2e/unauthenticated/` (anonymous game flow across all three question sources, question reporting, route guards, embed mode, the pre-boot recovery notice, and the preview-only service-worker/CSP spec below) and `cypress/e2e/authenticated/` (email sign-up + verification, sign-in, saving a score, profile management, Pro-gated `/add-question` access, question source attribution, and Stripe checkout), run via `npm run e2e` (headless) or `npm run e2e:open` (interactive).
- Both commands first `npm run functions:build`, then wrap `firebase emulators:exec --project demo-trivia-app-e2e --only auth,firestore,functions` (**functions** included since this PR — see `stack.md` §2.4), which starts a throwaway local Firestore + Auth + Functions emulator trio, runs the wrapped command, and always tears the emulators down afterward — no real project is ever touched.
- The app itself only connects to the emulators when built with a configuration that sets `useEmulators` — `e2e` and, since `FEAT-012`, `development` (see §4.5): `FirebaseAppService` skips the `/__/firebase/init.json` fetch and synthesises a config from `environment.emulatorProjectId` instead, which is `demo-trivia-app-e2e` here and `demo-trivimind-local` for `npm start`. Two ids rather than one, so an e2e run — which wipes state between specs — cannot empty the data you were developing against, and `AuthService` calls `connectAuthEmulator`, and `FirestoreRestClient` selects its emulator base URL (`http://127.0.0.1:8080/v1`).
- `cypress/tasks/firebase-emulator-tasks.ts` uses `firebase-admin` (talking to the emulators only) to reset all Auth users/Firestore docs before every test, seed `custom_questions`/`leaderboard` documents bypassing `firestore.rules`, create already-verified users, fetch pending email-verification links from the Auth emulator's testing REST endpoint, and (new) `setProSubscription`/`seedProProduct` to drive a user into a "Pro" state (custom claim + subscription doc) or seed a fake Pro price without ever calling Stripe.
- **`pricing.cy.ts`** covers the Subscribe flow against the _real_ `createCheckoutSession` function (in `STRIPE_MOCK_CHECKOUT` mode, `stack.md` §2.4) end-to-end — click → Firestore write → Functions-emulator trigger → write-back → client poll → same-origin redirect — plus the anonymous sign-in prompt and the already-subscribed state (via `setProSubscription`). **`add-question-pro-gating.cy.ts`** covers the free-tier upgrade prompt and, for a freshly-`setProSubscription`'d account, that the subscription read + forced token refresh actually let the `custom_questions` write through under the updated `firestore.rules`.
- Real bugs found and fixed by this suite (beyond the two below, pre-dating the Pro tier): `PricingComponent` briefly misfiring "verify your email" for a click landing before the first auth state resolves (`app.md` §1.6); and a pre-existing `sign-up-verify.cy.ts` race — `signInViaUi`'s `openAuthMenu()` racing the still-open dropdown from a prior "Sign out" click, which only closes after its async re-anonymous-sign-in resolves — surfaced (not caused) by the added Functions emulator's extra CPU contention, fixed with an explicit wait for the dropdown to close first.
- Two earlier real bugs were found and fixed by this suite: a race in `AuthService.ensureSignedIn()` where a returning user's persisted session could be clobbered by a fresh anonymous sign-in (fixed with `auth.authStateReady()`), and a stale-UI bug where linking an anonymous session to a real credential mutates the Firebase `User` object in place without firing `onAuthStateChanged`, so `isAnonymous`/`isFullyAuthenticated` never updated until fixed by explicitly re-pushing the user into the auth signal after linking.
- **`cy.startGame()`/`cy.startNewGame()` wait for `/play` to be rendered, not just for the questions response.** They used to end at `cy.wait('@questions')`, which is not the same thing: that response is what `GameControllerService.startGame()` awaits _before_ it navigates, so it resolves while the app is still on the setup screen with the lazy quiz-loop chunk unfetched. Callers that went straight to a positive retrying query were fine; a caller whose next command was `should('not.exist')` passed against `/` and tested nothing. That is not hypothetical — it is how the "an Open Trivia DB question gets no flag button" assertion came to be green against a screen that has no flag button under any circumstances. Fixed in the command rather than the caller so the trap cannot be inherited again, and the heading assertion is the load-bearing half: the URL can commit a tick before the outlet paints.
- **Test isolation covers the backend and the browser, and the browser half is not free.** `cy.resetBackend()` resets the emulators; Cypress's own `testIsolation` clears cookies, `localStorage` and `sessionStorage`. Neither touches **IndexedDB**, and there is no `cy.clearAllIndexedDb()` — so `OfflineDbService`'s database (the saved in-progress game, and the offline question pool) leaked from one test into the next. Measured before it was fixed: a test that starts a game leaves its record in `game-state`, and the next test's setup screen renders the resume banner for a game it never started. `cy.clearOfflineStorage()` now runs from the `beforeEach` in `cypress/support/e2e.ts` **and** `e2e.preview.ts` — the local database is just as dirty against a real deployment — and `test-isolation.cy.ts` pins it with two deliberately order-dependent tests: the first leaves a saved game on purpose, the second asserts a clean start. That ordering is the point. A hook that isolates nothing passes every other spec in this suite exactly as it does today, because leaked state has never yet been what made one of them fail.
- **Where that hook runs is the whole design, and two of the three plausible places are wrong.** `indexedDB.deleteDatabase()` blocks while any connection is open and the app holds one for the life of the tab, so this is a question about timing, not about API choice — and all three placements were run rather than reasoned about. `Cypress.on('window:before:load')` fires on **every** page load inside a test, `cy.reload()` included, and its deletion resolves in 16–45 ms: it reliably destroys the saved game _in the middle of_ the specs that exist to prove a game survives a reload. An `afterEach` is the more instructive failure — the app's connection is still open, so the deletion `onblocked`s and was still blocked after a full 5 s on every test, then lands whenever the window is torn down, and the following test came out **clean anyway**. It looks like it works while the deletion is happening at a moment no test controls. Only `beforeEach`-before-the-first-`cy.visit()` works, because `testIsolation` has already discarded the previous AUT window. One thing there had to be checked rather than assumed: that pre-visit window is `about:blank` and serializes its origin as `"null"`, but it shares storage with the app's — verified by writing a sentinel database from it and reading it back from the app's window. Had that not held, the hook would have deleted a database nobody uses and looked perfectly healthy doing it. `onblocked` is therefore treated as a hard failure rather than waited out; see `cypress/support/offline-storage.ts`.
- **`lifetime-stats.cy.ts` reads the database, because nothing renders these numbers yet.** `users/{uid}` is written by a callable and has no client write path at all, so a document appearing in the emulator is proof the function ran rather than proof the browser could reach Firestore — and with no profile UI shipped (`FEAT-005` is a separate feature) there is nothing in the DOM to assert against. Three rows, and the middle one is the point: a game is banked once, **reloading `/game-over` does not bank it again**, and an anonymous player gets no document at all. The reload row asserts on `gamesPlayed` rather than on the document existing, because a double-count produces a document either way — the existence check would pass against the exact bug `lastGameId` exists to prevent. The anonymous row counts the whole collection instead of inspecting a uid, so it states "nobody got one" directly rather than inferring it from an anonymous uid dug out of the browser's auth state, and it is preceded by a positive anchor for the reason the bullet above gives.
- **`answerQuestion` is scoped to `[data-cy="answer-option"]`, and the bug that forced it is the most expensive kind.** `cy.contains('button', text)` is a substring match taking the **first** hit in DOM order, and the top bar sits above the quiz. A signed-in account chip renders the display name or email inside its trigger button (the `sr-only` accessible name in `top-bar.component.html`), so against an address like `stats-1787954295926-k3x@example.com` the command answered `"4"` by **clicking the account chip and opening the auth menu**. Measured, not inferred: the first `<button>` whose text contains `4` is `auth-menu-trigger`.
  **The countdown hid it, and that is the part worth carrying.** The question nobody answered timed out, auto-advanced as wrong, and the game finished 4/5 — so the reported symptom was `correctAnswers` short by one, which reads as a stats or scoring problem and was investigated as a slow CI runner for two rounds. The deadline was not the cause; it was the anaesthetic. Removing it made the same defect fail loudly on the _next_ question ("cannot find 'True'"), which is what exposed it. **A failure that arrives one step downstream of its cause will be diagnosed one step downstream of its cause.** Anonymous specs were never affected, because the signed-out chip reads "Sign in" and carries no digits — which is also why this survived every local run.
  This is the third instance of the hazard `CLAUDE.md` §4.6 already names, after `cy.contains('button', 'Approve')` matching an **Approved** tab and `'Sign in'` matching **Sign in to subscribe**. The rule holds: address anything you click by `data-cy`, or scope the `contains` to a container.
- **The deletion test in `account-management.cy.ts` now plays a game first, and that is not decoration.** It asserts the stats document is gone afterwards — an assertion that was **vacuous** as first written, because the document is created lazily and an account that never finished a game has none, so `null` after deletion would have passed against a `deleteAccount` that swept nothing. It is the single test standing behind a published policy promise, so it has to prove there was something to delete.
- **`game-resume.cy.ts` covers the whole of B8's persistence, not just the reload that found B11.** Six tests: reload mid-game on `/play`; reload a _finished_ game on `/game-over` (persisted deliberately, so a refresh does not lose a score about to be submitted); the setup screen's resume banner reached by a fresh page load, which is the path a PWA relaunch actually takes since it lands on `/` rather than `/play`; that a completed game is deliberately **not** offered as resumable; Discard, asserted against storage rather than against the banner disappearing, since clearing the signals without clearing the record would bring the game back on the next load; and a flag surviving a reload along with the chosen time limit. The banner carries `data-cy` hooks (`resume-banner`, `resume-game`, `discard-game`) so none of this selects on the words "Resume"/"Discard". Each test was mutation-verified on its own, and reintroducing B11 itself — `[ngValue]` back to `[value]` on the question-count picker — now fails five of the six.
- **`daily-game-limit.cy.ts` seeds the counter rather than playing five games**, and its last test is the one worth keeping: it measures the **Start button's own top edge** before and after the allowance resolves, at 390×1000. The row existing is not the property that matters — the page not moving is, and §4.4 records that this class of shift measures 0px at one viewport height and 43px at another, so the height is part of the test rather than incidental to it.
- **`question-source-attribution.cy.ts` is under `authenticated/` for a reason that has nothing to do with auth.** Its third test is anonymous — it seeds two custom questions and plays them — but `cypress.preview.config.ts` takes all of `unauthenticated/` automatically and only two named specs from `authenticated/`, so the directory is how a spec that writes seeded documents stays off the shared real project. Three seams, none reachable more cheaply: that the **real rules** accept the document the _form_ builds (the rules suite proves the rule admits the fields, but it hand-builds the payload, and the two have disagreed before); that the reviewer's card renders the link, which is where the feature earns its keep; and that the recap renders **nothing** for a question with no source, which is the common case and the one a placeholder would quietly ruin. Its assertions use a single `should(($el) => …)` callback rather than a chain, because `should('have.attr', name)` with no expected value changes the subject to the attribute's string (`CLAUDE.md` §4.6).
- **`boot-fallback.cy.ts` tests a failure the suite cannot otherwise reach: no application code running.** The pre-boot recovery notice (`app.md` §1.8) is markup in `index.html` revealed by a CSS delay, for the case where a stale service worker serves a cached document whose entry script no longer exists. The spec reproduces that with a `cy.intercept` returning `404` for `**/main*.js` rather than with a worker, because the worker is not the mechanism under test and this runner emits none. Two tests, and the first matters most: **the notice is absent from the DOM on a normal load**, since Angular replaces `<app-root>`'s contents on bootstrap — a regression that leaked it into the running app would be visible to every user, and nothing else would catch it. The reveal delay is asserted on the computed `animation-delay` rather than by watching a clock, so the check does not depend on runner speed.
- **It is excluded from the preview config, and the reason is a property of the deployment rather than of the spec.** `firebase.json` serves `**/*.@(js|css)` as `max-age=31536000, immutable`, so against a real channel an earlier spec has already loaded the app and the browser satisfies the entry script from its own HTTP cache. Nothing reaches the network, the intercept never matches, and `cy.wait` fails with **"No request ever occurred"** — which is exactly how the file failed on its first CI run. No rewriting fixes that; the request the test needs to see does not exist.
- **Nothing tests the recovery _within_ one test, and that gap is deliberate and unexplained.** Two versions were tried — clicking the reload link, and `cy.reload()` after a `times: 1` intercept — and both fail on the assertion **after the second page load**, in CI and on a developer machine, on every attempt including Cypress's own retry. The same sequence driven by hand in Chromium recovers correctly in all four configurations tried: production build and `ng serve`, top-level and inside an iframe (which is how Cypress hosts the app). **The cause is not understood** — it is not the element, the build, the framing, or the click. What matters for coverage is that the dropped test proved nothing new: that the link resolves to the app root is asserted without a second load, and that a load with the script available boots the app and leaves no notice behind is the first test. Its only unique contribution was a failure belonging to the runner. Worth generalising: when a composite assertion fails on the runner rather than the product, check whether its parts are already covered before spending more on the composition — here they were.
- **A `should('not.exist')` needs a positive anchor in front of it.** The same class of defect appears whenever a negative assertion is the first thing after a navigation — it is satisfied by a page that has not rendered yet, and Cypress will never retry a satisfied assertion into failure. Every negative assertion in `question-reporting.cy.ts` is now preceded by something that can only be true once the screen is really there.
- **…and a `should('exist')` on a _transient_ element needs the transience removed, not more retries.** The mirror image of the bullet above, and it cost two red runs on `main` before it was diagnosed. `game-flow.cy.ts`'s "does not resize the leaderboard when the scores arrive" opens by catching the loading skeleton — but `isLoadingLeaderboard` flips the instant `getTopScores` resolves, and against the local Firestore emulator that is fast. Instrumented in Chromium with a `MutationObserver`, the skeleton's real lifetime is **30–38ms on `main` and 36–147ms on the branch that happened to be red**, against a Cypress retry interval of **50ms**. So the assertion was not testing the leaderboard at all; it was testing whether a poll landed inside a window narrower than the gap between polls, and it passed roughly four times in five. Retrying longer cannot help — the element is already gone. The fix is a `cy.intercept` holding the `:runQuery` response for 500ms, which makes the loading state deterministic while leaving every assertion and the real fetch untouched. Two things worth carrying: **the preview suite ran the same spec and never failed**, because real network latency is far wider than the window — an environment where the bug is invisible is not evidence the test is sound — and the intercept is matched on **path only** (`/\/leaderboards\/[^/]+:runQuery/`), so emulator and production Firestore are covered by one pattern. `cy.wait('@topScores')` is deliberately kept afterwards: without it, an intercept that silently stopped matching would leave the test passing by luck again, which is the same silent-hollowing failure `CLAUDE.md` §4.6 catalogues.
- CI: `.github/workflows/e2e.yml` runs the full suite on every PR targeting `main` (and on push to `main`), separately from the merge-to-deploy pipeline in §4.2 — including installing/building `functions/` first.

**Running the same suite against a real preview instead of the emulator** (`cypress.preview.config.ts`, driven by the `e2e-preview` job in §4.2a): a deliberately narrower slice, because this hits the real, persistent `trivimind-dev` project — there's no throwaway emulator to reset:

- `specPattern` includes all of `cypress/e2e/unauthenticated/` **except `question-reporting.cy.ts`** (the one `excludeSpecPattern` entry), plus only `sign-in-save-score.cy.ts` and `profile.cy.ts` from `cypress/e2e/authenticated/`. The reporting spec is emulator-only for two reasons: it asserts the written report through an Admin-SDK read of `question_reports`, a collection no client may read by rule — implementing that task for the real project would hand the preview suite console-level read access to real users' reports — and its writes would outlive the run, since `finalCleanup` sweeps uids and seeded documents but not reports, leaving real rows in the owner's review queue after every preview. `sign-up-verify.cy.ts` is excluded permanently: it depends on the Auth emulator's testing-only `oobCodes` REST endpoint to read a verification link, which has no real-Auth equivalent without a live mailbox. `pricing.cy.ts` and `add-question-pro-gating.cy.ts` are excluded too, on purpose: Cloud Functions aren't channel-scoped (§4.2a below), so a preview build shares the _real_, already-deployed `createCheckoutSession`/`stripeWebhook` — running the mock-mode checkout spec here would either hit real Stripe or silently no-op depending on that deployed project's own `STRIPE_MOCK_CHECKOUT` state, neither of which this suite should depend on.
- `cypress/tasks/firebase-preview-tasks.ts` is the real-project counterpart to `firebase-emulator-tasks.ts` — same task names/shapes (sharing types from `cypress/tasks/types.ts`) but **no blanket `resetBackend`**. Instead, every uid/doc a test creates (explicitly via a seed task, or implicitly — every `cy.visit()` triggers the app's own anonymous sign-in) is tracked in-process and swept up by a `finalCleanup` task, called from an `after()` hook in `cypress/support/e2e.preview.ts`. `cypress/support/auth-uid-tracker.ts` records **every** uid the browser persists, by wrapping `Storage.prototype.setItem` from `window:before:load` so each `firebase:authUser:*` write is seen as it happens; an `afterEach` hands the batch to `trackAuthUids`. It used to _sample_ instead — reading the current uid once per test — which only ever saw the last one, so every uid a test replaced along the way was left behind in the real project (finding C6): a sign-out mints a fresh anonymous account, and a sign-in can switch uid rather than link. Two details are load-bearing and were both found by instrumenting a failing run rather than by reading the code: it must wrap **`Storage.prototype`**, because assigning `localStorage.setItem` hits `Storage`'s named-property setter and stores the function _as an entry called `setItem`_, corrupting the store so the app's own writes never land; and the collected uids live on a **global**, because Cypress bundles the support file and each spec separately, so module-level state gives the writer and the reader different instances. `cypress/e2e/unauthenticated/auth-uid-tracking.cy.ts` pins all of this against the emulator — the only place the mechanism can be exercised without merging it.
- The two authenticated specs' previously-hardcoded fixture IDs (`existing-leader`, `q1`/`q2`) were made unique per run (timestamp-suffixed) so two preview deploys running concurrently against the same real project never race on the same document.
- Credentials: `FIREBASE_SERVICE_ACCOUNT_TRIVIMIND_DEV`, written to a temp file and picked up via `GOOGLE_APPLICATION_CREDENTIALS` (Admin SDK default credential lookup) — never the `FIRESTORE_EMULATOR_HOST`/`FIREBASE_AUTH_EMULATOR_HOST` env vars the emulator tasks rely on. Which project those tasks write to comes from `FIREBASE_PREVIEW_PROJECT_ID`, set in the workflow; `firebase-preview-tasks.ts` refuses to start without it and refuses the production id outright, rather than defaulting to anything.
- Run locally with `npm run e2e:preview` (needs `PREVIEW_URL` and `GOOGLE_APPLICATION_CREDENTIALS` set — the latter only matters for specs that seed/create via `firebase-preview-tasks.ts`; unauthenticated specs run fine without it).
- **`cypress/support/e2e.preview.ts` patches `window.fetch` for `/__/firebase/init.json` specifically**, before any app code runs, serving a real response fetched separately via `cy.request()`. Root cause: Cypress reserves paths starting with `/__` for its own runner/iframe machinery, which collides with Firebase Hosting's own `/__/` reserved namespace — _any_ request to a `/__/`-prefixed path (real endpoint or not) simply hangs forever when made as a real browser request inside a Cypress-controlled tab, confirmed across Electron and real Chrome, regardless of network/DNS/IPv6/QUIC (all ruled out first). `cy.intercept()` stubbing the same URL didn't help either, since it's routed through the same proxy layer that mishandles the path — only a direct `window.fetch` override, bypassing Cypress's browser-facing network layer entirely, actually works. `cy.request()` (Cypress's own Node-side HTTP client, never going through the browser) is unaffected and used to fetch the real config for the patch to serve.
- **`service-worker-oauth-origins.cy.ts` is the only spec that runs here and _not_ locally**, and it is the only one that registers the service worker. It is regression cover for PR #112: `ngsw-worker.js` re-fetches every request from inside the worker, where `connect-src` is the directive that applies, so an origin allowed only by `script-src` loads fine until the worker takes control and then fails as a synthetic 504 — which is how Google sign-in broke. **It imports the rule from `scripts/csp-rules.mjs` rather than restating it**, and applies it to the header a deployed channel actually serves; `npm run csp:verify` applies the identical function to the policy written in `firebase.json`. That split matters because they answer different questions — a `**` rule that stops matching, a deploy that didn't take, or a CDN rewriting the header are all invisible on disk — but it only stays one rule if there is one copy. There were two for the span of a single PR (#114 copied it, #113 then corrected it in the script alone) and they had already drifted about `frame-src`, `default-src` and directive-name casing. `cypress.config.ts` now carries an `excludeSpecPattern` naming it, because the local runner has nothing for it to test: `ng serve --configuration=e2e` sets no `serviceWorker` in `angular.json`, so no `ngsw-worker.js` is emitted, and a dev server sends none of `firebase.json`'s headers. It registers the worker explicitly (`app.config.ts` gates registration on `!navigator.webdriver`, which is true under Cypress) and unregisters it plus its `ngsw:` caches in an `after()`, since `testIsolation` does not — leaving it registered would slow every later spec on the same origin, the cost `app.config.ts` documents at ~7 s → 46 s+. **One half of it cannot work in a browser and is written knowing that**: Cypress strips `Content-Security-Policy` response headers from documents it loads, verified here by reverting the fix and watching the in-browser probe pass anyway, so the CSP assertion is made with `cy.request()` (Node-side, header intact) while the in-browser half proves only that the worker really does intercept and re-fetch cross-origin requests. Both halves were mutation-checked: reverting #112 fails the `cy.request` test naming both origins, removing the registration fails the in-browser test on "the page is controlled by a service worker", and pointing a probe at an unreachable origin fails it on the real synthetic 504.

### 4.4 Lighthouse CI (performance / accessibility / best-practices / SEO)

- `lighthouserc.json` drives both local (`npm run lighthouse`) and CI (`.github/workflows/lighthouse.yml`) runs identically: builds with the dedicated `lighthouse` Angular configuration (same optimizations/budgets as `production`, but with `fileReplacements` swapping in `environment.e2e.ts` like the `e2e` config does — see §4.5), starts the Firebase Emulator Suite (`hosting`, `auth`, `firestore`) via `firebase emulators:exec --project demo-trivia-app-e2e`, and runs Lighthouse 3× against `http://127.0.0.1:5000/` (the Hosting emulator, serving the real build), asserting each category's **median** score — `aggregationMethod: "median"`, set explicitly, because the default is `optimistic` and asserts the _best_ run (see below).
- **This intentionally serves from the Hosting emulator, not a bare static server**: only Hosting (real or emulated) resolves the reserved `/__/firebase/init.json` endpoint, so this is what lets `FirebaseAppService` actually initialize and `AuthService`/`FirebaseService` actually run anonymous sign-in and Firestore reads against the local emulators — exercising the real runtime code paths instead of everything failing silently. An earlier version of this check served a bare static build instead; that setup measured a _better_ best-practices score (Firebase never initialized at all, so nothing could log a runtime error) which would have masked exactly the class of regression this check exists to catch — first caught when a real Chrome DevTools run against the live production URL showed something not reflected by CI at all (turned out to be an unrelated noisy manual run — see below — but the gap in methodology was real).
- **The Lighthouse run serves through a _derived_ Hosting config**, `firebase.lighthouse.json`, generated from the real `firebase.json` by `scripts/make-lighthouse-firebase-config.mjs` and gitignored. It differs in exactly one way: `connect-src` gains `http://127.0.0.1:9099` and `:8080`. This check is the only one that builds with emulator endpoints (`environment.e2e.ts`) _and_ serves through production headers, and those emulator ports are separate origins from the page's own `127.0.0.1:5000`, so `'self'` does not cover them and the CSP refuses every Firebase request. Widening the real policy would ship a production CSP letting injected script reach services on a visitor's own machine; dropping the auth emulator would remove what this check exists to exercise; lowering the threshold is forbidden (`CLAUDE.md` §3). Deriving keeps the production policy authoritative with no second copy to drift, and everything else about the CSP is still exercised exactly as production has it — which is what caught the logo's inline `style` attribute.
- **`aggregationMethod` is set to `median` explicitly, and this file used to claim it already was.** The Lighthouse CI default is `optimistic`: for a `minScore` assertion it takes the most favourable run, so three runs of 0.84/0.66/0.62 passed a 0.75 threshold on the strength of the 0.84. Verified rather than inferred — replaying one CI batch (0.68/0.92/0.91) through `lhci assert` at `minScore: 0.92` passes under the default and fails under `median` with `found: 0.91`.
- **`pessimistic` was considered and rejected on the data.** Downloading the reports from three real CI runs showed the _first_ run of every batch is a cold-start outlier — 0.90, 0.68, 0.52 — while runs 2 and 3 sit at 0.91–0.92 every time. Asserting the worst run would fail constantly for reasons that have nothing to do with the code. Median over three runs discards exactly one outlier, which is precisely the shape of this noise; two bad runs still fail, which is the point.
- Thresholds: performance ≥ 0.85 (raised from 0.75 in the same change, since a threshold set to survive optimistic aggregation is not the same as one set against the median — observed CI medians were 0.92/0.91/0.92 and local 0.93 when it was set, so 0.85 looked like roughly 0.06 of headroom while still catching a real regression — **that headroom is gone, and the paragraph below records what replaced it**); accessibility/best-practices/SEO ≥ 0.95, left where they were (all measure a clean 1.0 in every local and CI run). Raising them to 1.0 would change nothing in practice: each category has few enough audits that a single failure drops it to roughly 0.93, already under 0.95 — which is exactly how the CSP's console error was caught. Performance measured 0.77–0.89 across local + emulator-backed runs while Inter was hot-linked from Google Fonts (and under optimistic aggregation, so those numbers flattered the build); self-hosting it (`stack.md` §2.1) moved that to ~0.91, and turning off critical-CSS inlining for the CSP (§4.1) to a very stable **0.93 / 0.93 / 0.93**. The tighter spread matters as much as the higher number: removing two preconnects and a render-blocking stylesheet from the critical path took out the most machine-dependent part of the measurement. The 0.75 threshold is deliberately left alone here — it is now very slack, but re-baselining it belongs with **D6** (which has to fix `aggregationMethod` first, since asserting the _best_ of three against a raised threshold would be worse than the current slack one).
- **The performance gate is marginal on CI runners, and it fails on unchanged artifacts.** Measured 30 August 2026 on [#148](https://github.com/shermam/trivia/pull/148), whose diff is one Cypress support file and one document — **no input to `ng build`, so the artifact was identical to `main`'s** — the three runs scored **0.81 / 0.84 / 0.89**, a median of 0.84, and the job went red. Re-running the same job on the same commit passed. Around the same window: `main` itself measured medians of 0.85 / 0.82 / 0.83 across three interleaved local rounds on a shared sandbox, while a quiet developer machine measured **0.92 on every one of twelve runs, with zero spread**.
  So the number is not drifting — the _variance_ is machine-dependent, and the 0.85 line sits inside the range a loaded runner produces. Two practical consequences. **A red `lighthouse` check is no longer evidence on its own**: before treating one as a regression, check whether the diff contains any input to `ng build` at all, because a docs- or test-only change cannot move the score. And **the cost lands on whoever is holding an unrelated PR**, who has to prove a negative each time.
  Deliberately **not** fixed by lowering the threshold, which would trade a false alarm for a blind spot and is what `CLAUDE.md` §3 forbids. The real fix is headroom, which is `FEAT-017`'s subject — its §0 records that ~1300 ms of the ~1900 ms FCP is JavaScript execution, so the room exists. Until then this paragraph is what stops the next person re-deriving it.
- A clean, extension-free, headless CLI run (`npx lighthouse <url> --chrome-flags="--headless=new"`) against the real deployed site is the trustworthy way to spot-check a production regression — a manual Chrome DevTools run can be skewed by browser extensions, a non-Incognito profile, or leftover site data, none of which reflect a real visitor's or CI's measurement.
- Reports (HTML + JSON) are uploaded as a `lighthouse-reports` build artifact on every CI run, pass or fail.

**Both deploying builds go through `scripts/build-with-commit.mjs`**, which passes the current commit to `ng build --define` so `src/app/build-info.ts` can name it and the footer can show it on hover. Three decisions worth not re-litigating:

- **`--define`, not a generated source file.** esbuild substitutes the identifier in the emitted JavaScript, so there is nothing on disk to generate, gitignore, keep in step, or accidentally commit with a real hash in it — and a fresh clone type-checks with no build step having run.
- **The commit _date_, never a build timestamp.** A clock in the bundle makes every rebuild of the same commit emit different bytes, hence a different content hash, a different `ngsw.json`, and a service-worker update pushed to every client for a deploy that changed nothing. The commit date answers the same "how stale is this?" question and is a property of the commit.
- **A script rather than `$(git rev-parse …)` inline in `package.json`.** npm runs scripts through `cmd` on Windows, where neither `$( )` nor `git log --format=%cd` survives — and the fallback belongs somewhere with `try`/`catch`, because building outside a checkout (a source tarball, a Docker context with no `.git`) has to degrade to an unstamped build rather than fail. `ng serve`, `ng test` and plain `ng build` pass no define at all, so the footer reads "local build" there; `build-info.spec.ts` runs under exactly that condition, which makes the undeclared-identifier path real rather than simulated.

**`ng test` runs with `--isolate` defaulting to _false_, so spec files are not independent.** Vitest's Angular builder documents the default as aligning with the Karma/Jasmine experience: spec files share a worker's module registry, which means they share the module-level state of everything they import. `fake-indexeddb/auto` is the case that bites — nine spec files import it, and they get **one** in-memory IndexedDB between them, so a unit test that writes real storage is not local to its own file.

That produced a ~40% flake with no local cause. `game-controller.service.spec.ts` did not stub `DailyGameLimitService`, so each of its five `startGame()` calls spent a real game against the real quota and persisted the count under today's date. Whenever that file ran before `daily-game-limit.service.spec.ts` in the same worker, the latter's **first** test opened on an exhausted allowance and failed with `expected +0 to be 5` — a failure naming a service the other file never mentions. Fixed on both sides, which is the shape worth copying: the controller spec stubs the collaborator it was never testing, and the daily-limit spec resets the counter in `beforeEach` as well as `afterEach`, so it does not depend on the next file to touch storage remembering to clean up. **A spec that leaves state behind is a defect in a file you have not opened.**

**`src/test-setup.ts`** is wired in as `setupFiles` on the `test` target in `angular.json`, and exists for one reason: **jsdom is not a browser**, and the honest place to say so is the test environment rather than the application. It currently shims `window.matchMedia`, which jsdom does not implement at all — calling it throws, which is how adding a breakpoint listener to `TopBarComponent` broke four unrelated `app.spec.ts` tests. The alternative was a `typeof window.matchMedia === 'function'` guard in the component: production code shaped around a test runner's gap, in a branch that would then never be exercised by anything. Anything added here should carry the same justification, and a spec that needs to _drive_ the shimmed API replaces it locally rather than making this one cleverer.

Package manager is pinned via `"packageManager": "npm@11.12.1"`. `functions/` is a separate npm package with its own `package.json`/lockfile (standard Firebase CLI convention), so the root `npm install`/`npm ci` doesn't reach it on its own — a root-level `postinstall` script closes that gap automatically (first materializing `functions/.secret.local` from its committed template — see `stack.md` §2.4 — then running `npm run functions:install`) so a plain `npm install` at the repo root is enough for `npm run functions:build`/`npm run e2e` to work right after cloning, without a separate manual step. That hook runs **`npm ci`**, not `npm install`: it used to be the latter, which meant every `npm ci` in CI — the command whose entire purpose is a reproducible tree — silently ran a non-deterministic install in `functions/` that was free to rewrite `functions/package-lock.json` as a side effect. The trade-off is that editing `functions/package.json` now makes the next root install fail loudly with an out-of-sync lockfile error; `npm run functions:install:update` is the deliberate escape hatch for that case, and the failure is the point — a lockfile should only change when someone meant to change it. `npm run e2e`/`npm run e2e:open`/`npm run rules:test` call the `firebase` binary directly now that `firebase-tools` (`^15.26.0`) is a real `devDependency` (`stack.md` §2.2, including the JDK 21 those scripts now need locally) instead of an `npx`-fetched tool. `npm run lighthouse` still uses the older `@13` major, which can't also be a `devDependency` alongside `@15`, so it stays on `npx --yes firebase-tools@13` — the `--yes` skips npm's interactive "ok to install?" prompt the first time that pin isn't already in the local npx cache (CI's shell is non-interactive, so it never saw that prompt either way; this is purely a local-DX fix).

### 4.6 Environments

- `.firebaserc` pins the default Firebase project to `intellectura-3b26a`. It is the only one named there; `trivimind-dev` is addressed by explicit `--project` flags in the npm scripts and workflows that target it (see `dev-environment.md`).
- `src/environments/environment.ts` / `environment.development.ts` carry `production` and `useEmulators` flags — no secrets or API keys live here, consistent with the runtime-config-fetch approach described in `stack.md` §2.3.
- `src/environments/environment.e2e.ts` sets `useEmulators: true` and is swapped in only by the `e2e` build/serve configuration (`angular.json`, `fileReplacements`) used by the Cypress suite (§4.3) — never by `start`/`build`/`build:prod`.
- Production build budgets (`angular.json`): 500 KB warning / 1 MB error (initial bundle), 4 KB warning / 8 KB error (per component style); output hashing enabled for cache-busting.
- `functions/` has its own env layer (`stack.md` §2.4): `.env.demo-trivia-app-e2e` (committed, non-secret — sets `STRIPE_MOCK_CHECKOUT=true`) and `.secret.local` (gitignored, generated by the root `postinstall` from the committed placeholder template `.secret.local.example` — the pin that keeps the emulator from fetching real secrets, and the one safe place for real test-mode keys). Everything else under `functions/.env*`/`.secret.local` is gitignored — see the comments in `functions/.gitignore` for why `.env.demo-trivia-app-e2e` and the `.example` template are the only committed exceptions.
