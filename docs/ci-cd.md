## 4. Deployment & CI/CD

### 4.1 Hosting & Functions configuration (`firebase.json`)

- Hosting serves the compiled Angular app from `dist/trivia-app/browser`.
- `theme-init.js` is served `no-cache` by its own rule (declared after the blanket `**/*.@(js|css)` immutable rule so it wins), for the same reason `ngsw-worker.js` is: it lives in `public/` and therefore has no content hash in its filename, so a year-long immutable cache would make any edit invisible to returning visitors.
- **Rewrites, in order.** `/api/geo` goes to the `geo` Cloud Function (`stack.md` §2.4); everything else (`**`) falls back to `/index.html` for client-side routing. Order is the whole mechanism — Hosting takes the first rewrite that matches, so the SPA catch-all has to stay last, and a `/api/geo` moved below it would silently start serving the app shell instead. That is also the failure mode this rewrite is most exposed to: the browser gets `200 text/html` rather than an error, the client reads it as "country unknown" and degrades to its time-zone fallback, and nothing goes red anywhere. `scripts/smoke-test.mjs` therefore checks the **content type** and not merely the status (§4.2 step 10). The `/api/geo` response also carries `Cache-Control: private, no-store` twice over — the function sets it, and a headers rule of its own restates it so the catch-all's `public, max-age=0, must-revalidate` cannot win on a path whose answer is different for every visitor. Neither the rewrite nor that header moves the service-worker policy fingerprint (below) — `FINGERPRINTED_HEADERS` covers response headers that govern what the worker may fetch, and a `Cache-Control` on one path is no more one of those than the `Referrer-Policy` the script already names as an example — and `ngsw-config.json` deliberately caches nothing under `/api/`: its asset groups name `/*.css`, `/*.js` and four specific files, and a programmatic `fetch` is not a navigation, so the worker passes it through to the network under `connect-src 'self'`.
- **Security headers** are set on the catch-all `**` rule so they cover every route: a strict `Content-Security-Policy` (below), `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, and a `Permissions-Policy` denying every powerful feature the app doesn't use (camera, microphone, geolocation, payment, USB, …). `Strict-Transport-Security` is deliberately **not** set here — Firebase Hosting already sends it on the live domain (`max-age=31556926`), confirmed by inspecting real response headers; the emulator does not, which is worth knowing when comparing the two.
- **The CSP contains no `unsafe-inline`, no `unsafe-hashes` and no hashes at all**, because the production build emits no inline `<script>`, no inline `<style>` and no inline `on*=` handler. Two things had to change for that: the theme initialiser moved to an external file (`app.md` §1.7), and Angular's critical-CSS inlining was turned off (`optimization.styles.inlineCritical: false` in `angular.json`, for both the `production` and `lighthouse` configurations). That setting is what injected the 10 KB inline `<style>` **and** a `<link … media="print" onload="this.media='all'">` — an inline event handler, which under a strict CSP is refused, leaving the stylesheet stuck at `media="print"` and the app rendering with critical CSS only. Disabling it measured as **free**: Lighthouse performance was 0.90/0.94/0.91 with it on and 0.89/0.94/0.92 with it off, i.e. inside run-to-run noise. The purged Tailwind stylesheet is small enough that inlining part of it and deferring the rest buys nothing here.
- **`frame-ancestors 'none'`** — nothing may embed the app in an iframe. See `known-gaps.md` §6 for what this means for the embeddable-quiz idea.
- `script-src` allows `https://apis.google.com` and `frame-src` allows the Firebase `authDomain` of **every project this config is deployed to** (`intellectura-3b26a.firebaseapp.com` and `trivimind-dev.firebaseapp.com`) — both are needed only by the OAuth popup resolver, which loads lazily (`app.md` §1.5). **`apis.google.com` is also in `connect-src`, and that is not redundancy.** The Angular service worker responds to every fetch the page makes, cross-origin included, and re-issues the ones it does not cache as a `fetch()` **from inside the worker** — where the governing directive is `connect-src`, not the `script-src`/`frame-src` the page would have used. Leaving it out breaks Google sign-in the moment the service worker takes control, which is what it did: `apis.google.com/js/api.js` came back as a synthetic `504 Gateway Timeout` (Angular's `safeFetch` turns a refused fetch into one), the popup resolver could not initialise, and sign-in failed with a message the client could not explain. The authDomain is a different case and does **not** need this: `__/auth/iframe` is an iframe navigation and `__/auth/handler` a popup, and a navigation is matched to a service worker by the _target_ origin, so our worker never sees either. Its `connect-src` entry is inert, and is being left in place only until the remaining OAuth investigation concludes. A hard reload bypasses the service worker and made it go away, which is why it went undiagnosed for weeks. `npm run csp:verify` fails the build on that, and on the harder version of the same mistake: an origin the app requests that is in **no** directive, which no self-comparison can see. `httpsCallable`'s `us-central1-…cloudfunctions.net` host was exactly that — `deleteAccount` and `exportAccountData` were refused in production while every emulator run passed, because the emulator points them at localhost with no CSP served at all.
- **The CSP is fingerprinted into `ngsw-worker.js` at build time** (`scripts/stamp-service-worker.mjs`, run by `build:prod`, so both `firebase-deploy.yml` and `firebase-preview.yml` get it). A service worker keeps the CSP it was installed with, and `ngsw-worker.js` is a static file that never changes between deploys — so the update check compares bytes, finds none changed, installs nothing, and the old policy survives indefinitely. That is why the `connect-src` fix above did not reach existing visitors: their worker went on refusing `apis.google.com/js/api.js` and synthesizing the `504`, with the console quoting the pre-fix `connect-src` verbatim while the server served the new one. Appending a hash of the policy makes the bytes move when the policy moves, which forces the re-install. The stamp is asserted against the deployed artifact by `service-worker-oauth-origins.spec.ts` (§4.3), recomputed from the header actually served rather than from `firebase.json` — a stamp describing a policy nobody serves is no protection. Unrelated headers deliberately do not move it: a `Referrer-Policy` tweak should not re-install everyone's worker.
- **A client already stuck on an old policy recovers by itself, unattended, and does not need to close the tab.** This was left as inference when the fix shipped, and it is worth pinning down, because "the fix is deployed" and "the fix has reached anyone" are different claims. The chain, end to end: the app calls `register()` on every load (`app.config.ts`, `registerWhenStable:30000`), and per the service-worker spec `register()` on an existing registration triggers a soft update — a script fetch and a byte comparison. That fetch genuinely revalidates rather than being served from the HTTP cache, because `/ngsw-worker.js` carries `no-cache` (§4.1); the stamped bytes therefore differ and the new worker installs. Angular's worker then calls `skipWaiting()` in its `install` handler and `clients.claim()` in `activate` (`ngsw-worker.js`), so it does **not** sit in "waiting" for every tab to close — it takes over the open page immediately. A stale visitor is therefore back on the current policy roughly thirty seconds into their next visit, having done nothing.
- **What is still stale on that first load is the _page's_ CSP**, which came out of the old worker's cached `index.html` and is only replaced on the next navigation. It does not matter for this bug and it is worth knowing why: the OAuth resources are loaded by the page under `script-src`, which allowed them before and after. The directive that was actually refusing them is the one governing the **worker's** `fetch`, and that belongs to the new worker the moment it claims the client.
- **One `firebase.json` serves more than one Firebase project, and three of the origins in the CSP are named after the project.** So a policy that is correct for one deployment is silently wrong for another, and it was: the CSP named production only, so on `trivimind-dev` — and therefore on every PR preview channel, which is the same project — Google sign-in was refused with `Framing 'https://trivimind-dev.firebaseapp.com/' violates ... "frame-src https://intellectura-3b26a.firebaseapp.com"`, and `deleteAccount`/`exportAccountData`/`recordGameResult` would have been refused the same way. `dev-environment.md` §3.1 said the headers were "the same by construction rather than by discipline"; they were the same, and being the same was the bug.

  **Nothing caught it, and the reason generalises.** Every check here compares the policy against itself or against a fixed host list, and both are blind to project _identity_ — `frame-src` naming _a_ `firebaseapp.com` origin satisfies them whichever project it belongs to. `csp:verify` was green, `lint` was green, and `E2E (preview)` was green **while running against the very deployment whose sign-in was broken**. `csp-rules.mjs` now carries `DEPLOY_TARGETS` and a third check, `findDeploymentOriginProblems`, which takes the project identity as an argument: `verify-csp.mjs` runs it over every target on disk, and the preview spec runs it with what the deployed channel's own `/__/firebase/init.json` reports — the stronger of the two, because it cannot be wrong about which project is actually being served. Adding a third deployment is one line in `DEPLOY_TARGETS`.

  **A related sharp edge worth knowing before editing `csp-rules.mjs`:** its types live in a hand-written `scripts/csp-rules.d.mts`, because `e2e/tsconfig.json` is `strict` with no `allowJs`. A new export is invisible to the spec until it is declared there — which fails loudly (`TS2305`), so the missing direction is self-catching; a _wrong_ signature would not be.

- **OAuth sign-in is still not in the e2e suite**, so the origins themselves come from `app.md` §1.5's recorded network trace and want a manual sign-in check after any CSP change. What `csp:verify` catches is the _shape_ of the mistake above, not whether the list is complete.
- **Header rule ordering matters here**: the catch-all `**` headers rule (the security headers above, no-cache, and `Cross-Origin-Opener-Policy: same-origin-allow-popups`, needed so Firebase Auth's popup-sign-in polling can read `popup.closed` without the browser blocking it — see `app.md` §1.5) is listed _first_, with the more specific rules listed _after_ — the hashed-asset ones (`**/*.@(js|css)`, images/fonts), then the three single-path `Cache-Control` overrides: `/theme-init.js` and `/ngsw-worker.js` (`no-cache`, for the reason above) and `/api/geo` (`private, no-store`, because its answer is different for every visitor). Hosting applies the last-declared matching rule per header key, so each of those overrides the broad one on its own path and nothing else about the broad rule is affected. An earlier version of this scoped the no-cache/COOP headers to the literal `source: "/index.html"`, which silently never matched any real request — every route (`/`, `/play`, `/game-over`, ...) is served via the `**` rewrite above, never a literal request for `/index.html` itself.
- `functions` config points at the `functions/` package (`stack.md` §2.4), with a `predeploy` hook (`npm --prefix functions run build`) so `firebase deploy --only functions` always deploys freshly-compiled code.
- Local emulator ports: Firestore `8080`, Auth `9099`, Functions `5001`, Hosting `5000`, plus the Emulator UI. `singleProjectMode` is enabled. The Auth and Functions emulators exist solely for the e2e suite (§4.3) — the app never talks to either outside that configuration.

### 4.2 GitHub Actions workflow (`.github/workflows/firebase-deploy.yml`)

**Trigger**: fires only when a pull request targeting `main` is **closed and merged** (not just closed).

Steps:

1. Checkout `main`.
2. Set up Node 24 (with npm cache, keyed off both `package-lock.json` and `functions/package-lock.json`).
3. `npm ci`.
4. `npm run build:prod` (production Angular build).
5. Deploy **Firestore rules + indexes** via `npx firebase-tools@13 deploy --only firestore:rules,firestore:indexes`, using the service account written to a temp `GOOGLE_APPLICATION_CREDENTIALS` file.
6. `npm ci --prefix functions`, then deploy **Cloud Functions** (`stack.md` §2.4) via `npx firebase-tools@14 deploy --only functions` (`@14`, not `@13` — see `stack.md` §2.2) — a separate step from #5 on purpose, so a functions-only failure is easy to spot on its own.
7. Delete the temp credentials file, immediately after its last user rather than at the end of the job — the Hosting step below authenticates from the secret directly and never reads it.
8. Deploy the built app to **Firebase Hosting** via `FirebaseExtended/action-hosting-deploy@v0` (channel: `live`), authenticated with the `FIREBASE_SERVICE_ACCOUNT_INTELLECTURA_3B26A` repo secret. **Last on purpose** — see the ordering note below.
9. Always clean up the temp service-account credentials file, even on failure.
10. **Smoke-test production** (`node scripts/smoke-test.mjs https://trivimind.com`): app shell served, CSP/`X-Content-Type-Options`/`Referrer-Policy` intact, `/__/firebase/init.json` resolving to this project, `theme-init.js` reachable, `/api/geo` reaching its function and answering uncacheable JSON with a two-letter country or `null` (§4.1 — the shape and the content type, never the country, which is wherever the runner is), and the callables deployed and still rejecting an unauthenticated caller with 401. It runs last and cannot undo anything — by the time it fails the deploy has shipped — but it is what turns a broken production into something someone is told about.

A separate **`report-failure` job opens a GitHub issue** (labelled `deploy-failure`, de-duplicated to one open issue) whenever **either** deploy job fails. This exists because the pipeline once failed on **four consecutive merges** while Hosting kept shipping and nothing surfaced it — see `INFRASTRUCTURE.md` §6.3a, which also holds the rollback procedure. The issue names both jobs and says to check which one failed, because a red run no longer implies production is affected. It previously said the steps ran Hosting → rules/indexes → functions, leaving a newer client against an older backend; that was **stale and backwards** — it contradicted the paragraph immediately below it, which is the one that was right.

**A second job, `deploy-dev`, ships the same commit to `trivimind-dev`** — checkout, `npm ci`, `npm run build:dev-project`, Firestore rules + indexes, then Hosting on channel `live`, authenticated with `FIREBASE_SERVICE_ACCOUNT_TRIVIMIND_DEV`. It runs **independently** of the production job: dev is not downstream of production, and holding one behind the other only widens the window in which they disagree. The commit is the one `E2E (preview)` already exercised end to end against this very project.

**Why it had to exist.** Nothing deployed dev's live channel before: `firebase-preview.yml` creates a per-PR channel on the same project, and `npm run firebase:deploy:dev` is a laptop command somebody has to remember — so `trivimind-dev.web.app` served whatever was last pushed by hand, indefinitely. That cost a diagnosis: [#153](https://github.com/shermam/trivia/pull/153) fixed a CSP that refused Google sign-in on dev, the next PR's preview channel picked the fix up immediately (it is built from that PR's head), and `trivimind-dev.web.app` went on refusing sign-in. Every client-side remedy — clearing storage, unregistering the service worker, reloading with cache disabled — was doomed by construction, because the stale artifact was a **response header** on the server. **The rules are the sharper edge:** `E2E (preview)` runs against this project's real Firestore, so a `firestore.rules` change that merged without reaching dev leaves the preview suite green about the _previous_ rules.

`deploy-dev` ships **hosting, Firestore rules/indexes and Cloud Functions**, so the mirror is complete. Functions were held back on the first cut, because the step needs `STRIPE_SECRET_KEY`/`STRIPE_WEBHOOK_SECRET` in the dev project (`dev-environment.md` §3.1 step 8) and a missing one would have failed on every merge — a guardrail that cries wolf on every commit gets switched off. Those secrets are set, so the steps are in.

**Its first run failed, and the reason is worth carrying.** Not the secrets — the _rules_ step, with `403, The caller does not have permission` from `firebaserules.googleapis.com`. The credential had been deploying preview channels to this same project on every PR for weeks, which read as proof that it worked and proved only that it could deploy **Hosting**: a key generated from Project settings carries the Admin SDK service agent role and nothing else, and Hosting, Firestore rules, Firestore indexes and Cloud Functions are four separate grants. **A credential already in use is not evidence it is sufficient for a new use of it.** The roles are now listed at `dev-environment.md` §3.3 step 10, beside the step that issues the key.

Note also which way that failure fell: backend-first ordering stopped the job before Hosting ran, so dev stayed on its old bundle. Once the IAM grants landed, the rules and indexes deployed cleanly and the **next** step failed instead — on GitHub, not Firebase: `403 Resource not accessible by integration` against `api.github.com/repos/…/check-runs`. `action-hosting-deploy` opens a check run named "Deploy Preview" whichever channel it targets, so `contents: read` alone is not enough; the job needs the same `checks: write` and `pull-requests: write` the production job carries. This paragraph two lines up already recorded that exact 403 against the production job, and giving the new job narrower permissions repeated it — **a permission set is a property of the action, not of the job's importance**, and "deploy-dev only reads the repo" was reasoning about the wrong thing. That is the right trade — a half-deployed mirror is worse than an un-deployed one — but it means a rules-permission problem presents as "the site did not update", which points at Hosting.

**The order is backend-first, deliberately.** Hosting used to deploy first, which put a new client live against an old backend for the length of the remaining steps — a window that only ever bites on the release where it matters, because that is the release that changed both (finding D2). The build also runs before any deploy, so a compile error aborts without having touched production at all.

The reverse exposure — an _old_ client against a _new_ backend — cannot be fixed by ordering: a visitor with the app open across a deploy, or one served the precached shell by the service worker (`app.md` §1.8), is running an old client whichever order the steps take. So a backend change has to stay compatible with the already-deployed client regardless, and once that is true, backend-first strictly dominates: it is the only order that also closes the new-client window.

Job permissions are scoped to `contents: read`, `checks: write`, `pull-requests: write` — the minimum needed for the hosting-deploy action to post a check/PR comment (this was tightened in a dedicated fix after the action initially hit a 403).

This is a **merge-to-deploy** pipeline: every PR merged into `main` auto-deploys hosting + Firestore rules/indexes + Cloud Functions to production (`intellectura-3b26a`), and hosting + Firestore rules/indexes to `trivimind-dev`. It deliberately doesn't re-run e2e itself — see §4.2a for why that's still safe.

**One-time setup this pipeline depends on** (not automatable from CI, done once by someone with Stripe/GCP console access): `firebaseRole: pro` metadata on **both the Stripe Product and the Price** — see the warning below, this is not either/or — and a webhook endpoint pointed at the deployed `stripeWebhook` URL (`stack.md` §2.4); `STRIPE_SECRET_KEY`/`STRIPE_WEBHOOK_SECRET` set via `firebase functions:secrets:set`; and the deploying service account granted the IAM roles a Gen 2 functions deploy needs. **That list is longer than it looks and this line used to understate it** — it said Cloud Functions Admin / Service Account User / Secret Manager Secret **Accessor**, and `secretAccessor` is the wrong secret role: it grants permission to read a secret's _value_ and none to see that the secret exists, so a deploy fails at `secretmanager.secrets.get` before it reads a payload. `dev-environment.md` §3.3 step 10 now carries the corrected set, with the gcloud commands, for both projects. This has now been completed against the real project, so step 7 above is expected to succeed on every merge going forward (no longer `continue-on-error`, so a regression here will now turn the workflow red instead of failing silently).

### 4.2a Preview channel deploy + real-preview e2e (`.github/workflows/firebase-preview.yml`)

**Trigger**: every PR targeting `main`, on open/sync/reopen **and close**. A `concurrency` group keyed on the PR number cancels a stale in-flight run if the PR gets pushed again before it finishes.

**It deploys to `trivimind-dev`, not to production.** A preview run is not read-only — the e2e job creates real Auth users, real `custom_questions` documents and real `leaderboards/{limit}/entries` rows, on every PR. `trivimind-dev` runs the same production build against the same rules, the same indexes and the same `firebase.json` headers, so what the preview validates is unchanged; what changed is whose data it writes to. `npm run env:verify` fails if this workflow names the production project again (§4.6).

Three jobs — the deploy and the e2e job that depends on it run on open/sync/reopen, the last only on close:

1. **`deploy-preview`** — checkout → Node 24 → `npm ci` → `npm run build:prod` → **deploy the PR's Firestore indexes to `trivimind-dev`** → `FirebaseExtended/action-hosting-deploy@v0` deploying to an ephemeral channel named `pr-<number>` (7-day expiry) instead of `channelId: live`. The action posts/updates a PR comment with the preview URL on every push. The step's `urls` JSON output is parsed (`jq`) into a job output consumed by the `e2e-preview` job.
2. **`e2e-preview`** (job name `E2E (preview)`) — runs a scoped slice of the e2e suite (§4.3) against the just-deployed preview URL, hitting the real `trivimind-dev` project instead of an emulator. One runner, unsharded: the slice is 96 tests and finishes in about a minute and a half.
3. **`cleanup-preview`** (job name `Delete preview channel`) — deletes the PR's channel when the PR closes, merged or not. A channel is created per PR and the 7-day TTL expires them more slowly than this repo merges, so without this they accumulate to Firebase's 50-channel-per-site cap, at which point _every_ new PR fails to deploy with `429 channel quota reached`. A missing channel counts as success; anything else fails the job, deliberately not `continue-on-error`, which would swallow a credential problem and let the channels pile up again.

Every credentialed job skips for Dependabot: each runs `npm ci` — the install scripts of the very dependency under review, and in `deploy-preview`'s case `npm run build:prod` on top — and only then hands over a Firebase deploy service account. A job skipped by a job-level `if` reports "skipped", which branch protection treats as success.

> **Indexes are the one piece of backend configuration a preview validates, and rules are deliberately not.** The emulator enforces no index configuration at all, so an index mistake is green in every local suite and fails only once deployed — which is how the production pipeline broke across four consecutive merges while Hosting kept shipping (D3, `data-model.md` §3). Deploying the PR's `firestore.indexes.json` to `trivimind-dev` before the channel goes up makes a bad index fail its own PR. It is safe to do from an unmerged branch because an index is **additive**: it affects no existing query, and creating one a later commit drops leaves an unused index rather than a broken read. Rules are the opposite on both counts — a security boundary every client of the shared dev project is already running against — so they stay with §4.2's merge-to-deploy pipeline.
>
> An index **build** is asynchronous: the step returns once creation is accepted, and a query needing a brand-new index is refused until it finishes. The `e2e-preview` job's own checkout, install and browser download sit in between, which is the slack that makes this workable — but a spec that introduces an index in the same PR should stay out of the preview slice for that one release (§4.3 names which, and why).
>
> **A new Cloud Function will look broken on its own preview channel.** Preview channels deploy Hosting only; the functions in the project are whatever §4.2's merge-to-deploy pipeline last shipped. So a PR that _adds_ a callable serves client code calling a function that does not exist yet, and the feature fails with `functions/not-found` on the preview while working perfectly against the emulator. This is expected, not a regression — verify such a feature with `npm run e2e` (which runs the Functions emulator) and re-check on the live site after merge. `AccountService` detects that specific error code and says so, rather than telling the user to retry something that can never succeed.
>
> **`/api/geo` is the shape to copy when a new function can afford to be absent.** It is reached through a Hosting rewrite rather than as a callable, so on a channel where the function is not deployed the request falls through to the SPA catch-all and comes back `200 text/html` — not an error the client could recognise, just the app shell. `GeoService` therefore treats anything that is not `200` plus a JSON content type as "country unknown" and falls back to the browser's time zone (`app.md` §1.6), which is exactly the path `ng serve` runs too. The feature is a pre-selected radio button, so degrading is the right answer; the point is that it degrades **by design** rather than by luck, because the failure this environment produces is indistinguishable from success at the HTTP layer.

> **The same is true of `firestore.rules`, and it is worse, because the failure does not name itself.** Rules are per _project_, not per channel, so a preview channel is the PR's client running against whatever rules `main` last deployed — there is no way to preview a rules change at all. A PR that changes a rule and the client code that satisfies it will look broken on its own preview, and the symptom is a bare `403 PERMISSION_DENIED` on `documents:commit`, surfaced by the app as its generic "please try again".
>
> Contrast the Functions case above: `functions/not-found` is a distinct error code that says exactly what is wrong. `PERMISSION_DENIED` is what a **genuine** rules bug looks like too, and the two are indistinguishable from the browser. That is the actual hazard here — not the false alarm, which costs a few minutes, but the true alarm dismissed as one.
>
> **So the rule is: before concluding a permission error on a preview is expected, diff the PR's `firestore.rules` against `main`'s and check the specific predicate the refused write hits.** If the PR does not touch rules, a `PERMISSION_DENIED` is real. This bit review-before-publish ([#123](https://github.com/shermam/trivia/pull/123)): the PR flipped `statusOnSubmission()` from `'approved'` to `'pending'` in both the rules and the client, so the previewed client wrote `status: 'pending'` into a project whose deployed rules still demanded `'approved'`, and every submission was refused. Verify that class of change with `npm run e2e` — which runs the rules in the emulator alongside the client — and re-check on the live site after merge.
>
> Note the preview suite cannot cover this either, and not by oversight: `add-question-pro-gating` is already outside the preview slice for an unrelated reason (§4.3). Adding it would not help — it would fail on exactly the PRs where the mismatch is expected, turning a real signal into a red that reviewers learn to ignore.

Preview channels are a **Hosting-only** feature — there's still a single Firestore database for the project, so a preview build (and its e2e run) reads/writes the same production `custom_questions`/`leaderboard` data as `main` and live. Firestore rules/indexes are also not redeployed per-preview (they're project-wide, not channel-scoped); only §4.2's merge pipeline touches them. There is no isolated staging _database_ — just an isolated hosting URL, backed by production data, that's now also exercised end-to-end before merge.

**Merge gating is live, and it covers every CI check — not just this one.** `main` is protected by a repository **ruleset** (`enforcement: active`) requiring the status checks below to pass before a PR can merge, and therefore before §4.2's deploy can fire at all:

| Required check           | Workflow                              |
| ------------------------ | ------------------------------------- |
| `test`                   | `unit-tests.yml`                      |
| `e2e`                    | `e2e.yml` (the gate over both shards) |
| `lighthouse`             | `lighthouse.yml`                      |
| `Deploy preview channel` | `firebase-preview.yml`                |
| `E2E (preview)`          | `firebase-preview.yml`                |
| `lint`                   | `lint.yml`                            |
| `rules-tests`            | `rules-tests.yml`                     |
| `functions-tests`        | `functions-tests.yml`                 |

> **`lint` is not one step.** `format:check`, then `npm run lint` over all three source trees, then `npm run typecheck:e2e`, then the four verifier scripts (`icons:verify`, `csp:verify`, `motion:verify`, `env:verify`). They share a job because they are one "does this code meet the static bar" question and splitting them would buy a second `npm ci` and nothing else. The typecheck in particular went here rather than into a fourth workflow — a deliberate exception to one-workflow-per-concern — because `lint` is already required, so a step added to it gates a merge **today**, whereas a new workflow reports without blocking until an admin adds it. See the row immediately below for what that state looks like in practice.

> **`e2e` is a gate job, not the job that runs the tests, and that is what keeps it requirable.** The suite runs as a two-shard matrix (§4.3), and a matrix job's status contexts carry the matrix value in their names (`e2e-shard (1)`), so neither shard can be the context the ruleset names. The gate `needs` them both, runs `if: always()` and fails unless every shard succeeded. Sharding further, or unsharding, therefore changes nothing about the ruleset — which is the point of the arrangement. The same is true of `E2E (preview)`: it is a job **name**, deliberately fixed, so the job under it can be rewritten without the requirement being touched.

> **`functions-tests` is not in the ruleset yet.** It runs on every PR and reports pass/fail, but a workflow cannot add itself as a required check — that needs a repo admin in Settings → Rules. Until then a red `functions-tests` will not block a merge (the other seven checks above are all required — `lint` and `rules-tests` went through this same lifecycle and have since been added, verified against `GET /repos/{owner}/{repo}/rules/branches/main` on 2026-08-10). The suite previously ran as a step inside the `e2e` job, so it was already gated there under the wrong name; splitting it out trades a short gating gap for a permanently clear signal — the accepted cost of one workflow per concern (see `INFRASTRUCTURE.md` §8).

`strict_required_status_checks_policy` is on, so a branch must also be up to date with `main` before merging. The ruleset additionally requires a pull request (with zero required approvals — this is a solo repo) and blocks branch deletion and non-fast-forward pushes.

One practical gotcha when verifying this: it's a **ruleset**, not classic branch protection, so the legacy `GET /repos/{owner}/{repo}/branches/main/protection` endpoint returns **404 "Branch not protected"** even though `main` is fully protected. Check `GET /repos/{owner}/{repo}/rules/branches/main` (or `/rulesets`) instead — the legacy endpoint's 404 is not evidence of anything.

### 4.3 E2E testing (Playwright, against the Firebase Emulator Suite)

**The suite is `e2e/`, and it is 190 tests across thirty-eight files.** Specs live under `e2e/specs/unauthenticated/` (the anonymous game flow across all three question sources, question reporting, route guards, embed mode, the mobile nav drawer, the adjustable timer, streak multipliers, question deduplication, the setup screen's topic filter, sound effects and the mute, saved-game resume, the daily allowance, the pre-boot recovery notice, a round played with the network gone, and the two preview-only service-worker specs below) and `e2e/specs/authenticated/` (email sign-up + verification, sign-in, saving a score, profile management, the lifetime totals — the callable that banks them and the `/profile` screen that shows them — account deletion and export, the reviewer queue, an author's own contributions on `/my-questions`, Pro-gated `/add-question` access, question source attribution, topic tags on a contributed question, Markdown and LaTeX question rendering, regional leaderboards, Stripe checkout, and the donation dialog). `e2e/fixtures/` holds the test fixtures and the two recorded Open Trivia DB responses every stubbed game is served from, `e2e/support/` the page helpers, and `playwright.config.ts` sits at the repo root. **185 of the 190 run on the emulator; the other five are `service-worker-oauth-origins.spec.ts` (four) and `service-worker-precache.spec.ts` (one)**, which run only against a deployed channel and belong with the preview slice below. (Every count in this section is what `playwright test --list` reports for the config in question — check it there rather than adding up files by hand.)

- Run with `npm run e2e` (headless) or `npm run e2e:open` (Playwright's UI mode). Both first `npm run functions:build`, then wrap `playwright test` in `firebase emulators:exec --project demo-trivia-app-e2e --only auth,firestore,functions` (**functions** included, see `stack.md` §2.4), which starts a throwaway local Firestore + Auth + Functions emulator trio, runs the wrapped command, and always tears the emulators down afterward — no real project is ever touched. The emulators live outside the runner; the Angular dev server is the one thing Playwright starts itself, through its `webServer` option pointed at `npm run e2e:serve`. **Behind an HTTP proxy, clear the four proxy variables for that one command** (`env -u HTTPS_PROXY -u HTTP_PROXY -u https_proxy -u http_proxy npm run e2e`) — firebase-tools ignores `NO_PROXY`, so it sends its own loopback traffic to the proxy and the emulators never come up.
- The app itself only connects to the emulators when built with a configuration that sets `useEmulators` — `e2e` and, since `FEAT-012`, `development` (see §4.5): `FirebaseAppService` skips the `/__/firebase/init.json` fetch and synthesises a config from `environment.emulatorProjectId` instead, which is `demo-trivia-app-e2e` here and `demo-trivimind-local` for `npm start`. Two ids rather than one, so an e2e run cannot write over the data you were developing against, and `AuthService` calls `connectAuthEmulator`, and `FirestoreRestClient` selects its emulator base URL (`http://127.0.0.1:8080/v1`).
- **`testIdAttribute` is set to `data-cy`**, which is the attribute the templates carry. The name is historical and the attributes are the test ids: they are what every spec addresses a clickable element by (`CLAUDE.md` §4.6), so renaming them across `src/` would be a large, entirely mechanical diff through the application for no change in behaviour.
- **The `firebase` fixture is the Admin SDK, called straight from the test body** — which runs in Node, so there is no process boundary to marshal across. It is worker-scoped — one Admin app per worker rather than one per test — and carries every operation the specs need: verified users, reviewer roles, Pro subscriptions and the product catalog, seeded questions and leaderboard rows, a single-round-trip read of what account deletion left behind, and the Auth emulator's out-of-band codes behind the email-verification and password-reset flows. Those last two are emulator-only by nature (`oobCodes` is a testing endpoint with no real-Auth equivalent short of a live mailbox, which is also why `sign-up-verify` is permanently outside the preview slice below), so the fixture throws rather than guessing when no emulator host is configured. Which project any of it writes to is the `FirebaseTarget`'s business (`e2e/fixtures/firebase-target.ts`) — the seam the preview target slots into — and the Admin app is created **named** and deleted on worker teardown, so two targets in one worker cannot end up sharing one app's credentials. `npm run env:verify` reads every `e2e/fixtures/*.ts` and fails if any of them names the production project.
- **There is no `resetBackend()`, and there will not be one.** Tests run in parallel against **one** shared emulator, so a blanket wipe from one worker would delete state another worker is mid-assertion on. Isolation comes from each test owning unique ids — a unique email, a unique question id — plus the fresh `BrowserContext` Playwright gives every test, which is a fresh anonymous uid, fresh cookies, fresh `localStorage` and **fresh IndexedDB**. The last of those removes an entire mechanism: `OfflineDbService`'s database holds the saved in-progress game and the daily-allowance counter, and clearing it by hand means a `beforeEach` timed against the app's own open connection, which blocks `deleteDatabase()` for the life of the tab. The same discipline is what the preview target needs against the real `trivimind-dev` project, so one spec body serves both. `test-isolation.spec.ts` is where the claim is checked rather than assumed: two tests in `mode: 'serial'`, the first leaving a saved game and an anonymous session behind on purpose so the second has something to be clean _of_. Serial mode buys the order **and** the same worker; it shares no context, which is the thing under test. Removing the context boundary — running both bodies inside one test — fails all four of its assertions, which is the mutation that says it is not vacuous.
- **Every uid the browser mints is recorded, by an automatic fixture** (`e2e/support/auth-uid-tracker.ts`, wired up in `e2e/fixtures/test.ts`). The accounts that accumulate in a real project are not the ones a test asks for by name — every page load signs in anonymously, and a sign-out mints another — so the sweep has to hear about those too, and reading the persisted uid once per test is a sample that only ever sees the last one (finding C6). A context init script wraps `Storage.prototype.setItem`, so each `firebase:authUser:*` write is seen as it happens; the wrapper hands the uid straight to Node through an exposed binding rather than parking it on a browser global, because a global lives in the page's JavaScript context and that is destroyed on every navigation — which is precisely the case being tracked. It must wrap **`Storage.prototype`**, not `localStorage.setItem`: assigning to the instance hits `Storage`'s named-property setter and stores the function _as an entry called `setItem`_, corrupting the store so the app's own writes never land. Automatic rather than opt-in, since a fixture a spec had to remember to request would be requested by the specs that already knew. `auth-uid-tracking.spec.ts` pins it against the emulator, the only place the mechanism can be exercised without merging it; the mutation that proves it — accumulate changed back to sample — fails that spec's middle test and nothing else.
- **Three specs needed a different _shape_ of isolation, and which ones is the useful part.** A unique email covers almost everything. The exceptions are the assertions that were about the **whole backend** rather than about the test making them, and each says so where it stands. `lifetime-stats`' anonymous row counted the entire `users` collection to state "nobody got a document", which means nothing once every other worker is writing rows to it — so it reads this session's own uid out of the `firebase:authUser:*` entry Firebase Auth persists and asserts that uid has no document, with the uid itself asserted non-empty so a failed read cannot turn the check into a vacuous pass. `review-queue` counted rows in a queue that lists every worker's contributions, so each question it seeds carries a per-test tag and every count is scoped to rows bearing it. `question-reporting` asserted "no report was written" by reading the whole of `question_reports` through the Admin SDK — so `getQuestionReports` takes the question ids to look for, and the ids being unique per test _is_ the isolation.
- **A custom-source game draws from the shared bank at random, which no tag can fix** — so every spec that plays one seeds its questions under a category unique to that test and selects it on the setup screen, `stubExtraCategory` having put the name into the stubbed Open Trivia DB category list the dropdown is built from. `getCustomQuestions` filters on category server-side, so the draw is then from that one test's questions. That is what makes `review-queue`'s "a pending question is never served" and "an approved one immediately is" about the status filter rather than about which of a hundred questions came up first, and what lets `question-reporting` say "the dialog offers **every** community question of this game" and "the flagged one and only it is led with" — assertions that are meaningless against a bank every other worker is writing into. `game-resume`'s flag test needs it for the weaker reason that a custom question is the only kind with a flag button at all. `review-queue` additionally assumes fewer than `REVIEW_PAGE_SIZE` (50) documents per status across the whole suite, since the queue it counts is paginated.
- **`retries: 0`, locally and on CI.** A retry turns a real intermittent defect into a green run that hides it, which is the failure mode `CLAUDE.md` §4.6 is a catalogue of. The per-test and `expect` timeouts are generous instead (120s and 20s), because the app's own 15-second per-question countdown sets the floor: a timeout below it means giving up on a button that is still there and still clickable.
- **Four workers per runner, and two runners.** Measured on a 4-vCPU box over the full suite: 4 workers 134s wall, 6 workers 109s. The knee is above four because these tests are _wait_-bound rather than CPU-bound — a five-question game spends ten of its twelve seconds sitting out the result banner's 2s pause. Four is nevertheless the setting, because the one thing over-subscription risks here is that same 15-second countdown: a worker starved past it loses the question and fails a test for a reason that has nothing to do with the code, and with `retries: 0` that is a red build. CI buys its wall clock by **sharding** instead — `playwright test --shard=n/2` on two runners, each with its own emulators and its own four workers — which is more parallelism without more contention per runner, and which took the job from 4m21s to roughly half of it.
- **The browser is pinned through the dependency, not through a path.** `@playwright/test` is an exact version (`1.56.1`, no caret), and that version decides which Chromium build `npx playwright install` fetches — so the browser is a property of the lockfile and a developer's machine, a container and the runner are all on the same build. The alternative, an executable-path override read from an environment variable, was rejected: it makes the browser a property of whoever is running, which is precisely the variable an e2e suite should not have. The cost is that upgrading Playwright changes the Chromium under the whole suite, which is the right place for that decision to be visible. A container that ships a pre-installed Chromium therefore has to hold the build that version expects (1.56.x is Chromium build 1194) rather than whatever is newest.
- **`startGame()`/`startNewGame()` wait for `/play` to be _rendered_, not for the questions response.** Those are not the same thing: the response is what `GameControllerService.startGame()` awaits _before_ it navigates, so it resolves while the app is still on the setup screen with the lazy quiz-loop chunk unfetched. A caller that goes straight to a positive retrying query is fine; a caller whose next assertion is a negative one passes against `/` and tests nothing. That is not hypothetical — it is how an "an Open Trivia DB question gets no flag button" assertion came to be green against a screen that has no flag button under any circumstances. The wait is in the helper rather than in the caller so the trap cannot be inherited again, and the heading assertion is the load-bearing half: the URL can commit a tick before the outlet paints.
- **A `should-not-exist` assertion needs a positive anchor in front of it.** A negative assertion placed first after a navigation is satisfied by a page that has not rendered yet, and no amount of retrying turns a satisfied assertion into a failure. Every negative assertion in `question-reporting.spec.ts` is preceded by something that can only be true once the screen is really there.
- **…and its mirror image: an assertion about a _transient_ element needs the transience removed, not more retries.** It cost two red runs on `main` before it was diagnosed. `game-flow`'s "does not resize the leaderboard when the scores arrive" opens by catching the loading skeleton — but `isLoadingLeaderboard` flips the instant `getTopScores` resolves, and against the local Firestore emulator that is fast. Instrumented in Chromium with a `MutationObserver`, the skeleton's real lifetime is **30–147ms**, against a retry interval of 50ms: the assertion was not testing the leaderboard at all, it was testing whether a poll landed inside a window narrower than the gap between polls, and it passed roughly four times in five. The fix is a `page.route()` that **holds the `:runQuery` response until the test has measured the skeleton**, rather than delaying it by a fixed amount — the gap between "the URL is `/game-over`" and the first query of the DOM measured 823ms here against a response released at 669ms, so a longer fixed delay would be the same coin flip with a bigger coin. Releasing on the measurement cannot quietly stop working when a machine gets slower. Nothing else changes: the fetch is real, the handler refetches and replays the genuine response, and the assertions are unchanged. The route is matched on **path only** (`/\/leaderboards\/[^/]+:runQuery/`), so emulator and production Firestore are covered by one pattern.
- **A route handler has no alias to wait on, so the ones that matter count their own hits.** Stubbing a response and proving the stub was reached are two jobs, and `page.route()` is only the first. The second is not decoration: `boot-fallback.spec.ts` asserts a recovery notice that appears when the entry script 404s, and a route that silently stopped matching would leave it asserting against a perfectly healthy page, failing on the notice rather than on the route. So the handler increments a counter and the test asserts it, the same shape `game-flow.spec.ts` uses for the held leaderboard query.
- **The layout assertions are made in a real browser, which is the only place they exist.** `boundingBox()` for a measured box, `toBeFocused()`, `toHaveAttribute()`, and `expect.poll()` where a group of measurements has to retry together rather than one at a time — a single `boundingBox()`/`count()`/`evaluate()` is a one-shot read, not an assertion, and cannot retry past a late layout frame. `e2e/support/layout.ts` holds the shared form of that: `drift()` for the sub-pixel tolerance, `expectSameHeight()` for the retrying comparison, and `settledHeight()` for the awkward half — the _first_ measurement of a before/after pair, which has no matcher to be read through because the value it should hold is exactly what the test does not know yet, so it polls until two readings agree. Where a viewport has to change, `mobile-nav.spec.ts` declares `test.use({ viewport })` per block rather than resizing a running browser: the viewport is a property of the `BrowserContext`, so the context is _built_ at that size and the first paint every test sees is already the one it is about.
- **A layout shift nothing in the DOM marks the moment of is measured every frame, not before and after.** `daily-game-limit`'s last test exists because the allowance row must not push the Start button down the page when the count resolves (`CLAUDE.md` §4.4) — but the count starts at 0 in the signal and reads back 0 from an empty database, so the row renders _the same sentence_ either side of the read. There is no state to wait for the absence of, and so no way to prove a "before" measurement was taken before anything happened. A sampler installed as an init script, recording the button's top on every animation frame from first paint, removes the ordering requirement instead of trying to satisfy it: the first sample is the first frame the button exists in, which is at or before any later shift, and the assertion is that every frame agrees. It seeds the counter rather than playing five games, and it runs at 390×1000 on purpose — §4.4 records that this class of shift measures 0px at one viewport height and 43px at another, so the height is part of the test rather than incidental to it. Mutation-checked by injecting a 40px displacement 600ms after load, which fails it.
- **`answerQuestion` is scoped to `[data-cy="answer-option"]`, and the bug that forced it is the most expensive kind.** An unscoped text match takes the **first** hit in DOM order, and the top bar sits above the quiz. A signed-in account chip renders the display name or email inside its trigger button (the `sr-only` accessible name in `top-bar.component.html`), so against an address like `stats-1787954295926-k3x@example.com` the command answered `"4"` by **clicking the account chip and opening the auth menu**. Measured, not inferred: the first `<button>` whose text contains `4` is `auth-menu-trigger`.
  **The countdown hid it, and that is the part worth carrying.** The question nobody answered timed out, auto-advanced as wrong, and the game finished 4/5 — so the reported symptom was `correctAnswers` short by one, which reads as a stats or scoring problem and was investigated as a slow CI runner for two rounds. The deadline was not the cause; it was the anaesthetic. Removing it made the same defect fail loudly on the _next_ question ("cannot find 'True'"), which is what exposed it. **A failure that arrives one step downstream of its cause will be diagnosed one step downstream of its cause.** Anonymous specs were never affected, because the signed-out chip reads "Sign in" and carries no digits — which is also why this survived every local run. `CLAUDE.md` §4.6 has the general form: address anything you click by `data-cy`, or scope the match to a container.
- **`pricing.spec.ts`** covers the Subscribe flow against the _real_ `createCheckoutSession` function (in `STRIPE_MOCK_CHECKOUT` mode, `stack.md` §2.4) end-to-end — click → Firestore write → Functions-emulator trigger → write-back → client poll → same-origin redirect, asserted on the URL hash — plus the anonymous sign-in prompt, the already-subscribed state (via `setProSubscription`), and the currency choice, whose real claim is the **price ID** the session document carries and is therefore read back through the Admin SDK rather than off the screen. It is `mode: 'serial'`: `products` is one global collection, so the tests that seed a second currency and take it away again decide what every other test in the file sees while they run. Which price the click actually used is addressed by the session's **document id**, which the mock redirect's hash carries — not by "the only document there is", since the page also creates one in the background (below). Three of its tests measure the Pro card instead, holding the catalog read open with a `page.route()` so the loading state can be measured rather than raced, then releasing it — the card must be the same height before the catalog answers, after it answers, across a switch between currencies, and when a seeded `localStorage` cache puts the amount on the first frame instead (`CLAUDE.md` §4.4). Two of the three were mutation-checked: collapsing the loading currency cell fails the single-currency one, and padding the placeholder pill differently from the radiogroup fails the two-currency one. Six more cover **which** currency the page opens on, and they have to fake both of its inputs, because neither is a property of the app: `page.route('**/api/geo')` stands in for the endpoint (`ng serve` has none, so every other test in the file runs the "unknown" path by construction) and `test.use({ timezoneId })` for the fallback, including a neutral `America/New_York` over the whole describe so no test silently asserts about where the runner is. The pair worth knowing about hold the geo answer open and release it: one proves a late answer moves the checked radio, the other that it does not overrule a click the reader has already made. They are written so the assertion survives the client's own two-second deadline expiring first — the second test's time zone is Brazilian as well, so the fallback answers the same country the held response would have. Five more cover the **speed** work (`app.md` §1.6): two seed `localStorage` through `page.addInitScript` — the only way to assert about a _first_ frame — and hold the catalog read open, so "the cached amount is on screen with no network answer" and "a cached amount the catalog disagrees with is corrected" are both decided rather than raced; three sign in as a verified account and count `checkout_sessions` documents through the Admin SDK, proving that the click reuses the session created while the reader was reading, that a reload reuses it, and that a **second tab** reuses it rather than replacing it. The last two wait out two real seconds, because their claim is that something does **not** happen and there is no event to wait on instead (`CLAUDE.md` §4.6). The second tab has to be a `context.newPage()` in the _same_ `BrowserContext`: a fresh context carries its own storage and its own session, so the collision the test is about could not occur in it and it would pass against the bug. **`add-question-pro-gating.spec.ts`** covers the free-tier upgrade prompt and, for a freshly-`setProSubscription`'d account, that the subscription read + forced token refresh actually let the `custom_questions` write through under the updated `firestore.rules`.
- **`question-source-attribution.spec.ts` is under `authenticated/` for a reason that has nothing to do with auth.** Its third test is anonymous — it seeds two custom questions and plays them — but the preview config takes all of `unauthenticated/` automatically and only two named specs from `authenticated/`, so the directory is how a spec that seeds documents and submits one through the UI (an auto-id no sweep list holds) stays off the shared real project. Three seams, none reachable more cheaply: that the **real rules** accept the document the _form_ builds (the rules suite proves the rule admits the fields, but it hand-builds the payload, and the two have disagreed before); that the reviewer's card renders the source link and the justification, which is where the feature earns its keep; and that the recap renders **nothing** for a question carrying neither, which is the common case and the one a placeholder would quietly ruin. Its two-question game answers by position rather than by text, which is safe because answering disables every option until the next question renders and a Playwright click waits for an enabled element — the app's own disabled state is the wait.
- **`lifetime-stats.spec.ts` reads the database rather than the screen, and that is the point rather than a workaround.** `users/{uid}` is written by a callable and has no client write path at all, so a document appearing in the emulator is proof the function ran rather than proof the browser could reach Firestore — and the risk it guards is a write that silently does not happen or silently happens twice, which looks identical from the front end whatever `/profile` renders. Three rows, and the middle one is the point: a game is banked once, **reloading `/game-over` does not bank it again**, and an anonymous player gets no document at all. The reload row asserts on `gamesPlayed` rather than on the document existing, because a double-count produces a document either way — the existence check would pass against the exact bug `lastGameId` exists to prevent. Each read goes through `waitForGameplayStats` rather than a single Admin-SDK call, because the callable is fire-and-forget: nothing in the DOM changes when it lands, and an Admin-SDK read is not a retrying query.
- **`profile-stats.spec.ts` is the other half of that pair, and drives the screen.** Five tests: a new account's `/profile` says nothing is banked yet and then, after a real game and a real `recordGameResult`, shows the five totals — one test rather than two, because the interesting property is the transition and two tests could each pass while the page was stuck in the state the other expected. Then the layout guard, which holds the `users/{uid}` read open with a `page.route()` so the loading state can be measured rather than raced and the card has to be the same height when the numbers land (`CLAUDE.md` §4.4); it **seeds** the totals through `firebase.seedGameplayStats` rather than playing for them, because the subject is the card and a game would cost fifteen seconds of numbers it never reads. Then the failed read, which is the state a test has to manufacture: a `page.route` refuses the `users/{uid}` request until the test lifts it, so the card has to say the read failed rather than that nothing is banked — the account has totals — and then the real "Try again" is clicked through to the numbers. It asserts where focus lands, which is the half no unit test can reach: jsdom neither computes `visibility` nor honours it in `focus()`, so only a browser can show that leaving focus on the button the retry hides would drop it to `<body>`. Then the anonymous visitor, who gets the explanation and a working sign-in button — every message is in the document at all times, stacked in one grid cell and separated only by `visibility`, so those assertions are `toBeVisible`/`toBeHidden` and an existence check would pass against any of them. And the mobile drawer, which is the only entry point to the page below `sm`.
- **The deletion test in `account-management.spec.ts` plays a game first, and that is not decoration.** It asserts the stats document is gone afterwards — an assertion that was **vacuous** as first written, because the document is created lazily and an account that never finished a game has none, so `null` after deletion would have passed against a `deleteAccount` that swept nothing. It is the single test standing behind a published policy promise, so it has to prove there was something to delete.
- **`game-resume.spec.ts` covers the whole of B8's persistence, not just the reload that found B11.** Six tests: reload mid-game on `/play`; reload a _finished_ game on `/game-over` (persisted deliberately, so a refresh does not lose a score about to be submitted); the setup screen's resume banner reached by a fresh page load, which is the path a PWA relaunch actually takes since it lands on `/` rather than `/play`; that a completed game is deliberately **not** offered as resumable; Discard, asserted against storage rather than against the banner disappearing, since clearing the signals without clearing the record would bring the game back on the next load; and a flag surviving a reload along with the chosen time limit. The banner carries `data-cy` hooks (`resume-banner`, `resume-game`, `discard-game`) so none of this selects on the words "Resume"/"Discard". Each test was mutation-verified on its own, and reintroducing B11 itself — `[ngValue]` back to `[value]` on the question-count picker — fails five of the six.
- **`streak-multipliers.spec.ts` and `streak-leaderboard.spec.ts`** cover `FEAT-004` at the two layers nothing else reaches. The first walks a round in a real browser — the badge appearing without re-wrapping the row it sits in, the run surviving a skip and resetting on a wrong answer, and the four numbers the results screen then reports. It is played with **no time limit on purpose**: it stops between questions to read a badge, and a 15-second countdown running underneath would make the deadline the subject of a test about something else, which is the shape of failure §4.3 already records once. Its layout assertion measures at **320px**, where the three badge pills do not fit on one line — at a larger phone width a conditionally-rendered badge would measure 0px of shift and the check would call the bug fixed while it was broken (`CLAUDE.md` §4.4); mutation-checked by wrapping the badge in an `@if`. The second is the two-ends check on the rules bound: a multiplied score saving against the real rules in the emulator, and a multiplied row rendering at the same height as an unmultiplied one, since the board holds both indefinitely.

- **`question-dedup.spec.ts` is the only place `FEAT-034` can be seen working at all.** The seen-set is IndexedDB, the marks are written as questions resolve, and the property is about the _second_ game a browser plays — so it needs a persistent context and a real bank, which no unit spec has. It seeds seven approved questions under a category it invents, plays three five-question rounds, and asserts the arithmetic that makes both halves of the rule observable at once: game two is the two never served plus the three answered _earliest_ in game one, and game three — with the whole bank now answered — is still five questions rather than a short game. Seven and five are chosen so the second game cannot be all-new; a larger bank would only prove the easy half. Played with **no time limit on purpose**, for the reason `streak-multipliers.spec.ts` is: fifteen questions in one test, and a countdown underneath each one makes a starved worker's lost question into a confusing failure about which questions were served. It is emulator-only — see the reason beside its entry in `playwright.preview.config.ts`.

- **`sound-effects.spec.ts` is the only place the audio graph is ever built.** Every cue path in `audio.service.spec.ts` runs under jsdom, which has no `AudioContext` at all — so the unit suite exercises the "no Web Audio" branch exhaustively and the oscillator code not once. This spec plays a round with Web Audio genuinely present and fails on any `pageerror` or script `console.error`, which is what a node scheduled in the past or a gain ramped to zero produces. **Two message classes are deliberately not failures**, and leaving either in makes it a test about something else. A browser that has not yet seen a user gesture _warns_ about a suspended context, which is the autoplay policy working. And Chromium logs a console **error** for every non-2xx response — including the `user_roles/{uid}` read that is absent for everybody who is not a reviewer — so `Failed to load resource` is filtered out and the URL is recorded for the errors that remain, since the browser's own text names no resource and a network failure otherwise reads as an application one. Its first round leaves question one to expire, because the countdown tick and the timeout cue cannot be reached by clicking and `page.clock` would replace the very timer under test (`CLAUDE.md` §4.6) — seventeen real seconds, which is why the rest of the round is folded into the same test. The drawer half measures the mute button's box in both states (jsdom has no layout) and reloads the page to prove the preference persists, which is the half a `TestBed` cannot claim since it writes the storage it then reads.
- **`boot-fallback.spec.ts` tests a failure the suite cannot otherwise reach: no application code running.** The pre-boot recovery notice (`app.md` §1.8) is markup in `index.html` revealed by a CSS delay, for the case where a stale service worker serves a cached document whose entry script no longer exists. The spec reproduces that with a route returning `404` for `**/main*.js` rather than with a worker, because the worker is not the mechanism under test and this runner registers none. Two tests, and the first matters most: **the notice is absent from the DOM on a normal load**, since Angular replaces `<app-root>`'s contents on bootstrap — a regression that leaked it into the running app would be visible to every user, and nothing else would catch it. The reveal delay is asserted on the computed `animation-delay` rather than by watching a clock, so the check does not depend on runner speed.
- **Nothing tests the recovery _within_ one test, and that gap is deliberate and unexplained.** Two versions were tried — clicking the reload link, and reloading after a one-shot 404 — and both fail on the assertion **after the second page load**, in CI and on a developer machine. The same sequence driven by hand in Chromium recovers correctly in every configuration tried: production build and `ng serve`, top-level and framed. **The cause is not understood** — it is not the element, the build, the framing, or the click. What matters for coverage is that the dropped test proved nothing new: that the link resolves to the app root is asserted without a second load, and that a load with the script available boots the app and leaves no notice behind is the first test. Its only unique contribution was a failure belonging to the runner. Worth generalising: when a composite assertion fails on the runner rather than the product, check whether its parts are already covered before spending more on the composition — here they were.
- Real bugs this suite has found and fixed: `PricingComponent` briefly misfiring "verify your email" for a click landing before the first auth state resolves (`app.md` §1.6); a race in `AuthService.ensureSignedIn()` where a returning user's persisted session could be clobbered by a fresh anonymous sign-in (fixed with `auth.authStateReady()`); and a stale-UI bug where linking an anonymous session to a real credential mutates the Firebase `User` object in place without firing `onAuthStateChanged`, so `isAnonymous`/`isFullyAuthenticated` never updated until fixed by explicitly re-pushing the user into the auth signal after linking.
- CI: `.github/workflows/e2e.yml` runs the suite on every PR targeting `main` (and on push to `main`), separately from the merge-to-deploy pipeline in §4.2 — including installing/building `functions/` first. Node 24 with the npm cache, Java 21, the emulator cache, a cache of `~/.cache/ms-playwright` keyed on the lockfile, and an `npx playwright install --with-deps chromium` step. It runs as a **matrix of two shards** (`e2e-shard`), each a full runner with its own emulators; `playwright.config.ts` reads the shard from `PLAYWRIGHT_SHARD` rather than a `--shard` flag, because the command line there belongs to `firebase emulators:exec` and a flag appended to `npm run e2e` would reach the wrapper instead of the runner. A third job, id `e2e` and therefore the required status check (§4.2a), `needs` the matrix, runs `if: always()` and fails unless every shard succeeded — a matrix job's own contexts carry the matrix value in their names, so no shard can be the required check on its own, and `always()` is what stops the gate being _skipped_ (which branch protection reads as success) when a shard fails. Each shard uploads `playwright-report/` and `test-results/` under a shard-specific artifact name on failure; the trace in the latter replays a failed run frame by frame with the DOM at every step, which is what makes a CI-only failure diagnosable without reproducing it.
- `npm run typecheck:e2e` (`tsc -p e2e/tsconfig.json --noEmit`) runs as a step of the `lint` job. `playwright test` transpiles specs without typechecking them, so without it a type error in the suite would surface as a runtime failure in a job that takes minutes, or not at all in a branch no test reaches.

#### The preview slice, against a real deployed channel

**A scoped slice of the same specs runs against a real deployed Hosting channel**, through `playwright.preview.config.ts` and `npm run e2e:preview`, behind the `E2E (preview)` job (§4.2a). It is deliberately narrower than the local suite, because this hits the real, persistent, publicly-readable `trivimind-dev` project: there is no throwaway emulator to reset, so every account and document a run creates has to be deleted again by name. 96 tests in eighteen files, in about a minute and a half on one runner.

- **The scope is per-spec rather than categorical.** Everything under `unauthenticated/` runs **except `question-reporting`** — it asserts the written report through an Admin-SDK read of `question_reports`, a collection only the appointed reviewers may read (implementing that against the real project would hand the preview suite console-level read access to real users' reports), and a report is keyed by nothing the sweep tracks, so its writes would outlive the run and leave real rows in the owner's review queue — and **except `boot-fallback`**, which cannot work here at all: `firebase.json` serves hashed JS as `max-age=31536000, immutable`, so against a real channel an earlier spec has already loaded the app and the browser satisfies the entry script from its own HTTP cache, the 404 stub never matches, and the wait fails with "No request ever occurred". That is a property of the deployment rather than of the spec, and the cost is that the preview suite does not check the recovery notice is absent on a healthy boot; the emulator suite does. It also runs **except `question-dedup`**, which buys nothing here and costs something: its subject is device-local IndexedDB — which questions this browser has answered — and the emulator exercises that identically, while the query shape and rules it rides on are already covered against the real project by `game-flow.spec.ts`'s custom-source game. Against `trivimind-dev` it would instead put seven approved questions into the shared bank on every PR and spend three full games of real Firestore reads restating a result the emulator already has. And **except `offline-play`**, which is emulator-only for a reason about the app rather than the data: its premise is that no service worker exists to re-issue the request it needs to fail, and on a deployed channel that holds only by accident (the bullet below). **`tag-filter` is out for one release only**, on the PR that introduces the composite index it needs: `deploy-preview` now creates the PR's indexes on `trivimind-dev` before the channel goes up (§4.2a), but an index _build_ is asynchronous, so the very first run after a new index is declared races it — and a `FAILED_PRECONDITION` there presents as an empty bank on a required check. Once the merge deploy has built the index the race is gone and the exclusion comes out; `playwright.preview.config.ts` says so at the line. From `authenticated/`, only `sign-in-save-score` and `profile` run. `sign-up-verify` and `password-reset` are out permanently — both read out-of-band action codes from the Auth emulator's testing-only `oobCodes` endpoint, which has no real-Auth equivalent without a live mailbox. `pricing` and `add-question-pro-gating` are out because Cloud Functions are not channel-scoped (§4.2a), so a preview build shares the _real_, already-deployed `createCheckoutSession`/`stripeWebhook`: the mock-mode checkout spec would either hit real Stripe or silently no-op depending on that deployment's own `STRIPE_MOCK_CHECKOUT` state, neither of which this suite should depend on. `account-management`, `lifetime-stats` and `profile-stats` are out for the same reason one step along — they drive the real `deleteAccount`, `exportAccountData` and `recordGameResult`. `review-queue` and `add-question-pro-gating` also submit questions through the UI, which gives them Firestore auto-ids that reach no sweep list; widening the slice to either means capturing what they write first. `streak-leaderboard` is out for a fourth reason worth naming on its own: **its subject is a `firestore.rules` bound**, and rules are per project, so on any PR that moves the multiplier ceiling it would fail here for a reason that is expected — a real signal turned into a red reviewers learn to ignore. The specs that do run against the real project write only documents `main`'s rules also accept: `sign-in-save-score` plays every game to a score no multiplier touches, and says so at the top of the file, because a perfect five-question round is exactly the entry that is legitimate on one side of a rules change and refused on the other.
- **The unauthenticated half is opt-out, which is the asymmetry to know before adding a spec.** A new file under `unauthenticated/` reaches the real project on the next PR unless `testIgnore` names it, while a new one under `authenticated/` runs nowhere near it until it is listed. That default is right for the specs there today — they visit pages and play games, so the footprint is the anonymous account every page load mints, which the sweep already tracks — but it is a claim about those specs, not a property of the glob: a new unauthenticated spec that seeds something, or writes through a path no sweep list covers, has to be excluded in the same PR.
- **The config is the emulator config plus a delta**, so the two cannot drift about what the suite _is_: same workers, same `retries: 0`, same timeouts, same Chromium, same `data-cy` test-id attribute. What it overrides is the `baseURL` (from `PREVIEW_URL`, which it refuses to start without), `testMatch`/`testIgnore` for the slice above, the `firebaseTarget` option, and `webServer: undefined` — the app under test is the deployed channel, and starting a dev server would quietly give the suite a second app to talk to, built against emulators that are not running.
- **`e2e/fixtures/firebase-preview-target.ts` is the other half of the `FirebaseTarget` seam**, so every spec body and every helper is written once and runs against either backend. It refuses three things rather than guessing at any of them: a missing `FIREBASE_PREVIEW_PROJECT_ID` (there is no value it could safely default _to_ — the only obvious one is the project it used to be hard-coded to); the production project, which it reads out of `.firebaserc` rather than restating, so the guard cannot end up naming a project nobody uses and `npm run env:verify`'s rule that no `e2e/fixtures/*.ts` may name production needs no exception carved out of it; and a set `FIRESTORE_EMULATOR_HOST`/`FIREBASE_AUTH_EMULATOR_HOST`, which would point the Admin SDK at an emulator while the browser talks to the real channel — seeding nothing the app can see and, worse, sweeping nothing the run created.
- **The sweep deletes what the run created, and fails the job when it cannot.** Everything it visits is keyed by something this run brought into existence — a uid that did not exist beforehand, or a document id the run chose — so it cannot reach a real visitor's data even if the list is wrong. Per tracked uid: the Auth account, `users/{uid}` (lifetime totals, written by `recordGameResult` the first time a signed-in account finishes a game, and otherwise orphaned beyond the reach of `deleteAccount`), `user_roles/{uid}`, `customers/{uid}` recursively (a document delete in Firestore does not remove the subcollection beneath it), and a leaderboard row on **every** board rather than the one the spec wrote to. Plus every seeded `custom_questions` id, and leaderboard rows for uids that were seeded without ever being accounts. Each delete is caught on its own so one failure cannot abort the rest, and the failures are then reported together with their paths — because a best-effort sweep that stays quiet is exactly how C6 went unnoticed for months.
- The two authenticated specs' fixture identities are unique per run — a timestamped uid and a short tag in the **displayed** leaderboard name, not only in the uid behind it — so two preview deploys running concurrently against the same real project never race on the same document, and an assertion that addresses a row by the text it shows cannot pass against the other run's row. The tag is short on purpose: `firestore.rules` caps a leaderboard name at 30 characters and the input carries `maxlength="30"`, so a long suffix is truncated by the browser before it is written and the assertion then looks for a string nothing shows.
- **There is no `/__/` workaround here**, because there is nothing to work around: Playwright reserves no URL prefix, so the app fetches its own runtime config from the channel exactly as a visitor does, and the spec that needs the deployment's identity reads `/__/firebase/init.json` through the `request` fixture directly.
- **`service-worker-oauth-origins.spec.ts` is one of the two specs that run here and _not_ locally**, and one of the two that register the service worker. It is regression cover for PR #112: `ngsw-worker.js` re-fetches every request from inside the worker, where `connect-src` is the directive that applies, so an origin allowed only by `script-src` loads fine until the worker takes control and then fails as a synthetic 504 — which is how Google sign-in broke. It is excluded by name from `playwright.config.ts` (nothing on a dev server for it to test: no `ngsw-worker.js` is emitted under the `e2e` build, and no `firebase.json` headers are served) and let back in by the preview config replacing that list. **It imports `findCspProblems`/`findDeploymentOriginProblems` from `scripts/csp-rules.mjs` rather than restating the rule**, and applies them to the header a deployed channel actually serves; `npm run csp:verify` applies the identical functions to the policy written in `firebase.json`. That split matters because they answer different questions — a `**` rule that stops matching, a deploy that didn't take, or a CDN rewriting the header are all invisible on disk — but it only stays one rule if there is one copy. There were two for the span of a single PR (#114 copied it, #113 then corrected it in the script alone) and they had already drifted about `frame-src`, `default-src` and directive-name casing. It also recomputes the worker's policy fingerprint with `node:crypto`, from the header actually served rather than from `firebase.json` — a stamp describing a policy nobody serves is no protection. It registers the worker explicitly, because `app.config.ts` gates registration on `!navigator.webdriver`; there is no teardown, because the registration belongs to the test's own `BrowserContext` and is discarded with it. The header assertions go through the `request` fixture, since reading a response header is not something a page can do for itself, while the in-browser probes run under the policy actually being enforced. Both halves were mutation-checked: reverting #112 fails the test naming both origins, removing the registration fails the in-browser test on "the page is controlled by a service worker", and pointing a probe at an unreachable origin fails it on the real synthetic 504.
- **`service-worker-precache.spec.ts` is the other one**, and it is here for the same structural reason: `ng serve --configuration=e2e` emits no `ngsw-worker.js` and no `ngsw.json`, so there is no install to inspect. It registers the worker by name, waits for ngsw's own `/ngsw/state` to report `Driver state: NORMAL`, then reads the manifest the worker installed from and asks Cache Storage whether each game-route chunk is actually there — and whether the deferred ones, which nobody has visited, are actually not (`app.md` §1.8).
  **It asks Cache Storage rather than cutting the network and playing a round, and that is a finding rather than a shortcut.** `context.setOffline(true)` is emulated on the _page's_ network context; a service worker has its own, and Playwright leaves it connected. Both consequences were measured here. Against a build with `/play` and `/game-over` deliberately demoted to the lazy group, a round played "offline" still passed, with the origin's log showing it serving both chunks mid-test — so the round could not have caught the regression it was written for. And on a runner with real egress the app's own `opentdb.com` request came back through the worker as well, so the offline pool was never reached and the round failed on an offline banner that had no reason to appear. Playing with no network is covered where it can be made to mean something: `offline-play.spec.ts`, on the emulator, where there is no worker to re-issue anything.
- **`offline-play.spec.ts` covers that other half, on the emulator, and is excluded from the preview config by name.** Its premise is that no service worker exists to re-issue the request it needs to fail, and on a deployed channel that holds only because nothing there registers one — an accident rather than a guarantee, so it is written down in `playwright.preview.config.ts` beside the other exclusions. It plays one round online — which is what loads the `/play` and `/game-over` chunks, and is also the state a player who was already playing when the signal went is in — then seeds the offline pool, revokes the Open Trivia stub with an aborting route, goes offline, and plays a second round from storage. The revocation is load-bearing and was mutation-checked: `page.route` fulfils without touching the network, so a stub left in place goes on answering perfectly while the test believes it has cut the connection. The offline banner is what distinguishes a round served from the pool from one that quietly succeeded.
- Credentials: `FIREBASE_SERVICE_ACCOUNT_TRIVIMIND_DEV`, written to a temp file and picked up via `GOOGLE_APPLICATION_CREDENTIALS` (Admin SDK default credential lookup) — never the `FIRESTORE_EMULATOR_HOST`/`FIREBASE_AUTH_EMULATOR_HOST` env vars the emulator target relies on. Run locally with `PREVIEW_URL` and `FIREBASE_PREVIEW_PROJECT_ID` set; `GOOGLE_APPLICATION_CREDENTIALS` matters only for the specs that seed.

### 4.4 Lighthouse CI (performance / accessibility / best-practices / SEO)

- `lighthouserc.json` drives both local (`npm run lighthouse`) and CI (`.github/workflows/lighthouse.yml`) runs identically: builds with the dedicated `lighthouse` Angular configuration (same optimizations/budgets as `production`, but with `fileReplacements` swapping in `environment.e2e.ts` like the `e2e` config does — see §4.5), starts the Firebase Emulator Suite (`hosting`, `auth`, `firestore`) via `firebase emulators:exec --project demo-trivia-app-e2e`, and runs Lighthouse 3× against `http://127.0.0.1:5000/` (the Hosting emulator, serving the real build), asserting each category's **median** score — `aggregationMethod: "median"`, set explicitly, because the default is `optimistic` and asserts the _best_ run (see below).
- **This intentionally serves from the Hosting emulator, not a bare static server**: only Hosting (real or emulated) resolves the reserved `/__/firebase/init.json` endpoint, so this is what lets `FirebaseAppService` actually initialize and `AuthService`/`FirebaseService` actually run anonymous sign-in and Firestore reads against the local emulators — exercising the real runtime code paths instead of everything failing silently. An earlier version of this check served a bare static build instead; that setup measured a _better_ best-practices score (Firebase never initialized at all, so nothing could log a runtime error) which would have masked exactly the class of regression this check exists to catch — first caught when a real Chrome DevTools run against the live production URL showed something not reflected by CI at all (turned out to be an unrelated noisy manual run — see below — but the gap in methodology was real).
- **The Lighthouse run serves through a _derived_ Hosting config**, `firebase.lighthouse.json`, generated from the real `firebase.json` by `scripts/make-lighthouse-firebase-config.mjs` and gitignored. It differs in exactly one way: `connect-src` gains `http://127.0.0.1:9099` and `:8080`. This check is the only one that builds with emulator endpoints (`environment.e2e.ts`) _and_ serves through production headers, and those emulator ports are separate origins from the page's own `127.0.0.1:5000`, so `'self'` does not cover them and the CSP refuses every Firebase request. Widening the real policy would ship a production CSP letting injected script reach services on a visitor's own machine; dropping the auth emulator would remove what this check exists to exercise; lowering the threshold is forbidden (`CLAUDE.md` §3). Deriving keeps the production policy authoritative with no second copy to drift, and everything else about the CSP is still exercised exactly as production has it — which is what caught the logo's inline `style` attribute.
- **`aggregationMethod` is set to `median` explicitly, and this file used to claim it already was.** The Lighthouse CI default is `optimistic`: for a `minScore` assertion it takes the most favourable run, so three runs of 0.84/0.66/0.62 passed a 0.75 threshold on the strength of the 0.84. Verified rather than inferred — replaying one CI batch (0.68/0.92/0.91) through `lhci assert` at `minScore: 0.92` passes under the default and fails under `median` with `found: 0.91`.
- **`pessimistic` was considered and rejected on the data.** Downloading the reports from three real CI runs showed the _first_ run of every batch is a cold-start outlier — 0.90, 0.68, 0.52 — while runs 2 and 3 sit at 0.91–0.92 every time. Asserting the worst run would fail constantly for reasons that have nothing to do with the code. Median over three runs discards exactly one outlier, which is precisely the shape of this noise; two bad runs still fail, which is the point.
- Thresholds: performance ≥ 0.85 (raised from 0.75 in the same change, since a threshold set to survive optimistic aggregation is not the same as one set against the median — observed CI medians were 0.92/0.91/0.92 and local 0.93 when it was set, so 0.85 looked like roughly 0.06 of headroom while still catching a real regression — **that headroom is gone, and the paragraph below records what replaced it**); accessibility/best-practices/SEO ≥ 0.95, left where they were (all measure a clean 1.0 in every local and CI run). Raising them to 1.0 would change nothing in practice: each category has few enough audits that a single failure drops it to roughly 0.93, already under 0.95 — which is exactly how the CSP's console error was caught. Performance measured 0.77–0.89 across local + emulator-backed runs while Inter was hot-linked from Google Fonts (and under optimistic aggregation, so those numbers flattered the build); self-hosting it (`stack.md` §2.1) moved that to ~0.91, and turning off critical-CSS inlining for the CSP (§4.1) to a very stable **0.93 / 0.93 / 0.93**. The tighter spread matters as much as the higher number: removing two preconnects and a render-blocking stylesheet from the critical path took out the most machine-dependent part of the measurement. The 0.75 threshold is deliberately left alone here — it is now very slack, but re-baselining it belongs with **D6** (which has to fix `aggregationMethod` first, since asserting the _best_ of three against a raised threshold would be worse than the current slack one).
- **The performance gate is marginal on CI runners, and it fails on unchanged artifacts.** Measured 30 August 2026 on [#148](https://github.com/shermam/trivia/pull/148), whose diff is one e2e support file and one document — **no input to `ng build`, so the artifact was identical to `main`'s** — the three runs scored **0.81 / 0.84 / 0.89**, a median of 0.84, and the job went red. Re-running the same job on the same commit passed. Around the same window: `main` itself measured medians of 0.85 / 0.82 / 0.83 across three interleaved local rounds on a shared sandbox, while a quiet developer machine measured **0.92 on every one of twelve runs, with zero spread**.
  So the number is not drifting — the _variance_ is machine-dependent, and the 0.85 line sits inside the range a loaded runner produces. Two practical consequences. **A red `lighthouse` check is no longer evidence on its own**: before treating one as a regression, check whether the diff contains any input to `ng build` at all, because a docs- or test-only change cannot move the score. And **the cost lands on whoever is holding an unrelated PR**, who has to prove a negative each time.
  Deliberately **not** fixed by lowering the threshold, which would trade a false alarm for a blind spot and is what `CLAUDE.md` §3 forbids. The real fix is headroom, which is `FEAT-017`'s subject — its §0 records that ~1300 ms of the ~1900 ms FCP is JavaScript execution, so the room exists. Until then this paragraph is what stops the next person re-deriving it.
- A clean, extension-free, headless CLI run (`npx lighthouse <url> --chrome-flags="--headless=new"`) against the real deployed site is the trustworthy way to spot-check a production regression — a manual Chrome DevTools run can be skewed by browser extensions, a non-Incognito profile, or leftover site data, none of which reflect a real visitor's or CI's measurement.
- Reports (HTML + JSON) are uploaded as a `lighthouse-reports` build artifact on every CI run, pass or fail.

**`motion:verify` scans `src/app/**/*.{html,ts}`, not the templates alone.** A Tailwind class list is as often computed in a component as written in a template — a `switch` returning one string per state, a `[ngClass]` binding built in TypeScript — and a `.html`-only glob cannot see any of it. That is the difference between a guardrail and a comment: the rule it enforces is invisible to whoever breaks it (an ungated animation looks perfect to the author, the reviewer, Lighthouse and the e2e suite unless the OS setting happens to be on), so a hole the size of "put the class in a variable" would not be noticed from the outside. The same patterns run over both file types; turning the TypeScript half on found no offence other than the one it was added for.

**Both deploying builds go through `scripts/build-with-commit.mjs`**, which passes the current commit to `ng build --define` so `src/app/build-info.ts` can name it and the footer can show it on hover. Three decisions worth not re-litigating:

- **`--define`, not a generated source file.** esbuild substitutes the identifier in the emitted JavaScript, so there is nothing on disk to generate, gitignore, keep in step, or accidentally commit with a real hash in it — and a fresh clone type-checks with no build step having run.
- **The commit _date_, never a build timestamp.** A clock in the bundle makes every rebuild of the same commit emit different bytes, hence a different content hash, a different `ngsw.json`, and a service-worker update pushed to every client for a deploy that changed nothing. The commit date answers the same "how stale is this?" question and is a property of the commit.
- **A script rather than `$(git rev-parse …)` inline in `package.json`.** npm runs scripts through `cmd` on Windows, where neither `$( )` nor `git log --format=%cd` survives — and the fallback belongs somewhere with `try`/`catch`, because building outside a checkout (a source tarball, a Docker context with no `.git`) has to degrade to an unstamped build rather than fail. `ng serve`, `ng test` and plain `ng build` pass no define at all, so the footer reads "local build" there; `build-info.spec.ts` runs under exactly that condition, which makes the undeclared-identifier path real rather than simulated.

**`ng test` runs with `--isolate` defaulting to _false_, so spec files are not independent.** Vitest's Angular builder documents the default as aligning with the Karma/Jasmine experience: spec files share a worker's module registry, which means they share the module-level state of everything they import. `fake-indexeddb/auto` is the case that bites — seven spec files import it, and they get **one** in-memory IndexedDB between them, so a unit test that writes real storage is not local to its own file.

That produced a ~40% flake with no local cause. `game-controller.service.spec.ts` did not stub `DailyGameLimitService`, so each of its five `startGame()` calls spent a real game against the real quota and persisted the count under today's date. Whenever that file ran before `daily-game-limit.service.spec.ts` in the same worker, the latter's **first** test opened on an exhausted allowance and failed with `expected +0 to be 5` — a failure naming a service the other file never mentions. Fixed on both sides, which is the shape worth copying: the controller spec stubs the collaborator it was never testing, and the daily-limit spec resets the counter in `beforeEach` as well as `afterEach`, so it does not depend on the next file to touch storage remembering to clean up. **A spec that leaves state behind is a defect in a file you have not opened.**

**`src/test-setup.ts`** is wired in as `setupFiles` on the `test` target in `angular.json`, and exists for one reason: **jsdom is not a browser**, and the honest place to say so is the test environment rather than the application. It currently shims `window.matchMedia`, which jsdom does not implement at all — calling it throws, which is how adding a breakpoint listener to `TopBarComponent` broke four unrelated `app.spec.ts` tests. The alternative was a `typeof window.matchMedia === 'function'` guard in the component: production code shaped around a test runner's gap, in a branch that would then never be exercised by anything. Anything added here should carry the same justification, and a spec that needs to _drive_ the shimmed API replaces it locally rather than making this one cleverer.

Package manager is pinned via `"packageManager": "npm@11.12.1"`. `functions/` is a separate npm package with its own `package.json`/lockfile (standard Firebase CLI convention), so the root `npm install`/`npm ci` doesn't reach it on its own — a root-level `postinstall` script closes that gap automatically (first materializing `functions/.secret.local` from its committed template — see `stack.md` §2.4 — then running `npm run functions:install`) so a plain `npm install` at the repo root is enough for `npm run functions:build`/`npm run e2e` to work right after cloning, without a separate manual step. That hook runs **`npm ci`**, not `npm install`: it used to be the latter, which meant every `npm ci` in CI — the command whose entire purpose is a reproducible tree — silently ran a non-deterministic install in `functions/` that was free to rewrite `functions/package-lock.json` as a side effect. The trade-off is that editing `functions/package.json` now makes the next root install fail loudly with an out-of-sync lockfile error; `npm run functions:install:update` is the deliberate escape hatch for that case, and the failure is the point — a lockfile should only change when someone meant to change it. `npm run e2e`/`npm run e2e:open`/`npm run rules:test` call the `firebase` binary directly, `firebase-tools` (`^15.26.0`) being a real `devDependency` (`stack.md` §2.2, including the JDK 21 those scripts now need locally) instead of an `npx`-fetched tool. `npm run lighthouse` still uses the older `@13` major, which can't also be a `devDependency` alongside `@15`, so it stays on `npx --yes firebase-tools@13` — the `--yes` skips npm's interactive "ok to install?" prompt the first time that pin isn't already in the local npx cache (CI's shell is non-interactive, so it never saw that prompt either way; this is purely a local-DX fix).

### 4.6 Environments

- `.firebaserc` pins the default Firebase project to `intellectura-3b26a`. It is the only one named there; `trivimind-dev` is addressed by explicit `--project` flags in the npm scripts and workflows that target it (see `dev-environment.md`).
- `src/environments/environment.ts` / `environment.development.ts` carry `production` and `useEmulators` flags — no secrets or API keys live here, consistent with the runtime-config-fetch approach described in `stack.md` §2.3.
- `src/environments/environment.e2e.ts` sets `useEmulators: true` and is swapped in only by the `e2e` build/serve configuration (`angular.json`, `fileReplacements`) the e2e suite serves the app with (§4.3) — never by `start`/`build`/`build:prod`.
- Production build budgets (`angular.json`): 500 KB warning / 1 MB error (initial bundle), 4 KB warning / 8 KB error (per component style); output hashing enabled for cache-busting.
- `functions/` has its own env layer (`stack.md` §2.4): `.env.demo-trivia-app-e2e` (committed, non-secret — sets `STRIPE_MOCK_CHECKOUT=true`) and `.secret.local` (gitignored, generated by the root `postinstall` from the committed placeholder template `.secret.local.example` — the pin that keeps the emulator from fetching real secrets, and the one safe place for real test-mode keys). Everything else under `functions/.env*`/`.secret.local` is gitignored — see the comments in `functions/.gitignore` for why `.env.demo-trivia-app-e2e` and the `.example` template are the only committed exceptions.
