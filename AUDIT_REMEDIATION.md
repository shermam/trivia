# Audit Remediation Plan

A full audit of this repo (security, correctness, data model, CI/CD, testing, accessibility, product/compliance) produced **55 findings**, and fixing them has since surfaced two more, and one turned out to be two, and production surfaced one the audit never had — **59** in the register today. They are being fixed as a series of small, individually-reviewable pull requests.

This file is the **shared source of truth** for that work: what was found, what is done, what is next, and the decisions taken along the way. It is deliberately in the repo rather than in any assistant's private memory, so progress is reviewable and the work can be picked up in a new session — or by a different person — without reconstructing context.

Related documents:

- **`CLAUDE.md` §4** — the invariants these fixes establish, written as a contract so they can't silently regress.
- **`INFRASTRUCTURE.md` §10** — the infra-layer counterpart.
- **`docs/known-gaps.md` §6** — Known Gaps, the running record of what is still open in the product itself.
- **`FIRESTORE_SDK_VS_REST.md`** — a costed comparison of replacing the Firestore client SDK with its REST API, written after B6 showed the SDK offers no cancellation. Not scheduled; read it before anyone proposes the migration, and before assuming the SDK's offline cache is doing something here (it is switched off).

## 2. How to resume this work in a new session

Start a new Claude Code session in this repo and paste something like:

> Read `AUDIT_REMEDIATION.md`, then continue the audit remediation from where it left off. Follow the working rules in §3 and pick up the next item in §5.

That is enough. The assistant will read this file, `CLAUDE.md`, and `PROJECT_OVERVIEW.md`, and has everything it needs.

**To work on something specific instead**, name the finding ID:

> Read `AUDIT_REMEDIATION.md`, then fix finding **B3** (cached rejected promise in `TriviaService.getCategories`). One PR, branched fresh off `main`.

**Useful things to say when resuming:**

| You want                    | Say                                                                |
| --------------------------- | ------------------------------------------------------------------ |
| Just keep going             | "Continue from §5, next unstarted item."                           |
| A specific finding          | "Fix finding **A6**."                                              |
| Several small ones together | "Fix **B6** and **B7** in one PR — they're both one-line changes." |
| Re-prioritise               | "Do the accessibility findings (G1–G6) next."                      |
| Check state                 | "What's the current status of the audit remediation?"              |

**Keep this file current.** Every PR in the series should update §1 and §5 as part of the change, the same way `CLAUDE.md` §2 requires `PROJECT_OVERVIEW.md` to be updated. A stale plan is worse than none.

Two things this series learned the hard way, both worth carrying:

1. **The emulator cannot see index configuration, and CI is not the only thing that can break silently.** A `firestore.indexes.json` mistake took the production deploy pipeline down for four merges while Hosting kept shipping; `--dry-run` reported success throughout. 2. **Verify in the thing you are changing.** Two bugs this session — a corrupted `localStorage`, and a skip link that announced a page change that had not happened — passed unit tests and were only found by driving a real browser. Where a change is CI-only or focus-related, get it into a suite that can be run locally before shipping it.

## 3. Working rules

Agreed at the start of the series and unchanged since:

1. **One PR per finding**, except where two findings edit the same lines and can't be reviewed apart. Roughly ~25–30 PRs for 56 findings.
1. **Branch fresh off `main`** by default. Stack only when a conflict is genuinely unavoidable, and say so in the PR body.
1. **Integrate `main` by rebasing**, never by merging `main` into the branch. Push with `--force-with-lease`, and re-run the verification gates _after_ rebasing — integrating `main` is exactly where a newly-added gate breaks.
1. **Risk-scoped verification** (`CLAUDE.md` §3a): the full four-command suite for anything touching `src/app/`, `firestore.rules`, `firebase.json`, or `functions/src/`; unit + functions + build only for docs/CI/config-only changes. Always name which commands ran in the PR body.
1. **A `firestore.rules` change ships with rules tests, and the rules get mutation-tested** — break the rule on purpose, confirm a test fails, restore. A rules suite that passes against broken rules is worse than none.
1. **New CI checks get their own workflow**, even though that means a manual step to add them to the ruleset. One workflow per concern; a bundled check produces a muddier signal permanently to save a one-off settings change.

### Verification commands

```bash
npm run format:check   # Prettier
npm run lint           # ESLint + angular-eslint
npm test               # Vitest unit suite
npm run functions:test # Cloud Functions unit tests
npm run rules:test     # firestore.rules suite against the Firestore emulator
npm run e2e            # Cypress against the full Firebase Emulator Suite
npm run lighthouse     # Lighthouse CI
```

Approximate local cost: e2e ~4m, Lighthouse ~2m15s, rules ~6s, everything else seconds. Verification **cannot be parallelised** — the emulator ports are fixed, so two suites on one machine collide.

### What A2 + A3 + A7 actually shipped

Two things were worth more than the plan anticipated, and one was a trap.

**The strongest fix for three of the four A2 fields was to stop accepting them.** `mode` had exactly one possible value; `success_url`/`cancel_url` had exactly one possible shape. Validating them would have been busywork guarding a field nobody needed — removing them means there is no client-chosen value left on that path to get the validation wrong about. Only `price` survives as client input, and only because keeping it avoids reaching into two unrelated findings (§4).

**The A3 cap needed a mechanism, not a threshold.** The obvious reading of "add a rate limit" is a number, but rules have nothing to count with. The document ID turned out to be the whole answer: `create` is the one verb that already refuses to run twice on the same name, so a name derived from server time _is_ a counter, at zero extra reads. The cost is that the client has to derive the same name from its own clock, which is why the window is 5 minutes wide and ±1 window is tolerated — the same skew `isNearRequestTime()` already accepts.

### What A4 + A5 actually shipped, and the finding it produced

**A4 was bigger than the register said.** The finding named `setCustomUserClaims(uid, null)` as the destructive call. It is — but so is the other branch: the API replaces the entire claims object, so `setCustomUserClaims(uid, { stripeRole: 'pro' })` erases every claim that isn't `stripeRole` just as completely. Both paths now go through a read-merge-write. Worth noting _why_ this was invisible: with exactly one claim in the system, both calls are correct by accident. The bug activates the day someone adds a second claim, in a file they didn't touch, on the next webhook delivery.

**A5 is narrowed, not closed, and the invariant that specified it was overconfident.** `CLAUDE.md` §4.2 said revoking a privilege "revokes the token that carries it". `revokeRefreshTokens` does not do that: it invalidates refresh tokens, so the user cannot mint a new ID token and is forced to re-authenticate — but the ID token already in their browser keeps asserting `stripeRole: 'pro'` until it expires, and **`firestore.rules` does not check revocation**. So a lapsed subscriber can still write a custom question for up to an hour. That is a real improvement over doing nothing, and it is not what the invariant claimed. §4.2 has been rewritten to say what revocation does and does not buy, per §4's own rule about not leaving silent exceptions.

The residual is now **A13**. It is closable: `request.auth.token.iat`, `auth_time` and `exp` were all probed against the emulator and are addressable in rules. Two mechanisms, neither free, which is why it is its own decision rather than scope creep here:

- **Compare `iat` against a server-written "entitlement changed at" timestamp.** Exact, but costs a `get()` — one billed read on every privileged write.
- **Require a freshly-issued token for privileged writes** (`iat` within N minutes). Costs nothing, and `AddQuestionComponent` already force-refreshes immediately before its write, so the client satisfies it today. But it couples the rules to that client behaviour, and a failed refresh becomes a rejected write.

### What B1 + B2 actually shipped

**Bundled because they are the same lines**, not merely the same area: both live in how an answer is rendered and identified.

**B1 was two bugs from one cause** — the answer's display text was also being used as its identity _and_ as the way to decide whether it was correct. A question carrying the same text twice therefore produced duplicate `@for` track keys and let the wrong option score as correct. Answers are now `{ id, text, isCorrect }`, with ids derived from position in the source arrays rather than from text.

**Fixed at both ends, on purpose.** `firestore.rules` now rejects a `custom_questions` write whose `correct_answer` appears among the incorrect ones, or that repeats an incorrect answer — but questions also come from Open Trivia DB, which this app doesn't control, and the bank already holds documents written before the rule existed. Fixing only the writer would leave the reader wrong for data that already exists; fixing only the reader would leave the ambiguity in the data for the next reader to rediscover.

**B2 was fixed by deriving rather than by extending.** `ANSWER_LABELS` had four entries while the rules permitted six answers. Rather than add two letters, the label is computed from the index, and the rules ceiling is tightened to the three incorrect answers the form can actually produce — so the two can't disagree again.

**One migration fell out of it.** `all_answers` is persisted in the offline IndexedDB pool, so entries cached under the old shape would render `undefined` for every option. The store is recreated on upgrade rather than migrated: it is a cache, and one refill is cheaper than a migration that would never be exercised again. The tests were pinning `indexedDB.open(name, 1)` and had to stop naming a version at all.

### What D6 actually shipped

**The default really is `optimistic`, and it was verified rather than inferred.** Replaying one real CI batch (0.68/0.92/0.91) through `lhci assert` at `minScore: 0.92` passes under the default and fails under `median` with `found: 0.91`. Same three reports, same threshold, opposite verdicts.

**`pessimistic` looked like the obviously stricter choice and would have been wrong.** Downloading the reports from three real CI runs — the workflow has been uploading them as artefacts all along — showed the _first_ run of every batch is a cold-start outlier: 0.90, 0.68, 0.52, against a steady 0.91–0.92 for runs 2 and 3. Asserting the worst run would have failed constantly for reasons unrelated to the code. Median over three discards exactly one outlier, which is the shape of the noise; two bad runs still fail.

**The threshold had to move in the same change.** 0.75 was chosen to survive optimistic aggregation, so leaving it under median would have quietly kept the gate slack. Raised to 0.85 against observed CI medians of 0.92/0.91/0.92 — about 0.06 of headroom, enough to absorb runner variance and still catch a real regression. The other three categories stay at 0.95: each has few enough audits that one failure drops it to roughly 0.93, so 0.95 already catches anything 1.0 would.

### What A8 + A9 actually shipped

**The CSP has no `unsafe-inline`, no `unsafe-hashes` and no hashes at all** — which was not the expected outcome. Angular's production build emitted a 10 KB inline `<style>` _and_ a `<link … media="print" onload="this.media='all'">`, and that `onload` is an inline event handler: under a strict `script-src` it is refused, the stylesheet never switches off `media="print"`, and the app renders with critical CSS only. So the choice looked like `'unsafe-hashes'` plus `style-src 'unsafe-inline'`, or turning `inlineCritical` off and paying for it in performance.

Measuring first turned out to be worth more than reasoning about it: **disabling `inlineCritical` is free here** — 0.90/0.94/0.91 with it on versus 0.89/0.94/0.92 with it off, inside run-to-run noise. The purged Tailwind stylesheet is small enough that inlining part of it and deferring the rest buys nothing. A strict CSP cost nothing at all.

**The theme script moved to an external file rather than taking a hash, because a hash fails silently.** Breaking one on purpose showed the browser refusing the script while the app still boots and still ends up correctly styled (`ThemeService` reapplies the class), leaving only a first-paint flash — no console error, no Lighthouse movement, no failing e2e. A guard test was written and then deleted: it needed `node:fs` in a spec, and the Angular app tsconfig has no Node types, so adding them would have let app code reference Node APIs and still typecheck. Removing the failure mode beat guarding it, and it matches how A7 was solved — make it structurally impossible, don't detect it.

**The first attempt shipped red, and the Lighthouse job is what caught it.** Two violations, both real, and both invisible to the way it was verified — a hosting-only emulator serving against _real_ Firebase, where every origin was allowed and no emulator ports were involved:

- **The brand mark carried an inline `style` attribute** (`fill:#ffffff` plus Inkscape residue). Refused under `style-src`, which drops the declarations while leaving the attribute in the DOM, so the white glyph rendered in the inherited colour and `getAttribute('style')` still returned exactly what was written. Fixed by making it a presentation attribute — the right fix, since relaxing the policy for it would have permitted every style attribute in the app. Worth noting the quiz progress bar's `[style.width.%]` binding is _not_ affected: Angular sets that through CSSOM, which CSP does not govern. Confirmed by watching for violations while playing a game.
- **`connect-src` refused the Auth emulator.** The Lighthouse build points at emulators on `127.0.0.1:9099`/`:8080` while serving through production headers, and those are separate origins from the page's `127.0.0.1:5000`. Resolved with a derived config rather than by widening the shipped policy — see `docs/ci-cd.md` §4.4.

**And a lesson about the verification itself.** Both were reported locally as passing, because the script reading `.lighthouseci/*.json` did not clear the directory first and picked up reports from an earlier, pre-CSP run. A green result was reported that was never green. Anything that reads build artefacts has to delete them first; a stale artefact is indistinguishable from a passing one.

**Two CSP entries are untestable here and were taken from the repo's own records.** `script-src https://apis.google.com` and `frame-src <authDomain>` exist only for the OAuth popup resolver, and OAuth sign-in is not in the e2e suite (a documented gap). They come from the network trace recorded in `docs/app.md` §1.5 rather than from a fresh observation — driving a real Google popup would have created a real user on the production project. They want a manual sign-in check after deploy.

### What H5 actually shipped

**The guidance in `INFRASTRUCTURE.md` §2 said to do the opposite, and was wrong.** It advised loading a brand font from Google Fonts via a preconnected `<link>` and treating the Lighthouse budget as the guardrail. No performance budget catches a legal exposure — that bullet is now rewritten to say self-host, with the reasoning, so a future project scaffolded from that file doesn't inherit the same finding on day one.

**Vendored rather than `@fontsource`**, chosen deliberately over an npm dependency: this repo already avoids one for icons (inline SVG, not `lucide-angular`), for Firebase (no AngularFire) and for IndexedDB (raw API), and a font is static bytes with no reason to be an exception. The SIL OFL text ships beside the files, which the licence requires of anyone redistributing them.

**Two subsets, not one, and the extra one is free.** `latin-ext` is 85 KB against `latin`'s 48 KB, which looks like a poor trade for an English trivia app — except `unicode-range` means the browser never fetches it unless a glyph in that range is actually rendered. Verified in a real browser rather than assumed: the page loads with `latin` alone, and `latin-ext` appears in the network log the moment an `Ā` is put on screen. It matters because `custom_questions` is user-authored.

**The filenames carry Google's `v20` revision.** `public/` is copied into the build verbatim with no content hash, while `firebase.json` serves `woff2` as `immutable` for a year — replacing a file in place would be invisible to every returning visitor for that year. The refresh procedure is in `public/fonts/README.md`, which is excluded from the deployed bundle while `LICENSE.txt` deliberately is not.

### What A6 actually shipped

**The idempotency record the finding asked for turned out to be the wrong mechanism.** Every write in the handler is already a `set(..., {merge:true})` or a `delete()`, so a redelivery changes nothing — duplication was never the bug. Ordering was: Stripe guarantees at-least-once and says nothing about order, so a stale `cancelled` could land on a fresh `active` and the `stripeRole` claim would then be recomputed from the older truth. A global processed-event log would have needed its own collection, its own TTL (cf. C2), and a read on every delivery to answer a question no document actually asked. A **per-document high-water mark** — the `created` of the event that last wrote it — covers both, and `CLAUDE.md` §4.3 already specified it that way.

**Deletes are the awkward case and needed the same guard.** Deleting a document takes its high-water mark with it, so a late `product.deleted` arriving after the product was recreated has nothing left to compare against. Deletes therefore go through the same transaction, checking the mark before removing the document.

**The `livemode` check shipped wrong and was fixed in a follow-up ([#52](https://github.com/shermam/trivia/pull/52)).** It derived the expected mode from the project ID — a real project must mean live — which is false on this very project: production deliberately runs an `sk_test_` key before launch (`docs/known-gaps.md` §6, recorded in [#50](https://github.com/shermam/trivia/pull/50) hours after A6 merged). The rule therefore refused _every_ genuine delivery, and the symptom would have been a completed checkout silently never granting Pro. Nothing was actually dropped — no events arrived between the deploy and the fix — but that was luck, not margin.

The expectation now comes from the deployed secret key's own `_live_`/`_test_` infix. That is the right authority because it _defines_ which Stripe the deployment talks to, so the check cannot contradict reality; the project ID was a guess about configuration that configuration was free to disagree with. Generalised into `CLAUDE.md` §4.2 as its own invariant, because "am I in production" gating on an environment's _name_ rather than its _credential_ is a shape that will recur.

**The `livemode` check acknowledges rather than rejects.** Returning 4xx would make Stripe retry and eventually disable the endpoint, and there is nothing to retry — the delivery is simply for the other mode. It returns 200 and writes nothing, which is the actual security property.

**`math.floor()` in the rules language returns a float.** `string(math.floor(x))` renders `"5954006.0"`, so every legitimate checkout was rejected and every hostile one was too — a rule that looks like it works and fails 100% closed. Plain integer division is correct. Caught only because the suite asserts the _accept_ cases as well as the reject ones; a suite of nothing but `assertFails` would have passed against it happily. Worth remembering next to the `math.round()` check A1 did: the rules language is close enough to JavaScript to be trusted by reflex, and isn't.

### What G3 turned out to be, and the decision it leaves open

**G3 was two findings sharing a row**, and only one of them is an implementation detail.

The announcement half is done: the result banner now has a permanent `role="status"` live region. The container is rendered **always** and only its text changes, because a live region inserted into the DOM already carrying its message is routinely missed — a mutation that wraps it in `@if (isAnswered())` looks correct and fails the suite.

The timing half is **G7**, and it is a product decision rather than a coding one. WCAG 2.2.1 accepts a timed limit only if the user can turn it off, adjust it to at least ten times the default, or extend it on warning — and the honest starting point is that this app offers none of those. Three routes, none free:

| Option                                                                                                            | What it costs                                                                                                                                                                                                                                                                                                                                                                                                 |
| ----------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A timer setting on the setup screen** (e.g. 15s / 30s / 60s / off), chosen before the limit is ever encountered | Satisfies "turn off" and "adjust" cleanly, and is discoverable. But the leaderboard then mixes runs played under different rules — a 25/25 with no timer is not the same achievement as a 25/25 at 15s, and `firestore.rules` currently validates only the score, not the conditions it was won under. Either the entry records the setting, or untimed games stop being publishable.                         |
| **Extend on request** — warn near expiry and offer more time                                                      | Closest to how the guideline is written, and the most intrusive: a warning on every question of every game, for a limit most players never come near.                                                                                                                                                                                                                                                         |
| **Claim the "Essential" exception** — argue the countdown _is_ the activity                                       | Defensible on paper (WCAG allows it where extending would invalidate the activity) and costs nothing. It is also the option that leaves the barrier exactly where it is, having written a paragraph about why that is acceptable. The audit already called a hard 15-second limit with no alternative a real barrier, so taking this route now would be reversing a stated position rather than answering it. |

Worth noting the leaderboard interaction is the actual hard part, not the timer UI. That is why this is not being decided in passing.

### What A1 actually shipped, and what changed from the plan

The planned design held on two points and was dropped on a third.

**Held — `totalQuestions` is a range, not the menu options.** A `custom` or `mixed` game legitimately returns fewer questions than requested when the bank is short, so 1–25 is the correct bound; restricting to 5/10/15/20/25 would have rejected real games. `GameSetupComponent`'s `Validators.max` was also tightened 50 → 25 to match, since 50 was never reachable through the UI.

**Held, and simplified — `percentage` uses exact equality.** The plan hedged toward a ±1 tolerance to dodge a possible rounding-mode mismatch. Probing Firestore's `math.round()` against JavaScript's `Math.round()` across `.5` boundaries (1/8, 3/8, 5/8, 7/8, 1/16 …) showed they agree on every case, so the tolerance was unnecessary.

**Dropped — the minimum-elapsed-time rule between improving updates.** The reasoning that justified it doesn't survive scrutiny: an elapsed-time check can only apply to _updates_, since a create has no prior document to compare against — and the maximum achievable score is reachable in a single create. It would have slowed incremental score-climbing, which no attacker needs to do, while risking rejection of a legitimately fast player. Dropped rather than shipped as security theatre.

### What D5 actually shipped

**The decision re-confirms, and measuring it moved the rationale from convenience to security.** The committed placeholder file was justified as letting the emulator boot cleanly on a fresh checkout. Probing firebase-tools 15 with the file absent showed the stakes are higher: secret resolution is lazy (boot is clean either way), but at the **first invocation** of any function declaring `secrets: [...]` the emulator falls through to a **real Secret Manager fetch** for every key `.secret.local` doesn't pin — and it errors only when the machine has no Google credential. On a logged-in machine the fetch succeeds silently, handing the local emulator the real production `STRIPE_SECRET_KEY` (post-launch, the live one). The placeholders are a shield against credential fallthrough, and the mechanism stays.

**What didn't survive review is the file being tracked.** `.secret.local` is a name every convention reads as "personal, gitignored" — an instruction to put secrets there — and the old design both tracked the file and told a developer testing against real Stripe to _delete_ it, when the natural move is to edit real keys into it, one `git commit -am` from publishing them. The shield now ships as a committed `.secret.local.example`; the root `postinstall` (`scripts/ensure-functions-secret-local.mjs`) copies it into place when `.secret.local` is missing — every CI workflow and fresh checkout already runs a root install, so nothing else changes — and `.secret.local` itself is genuinely gitignored, which flips the failure mode: putting real test-mode keys in it is now the supported workflow, and the ignore rule is what makes it safe. The generated file was probed to behave identically to the committed one (a real `createCheckoutSession` trigger round-trip against the emulator trio, plus create/idempotency/never-overwrite checks on the script), and `firebase.json` already excludes `*.local` from functions deploys, so neither variant ever ships. Generalised into `INFRASTRUCTURE.md` §10.2 as its own guardrail.

**One environment note for the record.** The full e2e and Lighthouse suites did not run in the authoring session — its sandbox's egress policy blocks the Cypress binary host — so this PR leaned on `CLAUDE.md` §3a (docs/config/install tooling only, none of the full-suite triggers touched) plus the targeted emulator probes above, with the PR's own required CI checks providing the full-suite run. The judgment call is named in the PR body, per §3a's own rule.

### What H4 actually shipped

**The mechanism was already in the repo; the decision was what "moderation" means.** Decided with the owner rather than in passing (§4): a reporting path now, review-before-publish reserved as its own feature. The reporting half reuses the A3 volume cap unchanged in spirit — `{window}-{slot}-{uid}` document IDs in a flat `question_reports` collection, where the uid suffix does the job nesting under `customers/{uid}` did for checkout sessions. Flat was chosen over nested deliberately: the owner reviews reports in the console, and a flat collection whose IDs start with the time window lists chronologically with no collection-group index and no `firestore.indexes.json` change — the file that once broke four consecutive deploys (D3) stays untouched.

**Two rule choices worth recording.** `questionId` is checked against the bank with `exists()` — one billed read per create, on a path that is rare and capped, to keep junk out of the review queue; this is the lookup rules _can_ do, unlike the A2 price check they can't. And no client may **read** a report back — not even its author — because a report can quote another user's content and names its author; review is console-only, so every verb but `create` is denied. The suite covers 21 cases and was mutation-tested per the working rules: six deliberate breaks (gate tightened to `isRealAuthedUser` — the reflex the anonymous-reporting decision exists to catch — cap regex dropped, `exists()` dropped, `reportedBy` unbound, reads opened, update/delete opened) produced 5/3/1/1/1/3 targeted failures, and the restored baseline went green again.

**A `setDoc` on a taken slot is an update, and update is denied — that _is_ the cap biting.** Worth stating because it makes the client's slot-retry loop and the honest failure message the same story: exhausting all ten slots usually means the volume cap, but an invalid payload is refused with the same `permission-denied` on every slot, and with reads denied the client cannot tell the two apart. The thrown message therefore advises without diagnosing ("try again in a few minutes") — claiming "too many reports" when the real cause was a skewed clock would be exactly the B4 mistake.

**An adversarial review pass caught what every green suite could not.** Three DOM-level accessibility defects survived the unit, rules and (planned) e2e coverage: a successful submit dropped focus to `<body>` (the trigger the focus effect would have restored was replaced by the "Reported" badge in the same change-detection pass, so the `isConnected` guard detected the problem without preventing it), a second identical outcome was never announced (signals drop same-value sets, and a live region only announces on mutation), and switching directly between two report panels restored focus to the wrong trigger (capture only ran on the closed→open transition). All three are fixed — the badge catches focus via `tabindex="-1"`, the status region passes through `''` while a write is in flight, capture follows every panel change — and the e2e now pins the first two. The review also flagged the trigger's missing `aria-haspopup`; that turned out to be correct ARIA for an in-place disclosure (the attribute's values enumerate genuine popups), so the exception is now documented in `CLAUDE.md` §4.5 rather than left silent, per §4's own rule.

**The UI landed on game-over, not in the quiz loop, because of G7.** An in-quiz report affordance has a 15-second countdown and a 2-second auto-advance to fight — pausing either reopens the timing questions G7 owns. Game-over has neither: it lists the game's community questions (only those — Open Trivia DB content isn't ours to moderate) with a per-question disclosure that follows the auth menu's contract (`aria-expanded`/`aria-controls`, Escape, focus in on open and back to the opener on close), a `role="radiogroup"` reason picker (G4), and outcomes announced through a permanent `role="status"` region (G3). The e2e spec asserts the written document through the Admin SDK, because clients are forbidden from reading reports — the UI saying "Reported" proves nothing about the write on its own.

### The H4 follow-up: what using it actually revealed

**The owner shipped it, used it, and didn't like it** ([#99](https://github.com/shermam/trivia/pull/99)) — which is the whole reason this is written down separately rather than folded into the paragraph above. The complaint was concrete: game-over listed every community question from the game, so the one they had a problem with sat in a list of ones they didn't. The fix inverts the default (see §4). The flag is a button on the question during play; game-over leads with only what was flagged; a modal dialog lists everything for the player who noticed but didn't flag.

**The G7 argument survived, which is the part that could easily have been lost.** The obvious reading of "put reporting in the quiz loop" is that the previous paragraph was simply wrong. It wasn't — what belongs under a countdown is the _flag_, which is one click and carries no information the player has to compose. The _reason_ still gets asked for on game-over, where there is no clock. Had the flag filed a report directly, the review queue would fill with rows saying nothing but "someone objected", and the timing objection would have been real. Splitting intent from detail is what let the affordance move without the argument moving with it.

**Three defects, all in DOM behaviour no signal-level test can see.** Consistent with the H4 review pass and with H6: the failures that survive this project's unit suites are the ones that live in the browser, not in the state.

- **The focus trap was inert.** The focusable-elements query filtered on `offsetParent !== null`, the standard visibility idiom. It is wrong twice: `offsetParent` is `null` for any `position: fixed` element — which the dialog is — and jsdom does not implement it at all. Both make the filter return an empty list, and the trap's empty-list branch bounces focus back to the dialog, so Tab appeared to be trapped while doing nothing. Removed rather than replaced: the template removes controls with `@if` instead of hiding them, so there is nothing for a visibility filter to do.
- **Shift+Tab was never handled.** The first version bound Angular's `keydown.tab`, which does not fire when Shift is held — so the one direction that escapes _backwards_ past the dialog's first control was the one direction with no handler. Now a plain `keydown` with an explicit `event.key` check.
- **Focus restore on close relied on `document.activeElement` at open time**, copied from the auth menu (G2), where it is right because that panel has several openers. This dialog has exactly one — and a click does not focus a `<button>` on Safari/macOS, so the captured value is `<body>`, which is connected, so the restore "succeeds" into nothing. It now restores to the trigger element directly.

**A second review pass, this time aimed only at the e2e spec, found two more.** The spec is the one file in this change that no local command can run — the sandbox's egress policy blocks Cypress's binary host — so it was audited against the templates and components by hand instead, adversarially, with every claimed mismatch checked back against the source before being believed. Most claims did not survive that check. Three did, and two of them were defects in the _app_, not the test:

- **`startGame()` reset every piece of game state except the flags.** Only `clearGameState()` cleared them, reachable from "Play Again" and the resume banner's Discard — but the top bar's logo is a plain `routerLink="/"`, so a player can abandon a flagged game and start another through neither, with `restoreSavedGame()` putting the old flags back into the signal on the way. Custom question ids are stable Firestore document ids, so this was not a harmless stale byte: draw the same question again and it renders pre-flagged, and game-over leads with "Questions you flagged" for a question never flagged in that game.
- **A flagged question was rendered twice while the dialog was open**, once by the card that leads the screen and once by the dialog list, both through the same `ng-template` against the same `openReportQuestionId` signal. That duplicated `report-panel-{id}` and `report-badge-{id}` in the document, and `viewChild('reportPanel')` returns the _first_ match in view order — the card, declared above the dialog. So opening a report form from inside the modal moved focus to the copy behind the backdrop, outside the trap the modal exists to provide. The card is now hidden while the dialog is open. Worth naming as a general shape: **one template rendered in two places at once is not a DRY win, it is duplicate ids and an ambiguous `viewChild`.**
- **The one confirmed test defect was a `should('not.exist')` with nothing in front of it.** `cy.startGame()` ended at `cy.wait('@questions')` — and that response is what `startGame()` awaits _before_ it navigates, so the assertion ran against the setup screen and would have stayed green with the `source === 'custom'` guard deleted outright. Fixed in the command rather than in the caller, so no future spec inherits it.

**What that pass says about the method.** Fourteen further claims were raised and refuted on the source — mis-cited lines, races that cannot occur, a `cy.trigger` call that was no longer in the file. That ratio is the point rather than an embarrassment: an audit that is allowed to be wrong out loud, and then checked, is how the three real ones surfaced at all. Two of the three would have shipped green, because the suite that would have caught them is the suite that cannot run here.

**The persistence question, and why the schema version did not move.** Flags survive a reload, because the flag is a promise ("you'll be asked for details at the end") and a reload that silently dropped it would break that promise with nothing on screen. `flaggedQuestionIds` was therefore added to the stored game — but **without** bumping `SCHEMA_VERSION`, unlike every field before it. The addition is additive and a missing value reads as "nothing flagged", so a record written by the previous build still restores; bumping would have discarded every in-progress game on deploy to prevent a problem that does not exist. The load path filters the ids against the questions actually in the save, so a hand-edited record cannot carry a flag for a question that isn't there.

### What H6 actually was, and why the audit missed it

**A user hit it before any suite did**, which is the useful part: 55 findings' worth of review, 174 unit tests, 168 rules tests and a green e2e run, and the thing that broke was a Pro account unable to add a question, reporting only "Could not save your question. Please try again."

**The trigger was configuration, and the code turned it into a trap.** `firebaseRole: pro` is read from two different Stripe objects — the **product**'s metadata (which `createCheckoutSession` validates against, so checkout works with only that set) and the **price**'s (which `subscription-mirror.ts` writes onto the subscription document, and which `deriveClaimRole()` needs to grant the claim). With it on the product alone, the subscription mirrored with `role: null`, no claim was ever set, and `firestore.rules` refused every privileged write — while Stripe, Firestore and the UI all looked healthy.

**The defect proper is that the client's predicate was _looser_ than the server's.** `SubscriptionService` unlocked Pro on `status: active` alone; the rules require the claim. A client entitlement signal is allowed to be optimistic about **timing** — that is what it is for, the subscription document lands before the next token refresh — but never about the **condition**, because the gap is a form a user can fill in and can never submit. Note the same file had already been corrected once in exactly this direction: `getProPriceId()` selects by role "matching the server" (C5). One half was fixed, the other was not, and nothing connected them. `CLAUDE.md` §4.2 now carries the general rule.

**Two further silences made it undiagnosable.** The form called `markAllAsTouched()` into a template with no error markup, so a missing category produced a Save button that did nothing at all — the user's actual first symptom, and unrelated to Stripe. And the submit handler's `catch {}` discarded the error, so nothing distinguished a rules rejection from a network failure. The message now names the missing claim **only when it has read the refreshed token and found it absent** — a checked cause, not B4's invented one — and stays generic otherwise.

**What would have caught it:** a test asserting the _stricter_ half of a mirrored predicate (`role: null` must not grant Pro), and a rendered test that a rejected submit puts something on screen. Both exist now, and both fail against the old code.

### What G7 actually shipped ([#101](https://github.com/shermam/trivia/pull/101), [#103](https://github.com/shermam/trivia/pull/103))

**Two PRs, because the deploy order forced it.** Rules reach production before the client that matches them (`ci-cd.md` §4.2), so adding the boards and switching the client in one change would have left a window where a cached client wrote to a collection the new rules had moved past. #101 added the boards and the migration with the old collection untouched; the owner ran the migration; the second PR moved the client and closed the old collection. Nothing was unavailable in between, which is the only reason to split a feature this way.

**The interesting decision was the schema, not the timer.** Three boards — `15`, `30`, `unlimited` — as `leaderboards/{limit}/entries/{uid}`, a **subcollection** rather than a `timeLimit` field on one flat collection. The flat version needs `where('timeLimit','==',x).orderBy('score','desc')`, which requires a composite index, and index configuration is the one thing the emulator cannot verify — the gap that took the deploy pipeline down for four consecutive merges (D3). This way `firestore.indexes.json` is untouched. A second benefit fell out for free: the improving-score rule reads `resource.data` at the board's own path, so a player's 15-second best cannot block their first unlimited entry without any extra logic.

**"Unlimited" had to mean no deadline, not a large one.** `startTimer()` returns before creating the interval. A very large number would satisfy the letter of WCAG 2.2.1 and miss its point, and it would also leave a timer for a backgrounded tab to throttle (B10's territory).

**Two things the change reached that the finding never mentioned**, and both would have been silent:

- **Account deletion removed one leaderboard entry.** With three boards, deleting an account would have left the user's name and score publicly readable on the two boards it did not visit — after they asked to be removed. `deleteAccount` now sweeps every board plus the legacy collection.
- **The data export returned one entry.** It now returns one per board, each labelled. Writing that revealed a bug worth recording: filtering the snapshots before pairing them with their board renumbers the survivors, so a player with an entry on only the second board gets it reported as the first's. Having entries on some boards but not all is the ordinary case, not an edge one. Pinned by a test that fails against the filter-then-index version.

**A vacuous test, caught by mutation and worth the retelling.** The first version of "never auto-answers an unlimited game" advanced Vitest's fake timers by an hour and asserted no answer was registered — and passed against a deliberately broken build that _did_ schedule a countdown. The countdown reads the wall clock (B10), and this file's `useFakeTimers` fakes only the interval, so `Date.now()` stayed real, the deadline stayed in the future, and the assertion held for a reason unrelated to the code. The existing B10 tests already knew this and spy on `Date.now`; the new ones now do too. Two lessons, both general: **the mutation is the test's test**, and a mutation that fails to apply looks exactly like one that was caught — the first attempt at this had a silently non-matching string replace, and only asserting that the mutation applied told the two apart.
